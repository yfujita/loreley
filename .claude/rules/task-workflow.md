# タスクワークフロー

`agent_tasks/` 配下でタスクを管理する。agent はこのルールに従って作業すること。

## ディレクトリ構成

```
agent_tasks/
└── {タスク名}/
    ├── STATUS.md   # タスクの現在状態(メインエージェントが更新)
    ├── 0000-requirements-definition.md   # 要件定義(ユーザが記載)
    ├── 0001-work-plan.md                 # 作業プラン(agent が記載)
    ├── 0002-{作業内容}.md                # 作業記録(agent が記載)
    └── ...
```

## ワークフロー

1. **要件確認**：`0000` と `STATUS.md` を読む。過去の作業記録は `STATUS.md` から参照されるもの、または現在の作業に直接必要なものだけを読む。不明点・矛盾・不足は `requirements-clarifier` で洗い出し、返された質問をユーザーに確認して要件定義を完成させる(軽微で自明な場合はメインエージェントが直接確認してよい)。
2. **プラン作成**：planner で作業プランを作る。作業記録 `NNNN-work-plan.md` として保存し、**ユーザーの承認を得てから**次に進む。
3. **実施**：プランを1フェーズずつ実施する。各フェーズが終わるたびに作業記録を残し、`STATUS.md` を更新する。
4. **レビュー**：プランで指定された、成果物に応じたレビュアー(code-reviewer / test-reviewer など)でレビューする。プランがレビューを省略している場合は、その理由を確認する。
5. **タスクレビュー**：プランで必要と判断された場合は、完了を報告する前に task-reviewer で全体を確認する。

## 要件定義

- タスクごとに `agent_tasks/{タスク名}/` ディレクトリを作成し、その中の `0000-requirements-definition.md` にタスクの要件を記載する。
- 要件定義の記載は**ユーザが行う**。agent が勝手に作成・書き換えしない。内容に不足・矛盾があれば、作業前にユーザへ確認する。

## タスクの実施

- agent は「〜のタスクを実施して」のようにタスク名で指示される。
- 指示されたら、まず `agent_tasks/{タスク名}/` 配下の `0000-requirements-definition.md` と `STATUS.md` を読む。過去の作業記録は全件を読み直さず、`STATUS.md` が参照するもの、または現在の作業に直接関わるものだけを読む。
- タスクの開始・再開時は、`STATUS.md` の「現在の状況」「次のアクション」「未解決事項」「ユーザー判断待ち」から作業を引き継ぐ。`STATUS.md` と最新の作業記録が食い違う場合、作業記録の内容を無条件に正としない。要件定義・実際のファイル・Git差分・検証結果(テスト実行結果など)を確認し、事実に基づいて `STATUS.md` を修正する。確認しても判断できない点は推測せず、ユーザーに報告する。
- 過去の作業内容・判断・未解決事項は、まず `STATUS.md` から引き継ぐ。`STATUS.md` に記載がなく判断に迷う場合に限り、関連する作業記録をさかのぼって読む。

### 途中の追加指示

- プランに含まれない追加・変更の指示を受けた場合、軽微なものはプランを作り直さずに対応してよい。ただし作業記録は必ず残す。
- 方針を変える指示(構成・スコープ・設計判断が変わるもの)の場合は、プランを更新する作業記録を残す。

## 作業記録

- 作業を行った場合は、**必ず** `agent_tasks/{タスク名}/NNNN-{作業内容}.md` という作業記録ファイルを残す。
- `NNNN` は4桁ゼロ埋めの連番(`0001`, `0002`, ...)。`0000` は要件定義専用。タスクディレクトリ内の最大番号 + 1 を採番する。
- `{作業内容}` は作業を端的に表す英語のケバブケース(例: `0001-implement-login-api.md`)。
- 既存の作業記録は書き換えず、新しい作業ごとに新規ファイルを作成する。
- 記載内容の目安:
  - 実施した作業の概要
  - 変更したファイル
  - 判断・設計上の理由
  - 未対応事項・次にやること

## STATUS.md

`agent_tasks/{タスク名}/STATUS.md` は、セッションをまたいでタスクを継続するための「現在状態」を1枚で示すファイル。作業記録(履歴・不変)と異なり、**常に最新の状態で上書きする**。
- 状態は `not_started` / `in_progress` / `blocked` / `done` のいずれか。

### 更新ルール

- **開始・再開時**：`0000-requirements-definition.md` と `STATUS.md` を読む。
- **各工程の完了時**：作業記録を作成し、**同じタイミングで** `STATUS.md` を更新する(「最新作業記録」を新しい作業記録に、「最終更新」を当日に)。作業記録だけ作って `STATUS.md` を放置しない。
- **中断時**(ユーザーへの確認待ち・セッション終了など)：現在の状況と次のアクションを `STATUS.md` に記録してから中断する。特に `requirements-clarifier` または `planner` が `STATUS: NEEDS_USER_INPUT` を返した場合は、提示した質問と(得られていれば)確定済みの回答を `STATUS.md` の「ユーザー判断待ち」に記録し、状態を `blocked` にする。これを怠ると、セッションをまたいだ際に同じ質問を繰り返すおそれがある。
- **完了時**：状態を `done` にし、次のアクションと未解決事項を整理する。
- **サブエージェント利用時**：`STATUS.md` の更新はメインエージェントに集約する。サブエージェントは `STATUS.md` を編集せず、報告に現在の状況・次のアクション・未解決事項を含める。メインエージェントがその報告をもとに更新する。

## サブエージェント

積極的にサブエージェントを活用する。

- **要件確認は `requirements-clarifier`**：要件定義の不明点・矛盾・不足の洗い出しと質問の整理を担当する。ユーザーへの質問と、確定した要件の作業記録への保存はメインエージェントが行う。`STATUS: NEEDS_USER_INPUT` が返ったら、ユーザーの回答を「確定済みの回答」として添えて再呼び出しし、`STATUS: REQUIREMENTS_READY` になるまで繰り返す。
- **サブエージェントを優先する**：独立性が高い作業(並行して進められる、メインの文脈がなくても遂行できる)、専門的なレビュー(code-reviewer / test-reviewer / document-reviewer / task-reviewer)、コンテキスト消費が大きい調査・技術調査。
- **メインエージェントが直接実施してよい**：数行〜1ファイル程度の軽微な実装・修正、簡単な調査・デバッグ、作業記録・`STATUS.md` の作成・更新。

サブエージェントを使うこと自体を目的にせず、分離のコスト(呼び出し先が文脈を読み直す手間、認識合わせ、結果の再確認)に見合うかで判断する。ただし、レビューを実装担当から分離する原則(`code-implementer` と `code-reviewer` / `test-reviewer` を同一エージェントにしない)は常に維持する。

作業記録と `STATUS.md` は**メインエージェントのみ**が作成・更新する。`requirements-clarifier`、`planner`、`document-writer` を含むすべてのサブエージェントは、どれほど内容が整っていても `agent_tasks` 配下の `STATUS.md` や `NNNN-*.md` を直接書き込まない。保存すべき内容は必ず最終報告としてメインエージェントに返し、メインエージェントが保存する。

### サブエージェントへの依頼

依頼文には次を必ず含める。

- タスク名
- 読むべきファイル(`STATUS.md` を含む)
- 作業範囲
- 禁止事項(作業記録・`STATUS.md` を書かない、など)
- 報告形式(結果・変更ファイル・判断理由・未対応事項・次のアクションを簡潔に)

`code-reviewer` / `test-reviewer` / `document-reviewer` にレビューを依頼する場合は、Git差分だけに委ねず、次も明示する。複数タスクの変更が作業ディレクトリに混在している場合や、途中でコミットしている場合は特に重要。

- レビュー対象ファイル(パスの一覧)
- 比較基準(例: 実装フェーズ開始時点のコミットSHA、または「直前の作業記録以降の変更」)
- 参照すべき文書(`0000-requirements-definition.md`、該当する作業記録・プラン)

## 完了チェックリスト

完了を報告する前に、次を確認する。

- [ ] プランが作業記録として残っていて、ユーザーの承認を得ている
- [ ] すべての作業に作業記録がある
- [ ] プランで指定されたレビュー(レビューフェーズ・タスクレビューフェーズ)を実施している。省略した場合は、その理由が記録されている
- [ ] 未対応事項を、最新の作業記録に書いている
- [ ] `STATUS.md` が最新の作業記録と一致している(状態・最新作業記録・次のアクション・未解決事項)
