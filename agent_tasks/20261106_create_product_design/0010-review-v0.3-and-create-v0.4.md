## ユーザーのレビュー指摘への対応

| 指摘 | v0.4での対応 |
| --- | --- |
| P0 D.2 差分検知と抽出失敗時の再試行の矛盾 | `can_skip` に処理状態を含めた。`extract_failed` が上限未満なら再処理、上限到達後は `mtime`・`size`・`extractor_version` の変化または手動再試行まで停止。`extractor_version` 変更を hash 一致より優先と明記 |
| P0 D.6 `pending_index` の期限切れ誤削除 | `pending_since` は警告のみに使う。Store層だけにある文書は MVP では自動削除せず、検出・表示・手動確認・安全な再登録にとどめる。v0.3 の仮決定を撤回と明記 |
| P1 リース切れ後の旧Worker | MVPは単一Worker直列。期限切れだけでは自動引き継ぎせず、Worker再起動時と管理者の解放に限る。`last_seen_at` は全文upsertでも max。分散フェンシングは将来拡張 |
| P1 Store/Index の不整合 | 突合ジョブで `content_hash` と `index_status` の食い違いも比較。`get_document` は Store の確定済み本文を返し、`pending_index` 時は `index_status` で示す(仮決定) |
| Origin検証 | MVPに含め、受け入れ基準に追加。`MCP_ALLOWED_ORIGINS`、不一致は403、Originなしは許可。認証は引き続き MVP 対象外 |
| Admin View の境界 | 検索対象を Compose の `:ro` マウントに限定。受け入れ基準に追加 |
| 軽微6点 | A.1 `raw_content` を取得済み原本に限定。D.3・D.5・F.4 は簡潔な方針と未決事項。D.4 は制限事項に明記。B.5 は開始前の書き込み終了確認を追記 |
| MVP方針の整理 | 9.1 に7項目の表を新設(要確認) |

## 文書レビュー・タスクレビューの反映

- E.2 に残っていた旧記述(期限切れ後に別Workerが取得する)を修正。
- 4.7 を「failed として検知し、再実行は再起動か管理者のロック解放後」に修正。
- D.6 の `last_seen_at`+TTL 削除への合流という記述を、「将来の方式は未決定(9.2 #17)」に変更。
- D.2 の `can_skip` に「上限到達後の `extract_failed`」を加え、`extract_fail_count` のリセットを「解除条件を満たして再処理を始める時点」に固定。
- 突合の `index_status` 比較は、長期継続する `pending_index` と、`extract_failed` と `indexed` の食い違いに限定(更新途中の通常の不一致は誤検出しない)。
- 要約ジョブはクロールと直列に処理すると明記。メンテナンス用ロックの区別は複雑になるため採用しない。
- F.4：確定済み本文がない場合は404でなく `index_status` を含み `content` なしで返す(仮決定)。新規文書の `text` は登録前に Store へ書く(仮決定)。
- 8.2 に「上限到達後は再処理されない」「`:ro` マウント」を追加。9.1 の見出しに「(要確認)」を付与。

## 判断・設計上の理由

- 新しい状態フィールドは追加していない(`get_document` への `index_status` 露出は既存フィールドの公開)。レビューの「複雑化させすぎない」に沿った。
- レビューで「実装しながら決めてよい」とされた点は、9.2 の12〜18に列挙するだけにした。
- 仮決定(要確認)：ロック引き継ぎを再起動時と管理者の解放に限る案、`get_document` の応答、新規文書の `text` の保存タイミング、MVP方針の整理表。
- 具体値(上限回数、リース時間など)は設計案であり、実機では検証していない。

## 未対応事項・次にやること

- 9.1 の「要確認」の仮決定をユーザーに確認する。特に、引き継ぎ条件(再起動時・管理者の解放)と、Store層のみの文書を手動対応にした点。
- 最終の修正(task-reviewer 指摘の反映)後に、v0.4 の全体通読はしていない。次の版の前に通読する。
- `last_seen_at` は検索インデックスにしかないため、Store層のみの文書の将来の自動削除方式は未決定(9.2 #17)。
- 新規文書の `fetch_fail_count` の保存先、Worker ID の安定化(再起動時の引き継ぎの前提)、削除保留の承認の競合、`get_document` のページングは実装時に決める(9.2)。
- `text` を書いた直後に失敗した場合の、`title` など他項目の書き込み順は未文書化。
- 前版からの未検証事項(kuromoji / Sudachi、Sudachi辞書のライセンス、付録Cのマッピング、TTL・削除率しきい値の既定値)は残っている。
- レビューの結論は「v0.4を実装のベースラインとし、実装とテストで設計を検証する段階」。
- v0.4は未コミット。
