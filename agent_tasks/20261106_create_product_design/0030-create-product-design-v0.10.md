## v0.10 の内容

- §1.3:削除保留の確認 → 削除結果(同期結果)の確認。
- §1.4・§2:削除の安全性の保証を TTL と割合ルールに書き換え。「0件列挙は異常」を外した。制限事項に「最小件数以下の小さなソースの 0件列挙」を追加。
- §4.1・§4.2・§4.7・§5.2:削除の判断・実行は Indexer。列挙の完了を通知するのが Crawler。同期結果が確定するまでクロールは終わらず、結果は Status API で確認する(1文)。

- §8.1・§8.2:受け入れ基準を新方針に(割合ルール、最小件数、強制削除、0件列挙)。
- §9.1:確定事項に5項目を追加(根拠:プラン承認、2026-11-08)。最小件数ルールを承認待ちから確定へ。
- §9.2:数値の既定値、強制削除 UI の詳細、Status API 確認がタイムアウトしたときの運用を追加。
- §10:「削除保留」を廃止。「削除の割合ルール」「強制削除モード」「同期(同期結果)」を新設。
- 変更なし:§1.6、§3、§7、「現時点の結論」。実装詳細(状態名、endpoint、`loreley-sync`、`force_delete`)は PD に書いていない(grep で 0 件)。

## 判断・設計上の理由

- 承認の廃止の理由は、「大量の削除は、承認ではなく割合ルールで自動では実行しない」とした。「承認待ちで同期が確定しない」などの運用上の理由は、SD に根拠がないため書いていない。
- §5.2 手順1の世代・件数照合は、「通知の内容が索引の状態と整合することを確かめる」の抽象度で、方針としてだけ書いた(式・状態名は SD に任せる)。
- §9.2 #9 の「決め方は MVP の運用結果を見て決める」は、SD の記述の範囲に合わせた表現。
