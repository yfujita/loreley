# 0025 プラン更新:Status API の追加、削除承認の廃止(0024 の更新)

状態: ユーザーの追加判断(2026-11-08)を反映したプラン更新。**下の「要確認」が未確認**のため、承認待ちのまま。

## ユーザーの追加判断(2026-11-08)

1. 全件削除するかどうかは **Indexer が判定**する。
2. Crawler は終了通知の結果を見られるようにする。そのために **Indexer に Status API** を置く。
3. **削除の承認(保留・承認・却下・全件削除の確認)は不要**にする。特定条件(例:ドキュメントが50%以上)を満たせば削除、満たさなければ削除しない。
4. product-design の新版は、不要なら作らない。

## 要確認(未決)

1. **割合ルールの意味**
   - 案: 「削除対象の件数 ÷ 削除前の同じ `source_id` の登録文書数」が 50% 以下なら削除、超えるなら削除しない(旧 §3.5 の保留の判定を、承認なしの自動判断にしたもの)。
   - 閾値(50%)はデータソースごとの設定。最小件数のルール(少数のソースで1件の削除が高い率になる問題)は残すか。
2. **全件削除の逃げ道**
   - 割合ルールでは、本当に全ファイルを消した場合(100% 削除)は永久に削除されない。
   - 案: ソース削除、または明示的な手動操作(承認ではなく、管理者が「今回は割合を無視して削除」を指示する経路)を用意する。承認をなくすなら、この経路の要否を決める必要がある。
3. **Crawler の Status API の使い方**
   - 案: 終了通知の後、Crawler が Status API を一定時間ポーリングして同期結果を確認し、ジョブの記録に結果の要約(削除件数・スキップ理由)を残す。ロックは同期結果が終端状態になるまで保持する(次クロールとの競合が減る)。タイムアウトしても、ジョブの status は変えず、警告にとどめる。
   - ジョブ status に削除結果を反映するか(Q2)も、ここで決める。案: 反映しない(切り離す)。
