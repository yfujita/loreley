## 設計の骨子(案)

- **世代**: 開始通知で `sync-{source_id}` の現行世代を `crawl_id` に更新。終了通知は現行世代と一致するときだけ検証・判断し、古い世代・未知の `crawl_id` は破棄(`discarded` を記録)。
- **結果を待たない帰結**: Crawler のロックは削除前に解放される。v0.3 §4.5 の「削除前のロック所有確認」は、世代判定とメンテナンスフラグ確認に置き換える。
- **開始通知** `POST /syncs/start`: `crawl_id`、`source_id`、`crawl_started_at`、設定スナップショット(TTL・しきい値・最小件数)。
- **終了通知** `POST /syncs/{crawl_id}/finish`: `outcome`(`enumeration_completed`/`failed`/`cancelled`)、`enumerated_count`、`skipped_document_ids[]`、`skipped_count`、`finished_at`。応答は 202 のみ。再送は冪等。
- **検証(状態を持たない)**: `enumerated_count == N_seen + E_missing`。`N_seen` = 当該 `source_id` で `last_seen_at >= crawl_started_at` の件数、`E_missing` = スキップ ID のうち索引に無い件数。不一致なら削除せず `validation_failed` を記録。
- **0件列挙**: `enumerated_count == 0` かつ既存文書ありなら削除せず「全件削除確認待ち」を記録。
- **削除実行**: バッチごとに再抽出→削除→世代再確認。新しい開始通知・メンテナンスフラグで中断。各削除は「その時点でも `last_seen_at + TTL < now`」を条件にする。順序は Store 層→検索インデックス(自己修復する極小の窓は v0.5 で消える旨を注記)。
- **受容事項**: 新クロールが削除前に始まると旧世代の削除は破棄される。新クロールが失敗し続けると削除は遅れるだけ(TTL 方式のため安全)。
- **ジョブ status と削除結果の切り離し(Q2 推奨)**: 削除結果は `syncresult-{crawl_id}` に別に持つ。0件列挙はジョブ `succeeded` + 同期結果「全件削除確認待ち」になる(E-1 と §3.3 の表が変わる)。

## 質問(推奨案つき)

- **Q1 全件削除(0件列挙)の承認後**: (推奨)承認を Indexer に期限付き(案: 24時間)で記録し、続けて通常クロールを起動。再列挙でも0件なら、その終了通知で全件削除。1件以上なら通常判定に進み承認は消費。Admin API が「承認→クロール起動」を順に呼ぶ。/ 承認時点で即全件削除(E-10 が成り立たなくなる)/ Indexer が Crawler に再列挙を要請(責務の向きが崩れる)。
- **Q2 ジョブ status と削除結果**: (推奨)切り離す。/ 0件列挙だけ Crawler が履歴で `failed` にする(判定が二重になる)。
- **Q3 表示と操作の経路**: (推奨)操作(承認・却下・全件削除確認)は Admin API → Indexer の固定経路、表示は Admin API が `loreley-sync` を読み取り専用で直接読む。/ 操作も表示も Indexer の HTTP API 経由。
- **P-b product-design の扱い**: v0.9 は削除の判断主体を書いておらず矛盾しない(曖昧なのは L130・L379の「削除の判定はこのクロールだけが行う」)。推奨は新版を作らず、必要なら v0.10 で §4.1/§4.2/§5.2 に1文足す。

- Crawler/Indexer の時刻ずれ → 同一ホスト前提を明記。
