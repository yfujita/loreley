## 概要

0018(縮小版プラン)・0019 に基づき P1 を実施した。ユーザーの承認は得ている(「承認します」)。
`system-design-v0.2.md` をもとに `system-design-v0.3.md` を新規作成し、レビュー(general-purpose)の指摘 Important 8件・Minor 7件を反映した。v0.2 は変更していない。

## v0.3 の内容

- 新章 §14「コンポーネント間通信の方針」(責務表、通信の流れ、ジョブ起動、障害時の考え方、メッセージング移行の前提)を末尾に追加した。既存の §1〜§13 の番号は維持した。
- §4 を Crawler 基準に書き換えた。ロック・リース・ハートビート・引き継ぎは Crawler が持つ。

- 細部(API仕様、数値、メンテナンスの細部、起動時回復の細部など)は §12.5 に集約した。新規テストは設計せず、§11.9 に影響を受ける既存IDを列挙した。

## ユーザー確認済み(0017 の Q1〜Q3)

- ジョブの起動と記録は Crawler(受信時にロックとジョブを保存し、202 を返す。重複は 409)。
- 責務:データは Indexer、ジョブは Crawler。
- Crawler → Indexer は同期HTTPのバッチ登録(形式・上限は未決)。

## ユーザー未確認の案(v0.3 §12.3 に「未確認の案」と明記)

- 0017 の「前提として置く案」:メンテナンス時の停止、`:ro` は Crawler のみ、Indexer 異常の扱い、内部ネットワーク、Admin API 中継、ソース削除・突合の呼び出し。
- レビュー反映で追加した案:
  - メンテナンスの手段を `loreley-jobs` のメンテナンスフラグに一本化する(ロックは受付時に作られ、クロール用ロックと区別できないため)。
  - `loreley-sources` の書き込み役は Crawler。
  - 所有確認の失敗は、スキップ・リトライの対象にせず `failed`(削除なし)。
  - 409 には既存ジョブの状態を含め、失効ロックなら警告する。
  - 孤児ロックを起動時回復の対象にする。`running` 遷移時にリースを設定し直す。
  - 要約生成は、再起動後に `summary_status=pending` から再走査する。確認手段は Indexer の停止。
  - Indexer は要請を直列処理し、所有確認は文書ごと。残る窓は既知の制限(完全なフェンシングは §4.7)。
  - 削除対象の抽出は Crawler が直接行う。ソース削除ではロックを先に削除してからジョブを終了する。
- §3.7 冒頭の表現の修正は、元の意図を推測したもの(本文に注記)。

## 判断理由

- 新章を末尾の §14 にしたのは、既存の §番号と参照を壊さないため。
- メンテナンスをフラグに一本化したのは、ロック文書に種別を持たせるより、変更範囲が小さいため。
- 要約生成をジョブにしないのは、Indexer 内部の処理にして `loreley-jobs` の書き込み役を Crawler だけにするため。再開の根拠は `summary_status` に置く。
