# 0041 作業プラン: 削除の「中断」概念の廃止(PD v0.13 / SD v0.7)

状態: **承認待ち**(planner の報告をもとにメインが保存。承認前は PD/SD を編集しない)

## 1. 目的
- 削除の「中断」を PD v0.13 と SD v0.7 から無くす。対象は次の3点。
  - 新しいクロールの開始による旧削除の中断。
  - 削除結果の状態 `interrupted`。
  - メンテナンス・Indexer再起動で止まった削除の `interrupted` 扱い。
- 削除が完了しなかった場合は、理由コード付きの `failed` として削除結果に残す。再開せず、残りは次のクロールに委ねる。
- 同じソースで旧削除と新削除が重なる場合は直列にする。

受け入れ基準:
- PD v0.13 / SD v0.7 に `interrupted` と「削除の中断」が、改訂履歴の経緯説明以外に残らない。
- PD/SD の記述、試験表、差分表が一致している。相互参照が PD v0.13 / SD v0.7 になっている。
- document-reviewer と task-reviewer の Critical / Important が解消している。

## 2. ユーザー確定事項(2026-11-09)
1. 新クロール開始による旧世代の削除の中断は廃止する。理由: 削除直前の `last_seen_at` 読み直しとTTL再確認(SD v0.6 §3.9 605行)により、新クロールが更新した文書は消えないため。
2. `interrupted` 状態は廃止する。`indexer_restart` と `maintenance` は理由コード付きの `failed` に統合する。
3. 旧削除と新削除が重なる場合は直列にする。

## 3. 直列化の方式(案。ユーザー未確定)

### 案B(推奨): Deletion Manager がソースごとに判定・実行を直列処理する
- 開始通知は従来どおり即時受理(現行世代の更新、`deletion_result` を `running` で作成、409規則は不変)。
- 受理した終了通知は、ソースごとのFIFOキューに入れる。先行する削除結果が終端になってから判定・実行を始める。待機中も `running`。
- 新しい開始通知は、`finish_received_at` が無い旧結果だけを `discarded`(`superseded`)にする(終了通知が届かなかった世代の整理であり、中断ではない)。受理済みの結果には何もしない。
- 「古い世代の終了通知」(`discarded`/`stale`)は終了通知の受理時に1回だけ判定する。バッチごとの世代確認は廃止し、メンテナンスフラグの確認は残す。
- 設定スナップショット(TTL、しきい値、最小件数、`force_delete`)を `deletion_result-{crawl_id}` に複写する。現行世代から読むと、新開始通知で上書きされた設定で旧削除が動いてしまうため(最大の波及)。
- 旧の件数照合は、新クロールの更新で不一致になりうるが、削除しない側に倒れるだけなので許容する。
- ソース削除(§1.2)の停止手段を残す。バッチ前に「ソースの記録が存在するか」を確認し、無ければ `discarded`(`source_deleted`)で止める。
- 旧削除が終わらない場合: Indexer停止は再起動時に `failed`(`indexer_restart`)、メンテナンスは `failed`(`maintenance`)、エラーはリトライ後に `failed`。上記以外のハング検知はMVPでは設けない(新削除が遅れるだけで安全)。
- Status API: 状態は増やさず、待機中は `running`。任意項目 `waiting_for`(先行する `crawl_id`)を返す案。
- Crawlerのロック: 変更しない。待機でポーリング上限を超えたら従来のタイムアウト経路を使う。

### 案A(不採用案): 旧削除中の開始通知を拒否する(`409 deletion_in_progress` など)
- 実装は単純だが、新クロールが開始時点で `failed` になり、「重なったら直列」という意図より「重なりを防ぐ」方向になる。Crawler側の待機・リトライ仕様も要る。

## 7. 承認時に確認したい点(推奨案つき)
1. 直列化の方式: 推奨は案B。代替は案A。
2. SD v0.7 の範囲: 推奨は中断廃止と直列化だけ。PD v0.12 の持ち越し項目(しきい値の入力検証、「結果未確認/不明」の表示ルール、登録結果のAPIなど)は別改版にし、改訂履歴に持ち越しと明記する。代替は同梱。PD 9.2 #11 は「次のSD改版で」と書いているため、同梱する場合は整合させる。
3. 旧削除がハングした場合の保護: 推奨はMVPでは設けない。代替は削除1回あたりの最大実行時間を §12.5 に設け、超過で `failed`(`timeout`)とする。
