## v0.4 の主な設計

- **責務**: 削除の判断(対象決定・割合ルール・TTL)と実行は Indexer の内部モジュール Sync Manager。Crawler が検索インデックスを直接読む例外は解消した。
- **専用領域**: `loreley-sync`(仮名)。Indexer だけが書く。`loreley-jobs` は Crawler 唯一の書き込み役のまま。
- **通知と結果確認**: 開始通知 `POST /syncs/start`、終了通知 `POST /syncs/{crawl_id}/finish`(202)、Status API `GET /syncs/{crawl_id}`。Crawler は Status API をポーリングし、結果の要約をジョブ記録に残す。ロックは同期結果が終端状態になるまで保持。ポーリングの失敗・タイムアウトは警告のみで、ジョブ status は変えない(ジョブ status と削除結果は切り離し)。
- **世代管理**: `crawl_id` = `job_id`。開始通知で現行世代を更新。古い世代の終了通知は `discarded`(`stale`)、未知の `crawl_id` は記録せず破棄。古い開始通知・終端済みの `crawl_id` は 409。
- **検証**: `enumerated_count == N_seen + E_missing`(Crawler が `document_id` で重複排除して数える)。不一致なら削除せず `validation_failed`。
- **割合ルール**: 削除対象 ÷ 削除前の登録文書数が閾値(データソース設定)以下なら削除。超えれば削除しない。最小件数以下なら割合に関わらず削除。削除の承認(保留・承認・却下・確認待ち)は廃止。
- **強制削除モード**: 割合ルールと最小件数ルールだけを無視。手動実行のみ。0件列挙でも全件削除(TTL 経過後)。
- **削除実行**: バッチの直前に世代とメンテナンスフラグを確認。各文書の削除の直前に索引の `last_seen_at` を読み直し、Store 層→索引の順に削除(索引側も条件付き)。Indexer の再起動時は `interrupted`、再開しない。
- テスト: D-11〜D-30(D-18 は欠番)、E-27〜E-29 を追加。E-1/E-4/E-8〜E-11/E-18/E-21/E-23、D-1〜D-10、L-5/L-7 を書き換え。

## 判断・設計上の理由

- 結果を待たない案から、Status API のポーリングに変更したのは、ユーザーが Crawler で結果を見られる方がよいと判断したため。
- 承認を廃止し、割合ルールと強制削除モードにしたのは、ユーザーの判断。
- document-writer・レビューを受けて補った「案」(§14.7 に確定と区別して列挙):
  - 同期結果の状態名、`interrupted` の理由、Status API の 404、終了通知の 409(内容が異なる再送)。
  - 開始通知の 409(古い `crawl_started_at`、終端済み)。終了通知後の取り消しは同期を止めない。ポーリング失敗は警告のみ。
  - 突合ジョブはクロールと同じロックを取り、同時に動かさない。
  - 小さなソース(削除対象が最小件数以下)では、0件列挙でも TTL 経過後に削除される(E-27。既知の制限)。
