## 判断・設計上の理由

- **推奨案を仮決定として採用した事項**（ユーザーへの個別確認はしていない）：
  - 要約はStore層にも保存する。
  - `last_seen_at` は共通ドキュメント形式に加えず、`crawl_started_at` を実行コンテキストで渡す。
  - MVPの文書形式はtxt・Markdown・HTML・PDFとし、Shift_JIS/CP932にも対応する。
- **v0.3レビューを受けた仮決定**（ユーザー確認が必要）：
  - 同一文書の連続失敗（例3回）で「恒久失敗」とし、削除を止める条件から外す。手動削除もできる。
  - 「既存文書があるのに0件」は、Admin Viewの承認で削除できる。承認後に再列挙して確認する。
  - 突合ジョブは双方向にする。`pending_index` が一定期間続いたStore文書は削除する。
  - 書き込み前・削除前にロックの所有を確認する(フェンシング)。`last_seen_at` の更新はmax比較にする。
  - 再インデックスはMVPでは手動手順とする。
- **document-writerが補った点**：`fetch_fail_count` フィールドの新設、恒久失敗文書は取得を試み続け成功すれば解除、恒久失敗文書は `pending_index` の期限削除から除く。
- 具体値(SHA-256のID、削除保留の最小件数10件・しきい値20%、リース5分など)は設計案であり、実機では検証していない。
