# 0029 レビュー後のユーザー判断(J1〜J3)と F5 の方針

## ユーザー回答(2026-11-10、0028 の質問への回答)
- **J1 ソース削除の delete_by_query**: 「再実行で消す」を採用。ソース削除は最終的に全文書を消す(ロック保持=削除中は新規クロールを起動しないことが前提)。「競合した文書は再登録が勝つ」は削る。実行前の refresh と、完了後の `source_id` の `_count`=0 確認を加える(0 でなければ再実行)。再実行の上限は未決(U-31)。
- **J2 要約の有効化・failed の再試行**: 「後で再検討するので、一旦簡単な記述ができていればよく、細かいフェールセーフなどは不要」。→ 要約の有効化後の既存文書と `failed` の再試行は、再書き込みモード(案 P39)で対応しうる旨と「再検討(未決)」を簡潔に書くだけにする。再走査の対象拡張・`failed` の遷移条件の作り込みはしない(7.3 の `failed` は、遷移条件が本書にないため「再検討」と一言)。
- **J3 インデックス喪失時の設定の戻し方**: 「ここはスナップショットにまかせる。運用者の責務。全てが同じ OpenSearch にあるからこそ、1スナップショットで完全に復元できる。」
  - 0023(スナップショットは設計の中心に置かない)との関係: 方針は変わらない。スナップショットは**運用者の責務**であり、設計書は手順を定めない。ただし**復旧の位置づけを次の整理にする**: Store 層(`loreley-sources` / `loreley-jobs` / `loreley-deletions`)と検索インデックスは同じ OpenSearch にあるため、運用者が取るスナップショット1つで、設定・ジョブ・削除結果・文書を整合したまま復元できる。スナップショットがない場合は再クロールで文書を戻す(データソース設定・ジョブ履歴・削除結果は失われるため、データソース設定は再登録が必要)。Indexer 設計書は復旧手順を仕様化しない。
  - PD 8.2 の README の行: 「バックアップ(スナップショット)は運用者の責務で、README にその旨を注記している」程度に直す(手順の仕様化はしない)。6.2「バックアップ・リストア手順を用意する」も同様に「運用者の責務」へ。

## F5 の方針
- 0028 の「修正で対応」の指摘を、各文書の document-writer が v0.6 を**その場で修正**する(v0.6 は未公開ドラフトのため新版は作らない。0020 と同じ扱い)。
- 担当: (1) architecture v0.6、(2) api v0.6 + search-index v0.6 + loreley-deletions v0.6、(3) product-design v0.16。3体を並列で実施し、メインが相互参照を確認する。
- 共通の決定: API-U-18 は api v0.6 で復活させ、「受理条件の採否(architecture U-28 / P36)」の項目とする(architecture と loreley-deletions の API-U-18 参照はそのまま有効になる)。`size` は `documents[].size`(Crawler が渡す)で search-index を揃える。確定は K12、K18、K19 のみ(今回の J1〜J3 は決定事項として確定欄に載せてよい: K20 = ソース削除は再実行で消す、K21 = スナップショットは運用者の責務で1つで完全復元できる前提)。
- 修正後は document-reviewer による再レビューを行い、Critical / Important が解消するまで繰り返す(その後 task-reviewer)。
