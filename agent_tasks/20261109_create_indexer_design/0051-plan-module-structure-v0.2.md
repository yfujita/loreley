# 0051 プラン更新: モジュール構成設計書 v0.2(外部レビューの反映)

## 経緯
ユーザーが外部レビュー(別の AI によるもの)を持ち込み、「適切な指摘なら反映してほしい」と指示した(2026-11-10)。指示を承認として扱う。ただし、レビューが適切でない部分は反映しない。
v0.1 は変更せず、`indexer-module-structure-v0.2.md` を新規に作る(版ごとに新ファイル)。

## 指摘の検証結果(architecture v0.9 と突き合わせた)

| 指摘 | 判定 | 根拠・扱い |
| --- | --- | --- |
| `deletion` が削除以外の責務を持ちすぎ(8 API のうち 6 を担当。名前と実態が不一致) | 適切 | arch 9章は開始・終了通知の受理、世代管理、Status API、削除の直列化、`loreley-deletions` への記録までを Deletion Manager に含める。v0.1 の `deletion` は名前が実態より狭い。改名し、内部を「クロール実行の状態管理(開始・終了・世代・受理条件・Status)」と「削除の判定・実行」に分ける。arch の「Deletion Manager」(K1)との対応は文書内に明記する |
| `indexing → deletion` が不自然 | 一部適切 | 名前が原因の違和感は、改名で解消する。ただし「依存がなくなる」わけではない。登録の受理条件を照会する依存(arch K23)は残る。依存の向き(照会のみ)は案として維持 |
| `storage` が業務モジュールと同じ階層にある | 適切 | 技術基盤(OpenSearch、LLM のクライアント)を `infrastructure/` にまとめ、レイヤーの違いを名前で示す |
| `extraction` を独立モジュールにしなくてよい | 適切 | 呼び出し元は登録処理だけ(v0.1 の依存でも `indexing` のみ)。`documents` の内部ディレクトリにする |
| 機能 3 つ+ API 層+ infrastructure の 3 層で整理する | 適切 | 読みやすさの目的に合う。構成図は責務と依存の向きだけに絞る(シーケンスは 6 章に分離済み) |
| `http/` は Python 標準ライブラリと衝突する。パッケージ層(`loreley_indexer/`)を設ける | 一部適切 | 実装言語は設計書にも `Dockerfile`(空)にも未決。衝突は言語・配置次第なので、パッケージ層は採用しない(実装タスクで決める)。ただし名前は `api/` に改める(`apps/api` との混同は、アプリが別なので実害が小さい) |
| 起動処理を `main.py` に | 一部適切 | 言語が未決なので、ファイル名は書かない。「エントリポイントを `src/` の直下に置く」案とする |
| モジュールを作りすぎない(M-1〜M-13、依存ルールが細かい) | 一部適切 | レイヤー分割に変わると依存ルールは減らせる。3 層ルール+個別の例外に整理する |
| LLM クライアントを `infrastructure/llm` に | 採用(案) | v0.1 の M-9(`summarization` 内)を改める。クライアントだけを移し、プロンプトの組み立て・モデル選定・再走査は `summarization` に残す |
| 「M-1 を撤回して設計し直す」 | 採用 | M-1 を新しい構成に差し替える。API、状態遷移、削除判定、競合制御は変えない |

## 方針
- 新構成(案): `api` / `crawl_runs`(内部に削除の判定・実行) / `documents`(内部に extraction) / `summarization` / `infrastructure`(opensearch、llm)。エントリポイントは `src/` 直下(案)。
- 仕様・数値・状態値・API 名は arch / api v0.9 のまま。変更するのはモジュール分割だけ。
- 新しく決めた事項は確定扱いにしない(確認状況に案として載せる)。
- v0.1 との差分は、文書末尾の「変更点」に短く残す(v0.1 → v0.2 の対応表)。
- 作成は document-writer、レビューは document-reviewer(可読性優先)。
