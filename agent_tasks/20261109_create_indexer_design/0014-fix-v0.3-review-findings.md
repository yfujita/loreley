## レビュー指摘と対応
- [Important] P26 の(a)経路の穴: (b)経路(原本ハッシュ一致・text 不一致)の全文 upsert が失敗すると Store に新 text と pending_index が残り、次回クロールで(a)に入って確定更新が行われず pending_index が永続する。→ (a)の条件を「確定済みと同じ content_hash、かつ index_status が indexed、かつ text も同じ」に変更。pending_index / extract_failed の文書は常に通常の更新経路で確定まで進める。E-40 に(c)「(b)の全文 upsert 失敗後の再クロール」を追加。loreley-texts 4章・search-index 3章にも同内容を反映。
- [Important] P29 の discard の位置づけ: ソース削除要請は Deletion Manager のソース単位直列実行で最優先とし、実行中バッチの完了直後、次バッチの前確認と待機中の判定より前に discarded を書く。そのソースの終端でない削除結果(待機中を含む)を全て discarded にしてから応答する。応答時点で当該ソースの削除バッチは動いていない。D-74 に(c)「後続の削除結果が待機中」を追加。
- [Important] 条件付き削除の条件外れ: 条件外れ・TTL 再確認で除外した文書は deleted_count に数えず、結果は deleted のまま終了し、次の期限削除に委ねる(案。deleted_count <= target_count)。9.7、9.8、D-14、D-73、loreley-texts 4.1、loreley-deletions に反映。
- [Suggestion/Nitpick] 全件対応: api 6章の旧い 409 記述の修正、search-index のテスト ID 衝突(E-7〜E-10 を削除し architecture の C-10/C-12/C-13/E-42 を参照、番号なしの「Schema 検証観点」を追加)、loreley-texts 4.1 の旧記述の削除と削除条件の書き分け(検索側は TTL 再確認、Store 側は if_seq_no)、skipped_count と oversize_document_ids の関係の明記(重複は和集合で1件)、ソース削除ロックのリース切れと lock_not_owned の関係を未決に追記、4.7 は書き込み排他に含めない(案)、9.5 の「全分岐が 202」、経緯表現(「従来」)の削除、U-26 と 15.4 の整合、P18 と P31 の関係を1行で整理。
