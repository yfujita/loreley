# 0025 プラン変更: 書き込みは PUT(Index API)基本

## ユーザー指示(2026-11-10)
1. 「ドキュメント更新が put を基本にして。update は負荷が大きい。」(実行中の F2 はユーザー操作で停止された)
2. 確認への回答:「本文が変わらないなら要約も更新しなくていいはず。もし要約更新が必要な場合は差分チェックしないモードでクロールを実行して本文ごと Index できればいい。last_seen_at だけの更新は Update を使う。」

## 0024(F1)の結論からの変更点
- 全文書き込み: **PUT(Index API)**。既存文書は GET → 組み立て → `if_seq_no` / `if_primary_term` 付き index、新規は `op_type=create`。409 は読み直して再実行。0024 の「スクリプト update + scripted_upsert + retry_on_conflict」は採用しない。
- `last_seen_at` だけの更新(本文が変わらない文書): **Update API を使う**(max 更新のスクリプトまたは部分更新。0024 のとおり条件外れは noop)。
- 要約の書き込み: 専用のスクリプト部分更新は持たない。非同期で生成した要約の書き戻しも PUT(GET → `content_hash` / `text_hash` が生成元と一致することを確認 → `if_seq_no` 付き index。不一致なら破棄、409 は読み直して再判定)。
- 本文が変わらない文書の要約は更新しない。要約の再生成が必要な場合(要約ロジックの変更など)は、**差分チェックなしのモード**でクロールし、本文ごと登録する(既存の force 系のモードがあればそれに合わせ、なければ案として記載)。
- 書き込み種別は「全文書き込み(PUT)」「`last_seen_at` 部分更新(Update)」の2種(+要約の書き戻しは全文書き込みの一種)。
- 削除は変更なし(`if_seq_no` / `if_primary_term` 付き条件付き削除、409 は読み直して再判定)。
- 引き続き未決(実機確認): Delete の `not_found` の扱い、存在しない文書への `if_seq_no` 付き操作の応答、`retry_on_conflict`(last_seen_at の Update 用)の値、PUT 競合の読み直し上限。

## 判断・理由
- ユーザー判断。Update API も内部では文書全体の再インデックスを行うが、更新頻度の高い `last_seen_at` のためだけに Update を残す(Crawler が本文を送らずに済む)。
- 書き戻し(要約)を PUT にするため、要約は競合したら読み直す。要約が古い本文の上に書かれることは hash 一致の確認で防ぐ。

## 影響
- 0022 の「書き込み種別3種」と 0024 の推奨を上記で置き換える。F2 の依頼文もこれに合わせて再依頼する。

## ステータス
範囲の調整(設計判断の更新)で、0022 の方針は変わらないため再承認は不要と判断。F2 を再依頼する。

## 未対応事項
- 要約の書き戻しが PUT で、要約と並行する last_seen_at の Update が競合しうる(要約 PUT の 409 → 読み直しで収束)ことを writer が設計書に明記し、reviewer が確認する。
