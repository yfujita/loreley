# 0010 indexer-api を API リファレンス形式に再構成 作業記録

## ユーザー指示
「indexer-api は、API リファレンスのような形式にして、どのような API があるかがわかりやすい形がいい。」(構成の変更。軽微な追加指示として扱い、プランは作り直さない。)

## 概要
document-writer が `indexer-api-v0.2.md` を API リファレンス形式にその場で再構成した(旧約460行を全面書き換え)。SD 参照なし(0008 の方針を維持)。v0.1 は変更していない。

## 変更したファイル
- docs/v0.x/system-design/indexer/indexer-api-v0.2.md のみ
- 他4文書(architecture、schema 3文書)は indexer-api の章番号を参照しておらず(参照はファイル名と `API-U-n` などの ID のみ)、修正不要。

## 新しい章構成
- 0 この文書について
- 1 API 一覧(表: API名、メソッド+パス、呼び出し元、用途、冪等性、確認状況、詳細章。9行 = 開始通知、last-seen、バッチ登録、終了通知、Status API、ソース削除1〜3、突合)
- 2 概要(通信の流れ。番号付きリスト)
- 3 共通事項(通信方式、ロック所有情報、共通ドキュメント形式、ID、エラー応答と HTTP ステータス表、冪等性・リトライ、時刻)
- 4 API リファレンス(4.1 開始通知 / 4.2 last_seen_at 部分更新 / 4.3 バッチ登録 / 4.4 終了通知 / 4.5 Status API / 4.6〜4.8 ソース削除1〜3 / 4.9 突合 / 4.10 補足: 原本サイズ超過)。各 API は 概要・エンドポイント・呼び出し元・リクエスト表+例・レスポンス表+例・エラー表・冪等性・注意事項・確認状況の同じ書式
- 5 Crawler 側のポーリング規約
- 6 確認状況(API-U-1〜14 一覧)

## 判断・設計上の理由
- 旧 5.1(エラー応答の形)を 3.5 に、旧 5.0 の方針を 3.2 と 3.6 に分割。last-seen をバッチ登録の前に置き、通信順に合わせた。
- ソース削除は API 一覧どおり 4.6〜4.8 の3節に分け、手順全体の説明は 4.6、ロックの未決(API-U-14)は 4.8 に置いた。API-U-12 は 4.7 を指すよう更新。
- 仕様・数値・状態値・ID・確定/案/提案の区分は変更なし(旧本文を1文ずつ新章へ振り分けて確認)。
- 新たに書き足した点(新仕様ではない): 各表の「型」「必須」列(例 JSON からの推定。冒頭に「型は案」と明記)、各エラー表の 400 `invalid_request` と 5xx `unavailable`(旧 5.1 の共通表の転記)、時刻を「ISO 8601(UTC)(案)」とする注記(例 JSON からの推定)。突合の冪等性は記載がないため「未定義」。
