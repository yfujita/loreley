# 0002 フェーズ0: 抽出マップ作成 作業記録

## 概要
承認済みプラン(0001)のフェーズ0として、document-writer が SD v0.8 全体(L1〜L1879)の抽出マップを作成した。マップ本体は本ファイル末尾に収録(スクラッチパッドの原本から複写)。

## 変更したファイル
- 本ファイルのみ(docs/ 配下の変更なし)

## 判断・設計上の理由
- 複数文書にまたがる項目は「記述を最も詳しく持つ文書」を主とした(開始/終了通知・Status API は API、削除判断・直列化は ARCH、`deletion_result` は DEL)。
- 登録結果の集計・ジョブ・ロック・スキップ記録は Crawler 領域(CRW)とし、Indexer 文書には境界・参照のみ置く。しきい値の入力検証は対象外。
- 主な食い違い: X1 Status API の利用者(用語集 vs 本文)、X2 `loreley-texts` 廃止が未決なのに L741 は廃止前提、X3 終了通知 202/409、X4 スナップショット項目名不統一、X5 判定番号体系が二重、X6 `loreley-jobs` 参照の散在、X7 `fetched_at`/`metadata` の所在、X8 `url`/`path`、X9 `summary_embedding`、X10 原本サイズ超過の拒否主体。

## 未対応事項・次にやること
1. API 契約は SD にほぼ未定義(形があるのは開始/終了通知・Status API のみで、それも案)。**メイン判断**: バッチ登録・`last_seen_at` 部分更新・ソース削除/突合の例は「提案(案)」と明記して追加し、確定扱いにしない(プラン P3 の未決は確定しない方針に沿う)。ユーザーには報告時に伝える。
2. §11 の E-11〜E-39、C-*、D-*(L1236-1258、L1264-1274、L1282-1353)はフェーズ1で転記前に全文確認する。
3. SD 自身が全文整合確認未完了(X13)。§3.7 冒頭は推測、§9・§11 は導出。確認状況表に明記する。
4. 食い違い X1〜X10 はフェーズ2で新文書側で解消し、根拠を「変更点」に残す。

## F. 後続フェーズへの申し送り(抽出マップ作成時の気付き)

1. **API は SD に契約として決まっているものが少ない**。確定的なのは開始通知・終了通知・Status API の3つ(それも案)と、バッチ登録の「同期・文書単位の結果・冪等」の方針のみ。バッチ登録、`last_seen_at` 部分更新、ソース削除、突合の呼び出しのエンドポイント・リクエスト/レスポンスは未定義(N-4)。v0.2 で「リクエスト/レスポンス例を追加」する(P3)場合は、未定義部分を創作しない扱い(例は案と明記)をユーザーに確認したほうがよい。
2. **Crawler 領域のうち Indexer 文書が必ず参照する境界**: 登録結果の集計(新規/更新の返却)、確認結果の区分(Status API の404/5xx の意味)、スキップ記録(Indexer は読まない)、ロック文書とメンテナンスフラグ(Indexer が読む)、リトライ設定(Indexer の削除エラーが共有: L744)。
3. **統合が必要な重複**: 責務表(L671-676 と L1761-1779)、強制削除モード(L562 と L736)、要約の整合(L371-379, L866, L1101-1121)、`summary_status`/`index_status` の値域(L337 と L1108)、メンテナンスフラグの停止対象(L387, L726, L814, L1825)。
4. **確認状況の粒度**: SD の確認状況は §12.3 と §14.7 に分散し、重複・入れ子がある。新文書では節ごとに「確定/案/未決/推測・導出」を付けるのが追跡しやすい(B 節の ID を流用可)。
5. **SD 内の語の使い分け**: 「リクエストのタイムアウト」と「ポーリング全体の上限時間」(L540)、「同期」は廃止語で「同期HTTP」のみ別義(L1735)。新文書でも「同期」を使うのは同期HTTPに限る。
6. **旧 § 参照**: SD の「§3.9」等は新文書内の参照に置換する。「PD v0.N」「PD v0.4 付録…」「本書v0.N」の表記は新文書に持ち込まない(根拠の記録は確認状況に「ユーザー確定（2026-11-09）」の形で残す程度にとどめる)。
