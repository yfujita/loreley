## v0.4 プラン(方針。ユーザー未確定のものは「案」と明記)
- 対象: Indexer 5文書を v0.4 として新規ファイルで作る(v0.3 以前は変更しない)。SD・旧版・「変更点」章への言及なし。
- ① P26 の改訂: (a)(原本ハッシュ一致・text 一致・index_status が indexed)の中で、Store 層とメタデータ(title、source_updated_at、mime_type、size、url/path は U-1 確定後)の差分を比較し、差分があれば `if_seq_no` 付きの部分更新を検索インデックスの upsert より先に行う(Store 層→検索の順を維持)。text・要約・index_status には触れず pending_index にも遷移しない。失敗しても次回クロールで自己修復。Store 層の seq_no が上がるため要約の Store 保存と衝突しうる→衝突時は読み直して再試行。C-10 を「メタデータ不変なら書かれない。変化時はメタデータのみ更新」に直し、メタデータだけ変更のテストを追加。U-5 / U-17(書き込み順)の一部を解消。
- ② `text_hash`(案 P35): 抽出後 text の SHA-256 を Store 層(`text_hash`)と検索インデックス(`text_hash`)に持つ。要約の生成元を `summary_text_hash`(Store 層)で識別。`summary_content_hash` は併存させ、既存の content_hash 条件に AND で `text_hash` 条件を加える(確定文言を変えない)。Store 層の要約保存は「現在の text_hash == 生成元」かつ `if_seq_no`、検索インデックスの要約反映は「検索側の text_hash == 生成元」のスクリプト条件。再構築では `summary_text_hash == text_hash` の要約のみ保持。P26 の判定は直接比較のまま(「導入しない」を「P26 の判定では使わず、要約整合のためだけに導入する」に改める)。U-9 の「旧要約の保存防止」を解消。C-12 に「生成中に(b)経路が走る」ケースを追加。
- ⑤ P33: 判定時刻を固定し(cutoff = 判定時刻 − TTL)、その条件で `document_id` ソートの `search_after` により全 ID を取り込んでメモリに保持。T は取り込んだ件数。バッチ実行直前の TTL 再確認で集合が縮むだけ(deleted_count <= T)。PIT は必須にしない。D-76 に判定時刻の固定を追加。100万件以上は実測項目。
- ⑥ API-U-18 → 案 P36: 照合先は `deletion_result-{crawl_id}` の複写 `crawl_started_at`。不一致はリクエスト全体のエラー(非リトライ、ジョブ `failed`)。`last-seen` API にも同じ検証。`deletion_result` がない場合の応答(拒否してジョブ `failed` 等)を明記。テスト追加。
- ③: architecture 17章に「プロダクト設計 v0.14 §5.2 4(検索のみの文書は削除する)との差分(未反映)」を明記(U-27)。P28 採用ならプロダクト設計側の統一文面を案として併記。プロダクト設計は修正しない。
- ④ P31: 文面はそのまま、ユーザー確認待ち。
- ⑦: ソース削除 4.7・4.8 は何度でも再実行できること、リース切れの `lock_not_owned` でジョブが `failed` となり再実行で完了すること、どちらの扱いでも Indexer 側は正しいことを明記。ロック採否は Crawler 領域として未決のまま。
- ⑧: 各 Schema 文書に、フィールドごとに Crawler の `documents[]` → Store 層 → 検索インデックス → 書き込み主体 を対応づける表を追加(再構築可否の確認用)。マッピング JSON に `text_hash` を追加。url/path は U-1 決定後(Store 層と検索に同じ決定を適用すると記述)。
