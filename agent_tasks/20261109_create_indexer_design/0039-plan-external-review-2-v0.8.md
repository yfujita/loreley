- **指摘① 非同期削除に必要なスキップ文書 ID 一覧の保持先が未定義(優先度高)**: 妥当。設計書で確認した: loreley-deletions-v0.7 の入力対応表(95行付近)に「ID リスト自体の保存先は本書では未記載」と明記されている。architecture は待ち行列を `loreley-deletions` の状態から導出し専用の待ち行列を持たない方針で、削除 B が待機する間、B の `skipped_document_ids`/`oversize_document_ids`(`E_missing` の計算と削除対象からの除外に必要。9.5、9.6)が参照できない恐れがある。→ `deletion_result` に保存する(推奨案を採用)。
- **指摘② 終了通知のダイジェストに `source_id` が含まれない(中)**: 妥当。ダイジェストに `source_id` を含めないのは writer の推測(0036: D-91(m)は「(推測)202」)で、ユーザー確定の内容ではない。K25 の目的(内容の異なる終了通知の検出)に照らし、同じ `crawl_id` で `source_id` が異なる通知は異常として検出するのが妥当。→ 終了通知の処理の前に `source_id` と `deletion_result.source_id` を照合し、不一致なら 409。D-91(m) の期待結果も 409。
- **指摘③ `rewrite_mode` の保持先と再送判定(中)**: 妥当。loreley-deletions-v0.7 の l.77 は `deletion_result` への複写を前提にしているが、U-1(l.209)と API-U-22 で保持先・再送判定が未決。→ `deletion_result` の設定スナップショットに保持し、バッチ登録では受理条件の確認で取得済みの `deletion_result` から参照し、開始通知の再送でも他の設定と同様に一致検証して異なれば 409。追加のデータストア・API 項目は不要。

## 決定の要点(確定)
- **K31(指摘①)**: 終了通知の受理時に、ダイジェストと同じ書き込みで、`skipped_document_ids` と `oversize_document_ids`(正規化した一覧)を `deletion_result` に保存する。削除の判定(`E_missing` の計算と削除対象からの除外。9.5、9.6)は、待機中の削除も含めて、`deletion_result` の一覧を使う。削除結果が終端状態になったら一覧を削除する(ダイジェストは残してよい)。Indexer 再起動時に未完了の削除を `failed(indexer_restart)` にする既存方針は変えず、待機中の削除も同様に実行しない。一覧の件数の上限は U-2(合計の上限)に従う。項目名は未決(U-14 と同様)。
- **K32(指摘②)**: 終了通知は、処理の前に `source_id` と `deletion_result.source_id` の一致を確認し、不一致なら 409(状態を変えない)。ダイジェストに `source_id` を含めるかは任意(含めない前提でよい。照合は事前確認で行う)。未知の `crawl_id`(分岐2)は従来どおり 202。エラー名は案。
- **K33(指摘③)**: `rewrite_mode` を `deletion_result` の設定スナップショットに保持する。バッチ登録時は受理条件の確認で取得した `deletion_result` から参照する。同じ `crawl_id` の開始通知の再送では、他の設定と同様に一致検証し、異なれば 409(K24 の比較項目に `rewrite_mode` を加える。省略と未指定・false の扱いの正規化は API-U-20 で扱う)。API-U-22 のうち、保持先と再送判定は解消。名称(`rewrite_mode` は仮)と指定経路(開始通知の任意項目。推測)は未決のまま。
