# 0044 ユーザー判断待ちの項目一覧(v0.8 / PD v0.17 時点)

## 位置づけ
- ユーザーの指示(2026-11-10)「私の判断が必要なものをリストアップして」「作業記録としてリストアップをまとめて。また、『一覧の合計件数が上限を超えた時』のような記載だと何の一覧かわからないので、主語を明確にするようにお願い」に基づく記録。設計書は変更していない。
- 確定済みは K12、K18〜K33(architecture v0.8 の 17.1)。以下はすべて未確定で、ユーザーの判断を待つ。
- 「推奨」は writer・reviewer・メインの推奨であり、ユーザーが選ぶまでは確定ではない。「回答」欄はユーザーが回答するときの記入欄。
- 用語の統一(この記録内):
  - **スキップ文書 ID 一覧** = 終了通知の `skipped_document_ids`(取り込みをスキップした文書の ID の一覧)。
  - **サイズ超過文書 ID 一覧** = 終了通知の `oversize_document_ids`(原本サイズの上限を超えて登録されなかった文書の ID の一覧)。
  - **ID 一覧の合算件数** = 上の2つを合わせた件数(上限は architecture の U-2、api の API-U-5。同じ論点)。
  - **保存した ID 一覧** = 終了通知の受理時に、`deletion_result`(削除結果のレコード)へ保存した、上の2つの一覧(K31)。
  - **終了通知のダイジェスト** = 終了通知の内容(`outcome`、`enumerated_count`、重複を除いてソートしたスキップ文書 ID 一覧とサイズ超過文書 ID 一覧)から計算したハッシュ。再送の内容が最初の通知と同じかを判定するために保存する(K25)。

## A. 実装前に決めたい項目(設計に直接影響)

### A1. 終了通知の ID 一覧の合算件数が上限を超えたとき(architecture P42(1)。案)
- **何の判断か**: 終了通知の `skipped_document_ids` と `oversize_document_ids` の合算件数が、上限(U-2 / API-U-5)を超えていたときに、Indexer がどう扱うか。
- **現行案**: 終了通知は受理して 202 を返す。2つの ID 一覧は保存せず、「上限を超えた事実」と「合算件数」だけを `deletion_result` に記録する。削除の判定の順番が来たときに、`deletion_result` の状態を `validation_failed` にして、削除しない。判定の順番が来るまでは `status` は `running` のまま。
- **代替案**: 終了通知を受理した時点で上限超過を判定して、`validation_failed` にする。
- **推奨**: 現行案(判定の時点で `validation_failed`)。削除の判定を、ソース単位の直列処理の順(architecture 9.7)に揃えられて実装が単純。
- **関連**: architecture 9.4・9.6・15.6・D-92(c)、loreley-deletions 7章。

### A2. 保存した ID 一覧を削除するタイミング(architecture P42(2)。案)
- **何の判断か**: 終了通知の受理時に `deletion_result` へ保存した、スキップ文書 ID 一覧とサイズ超過文書 ID 一覧を、いつ削除するか。
- **現行案**: `deletion_result` が終端状態(`deleted`、`validation_failed`、`failed` など)へ遷移する書き込みと同じ書き込みで削除する。ダイジェストは残す。
- **代替案**: 終端状態へ遷移する書き込みのあとの、別の書き込みで削除する(書き込みに失敗して ID 一覧が残る場合がある)。
- **補足(どちらの場合も)**: 削除し損ねて残った保存済みの ID 一覧は、削除の判定には使わず、`deletion_result` の保持件数 N の整理で、結果ごと消える(案)。
- **推奨**: 現行案(同じ書き込みで削除)。
- **関連**: architecture 9.4・9.7・9.8・15.6・D-93、loreley-deletions 6章。

### A3. `outcome` が `failed` / `cancelled` の終了通知のとき、ID 一覧を保存するか(architecture P42(3)。案。導出)
- **何の判断か**: クロールが失敗・取り消しだったことを知らせる終了通知(件数照合も削除もしない)に、スキップ文書 ID 一覧とサイズ超過文書 ID 一覧が含まれていたとき、それらを保存するか。
- **現行案**: 保存しない。ダイジェスト(再送の判定用)だけ保存する。
- **推奨**: 現行案。
- **関連**: architecture 9.4・D-17、loreley-deletions 2.2。

### A4. 開始通知の `rewrite_mode` を省略したときの扱い(API-U-20。未決)
- **何の判断か**: 開始通知の `rewrite_mode`(再書き込みモードの指定。名称は仮)を省略した場合と `false` を指定した場合を、同じとみなすか。みなす場合、`deletion_result` へ複写するときに省略を `false` に補うか、省略のまま保持するか。同じ `crawl_id` の開始通知の再送で、省略と `false` の違いを 409 にするかどうかが、この判断で決まる(K24 の一致検証、K33)。
- **推奨**: 省略と `false` は同じとみなし、複写時に `false` に補う。
- **関連**: api 4.1・API-U-20、loreley-deletions 4章、architecture D-94(c)(d)、C-27(b)。

### A5. 終了通知の処理順(architecture 9.5、api 4.4。案)
- **何の判断か**: 終了通知を受けたとき、「リクエストの形式の検証(400)」と「`source_id` の事前照合(409)」のどちらを先にするか。確定済みなのは「処理の前に `source_id` を照合する」まで(K32)。
- **現行案**: 形式の検証(400)→ `source_id` の事前照合(409)→ 再送の判定(同内容なら 202、内容が違えば 409)。
- **推奨**: 現行案を確定にする。
- **関連**: architecture 9.5・D-91(o)(p)(q)、api 4.4。

### A6. 数値(U-2 ほか)
- **何の判断か**: 終了通知のスキップ文書 ID 一覧とサイズ超過文書 ID 一覧の合算件数の上限、`deletion_result` の保持件数 N、削除バッチの件数、ポーリング間隔、リトライ回数、`retry_on_conflict` の値、読み直しの上限など。
- **推奨**: 実装して実測してから決める(今は決めない)。
- **関連**: architecture U-2・U-31、api API-U-5。
