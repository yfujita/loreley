## v0.3 プラン(方針)
- 対象: Indexer 5文書(architecture、api、search-index、loreley-texts、loreley-deletions)を v0.3 として新規ファイルで作る(v0.2 は変更しない。SD への言及なし、変更点の章は設けない)。
- 設計判断(ユーザー未確定のものは「案」として明記し、確定扱いにしない):
  - 同一 content_hash: 原本ハッシュ一致かつ抽出 text 一致→Store を書かず検索の全文 upsert のみ(要約は引き継ぐ)。原本ハッシュ一致で text 不一致→pending_index 経路に乗せ要約を無効化。`text_hash` は導入しない(`extractor_version` 導入時に再検討)。[P26]
  - 削除: 削除順序(Store→検索)は維持。文書単位の処理(再確認〜Store 削除〜検索削除)を登録・last_seen 更新と同じ書き込み排他に含め(単一 Indexer のプロセス内ロック)、Store 削除も `if_seq_no` 条件付きにする。窓で Store 文書が消えたときの Store 確定更新の 404 は文書単位の失敗としてリトライ(案)。[P27]
  - 突合: 検索にだけある文書は MVP では削除せず検出・表示のみ。[P28]
  - ソース削除: ジョブは source_id 単位のロックを最後まで保持し、ロック文書の削除は最後。`discarded` 要請への応答は実行中バッチの終了後(Deletion Manager のソース単位直列実行に載せる)。バッチ内ハングでは待ち続ける(受容事項に追記)。Crawler 側のロック設計の決定が前提(未決として明記)。[P29]
  - 要約: Store の `summary_status` は検索への反映成功まで `pending` のまま。要約テキストと `summary_content_hash` を先に保存。再走査では `pending` かつハッシュ一致→反映のみ、不一致→再生成。[P30]
  - 終了通知の応答喪失: K12 の文言は変えず、適用範囲(受理されなかった場合)と、受理後に応答が失われ再送もすべて失敗した場合の例外を案として併記。ユーザー確認待ち。[P31]
  - 件数照合: 終了通知に `oversize_document_ids` を `skipped_document_ids` と別項目で追加し、E_missing の対象に含める。上限(U-2)は両リストの合計。拒否主体(API-U-4/arch U-5)は未決のまま。[P32]
  - 削除対象の取得: 開始時に対象 ID を1回抽出してメモリ上で順に処理(または `search_after`)。削除直前の TTL 再確認は維持。from/size の上限を避ける。[P33]
  - 終了通知の再送: 409 をやめ、2回目以降は常に冪等な 202(先着採用)を案とする。[P34]
  - api 4.3 に `crawl_started_at` を追加(開始通知と異なる値の検証は必須にしない)。`deletion_result` の複写項目にも `crawl_started_at` を追加。
  - 低8: (a) 正規化規則の二重実装は API-U-7 に共有ライブラリ/テストベクタの選択肢を追記(構成は変更しない)、(b) 再送集計は Crawler が `document_id` ごとに最初の成功結果を保持する規則を推奨として未決に記載、(d) base64 の実測項目(原本上限・バッチサイズ・メモリ)を 15.4 に追加、`content_hash` の照合有無を未決に追加。
  - テスト観点: 外部提案の7ケースとページングのケースを architecture 16章(および search-index のテスト観点)に追加。
- ID は既存を renumber せず、新規は architecture P26〜P34 のように採番。他文書は「architecture P-n」で参照する。
- 外部レビュー指摘中の PD v0.14 の修正は本タスクの対象外(別途ユーザー判断)。

- `loreley-texts` 廃止(U-21)は変更せず未決のまま
