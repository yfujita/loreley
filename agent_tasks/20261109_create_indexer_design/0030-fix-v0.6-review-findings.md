## 変更内容の要点
- **J1(K20)**: ソース削除は「refresh → delete_by_query(conflicts=proceed)→ refresh と `_count`=0 の確認 → 0 でなければ再実行」。「再登録が勝つ」を削除(否定文の記載のみ残る)。ロック保持(削除中は新規クロールを起動しない)が前提で、破られると文書が残りうる旨も書く。再実行の上限は U-31(超過は 5xx `unavailable` の案)。
- **J2**: 要約の有効化後の既存文書と `failed` の再試行は「再検討(未決)。再書き込みモード P39 で対応しうる」と簡潔に(architecture 7.3、U-9、PD 9.2)。
- **J3(K21)**: スナップショットは運用者の責務。Store 層と検索インデックスは同じ OpenSearch にあり、1つで設定・ジョブ・削除結果・文書を整合して復元できる。ない場合は再クロール(データソース設定は再登録、ジョブ履歴・削除結果は失われる、`last_seen_at` は初期化、要約は再生成)。手順は仕様化しない。PD 8.2 の README の行は「運用者の責務である旨を注記」に変更。
- **architecture**: `extract_failed` の `summary_status` は `disabled`(再走査の対象外。案)。「変更なしは書かない」は導出(G-10)、補完 Update は 4.2 の失敗・省略時のみ(G-11)、要約生成の起動契機(G-12)。読み直しの上限は 4.4 の Crawler 再送とは別の層(U-31(4))。要約書き戻しの条件に `summary_status=pending` を追加。日時は UTC・ISO 8601・ミリ秒(U-31(7))。`_reindex` の中断と切り替え前確認、`_aliases` の remove+add、`index_not_found_exception` は全体異常。U-32(`indexed`→`extract_failed` の旧 `content`・要約の扱いは未決)。確定は K12、K18〜K21。
- **テスト観点(architecture 16章)**: 追加 C-24(再走査)、C-25(書き戻し正常系)、C-26(日時形式)、E-45(indexed→extract_failed)、R-9(再クロール復旧)、D-87(c)。分割 C-18a〜c、C-19a〜c、C-10a/b。修正 S-8、S-9、D-9、D-90、E-20、E-44、C-1/C-15、C-20(先着順2通り)、C-21、C-22、C-23(Indexer 側に限定。範囲切り出しは 16.10 の Search API 側)、R-8(R-4 との違いを注記)。16.1 に競合系の決定的な再現方針(フック・応答差し替え)。

## 確認(メイン)
- 禁止語(`pending_index` `reconcile` `summary_*_hash` `scripted_upsert` `v0.5` `従来` `変更点`)は、architecture の 17章(K18 決定文)以外で 0 件。`loreley-texts` と `突合` は architecture の 17章の欠番記録・K18 決定文、PD の改訂履歴・9.1 にのみ残る。
- API-U-18 は api 6章で復活(受理条件の採否)し、architecture U-28 と loreley-deletions の参照が有効。`extract_failed` の `summary_status=disabled` は architecture と search-index で一致。K20/K21 は architecture、api、Schema 2文書に反映(PD は K 番号を使わない)。「再登録が勝つ」は否定文(K20、9.14、D-90)にのみ残る。

## 判断・設計上の理由(writer の推測)
- `update_conflict` を文書単位にしたのは `write_conflict` と揃えて Crawler の分岐を増やさないため。Crawler の最終扱いは「リトライし、直らなければジョブ `failed`(案)」。
- 再書き込みモード直後の旧生成は `summary_status=pending` 条件では防げないため、再書き込みモードの前に要約生成を止める運用を案として併記。
- ソース削除の再実行上限超過は 5xx `unavailable` で止める案(再実行で続きから消せる)。
