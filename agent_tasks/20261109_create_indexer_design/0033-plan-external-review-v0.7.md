## レビュー指摘の確認結果
- ① **スナップショットの整合性保証が強すぎる(高)**: 妥当。v0.6 の「取得時点の状態に整合して復元できる」は、OpenSearch のスナップショットがシャードごとに取得時点が異なりうる(クラスタ全体の厳密な同一時点ではない)ため強すぎる。0031 でも「時点が揃う保証は未確認(推測)」と注記していた。→ スナップショットは運用者の責務(K21。ユーザー確定)という方針は維持し、「整合した復元を求める場合は、関連する書き込み(クロール、削除、要約の書き戻し)を止めてから取得する」「停止せず取得したスナップショットは、アプリケーション全体の整合(ジョブ・削除結果・文書の時点)を保証しない」と明記する(architecture 1.1・14.1・14.2・K21、search-index 6章、loreley-deletions 7章、PD 2章・6.2・8.2)。
- ② **`extract_failed` への遷移が未決(中〜高)**: 妥当。ユーザー回答(2026-11-10): **古い `content`・`text_hash`・要約を消す**(`extract_failed` は `content`・`text_hash`・要約を持たないという既存仕様のとおり)。U-32 を解消し確定欄に載せる。最終成功時の本文は MVP では保持しない。
- ③ **`last_seen_at` の更新負荷(中)**: 妥当。「変更なしは PUT しない」でも、列挙した全文書に `last_seen_at` の Update が発生し、Update は内部で文書全体を再インデックスする(TTL 方式と存在確認のコスト)。設計は変更しない。15.3 にその旨を明記し、15.4 の性能試験項目に「`last_seen_at` Update の処理時間・インデックスサイズ・マージ負荷」を追加する。
- ④ **要約書き戻しの全文 PUT の性能(中)**: 妥当。正しさの問題ではなく、大きな `_source` の GET と送信のコスト。PUT 基本の方針は変えず、15.4 に「要約の書き戻しの処理時間と競合回数」の測定項目を追加する。
- 総合評価の表と「案の確定」の表は、後者をユーザーが採用(下記)。
- 「システム設計 v0.8 は旧方針のまま」: PD 改訂履歴の注記どおり(要件で修正しない)。次の SD 改版で旧 Store 層・突合・再構築の記述を更新する必要があることを引き渡し事項に再掲。
- 「次は設計書の改訂を繰り返すより、実装して実機の競合試験・性能試験を始める」(提案): 記録する(設計書の範囲外。U-31 の実機確認項目が実装時の試験項目になる)。
