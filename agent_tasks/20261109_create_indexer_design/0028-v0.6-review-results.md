## 指摘(統合。重要度 Important を中心に)
### ユーザー判断が必要
- **J1 `delete_by_query` の競合文書(P41)**: 「競合した文書は消えない(再登録が勝つ)」と「`version_conflicts` が0になるまで再実行」が両立しない(architecture 9.14、D-90、P41、8章。api 4.7)。再実行すると再登録された文書も消える。さらに、直前の書き込みが未 refresh だと `delete_by_query` にヒットせず、「完了後に文書が残らない」も成り立たない(事前 refresh と完了後の `_count` 確認が必要)。(a)再実行で消えてよい(ロック保持前提。「再登録が勝つ」を削る) / (b)競合した文書は残し、再実行せず結果に記録する。
- **J2 要約の有効化・`failed` の再試行(architecture 7章)**: 要約を後から有効化した場合(`disabled`)や `failed` の文書は、通常クロールで `pending` に戻らず(変更なしは書かないため)、再走査も `pending` のみ対象で、永久に要約されない。7.3 の `failed` へ遷移する場面も本書にない。再書き込みモードの用途に含めるか、再走査の対象を広げるか。
- **J3 インデックス喪失時の `loreley-sources` の戻し方(PD)**: データソース設定・ジョブ・削除結果(Store 層)も同じ OpenSearch にあり同時に失われる。PD 6.2「設定ファイルはバックアップ」の意味が曖昧。「再クロールで戻す」はデータソース設定が残っている前提。(a)Admin View で再登録(設定のエクスポートは運用者の任意)/ (b)設定の正本を設定ファイルにも持つ。
- **J4(J1〜J3 に付随)** PD 8.2 の「スナップショット手順を README に記載」の受入基準と 6.2「バックアップ・リストア手順を用意する」は方針(スナップショットは運用者の任意)と矛盾 → 削除、または再クロール復旧・`_reindex` の手順に置換(修正方針は明確。ユーザー判断は不要と判断)。
