## レビュー指摘と対応
- [Important] P36 と突合ジョブ: 突合・ソース削除の要請は開始通知を伴わず deletion_result が存在しないため、P36 の照合対象を「開始通知を伴うクロールのバッチ登録と last-seen」に限定(突合・ソース削除は対象外。deletion_result を要求しない。案)。architecture 3.3、4.4、9.5、9.14、10章、api 3.2、4.2、4.3、4.9、loreley-deletions 4.1 に反映。終端状態(superseded/discarded/保持件数超過で消去)の deletion_result でも crawl_started_at が一致すれば受理(照合のみ。案)。
- [Important] search-index 3章の全文 upsert の要約保持条件が architecture 5章と矛盾: 「原本ハッシュ・抽出 text が既存と同じで Store 層の index_status が indexed(P26 の(a))のときだけ保持。どちらかが違えば無効化」に統一。
- [Important] テスト ID の参照のずれ: メタデータのみの変更は C-14、生成中の(b)経路は C-12、text_hash 不一致による旧要約の拒否は C-15、seq_no 衝突は C-16 と書き分け(search-index 8章、loreley-texts 6章)。
- [Important] 全文 upsert での要約の引き継ぎの原子性: 保持を検索インデックスのスクリプト(upsert 内)で行う(案)と明記。置き換え方式だと、読み出しと upsert の間に反映された新要約が消え Store=generated/検索=pending の食い違いが起きる点を記載。自己修復は再走査で Store の generated かつ summary_text_hash==text_hash のものを検索へ再反映。architecture 5章・7.4・U-9、search-index 3章、loreley-texts 4.2。
- [Suggestion] 応答コードの併記(architecture 9.5・U-4 に「案: 409(API-U-19)」。api 3.4)。P36 のユーザー判断項目を architecture U-28(新規)に追加: (a)照合する/しない、(b)deletion_result なし時は拒否か省略か、(c)終端状態の結果での登録要請は受理か拒否か。
- [Suggestion] text_hash の定義: 完全な定義(Store 層の text(サイズ上限で切り詰め後)の UTF-8 バイト列の SHA-256、16進小文字)を architecture 1.3 と loreley-texts 2章に置き、search-index は参照。extract_failed 文書は text が無いので text_hash を持たず要約も生成しない(案)。
- [Suggestion] 9.2 の規則を判定時刻(9.8)基準に改めた。T と D を同じ判定時点・同じリフレッシュ後に取得する旨を 9.3/9.8 に明記。
- [Suggestion] loreley-deletions 喪失時に進行中クロールの登録・last-seen は拒否される(案)を architecture 12章・14.4 に追記。
- [Nitpick] search-index 2.5 の summary 行に summary_content_hash の AND 条件を追記。
