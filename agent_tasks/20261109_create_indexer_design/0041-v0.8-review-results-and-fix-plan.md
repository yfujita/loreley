## 指摘と対応方針
### Important
1. **エラー名の食い違い(既知)**: 終了通知の `source_id` 不一致の 409 は、architecture が `crawl_source_mismatch` の流用案、api が `finish_source_mismatch`(案)。→ api の `finish_source_mismatch`(終了通知専用。案)に統一。architecture の参照先を「api の API-U-19」から API-U-21 に直す。名称の案の記載は P42(4)か U-4 の1か所に寄せ、K32 の行は「エラー名は案(api 3.4、4.4、API-U-21)」だけにする。loreley-deletions 2.2 も揃える。
2. **一覧の削除タイミングの扱いが不揃い**: architecture 9.4 は「同じ書き込みで削除(案。P42)」、9.7 の注記・9.8・D-93 は案の表示なしで断定、loreley-deletions 6章は「未決(実装時に決める)」、15.6 は「一覧は残らない。running の分だけ」と断定。→ 9.7、9.8、15.6、D-93 に「(案。P42)」を付け、15.6 は「P42(2) を採るなら」と条件を明記。別書き込みの場合・書き込み後に落ちた場合の残存した一覧の扱い(判定には使わない。保持件数 N の整理で結果ごと消える、など)を1行追記。loreley-deletions 6章と architecture の文言を揃える。
3. **P42(1)(上限超過時の記録)の保存先が未定義**: 「一覧を保存せず超過の事実と合計件数だけを記録する」の記録先がスキーマにない。loreley-deletions 7章は「保存するかは未決」。→ 記録先の項目を項目名は未決(U-14)として loreley-deletions のスキーマ表に1行足す(または「記録先は未決」と明記)。P42(1) を両文書で同じ文言に。超過を受理時に判定して `validation_failed` にするか判定時まで待つか(`status` は `running` のまま)を P42 に追記(案)。上限の呼び方(architecture U-2、loreley-deletions の API-U-5/U-5 表記)の相互参照を揃える。
4. **`rewrite_mode` の省略・未指定・false の扱い**: api 4.1 は「任意(既定 `false`)」と書き、一致検証での扱いは API-U-20 で未決、loreley-deletions 4章は「省略時の扱いは未決」。D-94(c)(d) が 409 と断定。→ api 4.1 の「既定 `false`」を「省略時の扱い(複写時に `false` に補うか、省略のまま保持するか)は未決(API-U-20)」に直す。D-94(c)(d) は正規化の方針に依存すると注記、または「未決」に。
5. **テスト(test-reviewer)**: D-91 に (m4)(未受理の `running` の結果に `source_id` 違いの初回の終了通知 → 409、ダイジェスト・一覧・`finish_received_at`・状態が変わらない。続けて正しい `source_id` の通知は通常どおり受理)。(k) の期待結果に「読み直し後、受理した1通のダイジェストと一覧が同じ通知の内容と一致する。一覧だけ・ダイジェストだけが残らない」。D-17 に「一覧が保存されない(ダイジェストは保存。案 P42(3))」、D-13・D-41/D-42 に「一覧が削除され、ダイジェストが残る(案 P42(2))」。D-92(c) に応答コード・検出時点・記録先は未決(案を1つ書く)・上限値は設定で小さくして再現と明記。
### Suggestion / Nitpick
- 処理順を architecture 9.5 と api 4.4 の両方に明記: 「形式検証(400)→ `source_id` の事前照合(409)→ 再送の判定」。テスト追加: 形式不正(400)で `source_id` も違う通知は 400、形式が正しく `source_id` だけ違う通知は 409(どちらも状態不変)、内容も `source_id` も違う再送は `source_id` 違い(409)として扱われる(エラー名は案なのでテストはコード名に依存しない形)。
- K32 の確定範囲: 「ダイジェストに `source_id` を含めない」は、ユーザー確定の「任意。含めない前提でよい」であり断定ではない。api の確定行・loreley-deletions の表・D-91(m) を「含めない前提(任意。K32)」の表現に揃える。
- 15.6: 64文字の出典(api 3.3)、`deletion_result` は処理中に何度も更新され、更新のたびに一覧を含む文書全体が書き直される(`deleted_count` の進捗更新の頻度との関係)、一覧はマッピング上は検索対象外にする案(`enabled: false` など)を未決として追記。
- D-92 の (a)→(b) は連続した1シナリオ、(c) は別ケースと明記し、(b) に具体数(既存スキップ 2 件、新規スキップ 1 件、サイズ超過 1 件など。A の一覧と数値を変える)を書く。D-93 は再起動後に `loreley-deletions` を直接読み、一覧が空であることと文書の削除が 0 件であることを確認(「順番が来ても」を言い換え)、期待結果を「(1)B、(2)A」の箇条に。C-27(b) に「保持値の確認は API-U-20 の決定による(未決)」の注記。D-94 に `rewrite_mode` が真偽値以外の場合を「未決」として項目だけ置く。D-20 と D-34 の重複は D-34 に寄せる(任意)。
- loreley-deletions 2.2 の `failed`/`cancelled` で一覧を保存しないことに「(導出。P42(3))」を付ける。
