# 20261127_implement_admin_view

## 背景・目的

Loreleyの管理者が、Webブラウザからデータソースの管理、クロールの操作、ジョブ状態の確認、インデックスの確認、各コンポーネントの稼働状態の確認を行えるようにする。

作成済みの機能設計書、UI設計書、フロントエンドアーキテクチャ設計書およびモジュール構成設計書に基づき、Admin Viewを実装する。

## 要件

### 現状(As-Is)

- Admin Viewの機能設計、UI設計、システム設計が完了している。
- Admin APIの実装および結合テストが完了している。
- Admin APIのOpenAPI定義における型の修正が完了している。
- `apps/web` にVue、TypeScript、Vuetify、Viteを用いた最小限のスキャフォールドが作成されている。
- webコンテナ(Nginx)による静的コンテンツの配信およびAPIへのリバースプロキシが実装されている。
- Admin Viewの各画面、共通コンポーネント、APIクライアントおよびテストは未実装である。

### あるべき姿(To-Be)

- Admin ViewのMVPとして定義されたすべての画面および機能が実装されている。
- 管理者がAdmin ViewからLoreleyの管理操作を行える。
- 実際のAdmin APIと連携し、データの参照および更新が行える。
- UI設計書およびデザインシステムに準拠した、一貫性のあるUIが提供されている。
- エラー、部分的な取得失敗、通信障害、操作結果不明などの異常系が適切に扱われている。
- 継続的な機能追加および保守が可能なモジュール構成とテスト基盤が整備されている。

### 具体的にやること

#### 1. フロントエンド基盤の実装

- 既存のスキャフォールドを基に、フロントエンドアーキテクチャ設計書およびモジュール構成設計書に従って実装基盤を整備する。
- 必要なライブラリおよび開発用ツールを導入する。
- Admin APIの実装からOpenAPI定義を出力し、APIクライアントおよび型定義を生成する仕組みを実装する。
- APIクライアント、データ取得、キャッシュ管理、エラー処理、ルーティングなどの共通基盤を実装する。
- ESLint、Prettier、型検査およびテストの実行環境を整備する。
- モジュール間の依存ルールを機械的に検査できるようにする。

#### 2. 共通UIの実装

- デザインシステムに基づくテーマ、デザイントークンおよび共通スタイルを実装する。
- アプリケーションシェル、ナビゲーション、パンくずリストなどの共通レイアウトを実装する。
- 各画面で利用する共通コンポーネントおよびページテンプレートを実装する。
- ローディング、空状態、エラー、部分失敗、通知、確認ダイアログなどの共通UIを実装する。

#### 3. 各画面の実装

以下の画面を、各画面のUI設計書および機能設計書に基づいて実装する。

| 画面ID | 画面 |
| --- | --- |
| D1 | Loreleyダッシュボード |
| S1 | データソース一覧 |
| S2 | データソース詳細 |
| S3 | データソース登録 |
| S4 | データソース編集 |
| J1 | ジョブ一覧 |
| J2 | ジョブ詳細 |
| X1 | 文書確認ビュー |
| O1 | OpenSearchダッシュボード |

上記に加えて、共通シェルおよび存在しないURLへのアクセス時の表示を実装する。

#### 4. 管理操作の実装

- データソースの登録・編集・削除
- クロールの起動・取消・再実行
- ロックの解放
- その他、機能設計書でMVPの対象とされている操作

各操作について、確認ダイアログ、入力値の検証、操作可能条件、二重送信の防止、操作結果の表示および操作後のデータ再取得を実装する。

特に、破壊的な操作および操作結果が不明な場合の挙動については、設計書に従って実装する。

#### 5. テストの実装

- フロントエンドアーキテクチャ設計書およびモジュール構成設計書のテスト方針に基づいてテストを実装する。
- Vitestによる単体テスト、コンポーネントテストおよびAPI契約テストを実装する。
- PlaywrightによるAPIモックを用いたE2Eテストを実装する。
- 正常系だけでなく、異常系、境界値、状態遷移および操作結果不明時の挙動を検証する。
- OpenAPI定義および生成コードが実際のAdmin APIの実装と一致していることを検証する。

#### 6. 実機確認・UIレビュー

- Docker Composeで起動した環境において、webコンテナを経由してAdmin Viewにアクセスできることを確認する。
- 実際のAdmin APIとの接続および代表的な管理操作を確認する。
- Viteの開発サーバーからwebコンテナを経由してAdmin APIにアクセスできることを確認する。
- ブラウザ上で各画面の表示、操作、レスポンシブ対応およびアクセシビリティを確認する。
- UI設計書、デザインシステムおよびモックアップと実際の画面を比較し、UIレビューを実施する。
- 実装時確認事項について検証し、その結果を記録する。

#### 7. ドキュメントの整備

- `apps/web/README.md` に開発、ビルド、APIクライアントの生成、テストおよび起動方法を記載する。
- 実装に伴って確定した事項、設計との差異および未解決事項を作業記録に残す。
- 実装に関連する既存ドキュメントを必要に応じて更新する。

- MVPの対象外とされているAdmin Viewの機能
- Admin APIの新規機能追加および大規模な設計変更
- Crawler、Indexer、OpenSearchなどのバックエンドコンポーネントの機能追加
- 認証・認可機能の実装
- TLS対応および外部ネットワークへの公開
- 実環境を対象とした独立した結合テストスイートの整備
- CI/CDパイプラインの整備
- 過去のタスクから申し送られている設計書の一括追従改訂

ただし、Admin Viewの実装に必要となる既存機能の不具合修正については、必要性および影響範囲を確認したうえで対応を検討する。

## 制約・前提条件

- 既存の機能設計書、UI設計書、デザインシステムおよびシステム設計書に従うこと。
- フロントエンドのシステム設計についてはv0.2を参照すること。
- APIの仕様については、実装済みのAdmin APIおよびOpenAPI定義を正とすること。
- 技術スタックおよびライブラリのバージョン管理方針は、既存の設計に従うこと。
- APIクライアントおよび型定義はOpenAPIから生成し、生成コードを手動で編集しないこと。
- Admin Viewはwebコンテナ(Nginx)から `/admin/` 配下に配信し、Admin APIへは同一オリジンの `/api/` を経由してアクセスすること。
- Crawler、Indexer、OpenSearchへフロントエンドから直接アクセスしないこと。
- APIのホストへの非公開方針およびwebコンテナのループバックアドレスへの公開方針を維持すること。
- 外部CDN、外部フォントなど、外部ネットワークへの接続を必要とするリソースに依存しないこと。
- 将来のSearch Viewとの共通化を考慮しつつ、現時点で不要な抽象化や機能追加を行わないこと。
- 設計上の未決事項や設計と実装の不整合が判明した場合は、対応方針を整理すること。仕様変更や重要な設計判断を伴う場合はユーザーに確認すること。
- 実装規模を考慮し、作業プランでは適切にフェーズを分割し、段階的に実装・検証・レビューを行うこと。
