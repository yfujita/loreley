## 2. I-1 `gen:api:check` の再設計(0002 フェーズ 1・9・11 を置換)

検査を 2 種類に分ける。

| 検査 | スクリプト | 方法 | 使う場面 |
| --- | --- | --- | --- |
| 再生成一致検査 | `npm run gen:api:check` | **Git に依存しない**。一時ディレクトリへ ① OpenAPI を書き出し ② そこから生成コードを出力し、作業ツリーの `openapi/admin-v1.json` と `src/admin/api/generated/` と `diff -r` で比較する。内容の差・追加・削除ファイルをすべて検出し、差があれば非 0 で終了する | 実装中、各フェーズの検証、品質ゲート |
| コミット後の整合性検査 | 手順(スクリプトにしない) | `npm run gen:api` の後、`git diff --exit-code -- openapi src/admin/api/generated` と `git status --porcelain -- openapi src/admin/api/generated` が空 | フェーズ 9 とタスクレビュー(フェーズごとにコミットするので成立する) |

- `gen:api:check` を実現するため、`openapi-ts.config.ts` の出力先を環境変数(例 `LORELEY_GEN_OUT`)で切り替えられるようにする。作業ツリーの生成物には書き込まない。
- フェーズ 1 の検証コマンドのうち `gen:api && git diff --exit-code && test -z "$(git status --porcelain ...)"` の行と「最初のコミット前は新規ファイルとして出る…」の注記は削除し、`npm run gen:api:check` に置き換える。
- フェーズ 1 の `code-reviewer` の確認点に「一時ディレクトリを使い、作業ツリーを変更しないこと」「ファイルの追加・削除を検出できること(わざとファイルを足して失敗することを確認)」を加える。

## 3. I-2 専用 compose 環境の事前確認と安全な起動・停止(0002 5 章に追加)

起動・停止は、scratchpad に置く 1 本のシェルスクリプト(例 `<scratchpad>/adminview-env.sh`。**リポジトリには置かない**)にまとめ、`up` と `down` が**同じ `-p`・`-f`・環境変数**を使うようにする。既存 IT の事前確認(`tests/integration/api/README.md:191`)に倣う。

**起動前の確認(1 つでも該当したら何も変更せず中止し、ユーザーに報告する。止める・消すことはしない)**

1. プロジェクト名 `loreley-adminview` のコンテナ(停止中を含む)、名前付きボリューム、ネットワークが存在しない(`docker ps -a` / `docker volume ls` / `docker network ls` をラベル `com.docker.compose.project=loreley-adminview` で絞る)。コマンドが失敗して確認できないときも中止。
   - 前回の自分の実行が残っている場合のみ、作業記録の起動記録(起動日時・プロジェクト名・使用ポート)と一致することを確かめたうえで、後始末してから作り直してよい。一致が確認できなければ中止してユーザーに報告する。
2. 使うホストポート(例 `OPENSEARCH_HOST_PORT=19200`・`INDEXER_HOST_PORT=18000`・`CRAWLER_HOST_PORT=18001`・`WEB_HOST_PORT=18090`。実際の値は事前に空きを確認して作業記録に書く)が空いている(`lsof`)。使用中のコンテナがあれば表示するが止めない(別プロジェクトの Fess 等)。
3. `CRAWLER_DOCUMENTS_DIR` の専用ディレクトリが存在しない、または空である(自分が作る)。
4. `docker compose -p loreley-adminview -f deploy/compose/compose.yaml [-f <override>] config` で展開結果を確認し、作業記録に保存する。確認項目: プロジェクト名、全ポートが `127.0.0.1` だけの publish で 2 のポートに一致、`api` が publish されていない、マウント元が専用ディレクトリ、ボリューム名が `loreley-adminview_*`。`deploy/compose/.env` やシェルの環境変数に左右されないよう、スクリプト内でポートとパスをすべて明示する。

**停止(`down -v`)の前の確認**

- `-p loreley-adminview` を必ず付ける。
- `docker compose -p loreley-adminview ... ps -a` と、プロジェクトのラベルが付いたボリュームの一覧を表示し、**すべてこのタスクの起動記録のもの**であることを確認してから `down -v --remove-orphans` を実行する。
- `down` が失敗したときは、専用ディレクトリを削除せず、手動で消す手順を報告する(使用中のマウント元を消さないため)。
- 専用ディレクトリの削除は、`down` が成功した後に行う。

## 4. I-3 Playwright の `webServer` を専用ポートにする(0002 2 章・フェーズ 1 を置換)

```ts
webServer: {
  command: 'npm run dev -- --port 15173 --strictPort',
  url: 'http://localhost:15173/admin/',
  reuseExistingServer: false,
  env: { LORELEY_DEV_API_TARGET: 'http://127.0.0.1:1' }, // 実環境に届かない転送先。モック漏れは失敗する
},
use: { baseURL: 'http://localhost:15173/admin/' },
```

- `strictPort` により、15173 が使用中なら起動に失敗する(別のサーバーを使わない)。
- 転送先を到達不能にして、モック設定の漏れが実 API に届かないようにする(多重防御)。未モックの `/api/` を失敗扱いにする仕組みは維持する。
- 手動確認・UI レビュー用の dev サーバーは 5173(`LORELEY_DEV_API_TARGET` に専用 web を指定)で起動し、E2E と衝突しない。
- **設計との差異として記録する**: E 10.2 / F の `baseURL`・`webServer` は 5173・`reuseExistingServer: !process.env.CI`。専用ポート・再利用なしへ変更する。設計書は Q2 のとおり改訂せず、作業記録と申し送りに残す。

**ユーザーの回答(2026-11-27)**: フェーズごとのローカルコミットを行う。**push・PR 作成は、ユーザーが指示するまで行わない**(0001 の方針のうち、コミットだけをこのタスクで許可に変更)。

運用:

- フェーズ 1 の開始前に、`main`(`8a20d67`)から作業ブランチ `feature/implement-admin-view` を作る(既存の `feature/…` の慣習に合わせた)。`main` には直接コミットしない。
- 比較基準は、各フェーズの**開始時点の SHA**(前フェーズ終了時の HEAD)。フェーズ 1 の基準は `8a20d67`。
- 各フェーズの流れ: 実装 → **実装コミット** → レビュー(対象は `開始SHA..HEAD`)→ 指摘の修正 → **修正コミット**(必要なだけ)→ 再レビュー → 作業記録・`STATUS.md` を更新 → **記録コミット**。コミットは Critical・Important が解消してから「フェーズ完了」とする。
- コミットメッセージは日本語で、フェーズ番号と内容を書く(例「Admin View フェーズ 1: ツールチェーン・型生成・テスト基盤を追加する」)。末尾に指定の `Co-Authored-By` 行を付ける。
- `agent_tasks/20261127_implement_admin_view/` の作業記録・`STATUS.md` も、各フェーズのコミットに含める(過去タスクの慣行)。`.env`・秘密情報・scratchpad のファイル・Playwright の出力は含めない(`.gitignore` で除外を確認する)。
- amend・rebase・force push はしない。ユーザー自身の未コミットの変更が作業ツリーにあるときは、それを巻き込まない(コミットは明示したパスだけを `git add` する)。
- レビュー依頼には、`開始SHA..HEAD`(または特定の 2 コミット)を比較基準として渡し、作業記録の変更ファイル一覧は補助に使う。
- **ロールバック(0002 13 章を置換)**: 作業ブランチ上で、ユーザーに確認のうえ `git revert`(フェーズ単位)で戻す。`git reset --hard`・`git checkout -- <path>` でユーザーや過去フェーズの成果物を消さない。`main` と他のブランチには触れない。実機環境は 3 章の手順で `down -v` する。
- 0002 13 章のリスク「差分が累積しレビュー範囲がぼやける」は解消扱いにする。
