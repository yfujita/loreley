# 0003 プラン更新: 静的コンテンツは Web コンテナ(Nginx)で配信する

- 日付: 2026-11-26
- 種別: 方針を変える指示(task-workflow「途中の追加指示」)に対するプラン更新。0002 は書き換えず、本記録の差分で上書きする(0002 と本記録が食い違う場合は本記録を正とする)
- 承認状況: **ユーザー承認待ち**(0002 + 本記録の差分で承認を取り直す)

## 1. ユーザーの指示(2026-11-26。プラン承認の質問への回答)

> Admin Viewの静的コンテンツはNginxで配信することになってたと思うんだけど、それは考慮されてるだろうか。もし未考慮ならばその前提としてほしい。APIコンテナで静的コンテンツを配信するのではなく、WEBコンテナ（Nginx）で静的コンテンツを配信する。Viewから叩くAPIもNginx経由でプロキシしてアクセスする。

## 2. 確認結果(メインエージェントが grep と該当箇所で確認)

- **未考慮**。`docs/v0.x/system-design`・`docs/v0.x/product-design`・`agent_tasks` に Nginx の記述はない
- 既存設計は逆の方針で確定している:
  - BAPI-K-2「Web UI は `api` が静的配信する(同一オリジン。CORS 不要)」(A 2.1。ユーザー確定 2026-11-22)、FARC-K-4(E)、HO-2(`web` は独立コンテナにしない)
  - A 2.2 の BAPI-P-2(`/admin/` の `app.frontend()` による配信・SPA フォールバック)、BAPI-U-1、G3-16(`WEB_DIST_DIR` の既定 `/app/web`)、HO-36(`api` の Dockerfile に Node ステージ)、HO-37(ビルドコンテキスト)
  - E v0.1 3 章(ビルド・配信)、開発プロキシ(FARC-P-19。`/api` → `127.0.0.1:8080`)
- システム設計 §7.2 は「`web`:Web UI(API と同居してもよい)」で、独立コンテナ化を禁じていない(`system-design-v0.8.md:1048`)。本指示は §7.2 の範囲内で「同居しない」を選ぶものであり、システム設計の改訂は不要(同居の形態の確定を A が行っていたため、A への追従が要る)
- 要件 0000 の「APIサーバーから静的配信する構成を基本とする」は、本指示により上書きされる。0000 はユーザー記載の文書のため書き換えず、本記録に残す

## 3. 前提の変更(確定事項として扱う)

| 項目 | 変更前(v0.1・A) | 変更後(本指示) |
| --- | --- | --- |
| 静的配信の担い手 | `api` コンテナ(FastAPI `app.frontend()`) | **`web` コンテナ(Nginx)**。`/admin/` 配下の SPA を配信し、未知パスの `index.html` フォールバックも Nginx が行う |
| Admin API への経路 | ブラウザ → `api`(同一オリジン) | ブラウザ → **Nginx → `api`**(`/api/` をリバースプロキシ。ブラウザから見て同一オリジンなので CORS は引き続き不要) |
| ビルド | `api` の Dockerfile に Node ステージ(HO-36) | **`web` の Dockerfile**(Node でビルドし Nginx イメージに `dist/` を載せる多段ビルド)。`api` イメージは Web に依存しない |
| 開発環境の `/api` プロキシ | Vite の `server.proxy` で `127.0.0.1:8080` | 維持(開発時のみ。Nginx 経由の確認は compose で行う) |

## 4. 影響と、プラン(0002)への差分

### 4.1 影響範囲

- E v0.2: 3 章(ビルド・配信)、4 章(アプリ構成)、開発環境、FARC-K-4・FARC-P-3・P-19・P-20 など。**FARC-K-4 は「ユーザー確定の事実」の変更**になるため、区分と理由(ユーザー指示 2026-11-26)を明記する
- F v0.2: 配信に関わる記述(`dist/` の置き場・依存ルールの検査・テスト配置)
- A 9 章(HO): HO-2 の内容が逆になる。HO-36・37 は「`api` の Dockerfile」から「`web` の Dockerfile・compose への `web` サービス追加」に読み替える。A 本文(2.1・2.2・BAPI-K-2・BAPI-P-2・BAPI-U-1・G3-16)の追従改訂は、0001 の前提(A は HO の追加・状態更新のみ)に従い **HO で申し送る**
- 前提タスク B は「`api` の `/admin/` 静的配信」から「**`web` コンテナ(Nginx)の追加**」に変わる(内容は 4.3)
- `api` 側: `web_dist.py`(`infrastructure/probes/web_dist.py`)の死活確認と `LORELEY_API_WEB_DIST_DIR`、README、`api` が `dist/` を要する前提が不要になる。**`api` の実装変更が必要になりうる**(スコープ外のため前提タスクに積む)

### 4.2 0002 の各フェーズへの差分

- **P1(照合)**: P1-3 の担当に「静的配信の撤去に伴う `api` 側の依存(`web_dist.py` のプローブ、`WEB_DIST_DIR`、`/healthz` の判定、README・OpenAPI の `servers`)の洗い出し」を追加する。あわせて `deploy/compose/` の `api` サービスの公開(`127.0.0.1` publish)と、`web` を足したときの公開範囲の整理を行う(コード変更はしない。読み取りのみ)
- **P2(技術検証)**: (b) のビルド検証に「Nginx 配信向けの成果物の確認」を加える: `dist/` が `base: '/admin/'` で出力されること、Nginx の `location /admin/` の `try_files` による SPA フォールバック設定案、`/api/` の `proxy_pass` 設定案(タイムアウト・本文上限 1 MiB との整合・`Cache-Control` の素通し)。**Docker が使える場合に限り `nginx -t` で設定構文を確認**し、コンテナを常駐起動しない。使えなければ「未検証」として実装時確認に回す。(a)・(c) は変更なし
- **P3(ゲート4)** に確認事項を追加:
  1. **配信方式の変更の承認**(FARC-K-4・BAPI-K-2 の変更。本指示の反映案: 上の 3 章)。**承認済みのユーザー指示の反映**であり、案の中身(Nginx の設定方針・`web` コンテナの構成・`api` の公開範囲)を承認対象にする
  2. 前提タスクの切り方(下の 4.3 の再定義で再提示)
  3. `api` をホストに publish し続けるか(Nginx 経由に一本化するか)。推奨: **`web` だけを `127.0.0.1` に publish し、`api` の publish は開発用に残すかを決める**(認証なしの破壊的操作を公開するため、公開範囲は現状の制約 `127.0.0.1` に限る)
- **P4・P5**: 上記を反映して E・F を書く。E の 3 章に「Nginx 配信」の方針(配信・フォールバック・プロキシ・キャッシュ・外部 CDN 非依存)を置く。Nginx の個別設定値は実装時確認(FARC-U)に回す範囲を P3 で決める
- **P6**: HO-2 の更新(「`web` コンテナ(Nginx)で配信。`api` は配信しない」への変更要求)、HO-36・37 の読み替え、A 本文の追従改訂の HO 追加(BAPI-K-2・P-2・U-1・G3-16 など)
- **P7**: レビュー観点 2(v0.1 承認済み方針の保存)に「ゲート4 で承認された配信方式の変更が、E・F・A の HO に矛盾なく反映されているか」を追加。観点 6(スコープ)に「`apps/api`・`deploy/` の変更なし」を維持
- **スコープ**: 要件 0000 のスコープ外(Admin API の実装変更、Dockerfile・compose の実装変更)は変えない。`api` の改修(プローブ・設定の削除)と `web` コンテナの追加は前提タスクとして一覧化するのみ

### 4.3 前提タスクの再定義(ゲート4 で切り方を決める)

- **前提タスク A「OpenAPI の型の修正」**: 変更なし(`ttl_days`・`ttl_seconds`、`openapi_export.py` の docstring)
- **前提タスク B「`web` コンテナ(Nginx)の追加」**(旧「`api` の静的配信と Docker ビルド」を置き換え): `apps/web` の Dockerfile(Node ビルド → Nginx)、Nginx 設定(`/admin/` の配信と SPA フォールバック、`/api/` のプロキシ)、compose への `web` サービス追加(公開範囲 `127.0.0.1`)、ビルドコンテキスト(HO-37 の読み替え)
- **前提タスク C「`api` からの静的配信の撤去」**(新規。小): `web_dist.py` のプローブと `LORELEY_API_WEB_DIST_DIR`、`api` の Dockerfile の古いコメント、README の更新、`app.frontend()` を実装していない(未実装)ことの確認。B と同時にまとめるか別にするかはゲート4 で決める
- 推奨: A(型の修正。フロント実装の着手前に必要)と、B+C(配信の整備。dev サーバー+プロキシで実装を始められるため、初回リリース前に必要)の **2 本**
