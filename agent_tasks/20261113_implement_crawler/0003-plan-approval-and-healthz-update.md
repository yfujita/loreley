## 2. プランの変更(方針を変える指示のため記録)

0002 は「`/healthz` を追加せず、Dockerfile に `HEALTHCHECK` も付けない」前提だった(§4.2、§9-2)。ユーザー回答でこれが変わった。0002 の他の部分(P1〜P9、レビュー計画、タスクレビュー、完了条件)は承認どおり維持し、次を変更・追加する。

### 2.1 追加: P0 設計書の改版(`/healthz`)— P1 の前に実施

- 理由: CM-U-5・CAPI-U-9(ヘルスチェックの要否)は「運用・crawler-api の改版時」に決める事項で、実装者は決められない(decisions v0.2 §5)。0002 §9-2 のとおり、`/healthz` を追加するには設計書の改版が先。ユーザーが要否を決定したので、改版に反映する。
- 内容: ユーザー回答(要=追加する)を CM-U-5・CAPI-U-9 の確定として記録し、設計書の新版を作る。仕様は module-structure CM-U-5 の既存の案(`api` が担当機能を呼ばずに受付開始後に 200 を返す。Indexer と同趣旨。契約外の API)を出発点にする。ユーザーが指定したのは「追加する」ことだけで、応答の形などの詳細は案のままとし、確定扱いにしない。
- 対象(最小限。必要な範囲を document-writer が判断して報告): `crawler-api-v0.3.md`(`GET /healthz` の追加、CAPI-U-9 の更新)、`crawler-module-structure-v0.4.md`(`api` の責務、CM-U-5 の更新、起動順との関係)。architecture・decisions は、CM-U-5 を参照する表などの整合に必要な場合のみ新版にする。旧版は変更しない(docs は版ごとに新規ファイル)。
- 担当: `document-writer`。レビュー: `document-reviewer`(別エージェント)。指摘の Critical / Important は解消してから P1 に進む。
- 他の未確定・案を確定扱いにしない。CA-U-14、CAPI-U-1・2・5・6 など他の項目は変更しない。

### 2.2 変更: P8(`api`)

- `GET /healthz` を実装する(P0 の新版どおり。担当機能を呼ばず、受付開始後に 200)。P8 の「`/healthz` が存在しないこと」のテストは、`/healthz` の応答テスト(200、担当機能を呼ばない、起動順どおり回復完了前は応答しない)に置き換える。

### 2.3 変更: P9(Dockerfile・起動確認)

- `Dockerfile` に `HEALTHCHECK` を付ける(`apps/indexer/Dockerfile` に倣う。P0 の新版の仕様に従う)。
- 起動確認(完了条件9): `docker build` の成功、必須設定なし/Indexer 上限超過で `docker run` し整合性検査の違反で異常終了すること(fail-fast)、非 root・import 確認。`/healthz` が `healthy` になることの確認は、起動時に実 OpenSearch への接続と起動時回復が必要なため、実 OpenSearch・実 Indexer を使う確認(Integration Test、スコープ外)に持ち越す。TestClient の単体テストで `/healthz` の応答は確認する。
- README に `/healthz` を記載する。compose へのヘルスチェック設定は infra 前提作業(別タスク)。

### 2.4 変更: 実装者への禁止事項(0002 §4.2)

- 「実装者は `/healthz` を追加しない」を「P0 の新版に従って実装する(P8)」に置き換える。他の禁止事項は変更なし。

## 3. 変更しないもの

- 設計書の改版は `/healthz`(CM-U-5・CAPI-U-9)に限る。0001 の「設計書(docs)は変更しない」は、本件に限り P0 の新版作成として例外とする(要件定義の対象範囲に `docs/system-design/crawler` が含まれる)。`apps/indexer`・infra・compose は変更しない。
- 採用案の一覧は設計書の承認ではない(0002 §9-4、承認済みの確認)。設計書 v0.2 の承認と decisions 4章の10件の確定はユーザー判断待ちのまま。
