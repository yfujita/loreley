## 2. ログ AST 検査の対象限定(P2-2。P2 のテストを変更)

0002 P2 の「ソース全体の AST 検査: `extra`/`exc_info`/`stack_info`/`.exception` 不使用」を次に置き換える。

- **ログ呼び出しに限定する**: 対象は、ログ出力のメソッド(`debug`・`info`・`warning`・`warn`・`error`・`critical`・`exception`・`log`)の呼び出しだけ。これらの呼び出しで、
  - キーワード引数 `extra`・`exc_info`・`stack_info` を使っていない
  - `.exception(...)` を呼んでいない(`exc_info` を暗黙に付けるため)
- ログ以外の `extra`(例: pydantic の `ConfigDict(extra="forbid")`、`model_config = {"extra": ...}`)は検査対象にしない。**自己テストで、これらが違反にならない正例を含める**
- 検査器の自己テスト: 合成ソースで、`logger.error("x", exc_info=True)`・`logger.info("x", extra={...})`・`logger.exception("x")` が違反、`ConfigDict(extra="forbid")` と `foo(extra=1)` が非違反になること
- 目的(値・例外メッセージをログに出さない。A 5.5)は、P2 の middleware テスト(ERROR ログに `exc_info` がなくメッセージのセンチネルが出ない)でも担保する

## 3. サブアプリの lifespan のテスト(P2-3。P3 のテストを追加)

0002 P3 のテストに次を追加する(ダミーのサブアプリと、テスト専用のリソースを使う。製品コードに終了処理の仕組みは足さない)。

- 親の lifespan(`create_app(lifespan=...)` に渡したもの)で、起動時に初期化処理が1回だけ実行される
- 親の終了時に終了処理が1回だけ実行される
- 親の lifespan で用意したリソースを、マウントしたサブアプリのハンドラが利用できる(例: `app.state` を介さず、クロージャで渡したダミーのクライアントが、リクエスト中は開いており終了後は閉じている)
- **マウントしたサブアプリ自身に lifespan を付けても、親の起動・終了では実行されない**(Starlette の挙動の確認。admin 実装時の注意の根拠を固定する)
- 不採用: 「複数の終了処理の一部が失敗しても他を実行する」テスト(上記の表のとおり、要件外)

## 4. OpenAPI との接続の申し送り(P3-1)

HO-51(§1)に次を含める。基盤では実装しない。
- サブアプリをマウントする構成では、外側の `app.openapi()` に Admin API のスキーマは集約されない。Admin API の OpenAPI は `create_admin_app(...).openapi()` で生成する(型生成の入力。A 5.4 の BAPI-P-9・BAPI-P-10 と整合)
- 外側アプリは `openapi_url=None` のため、公開する場合はサブアプリ側の設定で行う

## 5. 検証コマンドの修正(P3-2)

0002 の P4 の手動検証と P5 の検証の `curl -s …` を、ステータスコードを確認する形にする。
- `/healthz`: `curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:<port>/healthz` が `200`
- 本文: `curl -s http://127.0.0.1:<port>/healthz` が `{"status":"ok"}`
- 未知のパス: `curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:<port>/nope` が `404`、本文は `curl -s http://127.0.0.1:<port>/nope` で JSON(`error.code` が `not_found`)
- P5 の `<port>` は `18080`、P4 は `8080`(使用中なら変更)
