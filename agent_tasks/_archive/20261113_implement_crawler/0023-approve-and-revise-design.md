## 1. ユーザーの指示(原文)と解釈

「未確認事項について、設計書は承認する。2設計書の改版に反映する。それ以外は別タスク」

- 「未確認事項」= STATUS.md「ユーザー判断待ち」の5項目。
- 1「設計書の承認」→ **承認された**。2「設計書の改版」(「2設計書の改版」は判断待ち 2 の意)→ **実施した**(本記録)。3 infra 前提作業の起票・4 コミット・5 Integration Test →「それ以外は別タスク」。**本作業では何もしていない**。
- **メインの解釈**: 承認は「Crawler 設計書の現行版全体」(architecture・api・module-structure・decisions・connector の interface/file-system/web)。`-P-` は**承認済みの案**になる(案を変えるにはユーザー判断が要る)。decisions v0.3 の4章の10件と CM-U-4・CA-U-3 は案どおりで解消。**4章の ID 列にない `-U-` は新たに解消していない**(未回答の判断を承認扱いにしない)。`-K-`(確定)への付け替えはしない(確定の定義は不変)。承認は仮値(数値)の確定ではない。
  - 根拠: 判断待ち 1 の文面が「Crawler の設計書(architecture・api・module-structure・decisions の v0.2 と新版、connector の v0.2)はユーザー承認前」+「decisions 4章の10件も未回答」と、設計書全体と10件の両方を挙げていたため。
  - レビュー(document-reviewer)が「承認の範囲は『全 `-P-`』か『10件だけ』か、ユーザーに確認が望ましい」と指摘した(API 担当のレビューは Suggestion、module・decisions 担当のレビューは Important)。**ユーザーへの確認事項として残す**(§6)。

## 4. 実装(`apps/crawler`)との関係

- 設計書の新版は実装を正として書いた。**実装の変更は行っていない**(pytest 等は再実行していない。設計書のみの変更)。
- 実装が設計書の案から逸脱した箇所は、見つからなかった(各新版が自己申告した CA-P-60・62・70、CFS-P-25 は理由つきで書かれている)。

## 5. 最終整合レビューの結果

- **結果**: 軽微な修正で可(Critical なし。Important 5件)。1回目の指摘は実装と照合して正しく反映され、実装と食い違う新規の事実誤りはなかった。承認で解消した行はすべて ID 列(decisions v0.3 の4章の表+CM-U-4・CA-U-3)の範囲内、Web v0.3 の仕様変更なし(注記のみ)、実装で決めた内容を承認・確定と書いた箇所なし。
- **Important 5件と対応**(いずれも文言の統一。書き手に反映させた): (1) architecture 13.8 の CI-U-3・4 の「残る論点」を interface 11.4・decisions にそろえた (2) CA-U-9・CA-U-10 の残る論点を architecture・decisions・module でそろえた (3) 「connector-web は v0.2 のまま」の残りを v0.3 に (4) Web v0.3 の CA-U-19 (b)(c) を「採用しないと承認済み。再検討はユーザー判断と改版が要る」に (5) api の CAPI-U-7 の残る論点を 5.4 の (a)〜(c) にそろえた。Suggestion(CA-U-4 の残りの明示、decisions の CAPI-U-7 の二重掲載、module のフラグ読み取り回数の条件、CM-P-27 の表記、interface の旧参照、FS の参照確認の注記)も反映した。
- **3回目のレビューは省略**: 理由は、反映が文言の統一だけで仕様・ID・状態を変えていないこと。メインが機械検査した(「設計として確定」等の語の残りなし、`web-v0.2` の参照は前版表記のみ、旧版 docs の更新時刻・git 差分なし)。決定した ID 状態は書き手が最後に grep で再照合した。

## 6. 未対応事項・ユーザーに確認したいこと
