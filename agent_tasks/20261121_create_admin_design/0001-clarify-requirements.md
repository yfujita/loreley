## 確定した要件

### 目的・背景
- Admin View のデザインを作成する。機能設計(`docs/v0.x/system-design/ui-admin/ui-admin-functions-v0.1.md`)はあるがデザインがない。
- To-Be: デザインが揃い、実装を始められる状態。
- 機能は今後拡張されるため、簡単に機能拡張できるデザインにする。

### スコープ
- 対象: Admin View の MVP 全機能(AF-1〜20)の全画面。共通 design-system(トークン・共通コンポーネント・レイアウトシェル)。Search View でも流用できる形にする。
- 将来拡張(AF-21〜32)は画面を作らず、拡張ポイントと画面追加手順のみ仕様書に書く。
- 対象外: Search View / Chat View の画面、実装(`apps/web/` など)。

### 技術スタック(案)
- Vue 3 + TypeScript、Vite、PrimeVue 4(Styled mode。Aura を `definePreset` でトークン上書き)、PrimeIcons、Vue Router、TanStack Vue Query、Vitest + Vue Test Utils、Playwright、ESLint + Prettier。
- Admin API 設計後に OpenAPI から型を生成する。
- 初期は入れない: Pinia、Tailwind、vue-i18n。
- Web フォント・CDN は使わない(外部通信を必須としない方針。SD §7 冒頭)。
- 本タスクでは SD/PD を書き換えない。

### 完了条件・成果物
1. 仕様書2本: `design-system-v0.1.md`(トークン・共通コンポーネント・技術スタック案)、`admin-view-v0.1.md`(情報設計・ナビ・画面一覧・遷移・各画面仕様・拡張ガイド・AF トレーサビリティ)。1ファイルが大きくなる場合は `docs/v0.x/ui-design/admin/` 配下に画面グループごとに分割し、`admin-view` を索引にしてよい(設計者が判断して報告)。
2. AF→画面のトレーサビリティ表。AF-1〜20 のすべてが少なくとも1画面に対応づく。
3. 全 MVP 画面に ASCII ワイヤーフレーム。
4. 全 MVP 画面に静的 HTML モック(`docs/v0.x/ui-design/mockups/` 配下、画面グループごとの自己完結した1ファイル)。通常/空/エラー/読み込み中の状態と、危険操作(強制削除・データソース削除・ロック解放・再実行(`rewrite_mode` 指定を含む))の確認ダイアログを含める。
5. 375px と 1280px のスクリーンショットで確認済み。
6. document-reviewer のレビューを通している。
7. ユーザーが重要判断(方向性・トークン・ナビ構造・技術スタック)を承認している。
8. 進行は2段階: 第1段階で design-system・シェル・代表画面1つを作りユーザー承認 → 第2段階で残りの画面。

### 置き場所・命名・版
- `docs/v0.x/ui-design/`、モックは `mockups/`。仕様書 `{対象}-v{版}.md`、モック `{対象}-v{版}.html`。版は v0.1 から。冒頭に「版・更新日・前版・改訂の要点」。
- 0000「補足・参考情報」の `docs/v0.x/ui-admin/` は誤記。実際のパスは `docs/v0.x/system-design/ui-admin/ui-admin-functions-v0.1.md`(0000 は書き換えない)。

### 既存設計から導かれる制約
- MVP は認証なし・単一ホスト。要件にない機能は追加しない。
- 機能設計が画面設計に委ねた事項(AF-U-3(a)(c)、AF-U-5、AF-U-7、UC-18 など)は、デザイン案として提示しユーザー承認を取る。
- ユーザー未確認の導出(AF-8 の起動時指定の表示、AF-7・AF-8 のロック解放前後の区別、AF-18 の「判定不能」)を UI に反映する場合は「案」と注記する。
- Admin API は未設計。画面のデータ項目は機能設計書に基づく。
- web-ui-designer は `agent_tasks/`・`system-design/`・`product-design/` に書き込めない。不整合・追記の必要は報告で返す。

## 前提(案)— ユーザー未確認。プランおよび仕様作成フェーズで承認を取る

1. 画面設計に委ねられた点(AF-5〜AF-7 の確認操作の要否、強制削除の確認の出し方、`rewrite_mode` の案内など)は設計案を出して承認を取る。
2. デスクトップ優先(1280px 基準)、768px・375px は崩れない最低限。ライトテーマのみ。
3. 日本語のみ。用語は PD の用語集に従う。
4. 外部フォントは使わず、システムフォント。
5. アクセシビリティ: キーボード操作、フォーカス順序、ラベル、色だけに依存しない状態表示、コントラスト比。
6. テスト容易性: ロール・ラベル基準の要素特定。必要箇所のみ `data-testid` 命名方針。E2E テスト設計は対象外。
7. 拡張しやすさ: 左サイドバーシェル、ナビ項目を route `meta` で一元管理、画面テンプレート4型(一覧・詳細・フォーム/編集・ダッシュボード)、共通コンポーネント規約化(ステータスタグ、データテーブル、危険度別確認ダイアログ、キー・バリュー表示、空/エラー/読込状態)、画面追加手順と AF-21〜32 の型対応表。MVP にダミー項目は置かない。
8. データソース削除(AF-16)の確認は `source_id` 入力を案とする。他の危険操作も危険度の段階で整理。
9. 仕様書構成は 2本が基本。分割要否は設計者が判断。
