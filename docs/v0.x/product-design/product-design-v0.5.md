## 1. 目的とスコープ

### 1.1 概要

オンプレミス環境やローカル環境で動作し、AI Agentから利用できる**汎用的な社内ドキュメント検索基盤**を提供する。

複数のデータソースからドキュメントを収集して索引化し、OpenSearchで検索できるようにする。検索機能はSearch APIとMCPで提供し、Web UIからも直接検索できる。

中心的な責務は**ドキュメントの収集・管理・検索・取得**である。LLMによる回答生成は必須機能にしない。AI Agentや外部アプリケーションが検索結果を使って回答を生成する構成を基本とする。

### 1.2 目的

- 社内の設計書、手順書、議事録などを、AI Agentが横断して検索・取得できるようにする。
- 利用者がWeb UIから文書を検索し、出典（パス・URL）を確認できるようにする。
- 管理者が、検索対象、クロール周期、インデックスの状態を管理できるようにする。
- 外部サービスへの通信なしで、単一ホストに導入できるようにする。

### 1.3 想定ユーザー

| ユーザー | 主な用途 |
| --- | --- |
| AI Agent（MCPクライアント） | `search_documents`で候補を探し、`get_document`で必要な文書を読む |
| 利用者（社内の従業員） | Search Viewでキーワード検索し、要約・関連箇所・出典を確認する |
| 管理者・運用者 | データソースの登録、クロールの実行、失敗や削除保留の確認、再インデックス |
| 外部アプリケーションの開発者 | Search APIを使って独自のアプリケーションに検索を組み込む |

### 1.4 成功指標

非機能要件（文書数・レイテンシ・同時利用数など）は、実装後に実測して決める（9.2）。MVPでは次を指標とする。

| 指標 | 内容 |
| --- | --- |
| 検索品質 | 評価セット（50問程度）でRecall@10とMRRを測定し記録する。目標値は初回の測定後に決める（8.3） |
| 導入の容易さ | Docker Composeの起動から、ローカルディレクトリの登録、検索までを通して動作する |
| Agent利用 | 主要なMCPクライアントで、検索から文書取得までを実行できる |
| 削除の安全性 | 取得の失敗・一時的な空応答・マウント外れで、文書が誤って削除されない |

### 1.5 非目標

- LLMによる回答生成（Chat Viewは将来拡張）。
- MVPでの認証・認可、文書単位のアクセス制御。
- 原文への遷移（パスまたはURLの表示にとどめる。URLへの写像は将来拡張）。
- 画像のみのPDFのOCR、Office文書の抽出（次版）。
- ファイルのリネーム追跡、チャンク分割、ベクトル検索（評価結果を見て判断する）。
- 数十万件を超える規模や、高可用構成。

### 1.6 設計方針

- **セルフホストを基本とする**：Docker Composeで導入でき、外部サービスへの通信を必須としない。
- **検索基盤と回答生成を分離する**：特定のLLMやAI Agentに依存しない。
- **ドキュメント単位のインデックスを基本とする**：全文・タイトル・要約を検索対象とし、チャンク分割は必須にしない。
- **OpenSearchを検索基盤とし、設定や処理状態の保存にも使う**：専用のDBを置かず、Store層を介してOpenSearchをKVSとして使う。将来、バックエンドを差し替えられるようにする。
- **拡張できる構成にする**：Connector、検索方式、要約・Embeddingの生成方式、Store層のバックエンドを差し替えられるようにする。
- **安全な検索を前提とする**：閲覧できない文書を返さない。MVPはこの原則を「運用前提」で満たす（6.1）。
- **とにかく動かすことを優先する**：MVPでは保護機能や最適化より、動作する最小構成を優先する。割り切った点はリスクとして明記する（2章）。

## 2. 主要リスクと許容する制約

| リスク | 影響 | 緩和策・方針 | 検証項目 |
| --- | --- | --- | --- |
| 全件更新の負荷 | MVPでは差分検知をせず、毎回すべての文書を処理する。文書数に比例して、クロール時間と書き込み負荷が増える。1万〜10万文書の想定でも、クロール間隔内に完了するかは未検証 | 想定規模（9.1）の範囲で使う。クロール間隔は所要時間より長く設定する。負荷が問題になれば、差分検知（→ システムデザイン §3）を導入する | 代表的な規模でクロール所要時間と書き込み量を実測する |
| 読めない文書による削除の停止 | 権限エラーなどで読めない文書が1件でもあると、そのソースの削除が止まり続ける（恒久失敗の判定をMVPから外したため） | 管理者がAdmin Viewで失敗した文書を確認し、手動で削除または除外する | 読めない文書があるときの削除の停止と、手動対応の手順を試験する |
| Admin Viewを保護しない | 到達できる人は誰でも、データソースの登録（コンテナから見える任意のローカルパスを含む）、削除の承認、再インデックスを実行できる | MVPでは認証を実装しない。6.1の運用前提で使う。**検索対象のディレクトリだけを読み取り専用でマウントして、実行環境側の境界を厳格にする**（→ システムデザイン §6） | 将来の版で、管理者トークン、登録できるルートパスの制限を追加する |
| 日本語検索の品質 | 識別子・型番・複合語の検索漏れ | 日本語の形態素解析とn-gramの組み合わせを評価して選ぶ（→ システムデザイン §2） | 評価セットのRecall@10・MRR（8.3） |
| 長文のインデックスサイズ | 長文のハイライトのために索引が増える | 本文サイズの上限を設ける（→ システムデザイン §2、§10） | 増加量と上限値を実測する |
| OpenSearchをKVSにすることによる整合性・排他 | ニアリアルタイム検索、トランザクションなし、ノード障害時のデータ消失 | IDによる取得と条件付き更新を使う。スナップショットを取る（→ システムデザイン §1、§9） | 排他とリース切れの動作を実装時に試験する |
| 誤削除 | 取得の失敗で文書が消える | 列挙クロールの正常完了時のみ削除する。削除が多いときは保留する。0件列挙は異常扱いにする。Store層だけにある文書は自動削除しない（→ システムデザイン §3）。ただし、一部のディレクトリだけが消えた場合は0件保護で防げず、削除の保留しきい値以下の少数の消失は通常の削除になる。MVPはこれを制限事項とする | 異常系（マウント外れ、部分失敗）の試験 |
| 要約の品質・コスト | 要約が不正確、生成が遅い | 既定は無効。要約なしで検索できる（→ システムデザイン §8） | 要約モデルの選定と、生成時間・コストの測定 |
| プロンプトインジェクション | 文書中の指示がAgentの動作に影響する | 文書を加工せず、出典とともに「データ」と明示する（6.2） | MCPクライアントでの動作確認 |
| MCPの公開（認証なし） | 悪意あるWebページからローカルのMCPエンドポイントが呼ばれる可能性（DNS rebinding） | localhostだけで待ち受ける。**MCPのOrigin検証をMVPに含める**（6.1）。認証は引き続きMVPで実装しない | 許可外のOriginが拒否されることを試験する |

## 3. システム構成

```text
[社内ドキュメント / ファイル / Wiki / Git 等]
                    |
              Crawler / Connector
                    |
                 Indexer
        (抽出・正規化・要約生成)
               /         \
     検索インデックス      Store層（設定・ジョブ・抽出済みテキスト・処理状態）
               \         /     ※バックエンド差し替え可
               OpenSearch
          (検索用インデックス + KVS用インデックス)
                    |
                Search API
               /     |     \
         MCP Server Web UI  外部APIクライアント
              |       |
           AI Agent  利用者・管理者
```

※論理構成である。初期版では、複数のコンポーネントを同じプロセスやコンテナにまとめてもよい。

実装言語と技術スタックは、システムデザインで扱う（→ システムデザイン §7.5）。

## 4. コンポーネントと責務

### 4.1 Crawler / Connector

データソースから文書を列挙・取得し、Indexerに共通ドキュメント形式（→ システムデザイン §1）で渡す。ConnectorはデータソースごとのCrawlerの実装で、Crawlerはその実行・周期・同期状態を管理する。

- MVPのConnectorは、ローカルディレクトリ／ファイル共有のみ。HTTPサイト、Confluence、Gitなどは将来の拡張（Webページのスクレイピングも将来）。
- **列挙クロール**：データソース内のすべての文書を列挙するクロール。MVPのクロールはすべて列挙クロールで、削除の判定はこのクロールだけが行う。
- MVPは追加・更新の検知をせず、毎回すべての文書を取得・抽出して登録する（全件更新。差分検知は将来拡張）。削除は、最後に見つかった日時とTTLによる期限で判定する（→ システムデザイン §3）。
- 接続設定、認証情報の参照、実行周期、取得状況、エラーはStore層に保存する。

### 4.2 Indexer

収集した文書を検索できる形にして登録する。

- 文書形式に応じてテキストを抽出し、正規化する。MVPの対応形式はtxt・Markdown・HTML・PDF。Office文書は次版。文字コードは自動判定し、UTF-8のほかShift_JIS/CP932にも対応する。抽出ライブラリはシステムデザインで扱う（→ システムデザイン §7）。
- 抽出済みテキストをStore層に保存する。原本は保存せず、元システムを参照する。
- 文書全体の**検索用の要約**を生成する。主題、重要な概念、その文書で答えられる質問を表現する。既定では無効で、LLMを明示的に設定したときだけ有効になる。要約の失敗・遅延では、要約なしで先に登録し、後から非同期に生成する（→ システムデザイン §8）。
- 検索インデックスへの登録・更新・削除を行う。
- 抽出に失敗した文書は、タイトルとメタデータだけを登録し、抽出失敗としてAdmin Viewに表示する。本文がサイズ上限を超える場合は、上限までを索引化し、切り詰めたことを表示する。
- 登録に失敗した場合は、一定回数リトライし、それでも失敗したら個別文書の失敗として記録する。その場合、クロールは部分成功になり、削除は行わない（→ システムデザイン §3）。
- Embeddingの生成は初期版では任意とする。

### 4.3 検索インデックス（OpenSearch）

1文書 = 1検索レコードを基本とし、タイトル・要約・本文をBM25で検索する。日本語を主な対象とし、英語も併せて解析する。マッピング、検索クエリ、ハイライト、再インデックスは、システムデザインで扱う（→ システムデザイン §2）。

### 4.4 Search API

OpenSearchを使った共通の検索・文書取得インターフェースを提供する。MCP ServerとWeb UIは、原則としてこのAPI（または同じサービス層）を使う。

- ドキュメント検索：クエリ、データソース・文書形式・更新日による絞り込み、件数。
- ドキュメント取得：本文はStore層の抽出済みテキストから返す。AgentやUIを圧迫しないよう、範囲を指定して取得できる。
- 検索結果の整形：タイトル、要約、関連箇所、出典、スコア。
- 認証・認可は将来拡張（MVPでは実装しない）。

リクエスト・レスポンスの仕様は → システムデザイン §5。

### 4.5 MCP Server

AI Agentが文書を検索・取得するためのMCPインターフェースを提供する。Search APIの機能を公開するアダプタであり、独自の検索ロジックは持たない。

- Tool：`search_documents`、`get_document`、`list_sources`（仕様は → システムデザイン §5）。
- 通信方式はStreamable HTTP。Search APIと同じコンテナに置く。
- 読み取り専用。書き込み系のToolは提供しない。
- 認証は将来の版で追加する。MVPは6.1の運用前提で使う。ただし、DNS rebinding対策としてOriginの検証はMVPで行う（6.1）。
- クライアント互換性は、実装時に主要なMCPクライアントで確認する。

### 4.6 Web UI

**Search View（利用者向け）**

- キーワード検索と検索結果の一覧。
- 要約・関連箇所・出典（パスまたはURL）の表示。原文への遷移は提供せず、パスの表示にとどめる。
- 必要に応じた本文プレビュー。

**Admin View（管理者向け）**

- データソース・実行周期・TTLの設定と、クロールの手動実行。状態・エラー・最終同期時刻の確認。
- 抽出失敗・要約未生成・取得や登録に失敗した文書の確認と、失敗した文書の手動削除。登録が長く終わらない文書の警告。
- 削除保留と、0件列挙（全ファイルが消えた場合）の確認、承認、却下。Admin View上の表示を管理者への通知とみなし、メールなどの通知はMVPでは実装しない。
- 突合ジョブ（検索インデックスとStore層の食い違いの検出と安全な再登録）の手動実行と結果の確認。インデックス件数の確認。
- 再インデックスはMVPでは手動手順とし、画面からの実行は将来拡張とする。
- OpenSearch Dashboardsへの管理用の導線（任意。一般利用者には公開しない）。

**Chat View（将来拡張）**：Search APIを使った対話型の検索。初期版では必須にしない。

### 4.7 ジョブ管理

クロール・インデックス・要約生成はジョブとして管理し、状態をStore層に保存する。

- 同じデータソースのクロールは同時に1つだけ実行する。止まったジョブは失敗として検知する。再実行は、Worker再起動または管理者のロック解放のあとに行う。
- 一時的なエラーは、一定回数リトライする。失敗したジョブは、Admin Viewから再実行できる。
- 文書ごとの処理状態はジョブとは別に保持する。
- 状態遷移とリースの詳細は → システムデザイン §4。

### 4.8 データストア（Store層）

MVPではリレーショナルDBを使わず、**OpenSearchをKVSのように使って**設定・ジョブ・抽出済みテキスト・文書ごとの処理状態を保存する。コード上は検索インデックスとは別の「Store層」として扱い、アプリケーションはRepositoryインターフェースだけを経由して読み書きする。バックエンドは設定で差し替えられる。インターフェースの範囲（取得・保存・削除・単純な一覧・条件付き更新）は → システムデザイン §1.5。

- Connectorの認証情報は、Store層に平文で保存しない。環境変数や秘密情報ファイルで参照する。
- インデックス構成、真実の置き場所、排他と整合性は → システムデザイン §1。

## 5. データの流れ

### 5.1 収集・更新

1. Crawlerがデータソースを列挙する。
2. すべての文書を取得し、Indexerが本文を抽出・正規化して、Store層と検索インデックスに登録する（全件更新）。登録に成功してから、処理済みの印を確定する。途中で失敗した文書は、次回のクロールで再処理される。
3. 要約生成が有効なら、要約を非同期に生成し、本文が変わっていないときだけ反映する。

詳細は → システムデザイン §3、§8。

### 5.2 削除

1. 列挙クロールが正常に完了したときだけ、最後に見つかった日時にTTLを足した期限を過ぎた文書を、削除の対象にする。
2. 削除対象が多いときは、削除を保留して管理者の承認を待つ。保留はAdmin Viewに表示する（通知を兼ねる）。
3. 検索インデックスとStore層の食い違いは、突合ジョブで検出する。検索インデックスにだけある文書は削除し、Store層にだけある文書は、MVPでは自動削除せず、Admin Viewでの確認と安全な再登録にとどめる。

削除の判定、保留、突合の詳細は → システムデザイン §3。

### 5.3 検索・取得

1. AgentはMCP Serverを通じて、利用者はWeb UIを通じて検索する。
2. Search APIがOpenSearchを検索する（将来は認証・アクセス制御もここで適用する）。
3. タイトル・要約・関連箇所・出典を返す。
4. Agentは必要な場合だけ`get_document`で本文を取得する（長い文書は分割して取得する）。
5. 回答はAgent側で生成する（Chat Viewを設けた場合はChat Viewで生成する）。

## 6. セキュリティ・運用要件

### 6.1 アクセス制御と運用前提

MVPには認証・認可の仕組みがない。次の前提で運用する。

- 信頼できる社内ネットワーク内だけで公開する（インターネットに公開しない）。
- 利用者全員が閲覧してよい文書だけを検索対象として登録する。
- **Admin Viewも認証なしで、任意のローカルパスを登録できる。信頼できる環境だけで使う。**
- 既定ではlocalhostだけで待ち受ける。社内ネットワークへ公開するには、バインド先を設定で明示的に変更する。この前提はREADMEと導入手順で明示する。
- **実行環境側の境界を厳格にする**：Admin Viewは認証を省く代わりに、読み込めるディレクトリをコンテナへのマウントで限定する。検索対象のディレクトリは読み取り専用でマウントし、それ以外のホストのパスはコンテナに見せない。
- **MCPのOrigin検証（MVPに含める）**：DNS rebinding対策として、Origin検証をMVPに含める。**認証とは別の問題**であり、認証は実装しない（到達できる人は誰でも検索できる前提は変わらない）。許可Originの既定値、Originヘッダーのないリクエストの扱いは → システムデザイン §6.1、§6.2。

将来の版で、API/MCPのトークン認証、管理者トークン、登録できるルートパスの制限、データソース単位のアクセス可否、文書単位のACL同期、SSO連携を順に追加する。Search APIとMCPで同じ権限判定を適用する。

実装方法（Origin検証、ポートの制限、マウント、秘密情報の管理）は → システムデザイン §6。

### 6.2 その他の要件

- **機密情報**：Connectorの認証情報は平文で設定ファイルに書かない方法を用意する。ログに本文や秘密情報を記録しない。
- **OpenSearchの保護**：OpenSearchとDashboardsはホストの外に公開しない。Search APIだけを公開の窓口にする。
- **外部通信**：要約・Embeddingに外部LLMを使う場合は、明示的な設定を必須にする。既定の構成はオフラインで動作する。
- **プロンプトインジェクション**：文書を加工せずに返す。そのうえで、返す内容が「データソースから取得した文書」であることを出典とあわせて明示し、MCPのTool説明で、本文を指示として扱わないようAgentに注意を促す。
- **運用性**：クロール失敗の再実行、同期状態の確認、ログ、ヘルスチェック、バックアップ・リストア手順を用意する。
- **バックアップと再構築**：MVPではStore層もOpenSearchにあるため、OpenSearchのスナップショットと設定ファイルをバックアップの対象とする。検索インデックスは、Store層から再構築できる。検索インデックスとStore層の両方を失った場合は、再クロールが必要である（→ システムデザイン §9）。
- **再現性**：OpenSearchとプラグイン、各コンポーネントのバージョンを固定し、更新手順を提供する。

## 7. パッケージ化・配布

Docker Composeによるセルフホスト配布を基本とする。API（Search API / MCP Server）、Worker（Crawler / Indexer）、OpenSearch（MVPではStore層のバックエンドも兼ねる）、Web UIを構成要素とし、OpenSearch Dashboardsとローカルモデル用のコンテナは任意とする。

接続先、データの保存先、モデルの利用有無は、設定ファイルや環境変数で切り替えられるようにする。永続データはボリュームに保存する。日本語アナライザのプラグインを含む独自のOpenSearchイメージを配布する前提である。コンテナの分割、技術スタック、プラグインとバージョンの方針は → システムデザイン §7。

将来は、Kubernetes向けのHelm Chartなども検討する。

- [ ] Admin Viewからローカルディレクトリを登録し、クロールを手動実行できる。txt・Markdown・HTML・PDF（UTF-8とShift_JIS/CP932を含む）が検索できる。
- [ ] 日本語のキーワードで、タイトル・要約・本文が検索できる。ハイライトが長文でも失敗しない。

- [ ] 一部の文書の取得が失敗したクロール、列挙が0件のクロールでは、文書が削除されない。
- [ ] 削除対象が多いと削除が保留され、Admin Viewで承認すると削除される。

- [ ] 登録が長く終わらない文書はAdmin Viewで警告され、期限では自動削除されない。突合ジョブで、検索インデックスとStore層の食い違いが検出できる。
- [ ] 再インデックスの手順をREADMEに記載している。
- [ ] 検索対象ディレクトリのマウントが読み取り専用である。

## 10. 用語集

実装レベルの用語（`document_id`、`content_hash`、リース、`extractor_version`、`crawl_started_at`など）は → システムデザイン §13 で定義する。

| 用語 | 意味 |
| --- | --- |
| データソース | 収集対象の情報源（ディレクトリ、Wiki、Gitリポジトリなど）。管理者が登録する単位 |
| Connector | データソースごとの取得処理の実装 |
| Crawler | Connectorを実行し、スケジュールと同期状態を管理するコンポーネント |
| Indexer | 取得した文書からテキストを抽出・正規化し、要約を生成して、検索インデックスとStore層に登録するコンポーネント |
| Store層 | 設定・ジョブ・抽出済みテキスト・文書ごとの処理状態を保存する層。MVPではOpenSearchの別インデックスで実装し、Repositoryインターフェースで抽象化する |
| 検索インデックス | 検索用のOpenSearchインデックス。Store層とは別 |
| 列挙クロール | データソース内のすべての文書を列挙するクロール。削除の判定はこのクロールだけが行う |
| 全件更新 | 変更の有無を調べず、毎回すべての文書を取得・登録するMVPのクロール方式。対義は差分検知（将来拡張） |
| 最後に見つかった日時 | 列挙クロールで最後に見つかった日時。期限による削除の基準。フィールド名などの実装用語は → システムデザイン §13 |
| TTL | 最後に見つかった日時からの有効期間。データソースごとのクロール設定で指定する |
| 期限による削除 | 最後に見つかった日時にTTLを足した期限を過ぎた文書を、列挙クロールの正常完了後に削除する方式 |
| 削除保留 | 削除対象が多いときに、削除を止めて管理者の承認を待つ状態 |
| 突合ジョブ | 検索インデックスとStore層の食い違いを検出し、安全な範囲で直すジョブ |
| MCP | Model Context Protocol。AI Agentがツールを呼び出すためのプロトコル |
| Agent | MCPを通じて本プロダクトを利用するAI Agent |
| Search View / Admin View | Web UIの利用者向けの画面 / 管理者向けの画面 |

---

**現時点の結論**：ドキュメント単位の全文・要約検索を中心とする、セルフホスト型の検索基盤をMVPとして構築し、MCPから使えるようにする。MVPは認証なしで、信頼できるネットワーク内で使う前提とする。チャンク分割、ベクトル検索、Chat View、認証・認可は、評価セットによる実測と利用状況に基づいて段階的に追加する。実装レベルの設計は、システムデザインで扱う。
