## 1. 目的とスコープ

### 1.1 概要

オンプレミス環境やローカル環境で動作し、AI Agentから利用できる**汎用的な社内ドキュメント検索基盤**を提供する。

複数のデータソースからドキュメントを収集して索引化し、OpenSearchで検索できるようにする。検索機能はSearch APIとMCPで提供し、Web UIからも直接検索できる。

中心的な責務は**ドキュメントの収集・管理・検索・取得**である。LLMによる回答生成は必須機能にしない。AI Agentや外部アプリケーションが検索結果を使って回答を生成する構成を基本とする。

### 1.2 目的

- 社内の設計書、手順書、議事録などを、AI Agentが横断して検索・取得できるようにする。
- 利用者がWeb UIから文書を検索し、出典（パス・URL）を確認できるようにする。
- 管理者が、検索対象、クロール周期、インデックスの状態を管理できるようにする。
- 外部サービスへの通信なしで、単一ホストに導入できるようにする。

### 1.3 想定ユーザー

| ユーザー | 主な用途 |
| --- | --- |
| AI Agent（MCPクライアント） | `search_documents`で候補を探し、`get_document`で必要な文書を読む |
| 利用者（社内の従業員） | Search Viewでキーワード検索し、要約・関連箇所・出典を確認する |
| 管理者・運用者 | データソースの登録、クロールの実行、失敗や削除保留の確認、再インデックス |
| 外部アプリケーションの開発者 | Search APIを使って独自のアプリケーションに検索を組み込む |

### 1.4 成功指標

非機能要件（文書数・レイテンシ・同時利用数など）は、実装後に実測して決める（9.2）。MVPでは次を指標とする。

| 指標 | 内容 |
| --- | --- |
| 検索品質 | 評価セット（50問程度）でRecall@10とMRRを測定し記録する。目標値は初回の測定後に決める（8.3） |
| 導入の容易さ | Docker Composeの起動から、ローカルディレクトリの登録、検索までを通して動作する |
| Agent利用 | 主要なMCPクライアントで、検索から文書取得までを実行できる |
| 削除の安全性 | 取得の失敗・一時的な空応答・マウント外れで、文書が誤って削除されない |

### 1.5 非目標

- LLMによる回答生成（Chat Viewは将来拡張）。
- MVPでの認証・認可、文書単位のアクセス制御。
- 原文への遷移（パスまたはURLの表示にとどめる。URLへの写像は将来拡張）。
- 画像のみのPDFのOCR、Office文書の抽出（次版）。
- ファイルのリネーム追跡、チャンク分割、ベクトル検索（評価結果を見て判断する）。
- 数十万件を超える規模や、高可用構成。

### 1.6 設計方針

- **セルフホストを基本とする**：Docker Composeで導入でき、外部サービスへの通信を必須としない。
- **検索基盤と回答生成を分離する**：特定のLLMやAI Agentに依存しない。
- **ドキュメント単位のインデックスを基本とする**：全文・タイトル・要約を検索対象とし、チャンク分割は必須にしない。
- **拡張できる構成にする**：Connector、検索方式、要約・Embeddingの生成方式、Store層のバックエンドを差し替えられるようにする。
- **安全な検索を前提とする**：閲覧できない文書を返さない。MVPはこの原則を「運用前提」で満たす（6.1）。
- **とにかく動かすことを優先する**：MVPでは保護機能や最適化より、動作する最小構成を優先する。割り切った点はリスクとして明記する（2章）。

## 2. 主要リスクと検証項目

| リスク | 影響 | 緩和策・方針 | 検証項目 |
| --- | --- | --- | --- |
| `last_seen_at`の書き込み負荷 | 変更のない文書でも毎クロールで部分更新するため、OpenSearchでは文書全体（本文を含む）が再書き込みされ、書き込み量とセグメントのマージ負荷が増える | 現状は検索インデックスの文書に持つ。緩和策の選択肢として、更新の間引きがある（付録B.4）。間引くと、判定上のTTLが短くなるため、TTLはそれを見込んでクロール間隔より十分長く設定する | 実装時に、更新時間とインデックスの増加を実測し、間引きの要否を判断する |
| Admin Viewを保護しない | 到達できる人は誰でも、データソースの登録（コンテナから見える任意のローカルパスの登録を含む）、削除の承認、再インデックスを実行できる | MVPでは対応しない。6.1の運用前提で使う。コンテナにマウントしたディレクトリ以外は読めないため、Composeのマウント設定が実質の境界になる | 将来の版で、管理者トークン、登録できるルートパスの制限を追加する |
| 日本語検索の品質 | 識別子・型番・複合語の検索漏れ | kuromojiまたはSudachi、n-gramサブフィールドを評価して選ぶ | 評価セットのRecall@10・MRR（8.3） |
| 長文のインデックスサイズ | オフセット保存で索引が増える | 本文サイズの上限を設ける | オフセット保存による増加量と、上限値を実測 |
| OpenSearchをKVSにすることによる整合性・排他 | ニアリアルタイム検索、トランザクションなし、ノード障害時のデータ消失 | IDによるリアルタイム取得と条件付き更新を使う（付録C）。スナップショットを取る | 排他とリース切れの動作を実装時に試験 |
| 誤削除 | 取得の失敗で文書が消える | 列挙クロールの正常完了時のみ削除、削除率のしきい値、0件列挙は異常扱い（付録D） | 異常系（マウント外れ、部分失敗）の試験 |
| 要約の品質・コスト | 要約が不正確、生成が遅い | 既定は無効。要約なしで検索できる | 要約モデルの選定と、生成時間・コストの測定 |
| プロンプトインジェクション | 文書中の指示がAgentの動作に影響する | 文書を加工せず、出典とともに「データ」と明示する（6.2） | MCPクライアントでの動作確認 |
| MCPの公開（認証なし） | 悪意あるWebページからローカルのMCPエンドポイントが呼ばれる可能性 | localhostだけで待ち受ける。Originヘッダーの検証は未決定（9.2） | 実装時に検討 |

## 3. システム構成

```text
[社内ドキュメント / ファイル / Wiki / Git 等]
                    |
              Crawler / Connector
                    |
                 Indexer
        (抽出・正規化・要約生成)
               /         \
     検索インデックス      Store層（設定・ジョブ・抽出済みテキスト・処理状態）
               \         /     ※バックエンド差し替え可
               OpenSearch
          (検索用インデックス + KVS用インデックス)
                    |
                Search API
               /     |     \
         MCP Server Web UI  外部APIクライアント
              |       |
           AI Agent  利用者・管理者
```

※論理構成である。初期版では、複数のコンポーネントを同じプロセスやコンテナにまとめてもよい。

実装言語は、バックエンド（Crawler / Indexer / Search API / MCP Server）をPythonとする。Web UIの技術スタックは未決定である（9.2）。

## 4. コンポーネント

### 4.1 Crawler / Connector

データソースから文書を列挙・取得し、Indexerに共通ドキュメント形式（付録A.1）で渡す。ConnectorはデータソースごとのCrawlerの実装で、Crawlerはその実行・周期・同期状態を管理する。

- MVPのConnectorは、ローカルディレクトリ／ファイル共有のみ。HTTPサイト、Confluence、Gitなどは将来の拡張（Webページのスクレイピングも将来）。
- **列挙クロール**：データソース内のすべての文書を列挙するクロール。列挙したうえで、変更のあった文書だけを処理する（差分処理）。MVPのクロールはすべて列挙クロールである。削除の判定は列挙クロールだけが行う。
- 追加・更新の検知は、更新日時とサイズ、`content_hash`の順に行う（付録D.2）。削除は期限（`last_seen_at`とTTL）で判定する（付録D.3、D.4）。
- 接続設定、認証情報、実行周期、取得状況、エラーはStore層に保存する。

### 4.2 Indexer

収集した文書を検索できる形にして登録する。

- 文書形式に応じてテキストを抽出し、正規化する。MVPの対応形式はtxt・Markdown・HTML・PDF。Office文書は次版。文字コードは自動判定し、UTF-8のほかShift_JIS/CP932にも対応する。抽出ライブラリは未決定（9.2）。
- 抽出済みテキストをStore層に保存する。原本は保存せず、元システムを参照する。
- 文書全体の**検索用の要約**を生成する。主題、重要な概念、その文書で答えられる質問を表現する。既定では無効で、LLMを明示的に設定したときだけ有効になる。要約はStore層にも保存し、再インデックスで失わないようにする。
- 検索インデックスへの登録・更新・削除を行う。書き込みの種類ごとの競合の扱いは付録B.4に定める。
- 抽出に失敗した文書は、タイトルとメタデータだけを登録し、抽出失敗としてAdmin Viewに表示する（状態値は付録B.1）。本文がサイズ上限を超える場合は、上限までを索引化して`truncated=true`にする。
- Embeddingの生成は初期版では任意とする。
- 要約の失敗・遅延では、要約なしで先に登録し、後から非同期に生成する。要約の生成状態とモデル名・バージョンを保持し、後から再生成できるようにする。
- 検索インデックスへの登録に失敗した場合は、一定回数リトライし、それでも失敗したら個別文書の失敗として記録する。その場合、クロールは部分成功になり、削除は行わない（付録D.3）。ジョブ全体の失敗は、OpenSearch全体に接続できない場合などに限る。

### 4.3 検索インデックス（OpenSearch）

1文書 = 1検索レコードを基本とし、タイトル・要約・本文をBM25で検索する。日本語を主な対象とし、英語も併せて解析する。フィールドとマッピング、ハイライト、運用の詳細は付録Bに記す。

### 4.4 Search API

OpenSearchを使った共通の検索・文書取得インターフェースを提供する。MCP ServerとWeb UIは、原則としてこのAPI（または同じサービス層）を使う。

- ドキュメント検索：クエリ、データソース・文書形式・更新日による絞り込み、件数。
- ドキュメント取得：本文はStore層の抽出済みテキストから返す。AgentやUIを圧迫しないよう、文字オフセットと最大長で範囲を指定して取得できる。
- 検索結果の整形：タイトル、要約、関連箇所、出典、スコア。
- 認証・認可は将来拡張（MVPでは実装しない）。

リクエストとレスポンスの要点は付録Fに記す。

### 4.5 MCP Server

AI Agentが文書を検索・取得するためのMCPインターフェースを提供する。Search APIの機能を公開するアダプタであり、独自の検索ロジックは持たない。

- Tool：`search_documents`、`get_document`、`list_sources`（付録F）。
- 通信方式はStreamable HTTP。Search APIと同じコンテナに置く。
- 読み取り専用。書き込み系のToolは提供しない。
- 認証は将来の版で追加する。MVPは6.1の運用前提で使う。
- クライアント互換性は、実装時に主要なMCPクライアントで確認する。

### 4.6 Web UI

**Search View（利用者向け）**

- キーワード検索と検索結果の一覧。
- 要約・関連箇所・出典（`url`/`path`）の表示。原文への遷移は提供せず、パスの表示にとどめる。
- 必要に応じた本文プレビュー（Store層の本文を表示する）。

**Admin View（管理者向け）**

- データソース・実行周期・TTLの設定と、クロールの手動実行。状態・エラー・最終同期時刻の確認。
- 抽出失敗・要約未生成・恒久失敗（付録D.3）の文書の確認。恒久失敗の文書の手動削除。
- 削除保留と、0件列挙（付録D.4）の確認、承認、却下。Admin View上の表示を管理者への通知とみなし、メールなどの通知はMVPでは実装しない。
- 突合ジョブの手動実行（付録D.6）。インデックス件数の確認。
- 再インデックスはMVPでは手動手順とし、画面からの実行は将来拡張とする（付録B.5）。
- OpenSearch Dashboardsへの管理用の導線（任意。一般利用者には公開しない）。

**Chat View（将来拡張）**：Search APIを使った対話型の検索。初期版では必須にしない。

### 4.7 ジョブ管理

クロール・インデックス・要約生成はジョブとして管理し、状態をStore層に保存する。

- 状態は、実行待ち・実行中・成功・一部成功・失敗・取り消しの6つ（付録E.1）。
- 同じデータソースのクロールは同時に1つだけ実行する。止まったジョブは検知して再実行できる（付録E.2）。
- 一時的なエラーは、指数バックオフで一定回数リトライする。失敗したジョブは、Admin Viewから再実行できる。
- 文書ごとの処理状態（`index_status` / `summary_status`）はジョブとは別に保持する。

### 4.8 データストア（Store層）

MVPではリレーショナルDBを使わず、**OpenSearchをKVSのように使って**設定・ジョブ・抽出済みテキスト・文書ごとの処理状態を保存する。コード上は検索インデックスとは別の「Store層」として扱い、アプリケーションはRepositoryインターフェースだけを経由して読み書きする。

- バックエンドは設定で差し替えられるようにする。将来、PostgreSQLやSQLiteを追加しても呼び出し側を変えない。
- インターフェースは、IDによる取得・保存・削除、単純な条件での一覧、条件付き更新（楽観的排他制御）に限る。トランザクションと結合には依存しない。
- Connectorの認証情報は、Store層に平文で保存しない。環境変数や秘密情報ファイルで参照する。

インデックス構成、マッピング方針、排他制御の詳細は付録Cに記す。

## 5. データの流れ

### 5.1 収集・更新

概要は次のとおり。各ステップの詳細は付録Dに記す。

1. Crawlerがデータソースを列挙し、見つかった既存文書の`last_seen_at`を更新する（付録D.1）。
2. 更新日時・サイズ・`content_hash`で変更を検知し、変更のあった文書だけを処理する（付録D.2）。
3. Indexerが本文を抽出・正規化し、Store層と検索インデックスに登録する。登録が成功してから、処理済みの印（`content_hash`など）を確定する。途中で失敗した文書は、次回のクロールで再処理される（付録D.2）。
4. 要約生成が有効なら、要約を非同期に生成し、Store層に保存したうえで、本文が変わっていないときだけ検索インデックスに反映する（付録B.4、C.3）。

### 5.2 削除

1. 列挙クロールが正常に完了したときだけ、同じ`source_id`のうち`last_seen_at + TTL < 現在時刻`の文書を削除の対象にする（付録D.3）。
2. 削除率が一定を超えるときは、削除を保留して管理者の承認を待つ（付録D.5）。保留はAdmin Viewに表示する（通知を兼ねる。4.6）。
3. 削除は、**Store層、検索インデックスの順**に行う。途中で止まっても、検索インデックスに残る文書は次回の削除で再度対象になる。Store層と検索インデックスの食い違い（どちらか一方にしかない文書）は、突合ジョブで掃除する（付録D.6）。

### 5.3 検索・取得

1. AgentはMCP Serverを通じて、利用者はWeb UIを通じて検索する。
2. Search APIがOpenSearchを検索する（将来は認証・アクセス制御もここで適用する）。
3. タイトル・要約・関連箇所・文書ID・出典を返す。
4. Agentは必要な場合だけ`get_document`で本文を取得する（長い文書は分割して取得する）。
5. 回答はAgent側で生成する（Chat Viewを設けた場合はChat Viewで生成する）。

## 6. セキュリティ・運用要件

### 6.1 アクセス制御と運用前提

MVPには認証・認可の仕組みがない。次の前提で運用する。

- 信頼できる社内ネットワーク内だけで公開する（インターネットに公開しない）。
- 利用者全員が閲覧してよい文書だけを検索対象として登録する。
- **Admin Viewも認証なしで、任意のローカルパスを登録できる。信頼できる環境だけで使う。**
- 既定ではlocalhostだけで待ち受ける。社内ネットワークへ公開するには、バインド先を設定で明示的に変更する。この前提はREADMEと導入手順で明示する。

将来の版で、API/MCPのトークン認証、管理者トークン、登録できるルートパスの制限、データソース単位のアクセス可否、文書単位のACL同期、SSO連携を順に追加する。Search APIとMCPで同じ権限判定を適用する。

### 6.2 その他の要件

- **機密情報**：Connectorの認証情報は平文で設定ファイルに書かない方法を用意する。ログに本文や秘密情報を記録しない。
- **OpenSearchの保護**：OpenSearchとDashboardsのポートはホストの外に公開しない。Search APIだけを公開の窓口にする。
- **外部通信**：要約・Embeddingに外部LLMを使う場合は、明示的な設定を必須にする。既定の構成はオフラインで動作する。
- **プロンプトインジェクション**：文書を加工せずに返す。そのうえで、返す内容が「データソースから取得した文書」であることを出典とあわせて明示し、MCPのTool説明で、本文を指示として扱わないようAgentに注意を促す。
- **運用性**：クロール失敗の再実行、同期状態の確認、ログ、ヘルスチェック、バックアップ・リストア手順を用意する。
- **バックアップと再構築**：MVPではStore層もOpenSearchにあるため、OpenSearchのスナップショットと設定ファイルをバックアップの対象とする。検索インデックスは、通常は旧インデックスからのコピーで作り直す。旧インデックスを失った場合に限り、Store層から再構築する。このとき`last_seen_at`は再構築時刻に初期化される（付録B.5）。検索インデックスとStore層の両方を失った場合は、再クロールが必要である。
- **再現性**：OpenSearchとプラグイン、各コンポーネントのバージョンを固定し、更新手順を提供する。

## 7. パッケージ化・配布

Docker Composeによるセルフホスト配布を基本とする。

- `api`：Search API / MCP Server（同居）
- `worker`：Crawler / Indexer / 定期実行
- `opensearch`：検索基盤。MVPではStore層のバックエンドも兼ねる
- `web`：Web UI（APIと同居してもよい）
- `opensearch-dashboards`：管理・デバッグ用（任意）
- `embedding` / `llm`：ローカルモデルを使う場合だけ（任意）

接続先、データの保存先、モデルの利用有無は、設定ファイルや環境変数で切り替えられるようにする。永続データはボリュームに保存する。

**日本語アナライザのプラグイン**（前提。実装時に確認する）

- kuromojiもSudachiも、OpenSearchの既定の配布イメージには含まれない前提で、プラグインを導入した**独自のOpenSearchイメージ**をビルドして配布する。Sudachiは、辞書の入手とライセンスの確認も必要になる。
- OpenSearch本体とプラグインのバージョンは一致させて固定する。OpenSearchを更新するときは、プラグインも同時に更新して、再インデックスの要否を確認する。

将来は、Kubernetes向けのHelm Chartなども検討する。

## 10. 用語集

| 用語 | 意味 |
| --- | --- |
| データソース | 収集対象の情報源（ディレクトリ、Wiki、Gitリポジトリなど）。管理者が登録する単位で、`source_id`で識別する |
| Connector | データソースごとの取得処理の実装 |
| Crawler | Connectorを実行し、スケジュールと同期状態を管理するコンポーネント |
| Indexer | 取得した文書からテキストを抽出・正規化し、要約を生成して、検索インデックスとStore層に登録するコンポーネント |
| Store層 | 設定・ジョブ・抽出済みテキスト・文書ごとの処理状態を保存する層。MVPではOpenSearchの別インデックスで実装し、Repositoryインターフェースで抽象化する |
| 検索インデックス | 検索用のOpenSearchインデックス。Store層とは別 |
| `document_id` | 文書の一意なID。`source_id`と`external_id`から決定的に生成する（付録A.2） |
| `content_hash` | 文書の内容のハッシュ（SHA-256）。差分検知と、要約の書き込みの整合確認に使う |
| 列挙クロール | データソース内のすべての文書を列挙するクロール。削除の判定はこのクロールだけが行う |
| `last_seen_at` | 列挙クロールで最後に見つかった日時（クロール開始時刻）。検索インデックスの文書に持つ |
| TTL | `last_seen_at`からの有効期間。データソースごとのクロール設定で指定する |
| 期限による削除 | `last_seen_at + TTL`を過ぎた文書を、列挙クロールの正常完了後に削除する方式 |
| 削除保留 | 削除対象が多いときに、削除を止めて管理者の承認を待つ状態（付録D.5） |
| 突合ジョブ | 検索インデックスとStore層の食い違いを検出して直すジョブ（付録D.6） |
| リース | ジョブやロックの所有を、期限付きで主張する仕組み。期限が切れると別のワーカーが引き継げる（付録E.2） |
| `extractor_version` | 抽出ロジックとライブラリのバージョン。変わると再抽出の対象になる（付録D.2） |
| `crawl_started_at` | クロールの開始時刻。実行コンテキストとしてIndexerに渡し、`last_seen_at`に書く |
| MCP | Model Context Protocol。AI Agentがツールを呼び出すためのプロトコル |
| Agent | MCPを通じて本プロダクトを利用するAI Agent |
| Search View / Admin View | Web UIの利用者向けの画面 / 管理者向けの画面 |

---

**現時点の結論**：ドキュメント単位の全文・要約検索を中心とする、セルフホスト型の検索基盤をMVPとして構築し、MCPから使えるようにする。MVPは認証なしで、信頼できるネットワーク内で使う前提とする。チャンク分割、ベクトル検索、Chat View、認証・認可は、評価セットによる実測と利用状況に基づいて段階的に追加する。

# 付録

実装レベルの詳細を記す。決定事項は9.1と付録の双方を正とし、食い違いは見つけ次第直す。

## 付録A　共通ドキュメント形式とID生成

### A.1 共通ドキュメント形式

ConnectorがIndexerに渡す形式。

| 項目 | 説明 |
| --- | --- |
| `source_id` | データソースの識別子。登録後は変更できない |
| `external_id` | データソース内で一意な識別子（ルートからの相対パス、ページID等）。A.2の正規化を適用する |
| `title` | タイトル（取得できなければファイル名） |
| `url` / `path` | 原文への参照（表示用） |
| `mime_type` | 文書形式 |
| `raw_content` | 取得した原本、または取得用の参照。抽出前のデータであり、検索インデックスの`content`（抽出後の本文）とは別物 |
| `content_hash` | 原本のSHA-256 |
| `source_updated_at` | データソース上の更新日時（ローカルでは`mtime`） |
| `size` | 原本のサイズ（バイト） |
| `fetched_at` | 原本を取得した日時。取得を省略した場合は更新しない |
| `metadata` | Connector固有の追加属性 |

`last_seen_at`は共通ドキュメント形式に含めない。クロールの実行コンテキストとして`crawl_started_at`をIndexerに渡し、Indexerが`last_seen_at`に書く。`fetched_at`は「取得した日時」、`last_seen_at`は「列挙で見つかった日時」であり、変更のない文書は`last_seen_at`だけが更新される。

本プロダクト内で`content`の意味は場所ごとに異なる。

| 場所 | 名前 | 意味 |
| --- | --- | --- |
| Connector → Indexer | `raw_content` | 原本または参照 |
| Store層 | `text` | 抽出・正規化後のテキスト（サイズ上限で切り詰め後） |
| 検索インデックス | `content` | `text`と同じ内容を検索用に解析したもの |
| `get_document`の応答 | `content` | `text`の指定範囲 |

### A.2 ID生成

- `document_id` = `SHA-256(source_id + "\0" + external_id)`の16進文字列（小文字）。NUL文字で区切るため、連結で別の組が同じ値にならない。
- `external_id`は、ハッシュの前にUnicode NFCへ正規化し、パス区切りを`/`に統一する（ルートからの相対パス、先頭に`/`を付けない）。大文字小文字は区別したまま扱う。
- 同じ文書を再取得すると同じIDになるため、再実行しても重複しない。検索インデックスとStore層のどちらも、`document_id`を文書IDとして使う。
- `source_id`は登録後に変更できない。変更が必要なときは、新しいデータソースとして登録し直す。
- パスの変更やリネームは「旧IDの削除 + 新IDの追加」として扱う。リネームの追跡は初期要件にしない。
- データソースを削除するときは、その`source_id`の文書をStore層、検索インデックスの順にすべて削除し、そのあとでデータソース設定を削除する。途中で止まった場合に備え、設定の削除は文書の削除が終わってから行う。

## 付録B　検索インデックス

### B.1 フィールド

1文書 = 1検索レコード。`_id`は`document_id`。

| フィールド | 用途 |
| --- | --- |
| `document_id` | 一意な識別 |
| `source_id` | データソースによる絞り込み |
| `external_id` | データソース内の識別子（突合と、削除対象の特定に使う） |
| `title` | タイトル検索 |
| `summary` | 文書全体の主題による検索 |
| `content` | 細かい語句・識別子による全文検索（抽出・正規化後の本文） |
| `url` / `path` | 原文への参照（表示のみ） |
| `mime_type` | 文書形式による絞り込み |
| `source_updated_at` | 更新日による絞り込み |
| `indexed_at` | インデックスに登録した日時 |
| `content_hash` | 要約の条件付き更新の判定に使う |
| `summary_status` / `summary_model` | 要約の生成状態と、生成に使ったモデル・バージョン |
| `index_status` / `truncated` | 抽出状態と、本文を切り詰めたかどうか |
| `last_seen_at` | 列挙クロールで最後に見つかった日時（期限による削除の判定） |
| `acl` | アクセス制御用の属性（MVPでは使わない。将来に備えて予約） |
| `summary_embedding` | 意味検索用のベクトル（任意） |

`summary` / `summary_status` / `summary_model` / `index_status` / `truncated`は、検索結果の表示と絞り込みのための写しである。**正はStore層**に置く。`last_seen_at`だけは検索インデックスが唯一の保存場所である。

`summary_status`の取りうる値：`disabled`（要約が無効）、`pending`、`generated`、`failed`。`index_status`の取りうる値：`pending_index`（Store層のみ。登録前）、`indexed`、`extract_failed`。

### B.2 検索方式と解析

- 基本はBM25による全文検索とし、タイトル・要約・本文の重みを調整する。
- 日本語は形態素解析（kuromojiまたはSudachi。評価して決める）で解析し、英語は標準アナライザで併せて解析する。識別子や型番の検索漏れを防ぐため、n-gramのサブフィールドの追加も検討する。
- ユーザー辞書・同義語辞書はファイルで管理し、更新したら再インデックスで反映する。
- 将来は、要約Embeddingによるベクトル検索やハイブリッド検索を追加する。

### B.3 ハイライトとインデックス運用

- インデックスにはエイリアス経由でアクセスする。マッピングや辞書を変えるときは、新しいインデックスを作ってからエイリアスを切り替える。
- ハイライトに使うフィールド（n-gramなどのサブフィールドを含む）は、`index_options: offsets`でオフセットを保存する。ハイライタはunified（既定）を使う。オフセットがあると、unifiedハイライタは本文を再解析しないため、解析上限（`index.highlight.max_analyzed_offset`、既定は100万文字）は適用されない。この上限を理由に長い文書の本文を切り詰めない。
- plainハイライタは常に再解析し、上限を超えると検索リクエスト全体が失敗するため使わない。
- オフセットの保存でインデックスサイズが増える。増え方は実装時に計測する。本文サイズの上限は、リクエストサイズ・インデックスサイズ・処理時間などの観点で決める（9.2）。
- 長い文書で検索精度に問題が出た場合は、見出し・セクション単位の補助インデックスを追加できる構成にする。固定長チャンクへの分割は初期要件にしない。

### B.4 書き込み種別と競合

検索インデックスへの書き込みは次の3種類に分ける。

| 種別 | 書くフィールド | 書き込む側 | 競合時の扱い |
| --- | --- | --- | --- |
| 全文upsert | 全フィールド。`last_seen_at`は`crawl_started_at`、`summary`は書かず、`summary_status=pending`（要約が無効なら`disabled`）、`content_hash`は新しい値 | Indexer（本文の追加・更新時） | 文書全体を置き換える。旧本文向けの要約は残さない。同じデータソースのクロールは1つだけなので、同時の全文upsert同士は起きない |
| 要約の部分更新 | `summary`、`summary_status`、`summary_model`、`summary_embedding` | 要約生成（非同期） | **検索インデックス上の`content_hash`が、要約を生成した本文の`content_hash`と一致するときだけ**書く（条件付き更新）。不一致なら捨てる（本文が更新済みで、新しい要約が生成される）。更新の衝突は再試行する |
| `last_seen_at`の部分更新 | `last_seen_at`のみ | Indexer（列挙で見つかったとき） | 現在値と比べるスクリプト更新（max比較）。新しい値のときだけ書き、古い値で上書きしない。ほかのフィールドは変更しない。検索インデックスに文書がない場合（404）は何もしない（upsertしない） |

要約は、生成の完了後にまずStore層へ保存し、そのうえで検索インデックスへ反映する。Store層への保存も、生成元の`content_hash`が一致するときだけ行う（付録C.3）。

**間引き（任意。2章）**：部分更新の書き込み量を減らすため、現在の`last_seen_at`がTTLの1/3より新しければ更新しない。判定に必要な現在の`last_seen_at`は、検索インデックスから読む（スクリプト内の比較、または一括取得）。間引くと、判定上のTTLは最大でTTLの1/3だけ短くなる（実効TTLは最短でTTL×2/3）。そのため、TTL×2/3がクロール間隔より長くなるように設定する（付録D.4）。

### B.5 再インデックス

マッピングや辞書を変えるとき、またはインデックスを作り直すときは、次の2つの手段を使い分ける。どちらも、**再インデックスの対象のデータソース（インデックス全体を作り直すときはすべて）のクロールと要約の書き込みを止めてから**行い、完了後に再開する。削除も実行しない。要約の書き込みジョブも、書き込みの前に同じソースのロック（またはメンテナンスフラグ）を確認し、保持されている間は書き込まずに止まる（付録E.2）。止める手段は、対象のソースごとの実行ロック（付録E.2）を取得したままにするか、`loreley-jobs`にメンテナンスフラグを立てて、CrawlerとIndexerがフラグを確認して書き込みを控えるか、のどちらかとする。MVPでは手動手順（READMEに記載）とする。

| 手段 | 内容 | `last_seen_at` | 要約 | 使う場面 |
| --- | --- | --- | --- | --- |
| (a) `_reindex`で旧インデックスからコピー | 新しいインデックスを作り、旧インデックスの文書をコピーしてエイリアスを切り替える | 保持される | 保持される | マッピング・辞書・アナライザの変更（通常はこちら） |
| (b) Store層からの再構築 | Store層の抽出済みテキストから、検索インデックスを新しく作る。再クロールは不要 | 再構築時刻に初期化される（TTLの時計が再構築時から始まる） | Store層に保存している要約のうち、生成元の`content_hash`が本文と一致するものだけが保持される。不一致は`pending`に戻す | **旧インデックスを失った場合に限る**。抽出ロジックを変えたときは使わず、`extractor_version`の更新による再クロールで反映する（付録D.2） |

## 付録C　Store層

### C.1 インデックス構成

用途ごとに検索インデックスとは別のインデックスを分け、IDをキーにget/put/deleteする。

| インデックス | 内容 |
| --- | --- |
| `loreley-sources` | データソース設定（`source_id`、種別、ルート、周期、TTL、除外条件など。認証情報は参照名のみ） |
| `loreley-jobs` | ジョブ状態、ソースごとの実行ロック、削除保留 |
| `loreley-texts` | 文書ごとの抽出済みテキストと処理状態 |

`loreley-texts`の項目：`document_id`、`source_id`、`external_id`、`title`、`url`/`path`、`mime_type`、`text`、`truncated`、`content_hash`（確定済み）、`pending_content_hash`、`source_updated_at`、`indexed_at`、`size`、`extractor_version`、`index_status`、`extract_fail_count`、`fetch_fail_count`、`pending_since`（`pending_index`になった日時）、`summary`、`summary_content_hash`（要約の生成元の`content_hash`）、`summary_status`、`summary_model`。

**真実の置き場所**：文書の本文・要約・処理状態の正はStore層（`loreley-texts`）。検索インデックスはそこから作る派生物である。ただし`last_seen_at`は検索インデックスだけに持つ。`title`・`url`/`path`・`mime_type`・`indexed_at`もStore層に持つので、B.5(b)の再構築と`get_document`（F.4。`title`と`url`/`path`を返す）は、Store層だけで成立する。

### C.2 マッピング方針

- `dynamic: strict`にして、未定義のフィールドの混入を防ぐ。
- 検索や集計の対象にしない大きな文字列（`text`など）は、解析も索引化もしない（`index: false`、またはオブジェクトの`enabled: false`）。取得はIDによる`_source`の読み出しで行う。
- 条件で一覧する項目（`source_id`、`index_status`、`summary_status`など）は`keyword`にする。
- MVPは単一ノード前提で、`number_of_shards: 1`、`number_of_replicas: 0`とする。

### C.3 排他と整合性

- OpenSearchの検索はリフレッシュ後にしか反映されない（ニアリアルタイム）。状態の確認や排他の判定には、検索ではなくIDによる取得（リアルタイム）を使う。
- 条件付き更新には`if_seq_no`/`if_primary_term`を使う。要約をStore層へ保存するときは、読み出した文書の現在の本文のハッシュ（確定前は`pending_content_hash`、確定後は`content_hash`）が生成元と一致し、かつ`if_seq_no`/`if_primary_term`が一致するときだけ書く。本文を更新するときは、Store層の要約を消して`summary_status`を`pending`（要約が無効なら`disabled`）に戻す。
- 初回の作成は、存在しない場合だけ成功する作成（create）を使う。
- ノードが1つなので、データの消失に備えてスナップショットを取る。

## 付録D　クロール・差分検知・削除

### D.1 発見と取得の分離

列挙で文書が見つかった時点で、既存文書の`last_seen_at`を更新する。その後の取得・抽出・登録が失敗しても、`last_seen_at`は更新済みのままである。こうすると、取得の失敗が「見つからなかった」と区別され、失敗した文書がTTLで削除されない。`last_seen_at`の部分更新は、検索インデックスに文書がなければ何もしない（付録B.4）。新規の文書は、全文upsertで`last_seen_at`を書く。取得に失敗した新規文書は登録されず、次回のクロールで再度試みる。

### D.2 差分検知

1. Connectorが列挙時に`mtime`と`size`を取得する。Store層の前回値と**両方が一致**し、かつ`extractor_version`が現在と同じなら、取得も`content_hash`の計算も省略する。
2. 一致しなければ原本を取得して`content_hash`を計算する。確定済みの`content_hash`と同じなら、本文の再処理は省略し、`mtime`/`size`だけを更新する。
3. `content_hash`が違えば、再抽出して全文upsertする。
4. `extractor_version`（抽出ロジックとライブラリのバージョン）が変わった場合は、`content_hash`が同じでも再抽出の対象にする。全件を一度に再処理しないよう、クロールの中で順次処理する。
5. 検索インデックスへの登録に成功してから、**最後に**Store層の`content_hash`・`mtime`・`size`・`extractor_version`をまとめて確定する。途中で失敗すると確定されないので、次回のクロールで再処理される。登録前の間は`pending_content_hash`と`index_status=pending_index`を持つ。本文を更新した文書は、要約を引き継がず`summary_status=pending`に戻す。

`mtime`と`size`が同じまま内容だけが変わると見逃す。これは既知の限界で、MVPでは許容する。

`extract_failed`の文書は、次のクロールで再試行する。連続して失敗した回数（`extract_fail_count`）が上限（例：3回）に達したら、`content_hash`か`extractor_version`が変わるまで自動では再試行しない。Admin Viewからの手動の再試行は、いつでもできる。

### D.3 クロールの完了状態

| 状態 | 条件 | 削除 |
| --- | --- | --- |
| 正常完了（`succeeded`） | 列挙が最後まで完了し、発見した文書の取得・登録に失敗がない（抽出失敗と恒久失敗は、失敗に含めない）。列挙が0件の場合は、D.4の条件を満たす | 行う |
| 部分成功（`partially_succeeded`） | 列挙は最後まで完了したが、個別の文書の取得・登録に失敗がある（登録のリトライ後の失敗を含む） | **行わない** |
| 失敗（`failed`） | 列挙が途中で止まった、0件列挙が異常と判定された、またはOpenSearch全体に接続できない | 行わない |
| 取り消し（`cancelled`） | 管理者が実行を取り消した | 行わない |

部分成功と失敗のクロールの結果は、Admin Viewに失敗した文書の一覧とあわせて表示する。

**恒久失敗**：権限エラーなどで読めない文書があると、部分成功が続いて他の文書の削除が止まり続ける。これを防ぐため、同じ文書の取得・登録の連続失敗回数（`fetch_fail_count`）が上限（例：3回）に達したら「恒久失敗」とし、部分成功の判定から除外する。抽出失敗（`extract_failed`）と同様にAdmin Viewに表示する。恒久失敗の文書も取得は試み続け、成功すれば解除する。Admin Viewの承認による手動削除もできる。

### D.4 期限による削除

- 削除の対象は、**正常完了した列挙クロール**で、同じ`source_id`のうち`last_seen_at + TTL < 現在時刻`の文書である。差分だけを取るクロール（将来のConnector）では削除しない。
- TTLはデータソースごとに指定し、クロールの間隔より長くする。更新を間引く場合（付録B.4）は、実効TTL（TTL×2/3）がクロール間隔より長くなるようにする。例：日次クロールでTTLが3日なら、間引きなしでは3回続けて見つからなかった文書を削除する。間引きありでは、実効TTLが最短で2日になるため、2回目の未検出から削除対象になりうる。
- **0件列挙は異常扱い**：データソースに既存の文書があるのに列挙が0件のとき（マウント外れ、共有の切断など）は、`failed`（理由：空の列挙）にして、削除しない。「既存の文書がある」の判定元は検索インデックスである（当該`source_id`の件数。リフレッシュ後に数える）。
- **実際に全ファイルを消した場合**：0件列挙の`failed`は、Admin Viewに「全件削除の確認待ち」として表示する。承認すると、再度列挙し、なお0件のときだけ、そのデータソースの全文書を削除する（Store層、検索インデックスの順）。却下すると削除しない。
- 削除対象は検索で抽出するため、抽出前にリフレッシュする。削除は、Store層、検索インデックスの順に行う（5.2）。
- データソースから消えた文書は、削除されるまで検索結果に残る。検索時に`last_seen_at`で除外はしない。クロールが失敗し続けると、全文書が検索から消えてしまうためである。

### D.5 削除の保留

- **判定**：削除対象の件数が、削除前の同じ`source_id`の登録文書数（分母）に対して、しきい値（例：20%）を超えるときは、削除を保留する。ただし削除対象の件数が最小件数（例：10件）以下なら、率に関わらず保留しない（少数のソースで1件の削除が高い率になるため）。しきい値と最小件数は、データソースの設定にする。
- **保存先**：保留は`loreley-jobs`に記録する（`source_id`、クロールのジョブID、対象件数、分母、状態：`pending`/`approved`/`rejected`/`superseded`）。
- **保留中のクロール**：保留中のデータソースでも、次のクロールは実行できる。保留中に新しいクロールが正常完了したら、古い保留は`superseded`にして、新しく判定し直す。
- **承認時**：Admin Viewで承認すると、承認時点で`last_seen_at + TTL < 現在時刻`を満たす文書を検索し直して削除する。承認時に対象件数が保留時より増えているときは、再度保留にする。却下すると削除しない（`rejected`）。

### D.6 突合ジョブ

検索インデックスとStore層の食い違いを、双方向に検出して直す。Admin Viewから手動で実行でき、定期実行もできる。MVPでは手動実行を最低限とする。

- **検索インデックスにあってStore層にない文書**（削除が途中で止まった場合に発生しうる）：検索インデックスから削除する。
- **Store層にあって検索インデックスにない文書**（`index_status=pending_index`。登録の失敗で発生する）：次のクロールの差分処理で再登録される（登録成功まで`content_hash`が確定しないため）。`pending_index`のまま一定期間（例：TTLと同じ）を過ぎ、**かつ検索インデックスに存在しない**Store層の文書に限り、データソースから消えたものとみなして削除する（検索インデックスに存在する文書は、期限を過ぎても削除しない）。期間は`pending_since`から数える。`pending_since`は、文書の更新に失敗して`pending_index`になった時点で設定し、登録に成功して`pending_index`が解消するまで更新しない（再試行の失敗では更新しない）。ただし恒久失敗の文書（D.3）は対象外とし、Admin Viewで確認して手動で削除する。

## 付録E　ジョブ管理の詳細

### E.1 状態遷移

`queued` → `running` → `succeeded` / `partially_succeeded` / `failed` / `cancelled`。

### E.2 排他とリース

- ジョブには、`owner`（実行しているワーカー）、`heartbeat_at`、`lease_expires_at`を持たせる。
- `queued`から`running`への遷移は、`if_seq_no`/`if_primary_term`を使った条件付き更新で行う。成功したワーカーだけがジョブを取得する。
- データソースごとの実行ロックは、`loreley-jobs`のロック用文書（ID：`lock-{source_id}`）で表す。存在しない場合だけ成功する作成（create）か、リース期限切れの文書に対する条件付き更新で取得する。
- 実行中のワーカーは、リース期間（例：5分）の1/3程度の間隔でハートビートを送り、`lease_expires_at`を延長する。
- `lease_expires_at`を過ぎた`running`のジョブは、`failed`として扱う。別のワーカーがロックを取得し、再実行できる。リース期間の既定値は未決定（9.2）。
- 要約生成のジョブも同様にリースを持つ。要約の書き込み（Store層・検索インデックス）の前には、フェンシングと同様に、対象ソースの実行ロックがメンテナンス（再インデックス）のために保持されていないか、またはメンテナンスフラグが立っていないかを確認し、立っていれば書き込まずに止まる（付録B.5）。
- **リース切れ後の旧ワーカー対策（フェンシング）**：検索インデックスやStore層への書き込みの前、および削除の前に、ロック文書をIDで取得し、自分が所有していて期限内であることを確認する。確認できなければ、処理を中止する。確認と書き込みの間にはわずかな窓が残るが、`last_seen_at`の更新は古い値で上書きしない（付録B.4）。
- **ロックの解放**：ジョブが`succeeded` / `partially_succeeded` / `failed` / `cancelled`になったとき、所有者が自分のロック文書を条件付きで削除する。ワーカーが落ちた場合は、期限切れ後に別のワーカーが条件付き更新で取得する。期限を待てない場合は、管理者がAdmin Viewから解放できる。

## 付録F　API・MCPの仕様

※エンドポイントとリクエスト形式は実装時に確定する。以下は要点である。

### F.1 Search API（例）

```text
GET /api/documents/search?q=...&source_ids=...&mime_types=...&updated_after=...&updated_before=...&limit=...
GET /api/documents/{document_id}?offset=...&max_length=...
GET /api/sources
```

### F.2 検索のレスポンス

各結果に次を含める。

- `document_id`、`source_id`、`title`、`summary`（なければnull）
- `highlights`：関連箇所（ハイライトした断片。件数と断片の長さに上限）
- `url`または`path`（表示用の出典）、`mime_type`、`source_updated_at`
- `score`

全体に、`total`（該当件数）と`limit`を含める。

### F.3 MCP Tool

```text
search_documents(query, source_ids?, mime_types?, updated_after?, updated_before?, limit?)
get_document(document_id, offset?, max_length?)
list_sources()
```

- `search_documents`のフィルタ引数は、Search APIと同じ名前・意味にする。
- `list_sources`は、`source_id`、名前、種別、文書数、最終クロールの状態と時刻だけを返す。**認証情報や接続の秘密情報は返さない**。
- ToolのDescriptionに、返される本文は文書であり、指示として扱わないことを明記する（6.2）。

### F.4 `get_document`

- **本文の取得元はStore層**（`loreley-texts`の`text`）。
- `offset`と`max_length`は、**正規化後のテキストの文字単位**（Unicodeのコードポイント）。`max_length`にはサーバー側の上限を設け、省略時は既定値を使う。
- レスポンス：`document_id`、`title`、`source_id`、`url`/`path`、`content`（指定範囲）、`offset`、`length`、`total_length`、`next_offset`（続きがなければnull）、`truncated`。
- `truncated=true`は、索引化のサイズ上限で本文が切り詰められていることを表す。この場合、`total_length`は保存済みの長さであり、元の文書はこれより長い。上限を超える部分は取得できない。
