# プロダクト設計（v0.2）

## 1. 概要

オンプレミス環境やローカル環境で動作し、AI Agentから利用できる**汎用的な社内ドキュメント検索基盤**を提供する。

複数の情報源からドキュメントを収集・索引化し、OpenSearchによる検索機能をSearch APIおよびMCP経由で提供する。Web UIからの直接検索にも対応する。

本プロダクトの中心的な責務は**ドキュメントの収集・管理・検索・取得**であり、LLMによる回答生成は必須機能としない。AI Agentや外部アプリケーションが検索結果を利用して回答を生成する構成を基本とする。

### 想定する利用シーン

- AI Agentが社内の設計書、手順書、議事録などを横断検索する。
- 利用者がWeb UIからドキュメントを検索し、原文を確認する。
- 管理者が検索対象、クロール周期、索引の状態を管理する。

### 設計方針

- **セルフホストを基本とする**：Docker Composeで導入でき、外部サービスへの通信を必須としない構成を目指す。
- **検索基盤と回答生成を分離する**：特定のLLMやAI Agentに依存しない。
- **ドキュメント単位の索引を基本とする**：全文・タイトル・要約を検索対象とし、チャンク分割は必須にしない。
- **拡張可能な構成とする**：データソースaごとのConnector、検索方式、要約・Embedding生成方式を交換可能にする。
- **安全な検索を前提とする**：利用者が閲覧できないドキュメントを検索結果やMCPから返さない。

## 2. システム構成

```text
[社内ドキュメント / ファイル / Wiki / Git 等]
                    |
              Crawler / Connector
                    |
                 Indexer
        (抽出・正規化・要約生成)
                    |
                OpenSearch
                    |
                Search API
               /     |     \
         MCP Server Web UI  外部APIクライアント
              |       |
           AI Agent  利用者・管理者
```

※上記は論理構成。初期版では複数のコンポーネントを同一プロセスやコンテナにまとめてもよい。

## 3. コンポーネント

各コンポーネントについて、実装が必要な部分はPythonで実装するのを基本方針。

### 3.1 Crawler / Connector

指定された情報源からドキュメントを収集する。

- 情報源ごとのConnectorを用意する（例：ローカルディレクトリ、HTTPサイト、Confluence、Git）。
- 初回の全件取得と、以降の差分同期に対応する。
- 追加・更新・削除を検知し、Indexerへ通知する。
- 接続設定、認証情報、実行周期、取得状況、エラーを管理する。
- 取得失敗や一時的な空応答による誤削除を防止する。
- Webページなどはリンクを辿る必要があるため、最低限のスクレイピングが必要。

Connectorごとの取得方法は異なっても、Indexerには共通のドキュメント形式で渡す。

### 3.2 Indexer

収集したドキュメントを検索可能な形に変換し、OpenSearchに投入する。

- 文書形式に応じたテキスト抽出（HTML、Markdown、PDF、Office文書など。対応形式は段階的に追加）。
- 本文の正規化、タイトル・URL・更新日時などのメタデータ付与。
- 文書全体の**検索用途向け要約**の生成。単なる短縮ではなく、扱う主題・重要概念・回答可能な質問を表現する。
- OpenSearchへの登録・更新・削除。再実行しても重複しないようにする。
- 必要に応じてEmbeddingを生成する（初期版では任意）。

要約生成にはLLMを利用できる設計とするが、未設定でも全文検索で動作する。要約の生成状態やモデルのバージョンを保持し、後から再生成できるようにする。

### 3.3 OpenSearch

検索インデックスを保持する。

初期版は**1ドキュメント = 1検索レコード**を基本とし、以下のフィールドを想定する。

| フィールド | 用途 |
| --- | --- |
| `document_id` | 一意識別・情報源の特定 |
| `title` | タイトル検索 |
| `summary` | ドキュメント全体の主題による検索 |
| `content` | 詳細な語句・識別子の全文検索 |
| `url` / `path` | 原文への参照 |
| `updated_at` | 更新日による絞り込み |
| `acl` | アクセス制御用の属性 |
| `summary_embedding` | 意味検索用ベクトル（任意） |

検索の基本はBM25による全文検索とし、タイトル・要約・本文の重み付けを調整する。将来的に要約Embeddingを用いたベクトル検索やハイブリッド検索を追加する。

長大な文書で検索精度に問題が生じた場合は、見出し・セクション単位の補助インデックスを追加できる構成にする。固定長チャンクへの分割は初期要件としない。

### 3.4 Search API

OpenSearchを利用した共通の検索・文書取得インターフェースを提供する。MCP ServerとWeb UIは、原則としてこのAPI（または同一のサービス層）を利用する。

主な機能：

- ドキュメント検索（クエリ、情報源、件数、フィルタ条件）
- ドキュメント取得（全文または参照先）
- 検索結果の整形（タイトル、要約、関連箇所、出典、スコア等）
- 認証・認可、アクセス可能な範囲への絞り込み

API例：

```text
GET /api/documents/search?q=...
GET /api/documents/{document_id}
GET /api/sources
```

※エンドポイント・リクエスト形式は実装時に確定する。

### 3.5 MCP Server

AI Agentが社内ドキュメントを検索・取得するためのMCPインターフェースを提供する。

初期版で提供するTool：

```text
search_documents(query, source_ids?, limit?)
get_document(document_id)
list_sources()
```

検索結果では、Agentが次に読むべき文書を判断できるよう、`document_id`、タイトル、要約、関連箇所、原文URLを返す。検索と文書取得を分け、必要な文書だけを後から読めるようにする。

MCP Server独自の検索ロジックは持たず、Search APIの機能を公開するアダプタとして実装する。初期版では読み取り専用とし、通信方式とクライアント互換性は実装時に確認する。

### 3.6 Web UI

**Search View（利用者向け）**

- キーワード検索と検索結果一覧
- 要約・関連箇所・出典の表示
- 原文への遷移、必要に応じた本文プレビュー

**Admin View（管理者向け）**

- Connector・クロール対象・実行周期の設定
- クロールの手動実行、状態・エラー・最終同期時刻の確認
- インデックス件数、再インデックスの管理
- OpenSearch Dashboardsへの管理用導線（任意。一般利用者には公開しない）

**Chat View（将来拡張）**

- Search APIを利用した対話型検索
- 任意のLLMとの接続、引用元の表示
- 初期版では必須としない

## 4. データの流れ

### 4.1 収集・更新

1. Crawlerがデータソースからドキュメントを取得する。
2. Indexerが本文とメタデータを正規化する。
3. 要約生成が有効なら検索用途向け要約を生成する。
4. OpenSearchにドキュメント単位で登録・更新する。
5. 削除された文書は、安全な削除判定を経てインデックスから削除する。

### 4.2 検索・取得

1. AgentはMCP Server、利用者はWeb UIを通じて検索する。
2. Search APIが認証・アクセス制御を適用してOpenSearchを検索する。
3. タイトル・要約・関連箇所・文書ID・出典を返す。
4. Agentは必要な場合のみ `get_document` で本文を取得する。
5. 回答生成はAgent側で行う（Chat Viewを設けた場合はその機能で行う）。

## 5. セキュリティ・運用要件

- **アクセス制御**：情報源または文書単位の権限を保持し、Search APIとMCP経由で一貫して適用する。認証されていない利用者に社内文書を返さない。
- **初期版の制約**：元システムの細粒度ACL同期が未実装の場合は、閲覧権限が共通の利用者・文書だけを対象とするなど、対象範囲を制限する。
- **機密情報**：Connectorの認証情報を安全に管理し、ログに本文や秘密情報を不用意に記録しない。
- **外部通信**：要約・Embeddingで外部LLMを利用する場合は明示的な設定を必要とする。オフラインでの利用も考慮する。
- **運用性**：クロール失敗の再実行、同期状態の確認、ログ、ヘルスチェック、バックアップ・リストア手順を用意する。
- **再現性**：OpenSearchや各コンポーネントのバージョンを固定し、更新手順を提供する。

## 6. パッケージ化・配布

初期版は**Docker Composeによるセルフホスト配布**を基本とする。

想定コンテナ：

- `api`：Search API / MCP Server（同居可能）
- `worker`：Crawler / Indexer / 定期実行
- `opensearch`：検索基盤
- `web`：Web UI（APIと同居してもよい）
- `db`：Connector設定・ジョブ状態等の永続化（必要に応じて）
- `opensearch-dashboards`：管理・デバッグ用途（任意）
- `embedding` / `llm`：ローカルモデル利用時のみ（任意）

設定ファイルや環境変数で接続先、データ保存先、認証、モデル利用有無を切り替えられるようにする。永続データはボリュームに保存し、単一ホストでの導入と更新を容易にする。

将来的にはKubernetes向けのHelm Chartなども検討する。

## 7. 開発スコープ

### MVP（最初に提供するもの）

- ローカルディレクトリ等、少数のConnector
- 全件収集・差分更新・削除反映
- 本文抽出とドキュメント単位のOpenSearch登録
- BM25によるタイトル・要約・本文検索
- 要約生成（モデル設定時に有効。未設定なら全文検索で動作）
- Search APIとMCPの検索・文書取得
- 最小限のSearch View / Admin View
- Docker Composeによる起動・永続化

### 将来的な拡張

- 認証・アクセス制御の基本機構
- Connectorの追加（Confluence、SharePoint、Git等）
- 要約Embeddingによるベクトル検索・ハイブリッド検索
- Reranking、セクション単位の補助インデックス
- 元システムのACL同期、SSO連携
- Chat ViewとLLM接続
- Kubernetes対応、大規模構成への分離・スケールアウト

## 8. 未決定事項・検証項目

1. 最初に対応するデータソースと必要な認証方式
2. 文書原本の保存場所（元システム参照・ローカル保存など）
3. 要約生成に利用するモデル、コスト、オフライン動作要件
4. ドキュメントの最大サイズと、長文に対する検索品質
5. 利用者・情報源・文書ごとの権限制御方式
6. Web UIとAPIの技術スタック、コンテナ分割方針
7. 検索品質の評価方法（実際の質問・正解文書による検証）

---

**現時点の結論**：ドキュメント単位の全文・要約検索を中心とするセルフホスト型検索基盤をMVPとして構築し、MCPから利用できるようにする。チャンク分割、ベクトル検索、Chat Viewは実測に基づいて段階的に追加する。
