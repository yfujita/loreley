## 1. 概要

オンプレミス環境やローカル環境で動作し、AI Agentから利用できる**汎用的な社内ドキュメント検索基盤**を提供する。

複数のデータソースからドキュメントを収集して索引化し、OpenSearchで検索できるようにする。検索機能はSearch APIとMCPで提供し、Web UIからも直接検索できる。

本プロダクトの中心的な責務は**ドキュメントの収集・管理・検索・取得**である。LLMによる回答生成は必須機能にしない。AI Agentや外部アプリケーションが検索結果を使って回答を生成する構成を基本とする。

### 想定する利用シーン

- AI Agentが、社内の設計書、手順書、議事録などを横断して検索する。
- 利用者がWeb UIからドキュメントを検索し、原文を確認する。
- 管理者が、検索対象、クロール周期、インデックスの状態を管理する。

### 設計方針

- **セルフホストを基本とする**：Docker Composeで導入でき、外部サービスへの通信を必須としない構成にする。
- **検索基盤と回答生成を分離する**：特定のLLMやAI Agentに依存しない。
- **ドキュメント単位のインデックスを基本とする**：全文・タイトル・要約を検索対象とし、チャンク分割は必須にしない。
- **拡張できる構成にする**：データソースごとのConnector、検索方式、要約・Embeddingの生成方式を差し替えられるようにする。
- **安全な検索を前提とする**：利用者が閲覧できないドキュメントを、検索結果やMCPから返さない。MVPでは、この原則を「運用前提」で満たす（§5.1）。認証・認可の仕組みは将来の版で実装する。

## 2. システム構成

```text
[社内ドキュメント / ファイル / Wiki / Git 等]
                    |
              Crawler / Connector
                    |
                 Indexer
        (抽出・正規化・要約生成)
               /         \
     検索インデックス      Store層（設定・ジョブ・抽出済みテキスト）
               \         /     ※バックエンド差し替え可
               OpenSearch
          (検索用インデックス + KVS用インデックス)
                    |
                Search API
               /     |     \
         MCP Server Web UI  外部APIクライアント
              |       |
           AI Agent  利用者・管理者
```

※上記は論理構成である。初期版では、複数のコンポーネントを同じプロセスやコンテナにまとめてもよい。

## 3. コンポーネント

実装言語は、バックエンド（Crawler / Indexer / Search API / MCP Server）をPythonとする。Web UIの技術スタックは未決定である（§8）。

### 3.1 Crawler / Connector

指定されたデータソースからドキュメントを収集する。ConnectorはデータソースごとのCrawlerの実装であり、Crawlerはその実行と管理を受け持つ。

- データソースごとにConnectorを用意する（例：ローカルディレクトリ、HTTPサイト、Confluence、Git）。MVPではローカルディレクトリ／ファイル共有を対象とする。
- 初回の全件取得と、以降の差分同期に対応する。差分は、更新日時と`content_hash`を比べて判定する。
- 追加・更新・削除を検知し、Indexerに通知する。
- 接続設定、認証情報、実行周期、取得状況、エラーを管理する（Store層に保存する。§3.8）。
- Webページなどではリンクを辿る必要があるため、最低限のスクレイピング機能を持つ（MVP対象外）。

Connectorごとに取得方法が違っても、Indexerには共通ドキュメント形式（§3.1.1）で渡す。

#### 3.1.1 共通ドキュメント形式

| 項目 | 説明 |
| --- | --- |
| `source_id` | データソースの識別子（管理者が登録したConnector設定の単位） |
| `external_id` | データソース内で一意な識別子（ファイルの相対パス、ページID等） |
| `title` | タイトル（取得できなければファイル名） |
| `url` / `path` | 原文への参照 |
| `mime_type` | 文書形式 |
| `content` | 抽出前の本文、または取得用の参照 |
| `content_hash` | 本文のハッシュ値（SHA-256）。差分検知と冪等性の判定に使う |
| `source_updated_at` | データソース上の更新日時 |
| `fetched_at` | 取得日時 |
| `metadata` | Connector固有の追加属性 |

#### 3.1.2 ID設計

- `document_id`は`hash(source_id + external_id)`で決定的に生成する。同じ文書を再取得すると同じIDになるため、再実行しても重複しない。
- パスの変更やリネームは「旧IDの削除 + 新IDの追加」として扱う。リネームの追跡は初期要件にしない。

#### 3.1.3 期限による削除

取得の失敗や一時的な空応答によって、文書を誤って削除しないようにする。削除は期限（`last_seen_at`とTTL）だけで判定し、論理削除や猶予期間は置かない。

- クロールで見つけた文書には、変更の有無に関わらず`last_seen_at`（クロール開始時刻）を書き込む。変更のない文書（`content_hash`が同じ）は本文の再処理を飛ばし、`last_seen_at`だけを部分更新する。
- 全件を列挙するクロールが正常に完了したときだけ、同じ`source_id`のうち`last_seen_at + TTL < 現在時刻`の文書を削除する。失敗・中断したクロールと、差分だけを取るクロール（将来のConnector）では削除しない。
- TTLはクロール設定（データソースごと）で指定し、全件クロールの間隔より長くする。例：日次クロールでTTLが3日なら、3回続けて見つからなかった文書を削除する。
- 削除前に対象件数を数え、削除率がしきい値（例：対象件数の20%）を超えた場合は、削除を保留して管理者に通知する。管理者がAdmin Viewで承認すると削除を実行する。
- 削除対象は検索で抽出するため、抽出前にリフレッシュする。削除は、検索インデックスとStore層（抽出済みテキスト・文書ごとの処理状態）の両方から行う。
- データソースから消えた文書は、削除されるまで検索結果に残る。検索時に`last_seen_at`で除外はしない。クロールが失敗し続けると、全文書が検索から消えてしまうためである。
- トレードオフ：毎回すべての文書を部分更新するため、OpenSearchでは文書全体の再書き込みが発生する。負荷は実装後に実測する（§8.2）。

### 3.2 Indexer

収集したドキュメントを検索できる形に変換し、OpenSearchに登録する。

- 文書形式に応じてテキストを抽出する（HTML、Markdown、PDF、Office文書など。対応形式は段階的に増やす）。
- 本文を正規化し、タイトル・URL・更新日時などのメタデータを付ける。
- 抽出済みテキストをStore層に保存する。原本は保存せず、元システムを参照する。再インデックスするときは、再クロールせずに抽出済みテキストから作り直す。
- 文書全体の**検索用の要約**を生成する。単に短くするのではなく、扱う主題、重要な概念、その文書で答えられる質問を表現する。
- OpenSearchへの登録・更新・削除を行う。`document_id`をキーにして上書きするため、再実行しても重複しない。変更のない文書は、`last_seen_at`だけを部分更新する（§3.1.3）。
- 必要に応じてEmbeddingを生成する（初期版では任意）。

要約生成は**既定では無効**とし、LLMを明示的に設定したときだけ有効になる。要約がなくても全文検索で動作する。要約の生成状態とモデル名・バージョンを保持し、後から再生成できるようにする。

#### 3.2.1 エラー処理

| 事象 | 扱い |
| --- | --- |
| テキスト抽出に失敗 | タイトルとメタデータだけを登録し、`index_status=extract_failed`にする。Admin Viewに表示する |
| 本文がサイズ上限を超える | 上限までを索引化し、`truncated=true`にする |
| 要約生成の失敗・遅延 | 要約なしで先に登録する（`summary_status=pending/failed`）。要約は後から非同期に生成する |
| OpenSearchへの登録失敗 | 一定回数リトライしたあと、ジョブを失敗として記録する |

### 3.3 OpenSearch

検索インデックスを保持する。

初期版は**1ドキュメント = 1検索レコード**を基本とし、以下のフィールドを想定する。

| フィールド | 用途 |
| --- | --- |
| `document_id` | 一意な識別（§3.1.2） |
| `source_id` | データソースによる絞り込み |
| `title` | タイトル検索 |
| `summary` | 文書全体の主題による検索 |
| `content` | 細かい語句・識別子による全文検索 |
| `url` / `path` | 原文への参照 |
| `mime_type` | 文書形式による絞り込み |
| `source_updated_at` | 更新日による絞り込み |
| `indexed_at` | インデックスに登録した日時 |
| `content_hash` | 差分検知 |
| `summary_status` / `summary_model` | 要約の生成状態と、生成に使ったモデル・バージョン |
| `index_status` / `truncated` | 抽出状態と、本文を切り詰めたかどうか |
| `last_seen_at` | クロールで最後に見つかった日時（期限による削除の判定。§3.1.3） |
| `acl` | アクセス制御用の属性（MVPでは使わない。将来に備えて予約する） |
| `summary_embedding` | 意味検索用のベクトル（任意） |

#### 3.3.1 検索方式

- 基本はBM25による全文検索とし、タイトル・要約・本文の重みを調整する。
- **日本語を主な対象とする**。日本語は形態素解析（kuromojiまたはSudachi。どちらにするかは評価して決める）で解析し、英語は標準アナライザで併せて解析する。識別子や型番の検索漏れを防ぐため、n-gramのサブフィールドの追加も検討する。
- ユーザー辞書・同義語辞書はファイルで管理し、更新したら再インデックスで反映する。
- 将来は、要約Embeddingを使ったベクトル検索やハイブリッド検索を追加する。

#### 3.3.2 インデックス運用

- インデックスにはエイリアス経由でアクセスする。マッピングや辞書を変えるときは、新しいインデックスを作ってからエイリアスを切り替える。こうすると検索を止めずに再インデックスできる。
- 本文など、ハイライトに使うフィールド（n-gramなどのサブフィールドを含む）は、オフセットを保存してマッピングする（`index_options: offsets`）。ハイライタはunified（既定）を使う。こうするとハイライト時に本文を再解析しないため、ハイライトの解析上限（`index.highlight.max_analyzed_offset`、既定は100万文字）は適用されない。この上限を理由に、長い文書の本文を切り詰めない。plainハイライタは常に再解析し、上限を超えると検索リクエスト全体が失敗するため使わない。
- オフセットを保存するとインデックスサイズが増える。増え方は実装時に計測する。本文サイズの上限（§3.2.1）は、リクエストサイズ・インデックスサイズ・処理時間などの観点で決める（§8.2）。
- 長い文書で検索精度に問題が出た場合は、見出し・セクション単位の補助インデックスを追加できる構成にする。固定長チャンクへの分割は初期要件にしない。

### 3.4 Search API

OpenSearchを使った共通の検索・文書取得インターフェースを提供する。MCP ServerとWeb UIは、原則としてこのAPI（または同じサービス層）を使う。

主な機能：

- ドキュメント検索（クエリ、データソース、件数、フィルタ条件）
- ドキュメント取得（全文、または原文への参照）。AgentのコンテキストやUIを圧迫しないよう、**範囲指定・ページング**（文字オフセットと最大長）に対応する。
- 検索結果の整形（タイトル、要約、関連箇所、出典、スコアなど）
- 認証・認可、アクセス可能な範囲への絞り込み（将来拡張。MVPでは実装しない）

APIの例：

```text
GET /api/documents/search?q=...&source_ids=...&limit=...
GET /api/documents/{document_id}?offset=...&max_length=...
GET /api/sources
```

※エンドポイントとリクエスト形式は実装時に確定する。

### 3.5 MCP Server

AI Agentが社内ドキュメントを検索・取得するためのMCPインターフェースを提供する。

初期版で提供するTool：

```text
search_documents(query, source_ids?, limit?)
get_document(document_id, offset?, max_length?)
list_sources()
```

Agentが次に読む文書を判断できるよう、検索結果には`document_id`、タイトル、要約、関連箇所、原文のURLを含める。検索と文書取得を分けて、必要な文書だけを後から読めるようにする。`get_document`は長い文書を分割して取得できるようにし、続きがあるかどうか（次の`offset`）を返す。

MCP Server独自の検索ロジックは持たず、Search APIの機能を公開するアダプタとして実装する。

- **通信方式**：Streamable HTTPで提供し、Search APIと同じコンテナに置く。
- **読み取り専用**：初期版では書き込み系のToolを提供しない。
- **認証**：将来の版でトークン認証を追加する。MVPは§5.1の運用前提で使う。
- クライアント互換性は実装時に主要なMCPクライアントで確認する。

### 3.6 Web UI

**Search View（利用者向け）**

- キーワード検索と検索結果の一覧
- 要約・関連箇所・出典の表示
- 原文への遷移と、必要に応じた本文プレビュー

**Admin View（管理者向け）**

- Connector・クロール対象・実行周期・TTLの設定
- クロールの手動実行。状態・エラー・最終同期時刻の確認
- 抽出失敗・要約未生成の文書の確認
- 削除の保留（削除率がしきい値を超えた同期）の確認と承認
- インデックス件数の確認と再インデックスの管理
- OpenSearch Dashboardsへの管理用の導線（任意。一般利用者には公開しない）

**Chat View（将来拡張）**

- Search APIを使った対話型の検索
- 任意のLLMとの接続と、引用元の表示
- 初期版では必須にしない

### 3.7 ジョブ管理

クロール・インデックス・要約生成はジョブとして管理し、状態をStore層に保存する。

- ジョブの状態：`queued` → `running` → `succeeded` / `failed` / `cancelled`
- 同じデータソースのクロールは同時に1つだけ実行する（排他制御）。
- 一時的なエラーは、指数バックオフで一定回数リトライする。
- 失敗したジョブはAdmin Viewから再実行できる。
- 文書ごとの処理状態（`index_status` / `summary_status`）はジョブとは別に保持する。こうすると、一部の文書だけを再処理できる。

### 3.8 データストア（Store層）

MVPではリレーショナルDBを使わず、**OpenSearchをKVSのように使ってDBの代わりにする**。ただしコード上は、検索インデックスとは別の「DBサービス」として扱い、バックエンドを差し替えられるようにする。

- **抽象化**：アプリケーションは、Store層のインターフェース（Repository）だけを経由して永続データを読み書きする。OpenSearchのAPIを直接呼ばない。対象は、データソース設定・ジョブ状態・抽出済みテキスト・文書ごとの処理状態である。
- **初期実装**：OpenSearch実装を用意する。用途ごとに検索インデックスとは別のインデックスを分けて、IDをキーにget/put/deleteする（例：`loreley-sources`、`loreley-jobs`、`loreley-texts`）。
- **差し替え**：どのバックエンドを使うかは設定で選ぶ。将来、PostgreSQLやSQLiteの実装を追加しても、呼び出し側を変えずに済むようにする。
- **インターフェースの制約**：OpenSearchで実現できる操作に合わせて、インターフェースを最小限にする。
  - IDによる取得・保存・削除
  - 単純な条件での一覧
  - 楽観的排他制御による条件付き更新（OpenSearchでは`if_seq_no`/`if_primary_term`を使う）
  - トランザクションや結合（JOIN）には依存しない
- **整合性の注意**：OpenSearchの検索はリフレッシュ後にしか結果に反映されない（ニアリアルタイム）。状態の確認や排他の判定には、検索ではなくIDによる取得（リアルタイム）を使う。
- **認証情報**：Connectorの認証情報は、Store層に平文では保存しない。環境変数や秘密情報ファイルで参照する方式を基本とする。

## 4. データの流れ

### 4.1 収集・更新

1. Crawlerがデータソースからドキュメントを取得する。
2. `content_hash`で変更を判定し、変更がない文書は本文の処理を飛ばして`last_seen_at`だけを更新する。変更がある文書は`last_seen_at`も併せて書き込む。
3. Indexerが本文を抽出・正規化し、抽出済みテキストをStore層に保存する。
4. 要約生成が有効なら、検索用の要約を非同期に生成する。
5. OpenSearchにドキュメント単位で登録・更新する。
6. 全件クロールが正常に完了したら、`last_seen_at + TTL`を過ぎた文書を、削除率のしきい値の確認（§3.1.3）を経て、検索インデックスとStore層から削除する。

### 4.2 検索・取得

1. AgentはMCP Serverを通じて、利用者はWeb UIを通じて検索する。
2. Search APIがOpenSearchを検索する（将来は認証・アクセス制御もここで適用する）。
3. タイトル・要約・関連箇所・文書ID・出典を返す。
4. Agentは必要な場合だけ`get_document`で本文を取得する（長い文書は分割して取得する）。
5. 回答はAgent側で生成する（Chat Viewを設けた場合は、Chat Viewで生成する）。

## 5. セキュリティ・運用要件

### 5.1 アクセス制御

- **MVPの運用前提**：MVPには認証・認可の仕組みがない。そのため、以下の前提で運用する。
  - 信頼できる社内ネットワーク内だけで公開する（インターネットに公開しない）。
  - 利用者全員が閲覧してよい文書だけを検索対象として登録する。
  - この前提はREADMEと導入手順で明示し、既定ではlocalhostだけで待ち受ける。
- **将来の版**：API/MCPのトークン認証、データソース単位のアクセス可否、文書単位のACL同期、SSO連携を順に追加する。このとき、Search APIとMCPで同じ権限判定を適用する。

### 5.2 その他の要件

- **機密情報**：Connectorの認証情報は安全に管理する（平文で設定ファイルに書かない方法を用意する）。ログに本文や秘密情報を記録しない。
- **OpenSearchの保護**：OpenSearchとDashboardsのポートはホストの外に公開しない。Search APIだけを公開の窓口にする。
- **外部通信**：要約・Embeddingに外部LLMを使う場合は、明示的な設定を必須にする。既定の構成はオフラインで動作する。
- **プロンプトインジェクション**：検索結果や本文はAgentに渡るため、文書中の指示文がAgentの動作に影響するおそれがある。本プロダクトは文書を加工せずに返す。そのうえで、返す内容が「データソースから取得した文書である」ことを出典とあわせて明示し、MCPのTool説明で、本文を指示として扱わないようAgentに注意を促す。
- **運用性**：クロール失敗の再実行、同期状態の確認、ログ、ヘルスチェック、バックアップ・リストア手順を用意する。検索インデックスはStore層の抽出済みテキストから再構築できる。MVPではStore層もOpenSearchにあるため、OpenSearchのスナップショットと設定ファイルをバックアップの対象とする。
- **再現性**：OpenSearchと各コンポーネントのバージョンを固定し、更新手順を提供する。

## 6. パッケージ化・配布

初期版は**Docker Composeによるセルフホスト配布**を基本とする。

想定するコンテナ：

- `api`：Search API / MCP Server（同居）
- `worker`：Crawler / Indexer / 定期実行
- `opensearch`：検索基盤。MVPではStore層のバックエンドも兼ねる（§3.8）
- `web`：Web UI（APIと同居してもよい）
- `opensearch-dashboards`：管理・デバッグ用（任意）
- `embedding` / `llm`：ローカルモデルを使う場合だけ（任意）

接続先、データの保存先、モデルの利用有無は、設定ファイルや環境変数で切り替えられるようにする。永続データはボリュームに保存し、単一ホストで導入・更新しやすくする。

将来は、Kubernetes向けのHelm Chartなども検討する。

## 7. 開発スコープ

### MVP（最初に提供するもの）

- ローカルディレクトリ／ファイル共有のConnector
- 全件収集・差分更新・期限による削除（`last_seen_at`・TTL・削除率のしきい値）
- 本文の抽出と、ドキュメント単位でのOpenSearchへの登録
- 日本語に対応したBM25によるタイトル・要約・本文の検索
- 要約生成（既定は無効。モデルを設定したときだけ有効）
- Search APIとMCP（Streamable HTTP）による検索・文書取得（範囲指定に対応）
- ジョブ管理と、最小限のSearch View / Admin View
- Docker Composeによる起動と永続化
- 検索品質の評価セットと評価スクリプト（§7.1）
- 認証なし。§5.1の運用前提を明示する

### 7.1 検索品質の評価

- 実際の質問と正解文書の組（評価セット。初期目標は50問程度）を用意する。
- 指標はRecall@10とMRRとする。アナライザの選定、重みの調整、ベクトル検索・チャンク分割を追加するかどうかは、この指標で判断する。
- 検索方式を変えるたびに評価を実行し、結果を記録する。

### 将来的な拡張

- 認証・アクセス制御（API/MCPのトークン認証、データソース単位のアクセス可否）
- 元システムのACL同期、SSO連携
- Connectorの追加（HTTPサイト、Confluence、SharePoint、Gitなど）
- 要約Embeddingによるベクトル検索・ハイブリッド検索
- Reranking、セクション単位の補助インデックス
- Chat ViewとLLMの接続
- Kubernetes対応、大規模構成に向けた分離とスケールアウト

## 8. 決定事項・未決定事項

### 8.1 v0.2時点の仮決定

| 論点 | 仮決定 |
| --- | --- |
| MVPの認証 | 実装しない。信頼できるネットワーク内で、全員が閲覧してよい文書だけを対象にする（§5.1） |
| 最初のデータソース | ローカルディレクトリ／ファイル共有。規模は1万〜10万文書を想定するが、目標値ではない（§8.2） |
| 要約生成 | 既定で無効（オフライン）。LLMは明示的に設定したときだけ使う |
| 原本の保存 | 抽出済みテキストをStore層に保存し、原本は元システムを参照する |
| 永続化（DB） | 専用のDBは置かない。OpenSearchをKVSとして使い、Store層で抽象化してバックエンドを差し替えられるようにする（§3.8） |
| MCPの提供形態 | Streamable HTTPで、APIと同居させる。MCPの認証は将来の版に回し、MVPは§5.1の運用前提で使う |
| 削除方針 | `last_seen_at`とTTLによる期限での削除に一本化する（論理削除・猶予期間は置かない）。削除率がしきい値を超えたら保留して管理者の承認を待つ |
| 対象言語 | 日本語を主対象とし、英語も併せて扱う |

### 8.2 未決定事項・検証項目

1. 日本語アナライザの選定（kuromojiかSudachiか）と、n-gramを併用するかどうか
2. 文書の最大サイズ（索引化の上限）と、長い文書に対する検索品質
3. 要約生成に使うモデル、コスト、生成にかかる時間
4. TTLと削除率のしきい値の既定値
5. Web UIの技術スタックと、コンテナの分割方針
6. Store層のインターフェースの詳細と、OpenSearch以外のバックエンドに移る条件（件数・更新頻度・排他の要件など）
7. 将来の認証方式（トークンの発行・管理方法、データソース単位の権限モデル）
8. 非機能要件（文書数・検索レイテンシ・同時利用数・ホスト要件など）。設計段階では目標値を置かず、実装後に実測して決める

## 9. 用語集

| 用語 | 意味 |
| --- | --- |
| データソース | 収集対象の情報源（ディレクトリ、Wiki、Gitリポジトリなど）。管理者が登録する単位で、`source_id`で識別する |
| Connector | データソースごとの取得処理の実装 |
| Crawler | Connectorを実行し、スケジュールと同期状態を管理するコンポーネント |
| Agent | MCPを通じて本プロダクトを利用するAI Agent |
| 期限による削除 | `last_seen_at + TTL`を過ぎた文書を、全件クロールの正常完了後に削除する方式（§3.1.3） |
| `last_seen_at` | クロールで最後に見つかった日時。検索インデックスの文書に持つ |
| TTL | `last_seen_at`からの有効期間。データソースごとのクロール設定で指定する |

---

**現時点の結論**：ドキュメント単位の全文・要約検索を中心とする、セルフホスト型の検索基盤をMVPとして構築し、MCPから使えるようにする。MVPは認証なしで、信頼できるネットワーク内で使う前提とする。チャンク分割、ベクトル検索、Chat View、認証・認可は、評価セットによる実測と利用状況に基づいて段階的に追加する。
