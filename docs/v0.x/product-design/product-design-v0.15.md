## 1. 目的とスコープ

### 1.1 概要

オンプレミス環境やローカル環境で動作し、AI Agentから利用できる**汎用的な社内ドキュメント検索基盤**を提供する。

複数のデータソースからドキュメントを収集して索引化し、OpenSearchで検索できるようにする。検索機能はSearch APIとMCPで提供し、Web UIからも直接検索できる。

中心的な責務は**ドキュメントの収集・管理・検索・取得**である。LLMによる回答生成は必須機能にしない。AI Agentや外部アプリケーションが検索結果を使って回答を生成する構成を基本とする。

### 1.2 目的

- 社内の設計書、手順書、議事録などを、AI Agentが横断して検索・取得できるようにする。
- 利用者がWeb UIから文書を検索し、出典（パス・URL）を確認できるようにする。
- 管理者が、検索対象、クロール周期、インデックスの状態を管理できるようにする。
- 外部サービスへの通信なしで、単一ホストに導入できるようにする。

### 1.3 想定ユーザー

| ユーザー | 主な用途 |
| --- | --- |
| AI Agent（MCPクライアント） | `search_documents`で候補を探し、`get_document`で必要な文書を読む |
| 利用者（社内の従業員） | Search Viewでキーワード検索し、要約・関連箇所・出典を確認する |
| 管理者・運用者 | データソースの登録、クロールの実行、失敗やクロール結果（4.6）の確認、再インデックス |
| 外部アプリケーションの開発者 | Search APIを使って独自のアプリケーションに検索を組み込む |

### 1.4 成功指標

非機能要件（文書数・レイテンシ・同時利用数など）は、実装後に実測して決める（9.2）。MVPでは次を指標とする。

| 指標 | 内容 |
| --- | --- |
| 検索品質 | 評価セット（50問程度）でRecall@10とMRRを測定し記録する。目標値は初回の測定後に決める（8.3）。MVPの完成基準は「検索品質が達成されたか」ではなく「測定できたか」であり、品質目標はGA条件（8.5）で別に定める |
| 導入の容易さ | Docker Composeの起動から、ローカルディレクトリの登録、検索までを通して動作する |
| Agent利用 | 主要なMCPクライアントで、検索から文書取得までを実行できる |
| 削除の安全性 | 取得の失敗（読めない文書を含む）、クロール全体の異常、Indexer・Store層の障害（終了通知がIndexerに受理される前にクロールが失敗する場合）による誤削除を防止する。しきい値を超える削除は、TTLの経過と割合ルールにより、自動では実行しない（マウント外れなどで全件が消えたように見える場合を含む）。ただし、一部のディレクトリだけの消失、少数の消失、最小件数以下の小さなソースの0件列挙は防げない（MVPの制約。2章） |

### 1.5 非目標

- LLMによる回答生成（Chat Viewは将来拡張）。
- MVPでの認証・認可、文書単位のアクセス制御。
- 原文への遷移（パスまたはURLの表示にとどめる。URLへの写像は将来拡張）。
- 画像のみのPDFのOCR、Office文書の抽出（次版）。
- ファイルのリネーム追跡、チャンク分割、Embeddingの生成とベクトル検索（評価結果を見て判断する）。
- 数十万件を超える規模や、高可用構成。

### 1.6 設計方針

- **セルフホストを基本とする**：Docker Composeで導入でき、外部サービスへの通信を必須としない。
- **検索基盤と回答生成を分離する**：特定のLLMやAI Agentに依存しない。
- **ドキュメント単位のインデックスを基本とする**：全文・タイトル・要約を検索対象とし、チャンク分割は必須にしない。
- **OpenSearchを検索基盤とし、設定や処理状態の保存にも使う**：専用のDBを置かず、Store層を介してOpenSearchをKVSとして使う。将来、バックエンドを差し替えられるようにする。
- **コンポーネントを疎結合に保つ**：コンポーネント間の契約（API）を明確にする。将来キューが必要になれば、HTTP部分をメッセージングに置き換えられるようにする。そのため契約は次を満たす（→ システムデザイン §14、§14.6）。
  - クロールの一意なID
  - 存在確認と登録の区別
  - 列挙完了と処理完了の区別
  - 重複して届いても結果が変わらない冪等性
  - 全文書の結果を確認してから削除する順序
- **拡張できる構成にする**：Connector、検索方式（Embeddingを使うベクトル検索は将来）、要約の生成方式、Store層のバックエンドを差し替えられるようにする。
- **安全な検索を前提とする**：閲覧できない文書を返さない。MVPは認証を持たないため、この原則を「信頼できる利用者だけの検証環境」という運用前提で満たす（6.1）。
- **とにかく動かすことを優先する**：MVPでは保護機能や最適化より、動作する最小構成を優先する。割り切った点はリスクとして明記する（2章）。

## 3. システム構成

```text
[社内ドキュメント / ファイル / Wiki / Git 等]
                    |
        Crawler / Connector（コンテナ）  <--HTTPでジョブ起動-- Admin API <-- Web UI（管理画面）
                    |  HTTP（登録・存在確認・列挙の完了通知）
              Indexer（コンテナ）
        (抽出・正規化・要約生成・削除の判断と実行)
               /         \
     検索インデックス      Store層（設定・ジョブ・抽出済みテキスト・処理状態）
               \         /     ※バックエンド差し替え可
               OpenSearch
          (検索用インデックス + KVS用インデックス)
                    |
                Search API
               /     |     \
         MCP Server Web UI  外部APIクライアント
              |       |
           AI Agent  利用者・管理者
```

※CrawlerとIndexerは別コンテナとし、メッセージブローカーを使わずHTTPで直接通信する。ジョブの起動もHTTPで、Web UIの管理画面はAdmin APIを通じてCrawlerに起動を依頼する（Admin APIは、ジョブ状態と削除結果をStore層から読み取りのみで直接読む）。CrawlerとIndexerのHTTPは内部ネットワーク限定で、ホストの外に公開しない（→ システムデザイン §6.3、§7.3、§14）。それ以外のコンポーネントは、初期版では同じプロセスやコンテナにまとめてもよい。

実装言語と技術スタックは、システムデザインで扱う（→ システムデザイン §7.5）。

## 4. コンポーネントと責務

| コンポーネント | 主な責務 |
| --- | --- |
| Crawler | データソースの列挙と原本の取得、実行周期、ジョブ・設定のStore層への記録、存在確認の要請、列挙の完了の通知。削除の判断・実行はしない |
| Indexer | 文書の登録・更新・削除を担当するコンポーネント。抽出・正規化、検索インデックス・抽出済みテキストへの書き込み、**削除の判断と実行**（割合ルールを含む）、削除結果の記録と保持（登録結果の保持場所・項目は9.2） |
| Search API | 検索・文書取得の提供（読み取りのみ） |
| Admin API | ジョブ状態と削除結果の表示（Store層から読み取りのみ）。クロールの起動などの操作はCrawlerに中継する |

詳細な責務分担は → システムデザイン §14.2。

### 4.1 Crawler / Connector

データソースから文書を列挙・取得し、Indexerに共通ドキュメント形式（→ システムデザイン §1）で渡す。ConnectorはデータソースごとのCrawlerの実装で、Crawlerはその実行・周期・クロール状態を管理する。

- MVPのConnectorは、ローカルディレクトリ／ファイル共有のみ。HTTPサイト、Confluence、Gitなどは将来の拡張（Webページのスクレイピングも将来）。
- **列挙クロール**：データソース内のすべての文書を列挙するクロール。MVPのクロールはすべて列挙クロールで、削除の判断の入力になる列挙の完了を通知するのはこのクロールだけである（削除の判断と実行はIndexerが行う。4.2）。
- MVPは追加・更新の検知をせず、毎回すべての文書を取得・抽出して登録する（全件更新。差分検知は将来拡張）。削除は、最後に見つかった日時とTTLによる期限で判定する（→ システムデザイン §3.4）。
- 接続設定、認証情報の参照、実行周期、取得状況、エラーはStore層に保存する。

### 4.2 Indexer

収集した文書を検索できる形にして登録する。

- 文書形式に応じてテキストを抽出し、正規化する。MVPの対応形式はtxt・Markdown・HTML・PDF。Office文書は次版。文字コードは自動判定し、UTF-8のほかShift_JIS/CP932にも対応する。抽出ライブラリはシステムデザインで扱う（→ システムデザイン §7）。
- 抽出済みテキストをStore層に保存する。原本は保存せず、元システムを参照する。
- 文書全体の**検索用の要約**を生成する。主題、重要な概念、その文書で答えられる質問を表現する。既定では無効で、LLMを明示的に設定したときだけ有効になる。要約の失敗・遅延では、要約なしで先に登録し、後から非同期に生成する（→ システムデザイン §8）。
- 検索インデックスへの登録・更新・削除を行う。期限切れの文書の**削除の判断と実行も、Indexerが行う**（割合ルールの適用を含む。→ システムデザイン §3.9）。
- 抽出に失敗した文書は、タイトルとメタデータだけを登録し、抽出失敗としてAdmin Viewに表示する。本文がサイズ上限を超える場合は、上限までを索引化し、切り詰めたことを表示する。
- 原本の取得・登録の段階でも上限を設ける（本文の上限による切り詰めとは別）。MVPでは、上限を超えた原本は取り込まず、原本サイズ超過として文書単位のエラーに記録し、Admin Viewで確認できる（ユーザー決定）。存在確認日時は更新し、削除はしない。すでに索引にある同じ文書のデータを残すか、利用者への表示方法は未決（9.2 #8。→ システムデザイン §10.2、§12.5）。具体的な形式はSD v0.8でも未決で、§10.2、§12.5で決める。
- 取得できない文書（権限エラーなど）や登録に失敗した文書は、数回リトライし、それでも失敗したら**その文書だけスキップ**して個別文書の失敗として記録する。スキップはクロール全体・他の文書の登録・他の文書の削除判定に影響させない。列挙で見つかった文書は、スキップしても削除対象にしない（5.2。→ システムデザイン §3.1、§3.3）。抽出に失敗した文書は従来どおり`extract_failed`としてタイトルとメタデータを登録する（スキップではなく、スキップ件数にも数えない）。
- 取得・登録に失敗した文書のスキップは**文書固有の失敗**に限る。Indexer・Store層の障害（接続できない、タイムアウト、サーバ側エラーなど）は、スキップにせずクロールを失敗として扱う。終了通知がIndexerに受理される前に失敗した場合は削除しない（受理された後の扱いは5.2。→ システムデザイン §3.1、§3.3）。

### 4.3 検索インデックス（OpenSearch）

1文書 = 1検索レコードを基本とし、タイトル・要約・本文をBM25で検索する。日本語を主な対象とし、英語も併せて解析する。マッピング、検索クエリ、ハイライト、再インデックスは、システムデザインで扱う（→ システムデザイン §2）。

### 4.4 Search API

OpenSearchを使った共通の検索・文書取得インターフェースを提供する。MCP ServerとWeb UIは、原則としてこのAPI（または同じサービス層）を使う。

- ドキュメント検索：クエリ、データソース・文書形式・更新日による絞り込み、件数。
- ドキュメント取得：本文はStore層の抽出済みテキストから返す。AgentやUIを圧迫しないよう、範囲を指定して取得できる。
- 検索結果の整形：タイトル、要約、関連箇所、出典、スコア。
- 認証・認可は将来拡張（MVPでは実装しない）。

リクエスト・レスポンスの仕様は → システムデザイン §5。

### 4.5 MCP Server

AI Agentが文書を検索・取得するためのMCPインターフェースを提供する。Search APIの機能を公開するアダプタであり、独自の検索ロジックは持たない。

- Tool：`search_documents`、`get_document`、`list_sources`（仕様は → システムデザイン §5）。
- 通信方式はStreamable HTTP。Search APIと同じコンテナに置く。
- 読み取り専用。書き込み系のToolは提供しない。
- 認証は将来の版で追加する。MVPは6.1の運用前提で使う。ただし、DNS rebinding対策としてOriginの検証はMVPで行う（6.1）。
- クライアント互換性は、実装時に主要なMCPクライアントで確認する。

### 4.6 Web UI

**Search View（利用者向け）**

- キーワード検索と検索結果の一覧。
- 要約・関連箇所・出典（パスまたはURL）の表示。原文への遷移は提供せず、パスの表示にとどめる。
- 必要に応じた本文プレビュー。

**Admin View（管理者向け）**

- データソース・実行周期・TTLの設定と、クロールの手動実行。状態・エラー・最終クロール完了日時の確認。削除の割合ルールのしきい値（0%以上100%未満）と最小件数も、データソースごとに設定できる（5.2）。
- 手動実行のときだけ、**強制削除**（割合ルールを無視して削除する）を指定できる。TTLが経過していない文書は消えない。定期実行では指定できない（5.2。→ システムデザイン §3.4）。
- 抽出失敗・要約未生成・スキップされた文書（取得や登録に失敗した文書）の確認と、失敗した文書の確認結果に基づく、失敗原因の解消（アクセス権の修正、データソース設定の除外条件など）と再実行。登録が長く終わらない文書の警告。
- クロール結果（登録結果と削除結果）の確認。削除結果は、クロールごとの削除件数と、割合ルールで削除しなかった場合のその理由と件数である。登録結果は、最低限、列挙件数・登録件数（新規・更新）・スキップ件数・原本サイズ超過件数・エラー件数を表示する（削除件数は削除結果側。保持と返し方は、`loreley-jobs`に保持し、Crawlerが集計し、Admin APIが読み取りで返す。Status APIは削除結果のみ。→ システムデザイン §3.3。項目の記録方法などの細部はSD v0.8の案で、一部は9.2 #12）。確認が終わらなかった場合の削除結果は、「結果未確認」または「結果不明」と表示する（4.7）。削除の承認・却下はない。Admin View上の表示を管理者への通知とみなし、メールなどの通知はMVPでは実装しない（→ システムデザイン §3.5、§3.9）。
- 突合ジョブ（検索インデックスとStore層の食い違いの検出と安全な再登録）の手動実行と結果の確認。インデックス件数の確認。
- 再インデックスはMVPでは手動手順とし、画面からの実行は将来拡張とする（→ システムデザイン §2.5）。
- OpenSearch Dashboardsへの管理用の導線（任意。一般利用者には公開しない）。

**Chat View（将来拡張）**：Search APIを使った対話型の検索。初期版では必須にしない。

### 4.7 ジョブ管理

クロール・インデックス・要約生成はジョブとして管理し、状態をStore層に保存する。

- ジョブの起動と管理はCrawlerが行い、クロールの起動はHTTPで行う（経路は → システムデザイン §14.4）。CrawlerとIndexerの責務分担は → システムデザイン §14。
- 同じデータソースのクロールは同時に1つだけ実行する。止まったジョブは失敗として検知し、管理者が復旧する（復旧方法は → システムデザイン §4.3）。
- 一時的なエラーは、数回リトライする。失敗したジョブは、Admin Viewから再実行できる。
- 文書ごとの処理状態はジョブとは別に保持する。クロールジョブは、文書の取得・登録と、Indexerによる削除処理が完了した時点で終了する。割合ルールにより削除が見送られた場合も、正常終了として扱う。Crawlerの処理（列挙・取得・通知）の完了とジョブ全体の完了は区別し、Crawlerの処理が終わっても、原則として、Indexerの削除処理が終端状態になるまでジョブは完了しない。結果はIndexerが提供するStatus APIで確認する。
- ただし、確認には待ち時間の上限がある。上限を超えた場合、または結果が取得できない場合（接続エラー・5xx・404が続く場合）は、ジョブを実行中のまま保持せず、警告を残してジョブを終える（成否は変えない）。このとき削除結果は正常終了とみなさず、「結果未確認」として扱い、Admin Viewで確認できる。その後に表示される最新状態は、Indexer側の処理の完了（削除が完了しなかった場合の失敗を含む）である。Indexer側の結果自体が失われた場合（404が続く場合）は「結果不明」と表示する。削除結果の確認結果の区分はCrawlerがジョブ記録に持ち、Admin Viewが`loreley-deletions`の現在値と併記する。再確認は行わず、知らせ方はAdmin Viewの表示のみである（ユーザー確定。→ システムデザイン §3.3、§3.9）。区分の名称と判定（HTTP結果との対応）はSD v0.8の案である（→ システムデザイン §3.3）。待ち時間の数値は未決（9.2 #11）。なお、終了通知の応答が失われてCrawlerがジョブを失敗扱いにした場合でも、Indexerが通知を受理済みなら削除は進みうる。その結果は削除結果に残り、Admin Viewで確認できる場合がある（5.2の1）。
- 削除が行われなかった、または完了しなかった場合（原因は、クロールの失敗・取り消し、メンテナンス、Indexerの再起動、エラーなど。理由コードの一覧は案。SDで確定）は、理由とともに削除結果の状態を失敗として残し（ジョブの成否は変えない）、再開せず、残りの削除は次のクロールに委ねる。新しいクロールが始まっても、実行中の削除は止めない（各文書の削除直前にTTLを再確認するため、新しいクロールが更新した文書は消えない）。同じデータソースの削除が重なる場合は直列にし、前の削除が終わるまで、後の削除は始めない（方式は → システムデザイン §3.9。MVPでは、終わらない削除への強制終了タイムアウトは設けない）。SD v0.8で反映済み。
- ジョブの成否と削除結果は別に扱い、削除されなかったことはジョブの失敗にしない（→ システムデザイン §3.3、§3.9）。
- 状態遷移とリースの詳細は → システムデザイン §4。

### 4.8 データストア（Store層）

MVPではリレーショナルDBを使わず、**OpenSearchをKVSのように使って**設定・ジョブ・抽出済みテキスト・文書ごとの処理状態を保存する。コード上は検索インデックスとは別の「Store層」として扱い、バックエンドは設定で差し替えられる。インターフェースと排他の方式は → システムデザイン §1.5、§3.8。

- Connectorの認証情報は、Store層に平文で保存しない。環境変数や秘密情報ファイルで参照する。
- インデックス構成、真実の置き場所、排他と整合性は → システムデザイン §1。

## 5. データの流れ

### 5.1 収集・更新

1. Crawlerがデータソースを列挙する。
2. すべての文書を取得し、Indexerが本文を抽出・正規化して、Store層と検索インデックスに登録する（全件更新）。数回のリトライでも読めない文書はスキップして失敗として記録し、他の文書の処理を続ける。スキップした文書は、次回のクロールで再処理される（処理済みの印の確定順序は → システムデザイン §3.2）。Indexer・Store層の障害は文書固有の失敗ではないので、スキップにせずクロールを失敗として扱う（削除との関係は5.2）。
   - 列挙で見つかった時点で、Crawlerは存在確認日時（最後に見つかった日時）の更新をIndexerに要請する。更新を保存できなかったときは、その文書をスキップとして扱わず、クロールを完了扱いにしない（失敗として扱う。終了通知の受理前なら削除もしない。→ システムデザイン §3.1）。
3. 要約生成が有効なら、要約を非同期に生成し、本文が変わっていないときだけ反映する。

詳細は → システムデザイン §3、§8。

### 5.2 削除

1. 列挙クロールが最後まで完了したときだけ、CrawlerがIndexerに列挙の完了を通知する。Indexerは、通知の内容が索引の状態と整合することを確かめたうえで（→ システムデザイン §3.9）、最後に見つかった日時にTTLを足した期限を過ぎた文書を、削除の対象にする。読めない文書のスキップがあっても、列挙が完了していれば削除は行う（スキップした文書以外は通常どおり削除判定する）。
   - 列挙で見つかった文書は、取得・登録に失敗してスキップしても、最後に見つかった日時を更新する。読めないだけで期限を過ぎて誤削除されることを防ぐ。この更新を保存できなかったときは、クロールを完了扱いにせず、削除しない（5.1）。
   - 列挙の失敗・マウント外れなど、クロール全体の異常では、従来どおり削除しない。Indexer・Store層の障害により、終了通知がIndexerに受理される前にクロールが失敗した場合は、削除しない。終了通知がIndexerに永続的に受理された後は、応答喪失などによりCrawler側のジョブが失敗扱いになっても、削除処理が継続する場合がある（削除は、各文書の削除直前の期限（TTL）再確認、割合ルール、件数照合によって守られる）。Indexerが停止している間は、開始通知・登録・終了通知が失敗してクロールが失敗扱いになり、終了通知が受理されないので削除されない。削除の実行中に止まった場合は、残りを次のクロールに委ねる。個別文書の失敗（スキップ）とは区別し、スキップは削除を止めない（→ システムデザイン §3.1、§3.3、§3.9、§14.5）。0件列挙は異常とはせず、列挙の完了として2で判断する。TTLを過ぎていない文書は消えない。
2. Indexerが**割合ルール**で削除するかを判断する。削除対象が、削除前の登録文書数に対して設定したしきい値（データソースごとに設定。0%以上100%未満）を超えるときは、そのクロールでは削除しない。削除しなかった理由と件数は、削除結果としてAdmin Viewに表示する。承認は設けず、次のクロールのたびに新しく判断する。削除対象が最小件数以下の場合は、少数のソースで1件の削除が高い割合になるため、割合に関わらず削除する。しきい値0%は、最小件数を超える削除を自動では実行しない設定である。しきい値に100%以上を許さないのは、超えたときに削除を見送るルールなので、100%では全件削除を防げないためである。全件削除したい場合は強制削除を使う。
3. 大量の削除が意図したもの（全ファイルを消した場合を含む）であれば、管理者が**強制削除**を指定して手動でクロールを実行する。割合ルール（と最小件数ルール）だけを無視する。列挙の完了、通知と索引の整合、各文書のTTLの経過は無視しないので、TTLが経過していない文書は消えない。定期実行では指定できない。
4. 検索インデックスとStore層の食い違いは、突合ジョブで検出する。MVPの突合ジョブは、不整合の検出・表示と安全な再登録まで。検索インデックスにだけある文書も、Store層にだけある文書も自動削除せず、Admin Viewでの確認と安全な再登録にとどめる（期限による通常の削除は、従来どおりIndexerが実行する）。

削除の判定、割合ルール、Indexerの削除処理、突合の詳細は → システムデザイン §3.4、§3.5、§3.6、§3.9。

### 5.3 検索・取得

1. AgentはMCP Serverを通じて、利用者はWeb UIを通じて検索する。
2. Search APIがOpenSearchを検索する（将来は認証・アクセス制御もここで適用する）。
3. タイトル・要約・関連箇所・出典を返す。
4. Agentは必要な場合だけ`get_document`で本文を取得する（長い文書は分割して取得する）。
5. 回答はAgent側で生成する（Chat Viewを設けた場合はChat Viewで生成する）。

## 6. セキュリティ・運用要件

### 6.1 アクセス制御と運用前提

MVPには認証・認可の仕組みがない。**MVPは「信頼できる利用者だけの検証環境」向け**であり、一般的な社内公開（不特定の従業員への提供）は、認証機能を追加してから行う（8.5）。次の前提で運用する。

- 信頼できる社内ネットワーク内だけで公開する（インターネットに公開しない）。
- 利用者全員が閲覧してよい文書だけを検索対象として登録する。
- **Admin Viewも認証なしで、任意のローカルパスを登録できる。信頼できる環境だけで使う。**
- 既定ではlocalhostだけで待ち受ける。社内ネットワークへ公開するには、バインド先を設定で明示的に変更する。この前提はREADMEと導入手順で明示する。
- **実行環境側の境界を厳格にする**：Admin Viewは認証を省く代わりに、読み込めるディレクトリをコンテナへのマウントで限定する。検索対象のディレクトリは読み取り専用でマウントし、それ以外のホストのパスはコンテナに見せない。**読み取り専用マウントはファイルの変更を防ぐが、マウントされた文書の閲覧制限にはならない**（到達できる人は、マウントされた文書を検索・取得できる）。
- **MCPのOrigin検証（MVPに含める）**：DNS rebinding対策として、Origin検証をMVPに含める。**認証とは別の問題**であり、認証は実装しない。検証の詳細は → システムデザイン §6.1、§6.2。

将来の版で、API/MCPのトークン認証、管理者トークン、登録できるルートパスの制限、データソース単位のアクセス可否、文書単位のACL同期、SSO連携を順に追加する。Search APIとMCPで同じ権限判定を適用する。

実装方法（Origin検証、ポートの制限、マウント、秘密情報の管理）は → システムデザイン §6。

### 6.2 その他の要件

- **機密情報**：Connectorの認証情報は平文で設定ファイルに書かない方法を用意する。ログに本文や秘密情報を記録しない。
- **OpenSearchの保護**：OpenSearchとDashboardsはホストの外に公開しない。Search APIだけを公開の窓口にする。
- **外部通信**：要約に外部LLMを使う場合は、明示的な設定を必須にする（将来Embeddingを追加する場合も同様）。既定の構成はオフラインで動作する。
- **プロンプトインジェクション**：文書を加工せずに返す。そのうえで、返す内容が「データソースから取得した文書」であることを出典とあわせて明示し、MCPのTool説明で、本文を指示として扱わないようAgentに注意を促す。
- **運用性**：クロール失敗の再実行、クロール状態の確認、ログ、ヘルスチェック、バックアップ・リストア手順を用意する。
- **バックアップと再構築**：MVPではStore層もOpenSearchにあるため、OpenSearchのスナップショットと設定ファイルをバックアップの対象とする。検索インデックスは、Store層から再構築できる。検索インデックスとStore層の両方を失った場合は、再クロールが必要である（→ システムデザイン §9）。
- **再現性**：OpenSearchとプラグイン、各コンポーネントのバージョンを固定し、更新手順を提供する。

## 7. パッケージ化・配布

Docker Composeによるセルフホスト配布を基本とする。API（Search API / MCP Server）、Crawler、Indexer（CrawlerとIndexerは別コンテナ）、OpenSearch（MVPではStore層のバックエンドも兼ねる）、Web UIを構成要素とし、OpenSearch Dashboardsとローカルモデル用のコンテナは任意とする。

接続先、データの保存先、モデルの利用有無は、設定ファイルや環境変数で切り替えられるようにする。永続データはボリュームに保存する。コンテナの分割、技術スタック、OpenSearchイメージ（日本語アナライザのプラグインを含む）とバージョンの方針は → システムデザイン §7。コンポーネント間はメッセージブローカーを使わず、HTTPで直接通信する（→ システムデザイン §14）。

将来は、Kubernetes向けのHelm Chartなども検討する。

詳細なテストケースは → システムデザイン §11。

- [ ] `docker compose up`で全コンポーネントが起動し、ヘルスチェックが通る。
- [ ] Admin Viewからローカルディレクトリを登録し、クロールを手動実行できる。txt・Markdown・HTML・PDF（UTF-8とShift_JIS/CP932を含む）が検索できる。

- [ ] 文書の更新は次回クロールで反映される。削除は、TTL経過後の、列挙が最後まで完了したクロールで反映される（割合ルールで削除されない場合を除く。以下）。
- [ ] 一部の文書が読めないクロールでも、クロールは完了し、他の文書の登録と削除が行われる。読めない文書は、TTLを過ぎても列挙で見つかっている限り削除されない。列挙の失敗のクロールでは、文書は削除されない。

  - 注記：Admin APIを経由しない経路で入った範囲外の値は、SDの受容事項（既知の制限）であり、この基準の対象外である（→ システムデザイン §3.5、§3.9）。
- [ ] 削除対象が最小件数以下なら、割合に関わらず削除される。
- [ ] 削除対象が最小件数を超えるデータソースが0件列挙になっても、TTLを過ぎていない文書は削除されず、TTL経過後も割合ルールで全件削除されない（削除対象が最小件数以下の小さなソースは対象外。2章）。
- [ ] 手動実行のクロールで強制削除を指定すると、割合ルールを超える削除ができる。全ファイルを消したデータソースは、TTL経過後に、これで削除できる。TTLが経過していない文書は消えない。定期実行では指定できない。
- [ ] 抽出に失敗した文書と、スキップされた（取得・登録に失敗した）文書がAdmin Viewで確認できる。
- [ ] 上限を超えた原本は、取り込まれず、原本サイズ超過として文書単位のエラーに記録されてAdmin Viewで確認できる。存在確認日時は更新され、削除されない。
- [ ] クロールのたびに、内容が変わっていない文書も含めてすべての文書が処理される。
- [ ] 登録が長く終わらない文書はAdmin Viewで警告され、期限では自動削除されない。突合ジョブで、検索インデックスとStore層の食い違いが検出・表示できる。突合ジョブは、検索インデックスにだけある文書もStore層にだけある文書も自動削除しない。
- [ ] 再インデックスの手順をREADMEに記載している。
- [ ] 検索対象ディレクトリのマウントが読み取り専用である。
- [ ] MCPエンドポイントは、許可していないWebページ（Origin）からの呼び出しを拒否し、許可した呼び出し元と、ブラウザ以外のMCPクライアントからは利用できる（6.1。細部は → システムデザイン §6、§11）。
- [ ] 主要なMCPクライアントから、`search_documents`、`get_document`（分割取得を含む）、`list_sources`が実行できる。
- [ ] 評価セットと評価スクリプトがあり、Recall@10とMRRの結果を記録している。
- [ ] OpenSearchのスナップショットによるバックアップとリストアの手順を、READMEに記載している。

- 新しいクロールが始まっても、実行中の削除は止めない（旧版にあった新しいクロール起因の打ち切りは廃止。4.7）。
- 削除が行われなかった、または完了しなかった場合は、理由とともに削除結果の状態を失敗として残し（ジョブの成否は変えない）、再開せず、残りは次のクロールに委ねる（4.7）。
- 同じデータソースの削除が重なる場合は直列にする（前の削除が終わるまで、後の削除は始めない）。方式はSDに定めた（4.7。→ システムデザイン §3.9）。
- 旧い削除がハングした場合の保護（強制終了のタイムアウトなど）はMVPでは設けない。

次は、ユーザーが確認済み（2026-11-08）。根拠は、v0.11のレビュー反映の指示と、プラン（0032）の承認である。

- Indexer・Store層の障害でクロールが失敗扱いになったときは削除しない。個別文書の失敗（スキップ）とは区別する（2章、4.2、5.2、8.2）。**v0.15で保証範囲を明確化した**（2026-11-10のユーザー指示）：終了通知がIndexerに受理される前にクロールが失敗した場合に限る。受理後は、ジョブが失敗扱いになっても削除が継続する場合がある（5.2）。
- 上限を超えた原本は、MVPでは取り込まず、原本サイズ超過として文書単位のエラーに記録してAdmin Viewで確認できるようにし、存在確認日時は更新して削除しない。既存の索引データを残すかは未決（4.2、8.2、9.2 #8）。

**承認待ち（要確認）**

| 論点 | 内容 |
| --- | --- |
| MVPの認証 | 実装しない（Admin Viewも同様）。信頼できる利用者だけの検証環境向けとし、一般的な社内公開は認証の追加後とする（6.1、8.5） |
| 最初のデータソースと規模 | ローカルディレクトリ／ファイル共有。1万〜10万文書を想定するが、目標値ではない |
| 永続化（DB） | 専用のDBは置かず、OpenSearchをKVSとしてStore層で抽象化する（4.8） |
| MCPのOrigin検証・実行環境の境界 | Origin検証をMVPに含め、認証は実装しない。検索対象は読み取り専用マウントに限定する（6.1） |
| 取得・登録に失敗した文書（**v0.8でユーザー指示により変更。v0.4の「部分成功では削除しない」を撤回**） | 読めない文書は数回リトライし、失敗したらその文書だけスキップして失敗として記録する。クロール全体・他の文書の登録と削除には影響させない。列挙で見つかった文書は、スキップしても最後に見つかった日時を更新し、誤削除しない。列挙の失敗などクロール全体の異常では削除しない。0件列挙は異常とせず、割合ルールで判断する（v0.10で変更。2章、4.1、5.2）。恒久失敗の判定は不要になったため、将来拡張から外した |
| 登録に失敗した文書（**v0.3の仮決定「期限削除」を撤回**） | Store層だけにある文書も、検索インデックスにだけある文書も、自動削除はMVPでは行わず、検出・表示・手動確認・安全な再登録にとどめる（v0.15で、検索インデックスにだけある文書を追加。2026-11-10のユーザー指示。5.2） |
| その他 | 対象言語（日本語主、英語併用）、対応文書形式、要約の既定無効、原本を保存しないこと、MCPのStreamable HTTPとAPIとの同居、再インデックスの手動手順は、各章の記載のとおり（1.5、4.2、4.5、8.1） |

### 9.2 未決定事項・検証項目

プロダクトレベルの未決事項のみを挙げる。

1. OpenSearch以外のバックエンドに移る条件（件数・更新頻度・排他の要件など）
2. 将来の認証方式（トークンの発行・管理方法、データソース単位の権限モデル）
3. 非機能要件（文書数・検索レイテンシ・同時利用数・ホスト要件など）。設計段階では目標値を置かず、実装後に実測して決める（検討項目は → システムデザイン §10）
4. 全件更新の負荷の実測と、差分検知を導入する条件（2章）
5. 異なるConnectorで取得した同じ文書の重複の扱い（検索結果でまとめるか）
6. 検索品質の目標値（初回の評価の測定後に決める。8.3）
7. GA条件（認証、性能目標、検索品質目標など）。MVPの測定後に決める（8.5）
8. 上限を超えた原本のうち、すでに索引にある同じ文書のデータを残すか、利用者への表示方法。MVPの扱い（取り込まず原本サイズ超過として文書単位のエラーに記録、存在確認日時は更新、削除しない）は決定済み（4.2。→ システムデザイン §10.2、§12.5）
9. 削除の割合のしきい値、最小件数、TTLの既定値。設定できることは決めたが、数値は決めない（→ システムデザイン §3.5、§12.5）。決め方はMVPの運用結果を見て決める。しきい値を0%以上100%未満に限る入力検証は、SD v0.8で決定した（細部は案）：検証はAdmin APIだけで行い、CrawlerとIndexerは検証しない。Admin APIを経由しない経路の範囲外の値は、SDの受容事項（既知の制限）である（→ システムデザイン §3.5、§3.9）。SDでも未決で残る点：入力の単位、省略時（未指定）の扱い、最小件数とTTLの入力検証（→ システムデザイン §12.5）
10. 強制削除の指定方法の詳細（画面、確認の出し方）。システムデザインと画面設計で決める（4.6）
11. 削除結果の確認が上限を超えた、または取得できないときの運用。ジョブの成否は変えず、削除結果を「結果未確認」「結果不明」とするところまではPDで決めた（4.7）。区分と表示ルールはSD v0.8で決定した（細部は案）：Crawlerがジョブ記録に区分を持ち、Admin Viewが`loreley-deletions`の現在値と併記し、再確認は行わず、知らせ方はAdmin Viewの表示のみ（→ システムデザイン §3.3、§3.9）。SDでも未決で残る点：待ち時間の数値（ポーリングの間隔と上限時間、リトライ回数。→ システムデザイン §12.5）
12. 登録結果の保持場所とAPI。表示する最低限の項目は決めた（列挙件数、登録件数（新規・更新）、スキップ件数、原本サイズ超過件数、エラー件数。削除件数は削除結果側。4.6）。保持場所とAPIはSD v0.8で決定した（細部は案）：`loreley-jobs`に保持し、Crawlerが集計し、Admin APIが読み取りで返す。Status APIは削除結果のみ（→ システムデザイン §3.3、§14.2）。SDでも未決で残る点：原本サイズ超過件数とエラー件数の記録先と数え方（#8と連動）、登録件数の新規・更新の内訳の数え方（再登録や再送の扱い。内訳は目安に近い）、ジョブ記録の保持期間、Admin APIの応答の形（→ システムデザイン §12.5）

## 10. 用語集

実装レベルの用語（`document_id`、`content_hash`、リース、`extractor_version`、`crawl_started_at`など）は → システムデザイン §13 で定義する。

| 用語 | 意味 |
| --- | --- |
| データソース | 収集対象の情報源（ディレクトリ、Wiki、Gitリポジトリなど）。管理者が登録する単位 |
| Connector | データソースごとの取得処理の実装 |
| Crawler | Connectorを実行し、スケジュールとクロール状態を管理するコンポーネント |
| Indexer | 文書の登録・更新・削除を担当するサービス。取得した文書からテキストを抽出・正規化し、要約を生成して、検索インデックスとStore層に登録し、期限を過ぎた文書を削除するコンポーネント |
| Store層 | 設定・ジョブ・抽出済みテキスト・文書ごとの処理状態を保存する層。MVPではOpenSearchの別インデックスで実装し、Repositoryインターフェースで抽象化する |
| 検索インデックス | 検索用のOpenSearchインデックス。Store層とは別 |
| 列挙クロール | データソース内のすべての文書を列挙するクロール。列挙の完了を、削除の判断の入力としてIndexerに通知するのはこのクロールだけである（削除の判断と実行はIndexerが行う） |
| 全件更新 | 変更の有無を調べず、毎回すべての文書を取得・登録するMVPのクロール方式。対義は差分検知（将来拡張） |
| 最後に見つかった日時 | 列挙クロールで最後に見つかった日時（読めずにスキップした文書も、列挙で見つかれば更新する）。期限による削除の基準。フィールド名などの実装用語は → システムデザイン §13 |
| TTL | 最後に見つかった日時からの有効期間。データソースごとのクロール設定で指定する |
| 期限による削除 | 最後に見つかった日時にTTLを足した期限を過ぎた文書を、列挙が最後まで完了した後に、割合ルールの判断を経て削除する方式 |
| スキップ | 数回リトライしても読めない（取得・登録できない）文書を、その文書だけ処理から外して失敗として記録すること。Admin Viewで確認でき、クロール全体や他の文書には影響しない。抽出失敗や原本サイズ超過はスキップではない（抽出失敗は`extract_failed`として登録する）。Indexer・Store層の障害はスキップではなくクロールの失敗として扱い、終了通知が受理される前なら削除しない（5.2） |
| 削除の割合ルール | 削除対象が、削除前の登録文書数に対して設定したしきい値（データソースごと。0%以上100%未満）を超えるとき、そのクロールでは削除しないルール。承認は設けない。削除対象が最小件数以下なら、割合に関わらず削除する（→ システムデザイン §3.5） |
| 強制削除モード | 手動実行のクロールでだけ指定できる、割合ルールを無視して削除するモード。TTLが経過していない文書は消えない。定期実行では指定できない（→ システムデザイン §3.4） |
| クロール結果 | クロール1回分の結果の総称。登録結果と削除結果からなり、Admin Viewで確認できる |
| 登録結果 | クロール1回分の、文書の登録・更新の結果。最低限の表示項目は4.6。保持場所は`loreley-jobs`で、Crawlerが集計し、Admin APIが読み取りで返す（SD v0.8で決定。細部は案。→ システムデザイン §3.3）。未決の点は9.2 #12） |
| 削除結果 | クロール1回分の、削除の判断・実行の結果（削除件数、割合ルールで削除しなかった理由と件数）。Indexerが記録し、Admin Viewで確認できる（→ システムデザイン §3.9）。削除が行われなかった、または完了しなかった場合（クロールの失敗・取り消しで削除を行わなかった場合を含む）も、理由付きで、削除結果の状態を失敗として残る（再開せず、残りは次のクロールに委ねる）。ジョブの成否は変えず、削除されなかったことはジョブの失敗にしない（4.7） |
| 突合ジョブ | 検索インデックスとStore層の食い違いを検出・表示し、安全な再登録までを行うジョブ。MVPでは、食い違っている文書を自動削除しない |
| MCP | Model Context Protocol。AI Agentがツールを呼び出すためのプロトコル |
| Agent | MCPを通じて本プロダクトを利用するAI Agent |
| Search View / Admin View | Web UIの利用者向けの画面 / 管理者向けの画面 |
| GA | 一般利用者への提供開始。MVPの完成（8.2）とは別に条件を定める（8.5） |


### 旧用語との対応

PD v0.10以前と、システムデザインv0.5以前は、「同期」を使っている。システムデザインv0.6で置換済みである。旧版を読むときは、次のように読み替える。

| 旧用語（PD v0.10以前/SD v0.5以前） | 本書の用語（SD v0.8） |
| --- | --- |
| 同期結果（`syncresult-*`、Status APIの項目） | 削除結果（`deletion_result-*`）。SDの現状の項目は削除結果のみ |
| 同期管理、Sync Manager（SD §3.9） | 削除管理（Deletion Manager。Indexerの削除処理） |
| `loreley-sync`、`/syncs/*` | `loreley-deletions`、`/crawls/*` |
| 同期状態（Crawler） | クロール状態 |
| 最終同期時刻 | 最終クロール完了日時（PD v0.10の語）。SD側は`list_sources`の最終クロール時刻（SD v0.8 §5.3）が近い。未確認 |

---

**現時点の結論**：ドキュメント単位の全文・要約検索を中心とする、セルフホスト型の検索基盤をMVPとして構築し、MCPから使えるようにする。MVPは認証なしで、信頼できる利用者だけの検証環境で使う前提とし、一般的な社内公開は認証機能の追加後とする。チャンク分割、Embeddingとベクトル検索、Chat View、認証・認可は、評価セットによる実測と利用状況に基づいて段階的に追加する。実装レベルの設計は、システムデザインで扱う。
