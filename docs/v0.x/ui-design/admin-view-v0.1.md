## 0. この文書について

- 対象: Admin View の画面構成と画面ごとの仕様。見た目の部品・トークンは DS に集約し、本書から参照する。
- 構成: DS と本書の 2 本が基本(承認済みの前提 9)。第 2 段階で画面仕様が増えたため、**画面グループ別に `admin/` 配下へ分割し、本書を索引にした**(分割の要否は設計者判断。理由: 全画面を 1 本にすると 1,000 行を超え、レビュー・参照がしにくくなる)。分割先: `admin/sources-v0.1.md`(G1: S2・S3・S4)、`admin/jobs-v0.1.md`(G2: J1・J2)、`admin/documents-v0.1.md`(G3: X1)、`admin/opensearch-v0.1.md`(G4: O1)、`admin/dashboard-v0.1.md`(G5: D1)。S1 は第 1 段階でゲート B 承認済みの代表画面のため、本書 7 章に残す。
- 範囲: Admin View の MVP 全機能(AF-1〜20)。AF-21〜32(将来拡張)は画面を作らず、拡張の仕組みと追加手順だけを 8 章に書く。Search View・Chat View・実装は対象外。
- 決定の状態: 「承認済み」はユーザーが承認したと呼び出し元から渡された内容、「案」は未承認。DS 0.1 と同じ区別に従う。**第 1 段階の内容(ナビ構造、危険度の段階と割当、S1 の設計、AF-U-7 の強制削除・`rewrite_mode` の指定、AF-U-3(a)の通知方式、データソース削除の識別子入力、「削除中」の行の見せ方、技術スタック)は 2026-11-21 のゲート B で承認済み**(DS 0.1)。各章・見出しには承認区分(【承認済み(ゲート B)】【案】など)を付けてあり、**見出しの区分と DS 0.1 の区分が正**。**第 2 段階の内容(画面一覧の第 2 段階の画面(route・遷移)、AF-21〜32 の型対応表と拡張ガイド、ユーザー未確認の導出の表示、AF-U-7 の残り、AF-U-3(c)、AF-U-5、AF-7 孤児ロックの入口、タイムゾーン表示など)は、2026-11-22 のゲート C で承認済み**(10 章の一覧の #1〜#36 と R-1。作業記録 0020)。承認されていないもの: Admin API への申し送り(10.4)、SD/PD の追従改訂(10.3。別タスク)、実機 Vuetify 4.3.4 での確認事項、静的モックで未確認の挙動、`@mdi/js` の社内ポリシー上の扱い(案・要確認・未確認のまま)。

## 6. 危険度の段階と各操作への割当【承認済み(ゲート B)】(前提 8 の具体設計。AF-U-7 の強制削除・`rewrite_mode`。第 2 段階の操作(取消・再実行・ロック解放・削除の再実行)への割当は承認済み(ゲート C 2026-11-22))

操作の影響の重さで確認の強さを変える。全操作に入力確認を求めると運用が重くなり、確認が形骸化するため、段階を分ける。部品の構成は DS 4.8。

| 水準 | 確認の構成 | 割り当てる操作 | 理由 |
| --- | --- | --- | --- |
| 通常 | 確認なし | 設定の保存(登録・更新。AF-1)、一覧の更新、並べ替え、画面移動、ダッシュボードの更新(AF-18) | 元に戻せる・影響が小さい。保存の注意(実行中ジョブには反映されない)はフォームのヘルプで示す |
| 要確認・標準 | ダイアログ+[キャンセル][実行](primary) | クロール起動(強制削除・再書き込みモードの指定なし。AF-3)、ジョブの取消(AF-4)、失敗ジョブの再実行(元の指定が「なし」のとき。AF-5)、削除が失敗した後の「削除を再実行」(AF-16。同じ操作の再開) | 意図しない起動・停止を防ぐ。影響は限定的 |
| 要確認・警告つき | 上に加えて影響の警告枠+確認チェック(チェックするまで実行不可)。帯と実行ボタンの色で重さを示す(強制削除=赤、再書き込み・ロック解放=琥珀) | 強制削除モード指定での起動・再実行(AF-3、AF-5)、再書き込みモード指定での起動・再実行(AF-3、AF-5)、ロック解放(AF-7) | 削除の割合ルールを無視する、全文書を書き直す(準備が要る)、ジョブの状態が確定する、など結果が大きい・準備を伴う |
| 要入力確認 | 上に加えて識別子を入力し、完全一致で実行可 | データソースの削除(AF-16) | 取り返しがつかない(索引済み文書・記録・設定がすべて消える。API に確認の仕組みがない。機能設計書 3.6) |

- 「強制削除」と「再書き込み」を要入力確認にしない理由: 定期運用の中で手動実行する操作で、影響は「その 1 回のクロール」に限られる。警告枠と確認チェックで、内容の確認を強制すれば足りる(推奨)。要入力確認にする代替案もある(ユーザー判断)。
- 複数の指定を含むダイアログ(両方の指定をオンにした起動、両方を引き継ぐ再実行)の帯と実行ボタンの色は、最も重い指定に合わせる(強制削除を含めば赤、再書き込みだけなら琥珀。DS 4.8。承認済み(ゲート B))。
- ボタンの色は、確認ダイアログの**中**でだけ danger / warning を使う。一覧・詳細に危険色の常設ボタンを置かない。

### 7.6 クロール起動ダイアログ(DLG-1。AF-3。承認済み(ゲート B)。AF-U-7)

行の「クロール起動」で開く(モックの `#dlg-crawl`・`#dlg-crawl-force`・`#dlg-crawl-rewrite`)。

- 見出し: 「クロールを起動」。本文: 「データソース `識別子` のクロールを起動します。起動後はジョブとして実行され、状態は「ジョブ」で確認できます。」
- **起動オプション(手動起動のみ)**: 2 つのチェックボックス(既定はどちらもオフ)。各項目は枠付きの行(タイトル+1 行の説明)。
  - 強制削除モード(`force_delete`): 説明「削除の割合ルール・最小件数ルールを無視して削除します。」
  - 再書き込みモード(`rewrite_mode`): 説明「差分チェックをせず、全文書を再書き込みします。」
- オプションをオフにしている間: 水準は「要確認・標準」。実行ボタンは primary「クロールを起動」、帯なし。
- **強制削除モードをオン**にしたとき(水準は「要確認・警告つき」):
  - その項目の枠を `error` にし、項目の中に警告枠を開く: 「次のようになります」+「削除対象が割合のしきい値を超えていても削除されます。」「TTL が経過した文書だけが対象です。経過していない文書は消えません。」「削除された文書は検索から消え、元に戻せません。」(PD §5.2・用語集の強制削除モードの説明に基づく)
  - 確認チェック「割合ルールを無視して削除されることを理解しました」。チェックするまで実行ボタンは無効(理由を実行ボタンの下に「確認にチェックすると起動できます。」)
  - 実行ボタン: danger「強制削除モードで起動」。ダイアログ上端に `error` の帯。
- **再書き込みモードをオン**にしたとき(「要確認・警告つき」。AF-U-7 の `rewrite_mode` の準備案内):
  - その項目の枠を `warning` にし、警告枠を開く: 「実行前に確認してください」+「全文書を書き直すため、時間がかかります。削除の判断には影響しません。」「要約を有効にしている場合は、全文書が「要約未生成」に戻ります。実行前に Indexer の要約生成を止め、終えておく必要があります(手順は Indexer の運用手順)。」(機能設計書 AF-3・AF-14、Indexer 設計 K26)
  - 確認チェック「上記を確認しました」。実行ボタン: warning「再書き込みモードで起動」。帯は `warning`。
  - Admin View は要約が有効かどうかを知らない前提で、文言は「有効にしている場合は」と条件付きにする(要約の有効/無効を取得できる設計なら、無効のときは準備案内を出さない案もある。Admin API 設計次第)。
- **両方をオン**にしたとき: 両方の警告枠を出し、確認チェックを両方に置く。実行ボタンは danger「強制削除・再書き込みモードで起動」、帯は `error`。
- 実行後: 成功(受付)はダイアログを閉じ、スナックバー「クロールを受け付けました(ジョブ ID: …)」+「ジョブを表示」。拒否・失敗はダイアログを開いたまま 7.7 の表示。
- 「要確認・警告つき」のダイアログは `persistent`(Esc・背面クリックで閉じない。キャンセルで閉じる)。標準は Esc で閉じてよい。初期フォーカスは見出し(標準)、最初のオプション(警告つきを開く場合)。

### 7.7 起動拒否・指定無視の通知(AF-6、AF-19。AF-U-3(a)。承認済み(ゲート B。リース切れ・メンテナンス中・削除中の出し分けを含む))

**通知の方式(承認済み(ゲート B))**: 起動が拒否されたときは、ダイアログを**開いたまま**、本文の先頭にアラート(`role="alert"`)を出す。スナックバーは使わない(消えると見逃すため)。アラートは閉じるまで残り、理由・既存ジョブ・次の行動を示す。指定した `force_delete`・`rewrite_mode` が反映されなかったことは、アラートの中で太字で明示する。実行ボタンは「閉じる」に置き換える(再試行は、状況が変わってから開き直す)。

| 拒否の理由 | アラートの種別 | 内容 | 次の行動 |
| --- | --- | --- | --- |
| ロック保持中(`lock_held`) | error | 「起動できませんでした: 別のジョブが実行中です」。既存ジョブ(ID・種別・状態)・リース期限。強制削除モードまたは再書き込みモードを指定していた場合は、「指定した(強制削除モード/再書き込みモード)は反映されていません。起動していないため、実行中のジョブにも反映されません。」(機能設計書 AF-6・AF-U-3(a)) | 「ジョブを表示」(J2) |
| ロック保持中で、既存ジョブがリース切れ・失効したロック | warning | 「起動できませんでした: 止まったジョブのロックが残っています」。ジョブ ID・リース期限。「成功扱いにはなっていません。ロックを解放してから、もう一度起動してください。」(機能設計書 AF-6。SD §14.4 の案。表示は承認済み(ゲート B。AF-U-3(a))) | 「ジョブ詳細でロックを解放」(J2 → DLG-5) |
| メンテナンス中(`maintenance_enabled`) | error | 「起動できませんでした: メンテナンス中です」。「メンテナンスが終わるまでクロールを起動できません。メンテナンスの解除は運用者が行います。解除後にもう一度起動してください。」(AF-19。フラグ自体の操作・表示は画面に置かない) | なし(閉じる) |

### 7.8 データソース削除確認(DLG-2。AF-16。承認済み(ゲート B)。前提 8)

行メニュー「削除…」で開く(モックの `#dlg-delete`(入力できる見本)・`#dlg-delete-match`)。水準は**要入力確認**。

- 見出し: 「データソース「識別子」を削除」。上端に `error` の帯。
- 警告枠(`error-container`): 「取り消せません」+「索引済みの文書(N 件)が検索から消えます。」「スキップ・原本サイズ超過の記録、削除の記録、設定が消えます。」「削除は進行中に取り消せません。途中で失敗した場合は、同じ操作をやり直します。」(機能設計書 3.6・crawler-api §4.6 に基づく。N は一覧の登録文書数)
- 入力: ラベル「確認のため、識別子 `識別子` を入力してください」、入力欄(等幅)。貼り付け可、`autocomplete="off"`・`spellcheck="false"`、前後の空白は無視して完全一致(大文字小文字を区別)。
- 判定の表示: 入力が空の間は何も出さない。入力があって一致しない間は「識別子が一致しません」、一致したら成功色で「識別子が一致しました」(アイコン+文言。`aria-live="polite"`)。
- 実行ボタン: danger「データソースを削除」。**一致するまで無効**。理由を実行ボタンの下に「識別子を入力すると削除できます。」と出し、`aria-describedby` で結ぶ(一致後は消す)。入力前でも理由が分かる。Enter の送信も一致するまで行わない。
- 初期フォーカスは入力欄(削除ボタンではない)。`persistent`(Esc・背面クリックで閉じない)。
- 実行後: ダイアログを閉じ、スナックバー「データソース「識別子」の削除を受け付けました。完了まで「削除中」と表示されます。」。その行は「削除中」になり、操作は 7.3 のとおり。削除が完了(ジョブ成功かつ設定が消えた)すると一覧から消える(完了の判断は機能設計書 3.6)。削除ジョブの失敗は、行の補足文で示し、「削除を再実行」(要確認・標準)で復旧する。
- 取消はできない(機能設計書 3.6)。ダイアログの文言にその旨を含める。

### 8.1 画面追加の手順

1. **要件を確認する**: 機能設計書に AF を追加し、MVP か将来拡張かを区分する(要件にない画面は作らない)。
2. **ページテンプレートを選ぶ**(DS 6 章): 一覧(`list`)= 同種のものが並ぶ / 詳細(`detail`)= 1 件の属性と関連 / フォーム(`form`)= 値を入力して保存 / ダッシュボード(`dashboard`)= 状態の概況。どれにも当たらない場合は、新しい型を足す前に、既存の型の組み合わせ(タブ・カード)で表せないか検討する。
3. **ルートを足す**: route 定義に `meta`(`title`、`template`、`parent`、ナビに出すなら `nav`(ラベル・アイコン・グループ・順序))を書く。ナビへの追加はこの `meta` だけで完結する(DS 5.3)。**新しいナビグループのときだけ**、DS 5.3 のナビグループ定義表(`navGroups`)に 1 行足す(既存のグループ ID を使うなら定義表は触らない)。
4. **画面の中身を作る**: テンプレートの骨格(ページ見出し領域・カード)に、共通部品(データテーブル・キー・バリュー・フォーム・ステータスタグ・状態ブロック)を差し込む。部品にない見た目が必要なときは、DS に部品を追加してから使う。
5. **全状態を満たす**: 読み込み中・空・エラー・古いデータ・長文/大量件数(DS 4.5)。
6. **操作の水準を決める**: 新しい危険な操作は、6 章の水準のどれかに割り当てる(新しい確認の形を作らない)。
7. **状態の値を足す**: 新しい状態名は `StatusTag` のマップに行を足す(色・アイコン・文言。DS 4.1)。
8. **仕様とモックを足す**: 本書に画面 ID・トレーサビリティ・ワイヤーフレームを追記し、モックを追加する(版を上げる場合は新しいファイル)。
9. **アクセシビリティと `data-testid` の確認**: DS 8・9 のチェックリストに従う。

**例: 画面を 1 つ足すとき、触る場所**(実装者向けの目安)

| 触る場所 | 内容 |
| --- | --- |
| route 定義 1 か所 | `name`・`path`・`meta`(4.2 の表と同じ形)。ナビに出すなら `nav` を書く。`/x/new` は `/x/:id` より先に定義する |
| 画面コンポーネント 1 つ | テンプレートの骨格+共通部品。状態(読み込み中・空・エラー・古いデータ)を満たす |
| `StatusTag` のマップ | 新しい状態値があるときだけ行を足す |
| 仕様書・モック | 本書 4 章(画面一覧・遷移)・5 章(トレーサビリティ)と、`admin/` 配下に画面グループの仕様書、`mockups/` にモックを足す |
| ナビ・パンくず・`document.title` | route `meta` から自動で決まるため、触らない |

### 10.4 Admin API 設計への申し送り

画面は Admin API の形に依存しないよう、「判定結果の表示」に限定している。次を Admin API 設計で決める(機能設計書 AF-U-1・U-6・U-9・U-10・U-13 に対応)。

| 領域 | 申し送り事項 |
| --- | --- |

| データソース(S1〜S4) | 登録文書数の数え方(抽出失敗を含むか)、リース切れ・孤児ロックなど「ロック状態 6 種」の判定結果、「最新のジョブか」、TTL(秒)・しきい値(0〜1)と画面の入力単位(日・%)の変換、`ttl`・`min_delete_count` の検証(Crawler は範囲を検証しない)、cron のタイムゾーン取得(AF-U-13)、`connector_config` の項目と検証(Connector 設計) |
