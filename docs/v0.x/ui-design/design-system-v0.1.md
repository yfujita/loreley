## 1. 美的方向性【承認済み(ゲート B)】

### 1.1 利用者と使われ方

利用者は社内の検索・管理担当者。画面は毎日開く「運用の確認盤」で、見るのは識別子・状態・日時・件数と、起動・取消・解放・削除といった少数の操作。派手さより、状態が一目で分かること・誤操作しにくいことが価値になる。MVP は認証なし・単一ホスト・主に PC のブラウザ。

### 1.2 比較した方向性(3 案)

| 案 | 概要 | 長所 | 短所 |
| --- | --- | --- | --- |
| A. 静かな帳簿(推奨) | 冷たい灰青の紙面(`#F4F6F8`)に、墨色の文字、川の濁りのような落ち着いた青(`#1D5B87`)を 1 色だけ主役にする。罫線は細く、角丸は小さく、影はほぼ使わない。識別子だけ等幅。状態は色・形・文言の 3 つで示す | 情報密度が高くても疲れない。状態の違いが主役として際立つ。システムフォントで完結し、実装コストが低い | 地味。見た目の「華」はない(運用ツールとしては利点) |
| B. Material 標準寄り | Vuetify 既定(または `md3` blueprint)のまま、色だけ社内色に変える | 実装が最も速い。Vuetify の想定どおりに動く | 既定の Material 色(warning `#FB8C00` など)は白地で文字に使えない(コントラスト不足)。丸く大きな部品で表の密度が落ち、既定感が強い。`md3` blueprint は開発中扱いで依存したくない |
| C. コンソール調 | 暗色のサイドバー+高彩度のアクセント。ターミナル的な等幅フォントを多用 | 「運用ツール」らしい雰囲気 | ライトテーマのみの前提(承認済み)と相性が悪い。等幅の多用は日本語で崩れやすく可読性が落ちる。管理画面の既定的な見た目 |

### 1.3 推奨と理由

**案 A「静かな帳簿」を推奨する。** 理由は、(1) 利用者の主作業(状態の確認と少数の危険操作)に合う、(2) コントラスト比を守りながら Vuetify の `defaults` と SASS 変数だけで再現できる、(3) 色に頼らない状態表示(承認済みの前提 5)と整合する、の 3 点。

デザイン上の「1 つの見せ場」は **状態の言語**(ステータスタグの色・形・文言の組と、危険度に応じたダイアログの帯・色)に絞る。ほかの要素(サイドバー・表・カード)は静かに保つ。

### 1.4 既存デザインとの関係

`apps/` に Web UI の実装はなく、既存の画面・スタイル定義はない(2026-11-21 時点で `apps/` は `crawler/`・`indexer/` のみ)。このため踏襲する既存デザインはなく、本書が最初のデザイン定義になる。

### 2.2 タイポグラフィ

- 本文フォント(`$body-font-family`): `-apple-system, BlinkMacSystemFont, "Segoe UI", "Hiragino Sans", "Hiragino Kaku Gothic ProN", "Yu Gothic UI", "Meiryo UI", "Noto Sans JP", sans-serif`。macOS は欧文が SF・和文が Hiragino Sans、Windows は欧文が Segoe UI・和文が Yu Gothic UI か Meiryo UI になる。
- 等幅(識別子専用): `ui-monospace, SFMono-Regular, Menlo, Consolas, "Liberation Mono", monospace`。使うのは識別子(`source_id`、ジョブ ID、`external_id`)、cron 式、パスだけ。ラベルや装飾には使わない。
- 字間は広げない(日本語)。斜体は使わない。ルート `html` は 16px、本文は 14px(`.875rem`)。

### 2.3 余白・寸法

- 基準は 4px(Vuetify の `$spacer` 既定 4px、`pa-1` = 4px と一致)。使う値は 4 / 8 / 12 / 16 / 24 / 32 / 48px。
- 画面内の余白: ページの余白は、幅 1145px 以上が上 24px・左右 32px、840〜1144px が上 20px・左右 24px、840px 未満が 16px(サイドバーの表示は 840px 以上。余白の切替は lg=1145px のまま)。カード間・ページ見出しとカードの間は 16px。カードの内側は 16px。
- コンテンツ幅: 幅の上限は 1400px(左寄せ)。フォームの本体は最大 640px。説明文の行長は 70 文字程度まで。
- 高さ: ボタン 36px(幅 600px 未満は 44px)、**小型ボタン 32px**(表の行の操作・ツールバー・アラート内のボタン。幅 600px 未満は 44px。選択理由: 行が 2 行表示で 56〜60px になるため、36px だと行の密度が落ちる。24px 以上は満たす)、入力欄 40px(同 44px)、タグ 24px、表見出し 40px、表の行 48px 以上(2 行になる行は 60px 前後)、ナビ項目 40px。Vuetify の `density` との対応は実装後に実測して調整する(未確認)。
- タップ領域は最小 24×24px(WCAG 2.2 AA)を満たし、通常は 32px 以上、幅 600px 未満はボタン・入力欄・メニュー項目・スナックバーの閉じるボタンなどすべて 44px。リンクの操作領域は次のとおり(WCAG 2.2 の 2.5.8)。**表の識別子リンク**(ジョブ ID・データソースなど)は、行全体の余白で確保する(行の高さ 48px 以上で、隣のリンクとの間隔が十分あるため、2.5.8 の「間隔」の例外を使う)。**表以外の本文中のリンク**(タイル末尾のリンク、「データソースの詳細」など)は操作領域の高さを 24px 以上にする(行間・上下の余白 `padding: 3px 0` 以上で確保する。文中のインラインリンクは 2.5.8 の例外)。

### 2.4 角丸(用途で使い分ける)

Vuetify では角丸は CSS 変数ではなく SASS 定数(`$border-radius-root` 起点)。モックは独自の `--radius-*` で再現している。

| 用途 | 名前 | 値 | Vuetify の `rounded` | SASS の対応 |
| --- | --- | --- | --- | --- |
| チェックボックス、「必須」表示 | `--radius-sm` | 2px | `sm` | `$border-radius-root` の 0.5 倍 |
| ボタン、入力欄、タグ、アラート、メニュー | `--radius-md` | 4px | `md` | `$border-radius-root`(4px のまま) |
| カード、表の外枠、ダイアログ | `--radius-lg` | 8px | `lg` | `$border-radius-root` の 2 倍 |

`$border-radius-root` は既定の 4px のまま変更しない。`xl`(6 倍)と `pill` は使わない。

### 2.5 影・立体

- 通常の面(カード・表)に影は使わず、1px の境界線で区切る(`elevation: 0`+`border: thin`)。
- 浮かせるのはメニュー・スナックバー・ダイアログだけ。メニューとスナックバー: `0 4px 12px rgba(26,37,48,.16)`、ダイアログ: `0 8px 24px rgba(26,37,48,.20)`。Vuetify の `elevation`(0〜5)では 2〜3 相当を割り当て、見た目が離れる場合は SASS の影変数で調整する(実装時に確認)。
- ダイアログの背面(スクリム)は `rgba(26,37,48,.52)`。

### 2.6 フォーカス・動き

- フォーカスリング: `:focus-visible { outline: 2px solid #0B57D0; outline-offset: 2px }`(入力欄は `outline-offset: 1px` で枠の色を primary にする)。Vuetify 既定のフォーカス表現(不透明度 0.12 の重ね)は見えにくいため、アプリ共通 CSS で必ず上書きする。ボタン(primary 塗り)の上ではリングとの比が低い(1.13)ので、オフセットを空けて地の上に描く。
- 動きは最小限。使うのは、スケルトンの光沢(1.4 秒)と再取得中の細い進行バー(1.2 秒)のみ。`prefers-reduced-motion: reduce` では停止する(進行バーは静止した帯で示す)。画面遷移・ホバー・カードの登場にアニメーションは付けない。ダイアログ・ドロワーの開閉は Vuetify 既定のトランジションを使ってよい。

### 4.2 ボタン

| 種類 | 見た目 | 用途 |
| --- | --- | --- |

- ボタンの文言は動詞(「クロールを起動」「データソースを削除」)。同じ操作は通知・ダイアログ・見出しで同じ名前にする(例: 「クロールを起動」→ 通知「クロールを受け付けました」)。
- アイコン付きにする場合はアイコンを左に置く。アイコンだけのボタンには `aria-label` を付ける(行ごとの操作は対象の識別子を含める)。

### 4.3 データテーブル(一覧テンプレートの中核)

- 外枠はカード(境界線・角丸 8px)。上にツールバー(件数・最終更新・更新ボタン)、下にページング。
- 見出し行: `surface-variant` 面・12px / 600・`on-surface-variant`。高さ 40px。ソートできる列だけ見出しがボタンになり、`aria-sort` を付ける。
- 行: 高さ 48px 以上、区切りは境界線のみ(縞模様にしない)、ホバーは `primary` の 5% の面。
- 列の整え方: 文字は左揃え、数値は右揃え(等幅数字)、操作列は右端・右揃え。識別子は等幅でリンクにし、詳細画面へ移動する。日時と補足は 2 行(1 行目: タグまたは値、2 行目: 12px の補助文字)にしてよい。
- 行の操作は「主操作 1 つ(tonal ボタン)+その他の操作(`⋮` のメニュー。危険な操作は下段・赤字・区切り線の下)」。行の主操作ボタンの名前には対象の識別子を含める(視覚的に隠す文字で「(識別子)」を添える)。
- キーボード: Vuetify の `VDataTable` には行間の矢印キー移動の公式な仕様がないため、矢印キー移動には**頼らない**。リンクとボタンは Tab で到達できるようにし、ソートは見出しのボタンを Enter(Space は実装時に確認)で操作する。
- ページング: 1 ページの件数(既定 25。25 / 50 / 100)、「1–6 / 6 件」、前へ・次へ。サーバー側ページングを使う一覧(ジョブ・文書。件数が多い)では `VDataTableServer` を使い、page・sortBy・itemsPerPage を TanStack Query の queryKey に含める。取得中は前回のデータを保持する(TanStack Query v5 では `placeholderData: keepPreviousData`。v4 以前の同名オプションとは異なる。要確認)。`@update:options` が初期表示で発火して二重に取得しないよう実装時に確認する。件数が少ない一覧(データソース。数十件まで)は、Admin API が全件を返す設計なら `VDataTable`(クライアント側)でよい(Admin API は未設計。`admin-view-v0.1.md` S1)。
- 幅 840px 未満は行をカード状に積む(Vuetify の `mobile` 表示。見出しは隠れるため、並べ替えは別途セレクトで示す)。ラベルと値を並べ、操作は行の末尾に左寄せで置く。
- **840〜1144px の列の省略規則(承認済み(ゲート C。#14)。ユーザー指示によるサイドバー閾値の変更に伴う)**: コンテンツ幅が狭いため、画面仕様ごとに列の優先順位を定め、低い順に隠す。隠した情報は詳細画面で見られるようにする。判断基準は「状態の判断に要る列を残し、設定値・補足は詳細へ」。
  - 共通の優先順位(高→低): 識別子(ID)> 状態 > 日時(開始)> 件数 > 操作 > 種別・起動・周期・終了日時。
  - 表のカード幅が 720px 未満(サイドバー常時表示のとき viewport 約 1010px 未満)では、行の主操作(クロール起動など)のボタンを**アイコンのみ**にする(アクセシブルネームに「操作名(識別子)」を残し、ツールチップで操作名を出す)。
  - 補足のある操作(「削除を再実行」)は、文言を折り返す(最大幅 約 100px)。アイコンのみにしない(誤解を避ける)。
  - 画面ごとの適用は各画面仕様(S1: `admin-view-v0.1.md` 7.9、J1: `admin/jobs-v0.1.md`、X1: `admin/documents-v0.1.md` 10 章)。O1 にはデータテーブルがない(インデックス一覧は廃止し、シャード配置のマトリクスに統合。4.15。列の省略ではなく、列のページングで幅に収める)。
  - **省略の閾値は viewport ではなく、表を載せるカードの幅(コンテナクエリ)で決める(承認済み(ゲート C。#14)。レビュー 0014 への対応)**: 実アプリのカード幅は viewport からサイドバー 232px と左右の余白 64px(1145px 以上。840〜1144px は 48px)を引いた値で、同じ viewport でも画面の最大幅やサイドバーの有無で変わる。viewport で区切ると、全列が収まる幅の直前(1145〜約 1216px)で列が見切れる(J1 で確認)。画面ごとに「全列が収まるカード幅」(J1 は実測で約 920px。最小幅 916px)と「行の主操作をアイコンのみにするカード幅」(720px)を定め、表の親要素に `container-type: inline-size` を付けて `@container` で切り替える(または親要素の幅を測る `ResizeObserver` を使う小さな composable など。VueUse の `useElementSize` を使うなら 10 章の依存に足す)。ブラウザ要件(Chromium 119+ / Firefox 128+ / Safari 16.4+)はコンテナクエリに対応している。840px 未満の「行を積む」切替だけは、シェルの切替と同じ viewport 基準(`mobile`)のままにする。**S1・X1 の列の省略は、現状の viewport 基準(840〜1144px)のままでよい**(web-ui-reviewer の確認で、S1・X1 は 840〜1280px で表内スクロールがなく、見切れないため。実装時に表の幅を測って問題があれば J1 と同じ方式に改める)。
  - **例外(X1。承認済み(ゲート C。#14))**: 文書ごとの詳細画面が MVP にないため、「補足行」に移せない項目(スキップの「初回」の日時)は 840〜1144px で省かれ、その幅では見られない。許容しない場合は行の展開(開閉)に変える。

### 4.4 キー・バリュー表示(詳細テンプレート)

- Vuetify にキー・バリュー専用の部品はない。`<dl>` を使う自作部品 `KeyValueList` にする。
- 2 列(項目名 200px・値は残り)、行ごとに薄い区切り線、行の余白は上下 10px・左右 16px。項目名は `on-surface-variant`、値は本文。値が長いときは折り返す。
- 値がない項目は「—」を出し、読み上げ用に「未設定」「なし」を添える(視覚的に隠す文字)。補足(タイムゾーンなど)は値の下に 12px で添える。
- 幅 600px 未満は項目名の下に値を積む(1 列)。
- カード(見出し付き)の中に置く。1 つのカードに入れる項目は 10 件程度までとし、超えるときはカードを分ける。

### 4.6 フォーム項目と検証エラー

- ラベルは項目の**上**に置く(14px / 600)。必須は「必須」の小さな表示(枠付き・12px)をラベルの横に添え、アスタリスクだけにしない。任意の項目に印は付けない。
- ヘルプ文は入力欄の下(12px・`on-surface-variant`)。単位は入力欄の右に連結する付属ボックス(例: 「%」)に出す。
- 読み取り専用(登録後に変えられない項目など)は `surface-variant` 面+破線の枠で、編集できないことをヘルプで説明する。
- 入力欄の高さ 40px、枠 `line-strong`(4.27:1)、フォーカス時は枠 `primary`+フォーカスリング。**無効の入力欄(案。ユーザー指示 4 回目で、O1 の読み込み中に無効のフォームを出すために追加)**: 面を `surface-variant`、文字を `on-surface` の 46%、枠を `border` の 28% にし、`disabled` にする(カーソルは `not-allowed`)。値(URL から復元した条件など)は表示する。無効の状態は読み込み中などの一時的なもので、理由はページの状態表示で示す(4.5)。
- **検証エラー**: 項目の枠を `error` にし、入力欄の下に「アイコン(`mdiAlertCircleOutline`)+文言」(12px / 600・`error`)を出す。`aria-invalid="true"` と `aria-describedby`(エラー文)を付ける。文言は「0 以上 100 未満で入力してください」のように、直し方を示す。送信時はフォーム上部に件数付きのエラー要約(`role="alert"`。各項目へのリンク付き)を出し、フォーカスを要約に移す。サーバーが項目単位で返したエラーも同じ形で出す。
- 1 行のフォームは 1 列、最大幅 640px。ラベルと入力欄は縦に積む。

### 4.7 通知(アラートとスナックバー)

通知を出し過ぎない。

| 種類 | 用途 | 見せ方 | 備考 |
| --- | --- | --- | --- |
| スナックバー | 操作の**受付・保存の成功**だけ(「クロールを受け付けました(ジョブ ID: …)」+「ジョブを表示」) | 画面下部中央・`ink` 面・6 秒・同時に 1 つ(新しい通知で置き換える)・閉じるボタン付き | `role="status"`(`aria-live="polite"`)。操作の失敗には使わない |
| ページ内アラート | 画面の状態(古いデータ・注意) | カード上部に左帯付きの `*-container` 面。再読み込みなどのボタンを置いてよい | 取得失敗は `role="alert"` |

### 4.8 確認ダイアログ(危険度別)

危険度の段階の定義と各操作への割当は `admin-view-v0.1.md` 6 章。ここでは部品の構成を定める(`VDialog`)。

| 水準 | 構成 | 帯 | 実行ボタン | 初期フォーカス |
| --- | --- | --- | --- | --- |
| 通常 | ダイアログを出さない | — | — | — |
| 要確認・標準 | 見出し(動詞)+対象(識別子)・結果の説明 1〜2 文+[キャンセル][実行] | なし | primary | 見出し(`tabindex=-1`)。Tab で先頭の操作へ |
| 要確認・警告つき | 上に加え、**影響の警告枠**(`error-container` または `warning-container`)と、**確認チェック**(チェックするまで実行ボタンは無効) | 上端 4px の帯(`error` または `warning`) | danger または warning | 最初の入力要素(オプション、なければ確認チェック) |
| 要入力確認 | 影響の警告枠(`error-container`)+「確認のため識別子 `…` を入力してください」+入力欄。**識別子が完全一致するまで実行ボタンは無効** | 上端 4px の帯(`error`) | danger | 入力欄(実行ボタンにはフォーカスしない) |

- 共通: `role="dialog"`、`aria-labelledby`(見出し)、`aria-modal`(`VDialog` が付ける)。フォーカスはダイアログ内に閉じ込め、閉じたら開いた操作ボタンに戻す(実装後に E2E で検証する)。Esc で閉じる(「要確認・警告つき」「要入力確認」は誤って閉じないよう `persistent` にし、Esc・背面クリックでは閉じず、キャンセルで閉じる)。
- **色の規則(承認済み(ゲート B))**: 確認ダイアログが複数の指定を含む場合(クロール起動で強制削除と再書き込みの両方、失敗ジョブの再実行で両方を引き継ぐ場合など)、上端の帯と実行ボタンの色は、含まれる指定のうち最も重いものに合わせる(強制削除=赤 `error` / danger > 再書き込み・ロック解放=琥珀 `warning`)。警告枠と確認チェックは指定ごとに置く。
- 無効の実行ボタンには、必ず理由の文言を実行ボタンの下に出し(「確認にチェックすると起動できます」「識別子を入力すると削除できます」)、`aria-describedby` で結ぶ。
- 操作ボタンの並びは右寄せで [キャンセル](text)→[実行]。
- 要入力確認の入力欄: 貼り付けを許可し(`autocomplete="off"`、`spellcheck="false"`)、前後の空白は無視して完全一致(大文字小文字を区別)で判定する。一致したら「識別子が一致しました」(アイコン+文言。`aria-live="polite"`)を出し、実行ボタンを有効にする。一致しない間は入力があれば「識別子が一致しません」と示す。
- 見出しと説明は、結果を具体的に書く(「データソース「x」を削除」「索引済みの文書(N 件)が検索から消えます」)。ボタンの文言は見出しと同じ動詞。
- 実行後の挙動: ダイアログを閉じ、成功(受付)はスナックバー。失敗・拒否はダイアログを開いたまま内側のアラートで示す(4.7)。

### 4.9 日時・数値・識別子の表記

- 日時: `YYYY-MM-DD HH:mm`(24 時間。秒が必要な箇所だけ `:ss`)。ブラウザのローカル時刻で表示する(**承認済み(ゲート C 2026-11-22)。#36**。タイムゾーン略称は付けない)。API の時刻は ISO 8601 を想定する。Crawler の cron が解釈されるタイムゾーンだけは別に明示する(機能設計書 UC-19。`admin-view-v0.1.md`)。**ブラウザと Crawler のタイムゾーンが異なる場合の表示は未決**(14 章)。
- 数値: 3 桁区切り・右揃え・等幅数字。件数の「—」は「未取得」、「0」は 0 件。
- 識別子: 等幅・13px。折り返し可。クリップボードへのコピー補助は MVP では付けない(要件にない)。

### 4.13 状態に応じた操作の出し分け(承認済み(ゲート C))

ページ見出しの操作(`acts`)は、対象の状態で出し分ける部品規約。ルール: (1) 画面の主操作は 1 つ(primary)。主操作がない状態があってよい。(2) 今は実行できない操作は**出さない**か、**無効にして理由を近くに出す**。出さない = 実行の見込みがない(ソース削除ジョブの取消、削除中のデータソースの編集など。理由は補足文)/ 無効 = 状況が変われば実行できる(ロック未解放の間の再実行など。「ロックを解放すると再実行できます。」を `aria-describedby` で結ぶ)。(3) 操作の水準は 4.8 の段階で決める。実装は、状態→操作の対応を 1 つの表(関数)にまとめ、画面ごとに分岐を散らさない。

| `nav.external`(任意) | 真偽 | 外部リンク領域に出す(OpenSearch Dashboards。設定時のみ) |
| `featureFlag`(任意) | 文字列 | 設定されていないときにナビとルートを隠す(任意コンテナなど) |

## 9. `data-testid` 命名方針【承認済み(前提 6)。名前の細則は案】

- 要素の特定は、まずロールとラベル(Playwright の `getByRole` / `getByLabel`)を使う。`data-testid` は、ロールとラベルで一意にできない箇所だけに付ける。
- 命名: `kebab-case`、`{画面 ID を小文字にしたもの}-{要素}`(例: `s1-sources-table`、`s1-state-empty`)。複数行の行は `{画面 ID}-row-{識別子}`(例: `s1-row-demo-handbook`)。
- 付ける対象: 画面の状態コンテナ(`{画面 ID}-state-empty` / `-state-error` / `-state-loading` / `-state-stale`)、テーブル本体、ダイアログ(`dlg-{目的}`。例: `dlg-crawl-start`、`dlg-source-delete`)、ナビ項目(`nav-{route 名}`)。
- **例外(案。#38)**: データソースの登録・編集(S3・S4)は同じフォーム部品を共有するため、フォームの項目は画面 ID の接頭辞を付けず `source-form-{項目}`(例: `source-form-root`、`source-form-include-patterns-0`)とする(`admin/sources-v0.1.md` 2.7)。
- Vuetify の部品では、`data-testid` が部品のルート要素に付くか内側の要素に付くかが部品ごとに異なる(`VDialog` は内容側など)。実装時に付く位置を確認して固定する。
- E2E テストの設計自体は本タスクの対象外。
