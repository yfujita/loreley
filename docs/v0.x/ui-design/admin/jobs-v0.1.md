- 全データソースのジョブ(クロール・ソース削除)の実行履歴を、新しい順に確認する(AF-8)。気になるジョブを開いて J2 で結果を見る。行から実行待ち・実行中のクロールを取消できる(AF-4)。
- 主操作はなし(一覧)。route: `/jobs`(クエリ: `source`、`status`、`page`、`size`、`sort`。#34)。ナビの現在地は「ジョブ」。テンプレート: 一覧(`list`)。
- 絞り込みは機能設計書の範囲(AF-8「表示範囲(履歴の件数・絞り込み)は後続設計」)で最小限にする: **データソース**と**状態**の 2 つ。

### 1.3 列と表示規則

| 列 | 内容 | 表示 | 並べ替え |
| --- | --- | --- | --- |
| ジョブ ID | ジョブ ID | 等幅・リンク(J2 へ)。折り返さない | なし |
| データソース | `source_id` | 等幅・リンク(S2 へ) | なし |
| 種別・起動 | 種別(クロール / ソース削除)、起動(手動 / 定期)、起動時の指定 | 1 行目: 種別。2 行目: 起動(12px)。(列を省略する幅では、補足行に「… · クロール(手動)」と同じ並びでタグを出す。)指定が「あり」のとき、枠線の小さなタグ(「強制削除」「再書き込み」。導出。ゲート C 承認済み。**一覧では幅の都合で「モード」を省いた略記**。正式名「強制削除モード」「再書き込みモード」は J2 の概要で示す。タグには `aria-label` で正式名を付ける) | なし |
| 状態 | ステータスタグ(DS 4.1) | 「失敗(リース切れ)」は補足「ロック未解放」を 2 行目に(導出。ゲート C 承認済み) | なし |
| 開始 | 開始日時(実行待ちは「受付 日時」) | 12px | 降順(既定。新しい順)・昇順 |
| 終了 | 終了日時 | 12px。未終了は「—」 | なし |
| (操作) | 取消 | 実行待ち・実行中のクロールだけ(1.4) | — |

- **列の省略(DS 4.3 の規則に従う。閾値は viewport ではなく表を載せるカードの幅で決める)**: 優先順位(高→低)は ジョブ ID > 状態 > 開始 > 操作 > データソース > 種別・起動 > 終了。**全 7 列が収まる(実測)のはカード幅 約 920px 以上**(全列の最小幅の実測値 916px。列の左右余白を 12px にして、1280px 基準で収まるよう調整した。macOS/Chromium での実測で、フォントにより変わるため実装時に再測定する)。実アプリのカード幅は viewport からサイドバー 232px と左右の余白 64px を引いた値(1280px で約 984px)なので、**基準幅 1280px(1.2 の図)では全列表示**で、viewport 約 1216px 以上で全列表示になる。**カード幅 920px 未満(viewport 約 1145〜1215px と 840〜1144px)では**「データソース」「種別・起動」「終了」を隠し、ジョブ ID の下に補足行(「demo-shared-docs · クロール(定期)」。12px・等幅)を出して情報を残す。**起動時の指定が「あり」のジョブは、補足行にも枠線の小さなタグ(「強制削除」「再書き込み」)を出す**(一覧から指定が消えないようにする)。**カード幅 720px 未満では**さらに「取消」をアイコンのみにする(アクセシブルネーム「取消(job-…)」)。viewport 基準にしない理由: カード幅は画面の最大幅やサイドバーの有無で変わり、viewport の区切り(1145px)と、全列が収まる幅が一致しないため(1145px のカード幅は約 849px)。実装はコンテナクエリ(CSS `@container`)、または表の親要素の幅を測る `ResizeObserver` を使う小さな composable(VueUse の `useElementSize` を使うなら DS 10 章の依存に足す)で切り替える。モックは `@container` で再現している(モックは外枠の左右余白 24px があるため、同じ viewport でもカードが約 48px 狭く、全列表示は viewport 約 1264px 以上。1145 / 1200 / 1279 / 1280 / 1366 / 1440px で、操作列が見切れず表内スクロールがないことを確認した)。
- 840px 未満は行をカード状に積む(ラベル付き)。取消できないジョブの行には操作を出さない(読み上げ用の補足文を持つ)。
- ページング: サーバー側(`VDataTableServer`。DS 4.3)。既定 25 件(25 / 50 / 100)。page・sortBy・itemsPerPage・絞り込みを TanStack Query の queryKey に含め、URL のクエリと同期する。

## 2. J2 ジョブ詳細

### 2.1 目的・主要操作

- 1 つのジョブの状態・エラー・警告・起動時の指定(AF-8)、登録結果(AF-9)、削除結果(AF-10)を確認し、状態に応じて取消(AF-4)・再実行(AF-5)・ロック解放(AF-7)を行う。メンテナンス中の理由(AF-19)も失敗の理由として表示する。
- テンプレート: 詳細(`detail`)。route: `/jobs/:jobId`。`meta.parent` = ジョブ(J1)。ナビの現在地は「ジョブ」。

### 2.2 レイアウト(幅 1280px。モック `#j2-*`)

```text
ジョブ › job-0005-demo
job-0005-demo [✕失敗]                                        [↻ 再実行]
データソース demo-wiki-export のクロール
┌ (状態による)アラート ─────────────────────────────────────────┐
│ 取得元の文書を列挙できませんでした / 詳細 … / 次の行動               │
└───────────────────────────────────────────────┘
┌ 概要 ─ 種別 / 起動 / 起動時の指定 / 受付・開始・終了 / リース期限(必要時) ┐
┌ 警告(N 件)─ あるときだけ ──────────────────────────────────┐
┌ 登録結果 [確定|集計の途中|途中までの値] ── 列挙 / 登録 / スキップ / サイズ超過 / エラー ┐
┌ 削除結果 ─ 状態 / 理由 / 件数 / 割合ルール(クロールのときだけ)──────────┐
┌ ロック状態 ─ リース切れのときだけ ───────────────────────┐
```

- 上から: ページ見出し(識別子・状態タグ・操作)→ 状態によるアラート → 概要 → 警告 → 登録結果 → 削除結果 → ロック状態。ソース削除ジョブには登録結果・削除結果のカードを出さない(概要とアラートのみ。モック `#j2-source-delete`)。

### 2.3 ページ見出しの操作の出し分け(DS 4.13。承認済み(ゲート C))

| ジョブの状態 | 操作 | 備考 |
| --- | --- | --- |
| クロール・実行待ち / 実行中(リース期限内) | 「取消」(outlined。DLG-3)、「更新」 | 自動更新 10 秒ごと。取消は「取消要求の受付」までで、結果は状態で確認する(AF-4) |
| クロール・失敗(データソースの**最新**のジョブ) | 「再実行」(primary。DLG-4) | 元の指定を引き継ぐ |
| クロール・失敗(より新しいジョブがある) | 「再実行」を無効(outlined)+理由「新しいジョブ(ジョブ ID)があるため再実行できません。データソースからクロールを起動してください。」 | 再実行の対象範囲(AF-U-7。承認済み(ゲート C。#4)) |
| クロール・失敗(リース切れ・ロック未解放) | 「ロックを解放…」(primary。DLG-5)、「再実行」は無効+理由「ロックを解放すると再実行できます。」 | AF-5・AF-7。取消は出さない(取消が完了しないことがあるため。AF-4) |
| クロール・失敗(ロック解放済み) | 「再実行」(primary) | 情報アラート「ロックを解放しました。ジョブは再起動されません。「再実行」でクロールを起動し直してください」(導出。ゲート C 承認済み) |
| クロール・成功 / 一部成功 / 取消 | なし | 起動はデータソースから |
| ソース削除・実行待ち / 実行中 | なし | 補足「ソース削除ジョブは取消できません。完了を待ってください。」 |
| ソース削除・失敗 | 「削除を再実行」(primary。確認ダイアログ=要確認・標準) | 同じ操作の再開(AF-16。モック `#dlg-delete-rerun`) |

- リース切れのロック解放後、ジョブは保存上も失敗(`lock_released`)になり、見出しのタグが「失敗(ロック解放済み)」(枠線のみ)に変わる(導出。ゲート C 承認済み。モック `#j2-released`)。
- 操作は、すべて再取得後に出し分けを更新する。

### 2.4 概要カード(AF-8)

| 項目 | 表示 |
| --- | --- |
| 種別 | クロール / ソース削除 |
| 起動 | 手動 / 定期 |
| 起動時の指定 | 「強制削除モード: なし / 再書き込みモード: なし」。「あり」は枠線タグ(強制削除=`error` 枠、再書き込み=`warning` 枠)。ラベルの下に「導出。ゲート C 承認済み」(機能設計書で、ジョブ記録の受付時の指定を表示することはユーザー未確認の導出)。クロールのみ |
| 受付 / 開始 / 終了 | 3 つの日時を「 / 」で並べる。未到達は「—」 |
| リース期限 | 実行中・リース切れのとき。期限切れは「(期限切れ)」を添える |

### 2.5 失敗の理由(アラート。承認済み(ゲート C。#11)。コードの名称は上流設計の案)

失敗(`failed`)のジョブは、概要の前に error アラート(`role="status"`)で「見出し(日本語)+詳細+次の行動」を出す。コードの名称は案(crawler-architecture 4.8。CA-P-10)で、未知のコードは「失敗しました(コード)」+詳細にする。`failure_detail` は説明(分類名・切り詰めた相対パス・固定文)で、本文・認証情報は含まれない(CA-P-45・48)。

| 理由コード | 見出し(承認済み(ゲート C。#11)) | 次の行動 |
| --- | --- | --- |
| `config_invalid` | 設定が正しくありません | 設定を確認する(S4) |
| `enumeration_failed` | 取得元の文書を列挙できませんでした | 取得元のパスと共有のマウントを確認して再実行 |
| `indexer_unavailable` | Indexer に接続できませんでした | しばらくしてから再実行 |
| `indexer_rejected` | Indexer が要求を受け付けませんでした | 詳細を確認し、管理者に連絡 |
| `external_id_collision` | 文書の識別子が衝突しました | 取得元の文書名を確認 |
| `enumeration_too_large` | 列挙した文書数が上限を超えました | データソースの範囲を見直す |
| `skip_limit_exceeded` | 読めない文書が連続して上限に達しました | 文書の確認(X1)で原因を解消して再実行 |
| `conflict_unresolved` | 書き込みの競合が解消しませんでした | 再実行 |
| `lock_lost` | 実行権(ロック)を失いました | 再実行 |
| `document_id_mismatch` | 文書 ID が一致しません | 管理者に連絡 |
| `maintenance` | メンテナンス中のため実行できませんでした(AF-19) | メンテナンスの解除後に再実行 |
| `finish_notice_failed` | 終了通知を送れませんでした | 削除結果を確認 |
| `internal_error` / `store_unavailable` | 想定外のエラー / データの保存先に書き込めませんでした | 時間をおいて再実行 |
| `crawler_restart` | Crawler の再起動により中断されました | 再実行 |
| `lock_released` | ロックの解放により失敗扱いになりました(リース切れ) | 再実行 |

### 2.6 リース切れの区別(AF-7。導出。ゲート C 承認済み)

| 見出しのタグ | 保存上の状態 | 補足 |
| --- | --- | --- |
| 失敗(リース切れ) | 実行中のまま(ロックが残っている) | ページ見出し下の補足「ロック未解放」。warning アラート「このジョブは止まっています(リース切れ)。リース期限(日時)を過ぎても終了していません。ロックが残っているため、このデータソースのクロールを起動できません。ロックを解放すると、ジョブは「失敗(ロック解放済み)」になります」(`#j2-lease`) |
| 失敗(ロック解放済み)(枠線のみ) | 失敗(`lock_released`) | 解放後。再実行できる(`#j2-released`) |

「ロック状態」カード(リース切れのときだけ)に「ロックを保持しています。保存上のジョブの状態は「実行中」のままです」を出す。

### 2.7 警告(AF-8。UC-10。コードの形式は案 CA-P-73)

あるときだけ「警告(N 件)」カードを概要の上(失敗アラートの下)に出す(見落とさせないため)。表記(承認済み(ゲート C。#11)):

| 警告コード | 見出し(日本語) | 詳細 |
| --- | --- | --- |
| `invalid_external_id` | 識別子が不正な文書があります(N 件) | 「これらの文書は登録されません。TTL が経過する前に原因を確認してください。」+例(切り詰めた表示) |
| `enumerated_zero_after_nonzero` | 列挙が 0 件でした(前回は N 件) | 「共有のマウントが外れていないか確認してください。削除対象が最小件数以下の小さなデータソースでは、割合ルールで守られません。」+前回のジョブへのリンク |
| `finish_id_list_over_threshold` | 終了通知に載せる文書 ID の一覧が多すぎます | 件数・しきい値 |
| `finish_not_acknowledged` | 終了通知が受理されたか確認できませんでした | 削除結果で確認 |
| `polling_aborted` | 削除の確認を打ち切りました | 確認結果の区分 |

警告のコードは見出しの下に小さく(12px・等幅)添える(DS 4.11)。

### 2.8 登録結果(AF-9)

- 項目(DS 4.10 の件数ブロック): 列挙 / 登録(新規・更新の内訳を補足)/ スキップ / 原本サイズ超過 / エラー(抽出に失敗した文書)。スキップ・原本サイズ超過・エラーは、値がデータソースの「文書の確認」(X1)へのリンク。
- カード見出しの右に枠線タグ: 「確定」(`partial=false`)/ 実行中は「集計の途中」/ 失敗・取消で確定前に終わったときは「途中までの値」(集計の途中か確定済みかを区別。機能設計書 AF-9)。
- 数え方の細部(新規/更新の内訳は目安に近いなど)は AF-U-10(Admin API 設計)。画面は値をそのまま表示し、内訳は補足として添える。

### 2.9 削除結果(AF-10)

- クロールのジョブにだけ出す。カードの内容は、削除結果の状態で次のように表示する(状態名・理由コードの名称は案。loreley-deletions 3、3.1):

| 削除結果の状態 | タグ | 表示 |
| --- | --- | --- |
| `deleted` | 削除完了(success) | 削除件数 |
| `skipped_by_ratio` | 削除なし(割合ルール)(warning) | 理由「削除対象が割合のしきい値を超えたため、このクロールでは削除しませんでした。」、しきい値(%)、削除対象 / 削除前の登録文書数(件・割合)、削除件数 0 件。補足「承認・却下の操作はありません。削除してよい場合は、データソースの設定を見直して再度クロールします。」(PD §4.6) |
| `failed` | 削除なし(失敗)(error) | 理由(`outcome_failed`=クロールが失敗したため / `outcome_cancelled`=取消されたため / `maintenance`=メンテナンス中のため(AF-19)/ `indexer_restart`=Indexer の再起動により / `delete_error`=削除でエラー+詳細) |
| `validation_failed` | 削除なし(検証エラー)(error) | 詳細 |
| `discarded` | 削除なし(破棄)(中立) | 詳細 |
| `running` | 実行中(info) | 「削除の判断を実行しています」 |

- **結果未確認・結果不明**(PD §4.7): Crawler がジョブ記録に持つ確認結果の区分が `unconfirmed`(結果未確認)または `unknown`(結果不明)のとき、カード上部に warning アラート「削除の結果を確認できませんでした(結果未確認)」+「Crawler は、Indexer の削除が終わったことを確認できないまま確認を打ち切りました。削除が行われたかどうかは、下の「削除結果の現在値」を見てください。この画面から再確認はできません。」を出し、2 行の表で併記する: 「Crawler の記録(確認結果の区分)= 結果未確認 / 結果不明」と「削除結果の現在値」(状態タグ・削除件数・取得時刻)(`#j2-cancelled`)。結果不明(404 が続いた場合。保持件数を超えて消えた、または失った場合)の説明は「削除結果の記録が見つかりません」とし、現在値は「—」。
- **終了通知後の取消**(`CAPI-U-6`。示し方は承認済み(ゲート C。#9)): 終了通知(列挙の完了通知)を Indexer に送った後に取消が受け付けられたジョブでは、J2 の上部に情報アラート「取消は、削除を止めていません。取消は、列挙の完了を Indexer に通知した後に受け付けられました。Indexer の削除は止まらず、続いている可能性があります。結果は下の「削除結果」で確認してください。」を出す(`#j2-cancelled`)。

### 2.10 取消・再実行・ロック解放のダイアログ

| ダイアログ | 水準 | 内容(モック) |
| --- | --- | --- |
| DLG-3 取消 | 要確認・標準 | 「ジョブを取消しますか」。対象(ジョブ ID・データソース)。実行中は「取消要求が受け付けられた後、次の確認点で止まります。完了は、ジョブの状態で確認してください」、実行待ちは「すぐに取消されます」。実行ボタン primary「取消を要求」。実行後: スナックバー「取消を要求しました。完了はこの画面の状態で確認してください」(実行待ちは「取消しました」)。`job_already_finished` は成功として扱い、スナックバー「ジョブはすでに終了しています(状態: 成功)」(AF-P-2)(`#dlg-cancel`) |
| DLG-4 再実行 | 指定による。両方「なし」= 要確認・標準 / 強制削除あり = 要確認・警告つき(赤。複数指定は最も重い指定の色)/ **再書き込みのみ = 要確認・警告つき(琥珀)** | 「ジョブを再実行しますか」。「データソース X の失敗したジョブ J を、同じ指定で新しいジョブとして起動します」。「引き継ぐ指定」を**読み取り専用のタグ**で提示(UC-11・17)。指定ごとに警告枠(強制削除=割合ルールを無視して削除。再書き込み=要約生成を止めて終える準備。S1 の DLG-1 と同じ文言)と、確認チェック「引き継がれる指定とその影響を確認しました」(チェックまで実行不可。理由を実行ボタンの下に)。実行ボタン「同じ指定で再実行」。実行後は**新しいジョブの J2 へ移動する**(#32。J1 には戻らない)(`#dlg-rerun`) |
| DLG-5 ロック解放 | 要確認・警告つき(warning) | 「ロックを解放しますか」。リース切れのジョブ: 「ジョブは「失敗(ロック解放済み)」になります」「ジョブは再起動されません」。確認チェック「ジョブが動いていないことを確認しました」(チェックまで実行不可。理由を実行ボタンの下に)。解放できない場合の案内は `sources-v0.1.md` 1.5(`#dlg-unlock`) |
| 削除の再実行 | 要確認・標準 | 「データソースの削除を再実行しますか」「削除ジョブが失敗しました。削除を最初から再開します。削除は取り消せません。完了すると、データソースは一覧から消えます」(`#dlg-delete-rerun`) |

### 2.12 自動更新(承認済み(ゲート C。#8))

実行待ち・実行中のジョブでは 10 秒ごとに自動更新し(`refetchInterval`。終端状態で停止)、見出しに「自動更新 10 秒ごと · 最終更新 時刻」と手動の「更新」を出す。自動更新の失敗では通知を出さず、ページ内に古いデータの警告(DS 4.7)を出す。取消の要求後は、終端になるまで更新を続ける。

### 2.13 レスポンシブ・アクセシビリティ・`data-testid`

- レスポンシブ: DS 7 章。件数ブロックは 1145px 以上 5 列、1144px 以下 3 列、840px 未満 2 列。操作ボタンは折り返し、理由文は左揃えに変える(840px 未満)。キー・バリューは 600px 未満で 1 列。375px・320px で崩れない(確認済み)。
- a11y: `h1` はジョブ ID。状態の変化(自動更新による終端への遷移)は読み上げない(`aria-live` なし)。操作の無効理由は `aria-describedby`。削除結果の併記表は行見出し(`<th scope="row">`)を持つ。警告・失敗のアラートは `role="status"`(読み込み後の情報)、取得失敗は `role="alert"`。
- `data-testid`: `j2-state-loading` / `-error` / `-stale`、`j2-actions`、`j2-warnings`、`j2-registration`、`j2-deletion`、`dlg-job-cancel`、`dlg-job-rerun`、`dlg-lock-release`、`dlg-source-delete-rerun`。
