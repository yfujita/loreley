## 1. S2 データソース詳細

### 1.1 目的・主要操作

- 1 つのデータソースの設定値・ロック状態・直近のジョブ・インデックス件数を確認し(AF-2、AF-15、AF-8)、クロールを起動し(AF-3)、編集・削除に進み(AF-1、AF-16)、止まったロックを解放する(AF-7)。
- 主操作は「クロール起動」(primary)。「編集」は outlined、「その他の操作」(`⋮`)に「削除…」。
- テンプレート: 詳細(`detail`。DS 6.2)。route: `/sources/:sourceId`。`meta.parent` = データソース(S1)。ナビの現在地は「データソース」。

### 1.5 ロック状態カード(AF-7。導出。ゲート C 承認済み。取得経路は Admin API 設計)

カード見出しは「ロック状態」。ロックの有無・保持ジョブの状態・リース期限から次の 6 種を出し分ける(モック `#s2-lock`)。ボタンの色は確認ダイアログの中だけ warning にする(ページ上では outlined)。

| 状態 | 見せ方 | 操作 | 根拠 |
| --- | --- | --- | --- |
| ロックなし | チェック+「ロックはありません。クロールを起動できます。」 | なし | |
| 実行中のジョブが保持(リース期限内) | 「実行中」タグ+「ジョブが実行中です」+ジョブ ID・リース期限。案内「実行中のジョブのロックは解放できません。止めるには、ジョブ詳細で「取消」を使います」 | 「ジョブを表示」(J2) | crawler-api 4.3(リース期限内は解放不可。取消を使う) |
| リース切れのジョブが保持 | warning アラート(`role="status"`)「止まったジョブのロックが残っています」+ジョブ ID・リース期限。「クロールの起動は「ロック保持中」で拒否されます」 | 「ロックを解放…」(DLG-5)、「ジョブを表示」 | AF-7。ジョブ詳細(J2)にも同じ操作 |
| 孤児ロック(ジョブ記録がない、またはジョブが終了済み) | warning アラート「動いているジョブのないロックが残っています(孤児ロック)」+「対応するジョブ記録がない、またはジョブが終了済みです」。小さく「承認済み(ゲート C): 孤児ロックの解放の入口をこの画面に置く」 | 「ロックを解放…」(DLG-5 孤児版) | AF-7。入口の記載が機能設計書になく、S2 に置く(承認済み(ゲート C。#1)) |
| 削除ジョブが保持(リース期限内) | 「削除中」タグ+「削除ジョブがロックを保持しています」+ジョブ ID・リース期限。案内「リース期限内は解放できません。完了を待ってください」 | なし | crawler-api 4.3 |
| ロック取得の直後(受付の途中の可能性) | 時計アイコン+「ロックを取得した直後です」。案内「受付の途中の可能性があるため、解放できません。しばらくしてから再読み込みしてください」 | 「再読み込み」 | crawler-api 4.3(取得直後は解放しない) |

- 解放しても、ジョブは再起動されない。解放後は「クロール起動」(DLG-1)で起動し直す(AF-7)。
- 解放の確認ダイアログ(DLG-5)の孤児版: 見出し「ロックを解放しますか」。警告枠「解放すると次のようになります」+「ロックだけが消えます。対応するジョブはないため、ジョブの状態は変わりません」「ジョブは起動されません。解放後にクロールを起動してください」。確認チェック「ジョブが動いていないことを確認しました」(チェックするまで実行ボタンは無効。理由「確認にチェックすると解放できます」)。帯と実行ボタンは warning(水準は要確認・警告つき)。モック `#dlg-unlock-orphan`。リース切れジョブ版は `jobs-v0.1.md` の DLG-5。
- 解放できなかった場合(409 `lock_in_use`)は、ダイアログを開いたまま内側に消えないアラートで理由と次の行動を示す: リース期限内の実行中・実行待ち → 「ジョブが実行中です。ジョブ詳細で取消を使ってください」/ リース期限内のソース削除 → 「削除ジョブが実行中です。完了を待ってください」/ 取得直後 → 「ロックを取得した直後です。しばらくしてからやり直してください」。

#### 2.3.0 フォーム全体の規則(ゲート C 承認済み。#2・#3 ほか。#38 の案ではない)

- ラベルの横に「必須」(DS 4.6)。必須の項目を空のまま送信すると「…を入力してください」。
- **入力単位と変換(AF-U-7。承認済み(ゲート C。#2))**: 画面の入力は TTL=日、しきい値=%、最小件数=件。保存時に Admin API が TTL を秒(×86,400)、しきい値を割合(÷100)に変換する(crawler-api の値は秒・0〜1。変換は Admin API の領域。`CAPI-U-3`)。表示は逆変換。小数は、しきい値のみ小数第 2 位まで許可する(例: 12.5)。
- **既定値(AF-U-7。承認済み(ゲート C。#2))**: 補わない。必須項目は空欄で始め、例は「例: 30」のようにプレースホルダーで示す。理由: 削除の判断に関わる値で、既定値を決めていない(`CAPI-P-7`、Indexer 設計の未決 U-1)ため、意図した入力を求める。(取得設定の任意項目の既定値は、Connector 設計 FS 2.1 が定める既定どおりで、別の話。2.3.1)
- **`ttl`・`min_delete_count` の検証(AF-U-7。承認済み(ゲート C。#3))**: Crawler は整数であることしか検証せず、範囲を見ない(`CA-K-16`)。画面で範囲(上表)を検証し、Admin API でも同じ検証を行う前提で Admin API 設計に申し送る。上限は設けない(int64 の範囲外は考えない。ユーザー判断 2026-11-16)ため、桁数(9 桁)だけ入力で制限する。
- AF-U-5 は文書単位ビュー(X1)の未決で、G1 に該当する部分はない(次回の G3 で扱う)。

#### 2.3.2 パターン一覧入力・画面の検証・上限(案)

- **1 行 1 パターンの入力欄の一覧**。行は「n(行番号)・入力欄(等幅)・削除ボタン」。「パターンを追加」ボタンで末尾に行を足す。行の並べ替えはない(照合は順序に依存しない)。0 行から始める(「パターンはありません(既定の拡張子だけが対象です)」)。行番号は 1 起点で、`data-testid` の添字は 0 起点。
- **追加・削除・フォーカス**: 追加すると新しい行の入力欄にフォーカスを移し、状態通知(`role="status"`)で「n 行目を追加しました(全 N 件)」。削除すると、**次の行(なければ前の行)の入力欄**にフォーカスを移し、「n 行目を削除しました(残り N 件)」。行がなくなったら追加ボタンにフォーカスを移す。入力欄で Enter は、フォームを送信せず、**下に新しい行を追加して移る**(入力が空のときは何もしない)。複数行を貼り付けたときは、1 行ずつの行に分ける(案。実装で確認)。
- **件数と上限**: 一覧の下に「N / 100 件」。**100 件(`max_patterns`。仮値・設定可能)に達したら**、「パターンを追加」を `aria-disabled="true"`(押しても何も起きない)にし、件数を「100 / 100 件(上限)」とし、警告文「上限の 100 件に達しました。追加するには、不要な行を削除してください。」を出す。1 パターンは UTF-8 で 1〜1024 バイト(`max_pattern_bytes`。仮値・設定可能)。**800 バイトを超えた行の下に「n / 1,024 バイト」を出し**、1,024 を超えるとエラー(下表)。上限値は Admin API が返す値を使い(`../admin-view-v0.1.md` 10.4)、取得できないときは既定値(100・1,024)を使う。最終の判定は Crawler(サーバー)。
- **長いパターン**: 入力欄は 1 行で、長いパターンは欄の中で横にスクロールする(ページ・フォームの幅は広げない)。S2 の表示では折り返す(切り捨てない)。
- **空の行**はエラー(「パターンを入力するか、この行を削除してください」)にする。送るときに自動で除くと、サーバーの添字エラー(`include_patterns[2]`)と画面の行の対応がずれるため、行と添字を 1 対 1 にする。**ただし、行を追加しただけで何も入力せずに Tab で離れたときは出さない**(誤エラーを避ける)。一度でも入力があった行を空にして離れたとき、または送信時(2.4)から出す。
- **前後の空白・重複**(Crawler は前後の空白を除かず、重複も拒否しない): **エラーにしない**。前後に空白があるパターンには、その行の下に注意「前後の空白も、パターンの一部として扱われます。」(警告アイコン付き。`aria-describedby` に含める)を出し、保存する値は入力のまま(自動で除かない)。重複は何も出さず、ヘルプに「同じパターンを重ねて書いても構いません」と書く。
- **検証のタイミング**: 行ごと・項目ごとに、フォーカスが外れたときに検証して該当の行の下に出す。**フォーカスが外れたときの検証は入力欄だけ**(削除ボタン・追加ボタンからフォーカスが外れたときは何もしない。さもないと、削除ボタンを押す操作で別の行に誤ったエラーが出て、押下が失われる)。送信時に全項目を検証する(2.4)。
- **エラー・注記の `aria-describedby`**: 入力欄の `aria-describedby` は、バイト数・前後の空白の注記・エラーの id を、表示が変わるたび(入力中を含む)に**まとめて組み立て直す**(どれかが消えて他が外れることがないように)。上限に達する追加では、状態通知にも「(上限)」を含める(「100 行目を追加しました(全 100 件。上限に達しました)」)。

**画面のメッセージと Crawler の固定文の対応(FS 2.2。Crawler は最初の違反 1 件を「項目名(配列は添字): 違反の種類」の固定文で返し、入力値は含めない。画面は全項目・全行を検証し、すべて出す)**

| --- | --- | --- | --- |
| `root` | 空(画面は常に `root` を送るため、空文字として Crawler に届く) | 「取得元のパスを入力してください」(画面の検証。サーバーまで届くことは通常ない) | `/` で始まる絶対パスでない(空文字の場合。「必須の項目がない」はキーを省略したときだけで、画面は常に送るため通常出ない) |

**パターンの書き方のヘルプ(「パターンの書き方と例」。開閉式。FS 2.3 に従う)**: パターンは取得元のパスからの相対パス(区切りは「/」)の**全体**に一致させる。`*`=「/」以外の 0 文字以上、`?`=「/」以外の 1 文字、`**`=0 個以上のセグメント(必ず単独のセグメント。`docs/**` は docs 自体と配下すべて。`**.md` は不可で `**/*.md` と書く)。例: `docs/**`、`**/*.draft.md`、`**/node_modules/**`。`*.md` は取得元の直下の .md だけで、どの深さでも対象にするなら `**/*.md`。大文字小文字は区別する。`[ ]`・`{ }` は文字そのもの。`\` は使えない。先頭・末尾に `/` を付けない。`.`・`..` のセグメントと `**` の連続は使えない。同じパターンを重ねて書いても構わない。**名前が `.` で始まるものは、「隠しファイルを対象にする」がオフの間は、パターンに一致しても対象にならない。除外のパターンは、追加のパターンより優先される**(FS 4.1。ヘルプの最後の段落に書く)。

#### 2.3.3 折りたたみ(「詳細な取得設定」。案)

- **取得元のパス(必須)は常に表示**し、パターン・スイッチ・既定の拡張子の注記は「詳細な取得設定」(開閉式。Vuetify `VExpansionPanels` の 1 パネル。DS 4.20)に入れる。見出し行に**現在の設定の要約**を出す(「追加パターン 1 件 / 除外パターン 3 件 / シンボリックリンク: たどらない / 隠しファイル: 対象にしない」)ので、閉じていても何が設定されているか分かる。
- **初期の開閉**: **S3(登録)は閉じる**(必須は取得元のパスだけで、ほかは任意・既定のままで登録できるため、最初は 1 項目に見せる)。**S4(編集)は、既定と違う値(パターンがある・スイッチがオン)があれば開き、すべて既定なら閉じる**(編集に来た利用者に設定済みの内容を見せ、全置換の更新で見落として消さないため。「すべて既定で閉じて始める」見本はモック `#s4-config-default`)。**エラーがあるときは開く**。
- **エラー要約からの移動**: エラー要約(件数つき)のリンクは、閉じている「詳細な取得設定」を**自動で開いてから**、該当の項目・行の入力欄にフォーカスを移す(`aria-expanded` を更新)。閉じている間にエラーがあるときも、要約から開ける。サーバーのエラーも同じ。
- 縦の長さ: 全部開いた状態(パターンが空)で、取得設定のカードが約 950px(1280px のモック)。パターンが増えると行ぶん伸びる。折りたたむ理由の根拠は 4 章。


### 2.4 検証とエラー表示(DS 4.6)

- タイミング: 項目からフォーカスが外れたときに、その項目を検証して項目の下に出す。送信時に全項目を検証し、エラーがあれば送信せず、フォーム上部に件数付きのエラー要約(`role="alert"`、各項目へのリンク)を出し、フォーカスを要約に移す。**要約の文言は、行・項目のエラーの文言と同一にする**(2.3.2 の対応表の画面の文言が正。要約だけ短くしない)。
- サーバー(Crawler・Admin API)の項目別エラー(`details.errors` の `field`・`reason`)は、同じ形で項目の下に出す。`reason` と文言の対応(承認済み(ゲート C)。`reason` の値そのものは Crawler 設計の案):

| `reason` | 画面の文言 |
| --- | --- |
| `required` | 「…を入力してください」 |
| `format` | 項目ごとの形式の文言(上表) |
| `type` | 「…の形式が正しくありません」 |
| `unsupported`(種別) | 「この種別は選択できません」 |
| `unknown_field` / `read_only` | 画面は送らない項目のため通常は出ない。出た場合はフォーム上部のアラートに「想定外の応答です」+詳細 |
| 409 `source_already_exists` | 識別子の項目に「この識別子は既に登録されています…」。**`status=deleting` のデータソースの識別子でも同じ 409 が返る**(設定がまだ残っているため。crawler-api §4.4.1)。応答から削除中と分かる場合は、補足「削除中のデータソースと同じ識別子です。削除が完了してから登録してください」を添える(分からない場合は同じ文言のまま)(案) |
| 409(`status=deleting`。S4) | S4 全体を編集不可にする(2.6) |
| 400 `config_invalid`(取得設定の違反。#38) | Crawler は最初の違反 1 件を `message` の固定文「項目名(配列は添字): 違反の種類」で返す(例 `exclude_patterns[1]: ...`)。**Admin API が項目(`root`・`include_patterns[2]` など)と違反の固定文に分けて返す前提**(`../admin-view-v0.1.md` 10.4)。画面は、項目から該当の入力欄・行を決め、固定文を 2.3.2 の表の画面の文言に直して**該当の行の下に出す**(モック `#s4-config-server`)。**添字のない配列のエラー(`include_patterns: 100 件を超えている` など)は、行ではなく、その一覧の下(追加ボタンと件数の行の下)に出す**。対応のない固定文・項目を特定できない場合は、フォーム上部のアラートに固定文をそのまま出す。入力内容は残す。**要申し送り**: crawler-api v0.4 の `config_invalid` は `message` だけを返し(512 文字で切り詰め・エスケープ済み。CAPI-P-23)、項目別の構造は持たない。項目別の表示には、案 (a) Admin API が `message` の「項目名: 違反の種類」を分解して返す(切り詰め・分解できないときは上部のアラートにフォールバック)、(b) Admin API が同じ検証を先に行い、項目別のエラーを返す、のどちらかが要る(推奨 (b)。画面が送信前に全項目を検証するため、サーバーの項目別エラーは通常出ない。Admin API 設計で決める)。 |

- 通信エラー・サーバーエラー(5xx): 入力内容は残し、フォーム上部に消えないアラート「設定を保存できませんでした。Crawler に接続できません。入力内容はそのままです。時間をおいて、もう一度保存してください」(スナックバーは使わない。モック `#s4-submit-error`)。
- タイムゾーンを取得できないとき(AF-U-13。承認済み(ゲート C。#6)): cron のヘルプの最後に、警告アイコン付きの文「適用されるタイムゾーンを取得できません。Crawler の設定を確認してください。意図した時刻とずれる可能性があります。」(warning の文字色・600)。入力と保存は止めない(モック `#s4-tz`)。次回実行予定日時は表示しない(機能設計書 AF-U-13。MVP に含めない)。

### 2.5 保存の挙動

- 送信中: ボタンを無効にし、ボタン内に進行表示+「登録中…」(S4 は「保存中…」)。理由の文「登録しています。完了すると詳細画面に移動します。」(`role="status"`)。入力欄は変更できるままにする(失敗時に直せる)。二重送信を防ぐ。
- 成功: S3 は S2 へ移動し、スナックバー「データソースを登録しました」(+「クロール起動」への導線は置かない)。S4 は S2 へ移動し、スナックバー「設定を保存しました」。移動後に S2 のデータを再取得する。
- 反映の注意(S4。AF-1): フォーム上部に情報アラート(`role="note"`)「保存した設定は、次に開始するジョブから使われます。実行中のジョブには反映されません(実行待ちのジョブには、開始時に反映されます)。」
- キャンセル: 保存せずに S1(S3)または S2(S4)へ戻る。未保存の変更の離脱確認は置かない(要件にない。MVP)。

### 2.7 インタラクション・レスポンシブ・アクセシビリティ

- 項目の並びは上から下。Tab 順は、(パンくず → )アラート → 基本 → 取得設定 → 実行周期 → 削除の判断 → キャンセル → 保存。読み取り専用の項目もフォーカスできる(値を読み上げるため)。
- すべての入力に `<label>`。ヘルプ・エラーは `aria-describedby`。エラーのある項目は `aria-invalid="true"`。
- **取得設定の a11y(#38。案)**: 
  - パターン一覧は `role="group"`(`aria-labelledby`=ラベル、`aria-describedby`=説明文+一覧のエラー)。ラベルの「任意」の文字は `aria-hidden`(グループの名前に含めない)。各行の入力欄の `<label>`(視覚的に隠す)は「追加で対象にするパターン 3 行目」。削除ボタンの名前は「追加で対象にするパターン 3 行目を削除」(アイコンのみのボタン)、追加ボタンは「パターンを追加」。追加・削除の結果は `role="status"` で通知する(2.3.2)。行のエラー・バイト数表示は、その行の入力欄の `aria-describedby`。
  - スイッチは `role="switch"` の `<input type="checkbox">`+`<label>`(ラベルに状態の文字を含めない。状態は `aria-checked` 相当とスイッチの位置、見える「オン」「オフ(既定)」の文字。この文字は `aria-hidden`)。説明文・警告文は `aria-describedby`。
  - 折りたたみは `<details>`/`<summary>` 相当(Vuetify `VExpansionPanels`。`aria-expanded`)。見出し行の要約テキストは、閉じていても読み上げられる。
  - エラー要約は件数つき(`role="alert"`)で、リンクが閉じた折りたたみを開いて項目・行にフォーカスを移す(2.3.3)。
  - **タップ領域**: 幅 600px 未満で、入力欄・削除ボタン・追加ボタン・スイッチの行・折りたたみの見出し行・ヘルプの開閉は高さ 44px(それ以上は入力 40px・削除ボタン 40px・追加ボタン 32px・スイッチの行 32px 以上)。
  - **キーボード**: 行の入力欄で Enter=下に行を追加して移る。Tab の順は 行の入力欄 → その行の削除 → …(行ごと)→ 追加ボタン。スイッチは Space で切り替える。
- レスポンシブ: フォームは最大幅 720px。幅 600px 未満は入力欄の高さ 44px。単位付きの入力は最大 280px、狭い幅では幅いっぱい。ボタンは折り返す。

## 4. 検討した案(#38。取得設定の全 5 項目)

| 項目 | 検討した案 | 採用 | 理由 |
| --- | --- | --- | --- |
| パターン(配列)の入力形式 | 1 行 1 パターンの入力欄を「追加」「削除」で増減する一覧 / 1 行 1 パターンの複数行テキストエリア / チップ入力(Enter で確定) | **入力欄の一覧(案)** | 項目別エラー(`include_patterns[2]`)を該当の**行**に出せる(行と添字が 1 対 1)。行ごとに `<label>`・`aria-describedby`・`data-testid` を持て、バイト数・エラーを行単位で出せる。テキストエリアは貼り付けと一括編集が速いが、エラーを行番号で示すしかなく、行ごとのフォーカス・読み上げ・テストの特定が難しい。チップ入力は長い glob(最大 1024 バイト)の編集・エラー表示に向かない |
| パターンの行の並べ替え | 置く / 置かない | 置かない | 照合は順序に依存しない(FS 2.3)。要件にない |
| 空の行の扱い | 送るときに自動で除く / エラーにする | エラーにする | 自動で除くと、サーバーの添字エラーと画面の行の対応がずれる。行と添字を 1 対 1 に保つ |
| 真偽値 2 項目の部品 | スイッチ / チェックボックス | スイッチ(`role="switch"`。DS 4.19) | 設定のオン・オフを表す。4.17 の自動更新スイッチと同じ見た目・寸法。状態は位置+「オン」「オフ(既定)」の文字で伝える(色だけにしない) |
| 取得設定カードの長さ | 常に全項目を展開 / 「詳細な取得設定」を折りたたむ(S3 は閉、S4 は既定と違う値があれば開、エラーがあれば開) / パターンだけ別カードに分ける | **折りたたむ(案)** | 必須は取得元のパスだけで、パターン・スイッチは任意・既定のまま登録できる(S3 で最初から全項目を見せると、必須が埋もれる)。見出し行に現在の設定の要約を出し、閉じていても分かる。S4 は設定済みの内容を見落とさないよう、既定と違うときは開く。エラー要約からは自動で開く。常に展開する案は、パターンが多いと縦に非常に長くなる |
| `include_patterns` のラベル | 「追加で対象にするパターン」(意味を示す日本語の名前)/ キー名のまま | 「追加で対象にするパターン」 | 一般の glob の「対象を絞る」直感と逆に、既定の拡張子へ**加える**項目のため(FS 2.1 の設定画面の注意)。名前と説明文で「追加」「絞る用途ではない」を示す |
| 既定の拡張子の扱い | 読み取り専用の注記として表示 / 表示しない / 編集可能にする | 読み取り専用の注記 | 固定の集合で設定項目ではない(FS 2.1。項目の追加・変更はしない)。注記で、「追加」の意味と対象の全体が分かる |
| 上限(100 件・1024 バイト)の扱い | 件数・バイト数の表示+追加ボタンの無効化+エラー / サーバーのエラーだけに任せる | 前者 | 仮値・設定可能な値のため、Admin API が値を返す前提(10.4)。画面で先に気づけるようにし、最終判定はサーバー |
| S1 の取得元の表示 | S1 の一覧に取得元の列を足す / 足さない | 足さない(変更なし) | S1 の列は承認済み(ゲート B。7 章)で、取得元は詳細(S2)で見る。S1 には取得元の情報が出ていないことを確認した |

**提案(本タスクでは置かない。要件にない便利機能)**: 取得元のパスの存在確認(接続テスト)、ファイルブラウザ、パターンのプレビュー(一致するファイルの試し表示)。いずれも Connector 設計・Admin API の拡張が要るため、必要になれば後続設計で検討する。
