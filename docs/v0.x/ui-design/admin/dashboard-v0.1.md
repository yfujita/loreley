## 1. 目的・主要操作

- 利用者(管理者)が、各コンポーネントが落ちていないかを一目で確認する(要件 0000「各コンポーネントの起動状態」)。管理画面を開いたときの入口(`/`)で、全体として異常がないかを最初に答える(情報設計の優先 1)。
- 主操作はなし。操作は「更新」と「自動更新」の入切のみ(通常水準。確認ダイアログなし)。
- テンプレート: ダッシュボード(`dashboard`。DS 6.4)。route: `/`。ナビの現在地は「ダッシュボード」。
- route `meta`: `../admin-view-v0.1.md` 4.2 の表のとおり(`title: 'ダッシュボード'`、`template: 'dashboard'`、`nav: { label: 'ダッシュボード', icon: mdiViewDashboardOutline, group: 'overview', order: 0 }`)。値は 4.2 を正とし、本書では繰り返さない。

## 3. コンポーネントと状態の定義

### 3.1 状態の値(DS 4.1。承認済み(ゲート C。#24・#25))

| 値 | タグ | 色 | アイコン | 意味 | 区分 |
| --- | --- | --- | --- | --- | --- |
| 正常 | 「正常」 | `success-container` | `mdiCheckCircleOutline`(円) | 起動が完了して応答できる | UC-7 |
| 異常 | 「異常」 | `error-container` | `mdiCloseOctagonOutline`(八角形) | 確認できたうえで、応答がない・応答できない状態 | UC-7 |
| 未設定 | 「未設定」 | 枠線のみ(塗りなし)+点線のタイル | `mdiCancel`(円に斜線) | 任意のコンポーネントが設定されていない | UC-3・UC-7 |
| 判定不能(導出。ゲート C 承認済み) | 「判定不能」 | `warning-container` | `mdiHelpCircleOutline`(円に疑問符) | 確認そのものが失敗して分からない(接続エラー・時間切れ・結果が古い) | AF-18(導出。ユーザー未確認) |

- 「異常」と「判定不能」の境界(例: 接続を拒否された=異常、時間内に応答がない=判定不能)は、取得経路(AF-U-1)とともに Admin API が決めて、状態の値として返す(画面は返された値を表示する)。
- 異常のタイルは、左に 4px の `error` の帯と `error` の枠線(強調。色だけにせずタグの文言・形でも示す)。判定不能は `warning` の帯・枠線。未設定は破線の枠+`surface-variant` の薄い面。

### 3.2 コンポーネントの定義表(拡張点)

タイルは 1 つの定義表(配列 `dashboardComponents`)から描画する。コンポーネントの追加(将来の AF-22 メンテナンスフラグ、AF-26 コンテナ操作の入口など)は、行を足し、必要なら操作(ボタン・`⋮` メニュー)を持たせる。

| `id`(表示名。等幅) | 役割(12px) | 区分 | 導線(承認済み(ゲート C。#28)) |
| --- | --- | --- | --- |
| `crawler` | 文書の取得とジョブの実行 | 必須 | 「ジョブの状態を確認」→ J1 |
| `indexer` | 抽出・索引への登録・削除の実行 | 必須 | 「ジョブの状態を確認」→ J1 |
| `opensearch` | 検索インデックスとデータの保存先 | 必須 | 「OpenSearch の詳細」→ O1 |
| `api` | 検索と管理操作の窓口 | 必須 | なし |
| `web` | この管理画面の配信 | 必須 | なし |
| `opensearch-dashboards` | OpenSearch の管理・調査用 | 任意 | なし(外部リンクはサイドバーにある。AF-20) |
| `embedding` | ローカルの埋め込みモデル | 任意 | なし |
| `llm` | ローカルの要約モデル | 任意 | なし |

- 対象は機能設計書 AF-18 のとおり(`crawler`・`indexer`・`opensearch`・`api`・`web`、任意の `opensearch-dashboards`・`embedding`・`llm`)。要件にないコンポーネントは足さない。
- 名前は docker compose のサービス名(等幅)。管理者が compose の出力と対応づけられる。

### 3.3 タイルの内容

| 状態 | 1 行目 | 2 行目(補足) | 3 行目 |
| --- | --- | --- | --- |
| 正常 | 名前+「正常」 | 役割 | 「応答しています · 確認 10:48:02」 |
| 異常 | 名前+「異常」 | 役割 | 「応答がありません。コンテナが停止している可能性があります。確認 10:48:02」 |
| 判定不能(導出。ゲート C 承認済み) | 名前+「判定不能」 | 役割 | 「状態を取得できませんでした(時間内に応答がありませんでした)。」+「最後に確認できた状態: 正常(2026-11-21 10:31:05)」 |
| 未設定 | 名前+「未設定」 | 役割 | 「設定されていません(任意)。」 |

- 判定不能の理由の文言(承認済み(ゲート C。#25)。理由コードの一覧は Admin API 設計で決まる): 接続エラー=「接続できませんでした」/ 時間切れ=「時間内に応答がありませんでした」/ 結果が古い=「確認結果が古くなっています」。理由コードの一覧は Admin API 設計で決まる(未知の理由は「状態を取得できませんでした」だけを出す)。
- 「最後に確認できた状態・日時」は、コンポーネントごとの最終取得成功日時(導出。ゲート C 承認済み)。取得できないときは省略する。

### 3.4 概況

| 状況 | 見た目 | 文言 |
| --- | --- | --- |
| すべて正常(任意は未設定を許す) | `success` | 「すべてのコンポーネントが正常です」+「正常 N · 異常 0 · 判定不能 0 · 未設定 M」 |
| 異常あり | `error` の面・八角形 | 「異常のコンポーネントがあります(N 件)」+「異常: 名前」+件数 |
| 異常なし・判定不能あり(導出。ゲート C 承認済み) | `warning` の面・疑問符 | 「状態を確認できないコンポーネントがあります(N 件)」+「判定不能: 名前」+件数 |
| 取得失敗(前回データ) | `warning` の面・疑問符 | 「現在の状態を確認できません」+「判定不能 6 · 未設定 2(前回取得時の設定)· 前回の構成と同じ 8 件」(通常時の「正常 6 · 未設定 2」と合計が一致する) |

- 異常と判定不能の両方があるときは、異常を優先して表示し、件数行に両方を並べる。
- 概況は `role="status"` ではない(自動更新の結果を読み上げさせない。DS 8)。**手動の「更新」を押した直後だけ**、視覚的に隠した `role="status"` に「更新しました。異常 N 件、判定不能 M 件」を出す。

## 4. 更新と取得失敗(承認済み(ゲート C。#25・#26))

### 4.1 更新

- **手動更新**: 「更新」ボタン(outlined。最終取得成功日時の横)。更新中も表示は消さず、概況の上端に進行バーを出す。
- **定期更新**(承認済み(ゲート C。#26)): 既定オン。**30 秒ごと**(`refetchInterval: 30000`)。`refetchIntervalInBackground: false`(タブが見えていない間は止める)。ページ見出しの「自動更新(30 秒ごと)」のスイッチ(`role="switch"`)で一時停止できる。停止中は「自動更新は停止中です。「更新」で最新の状態を取得します。」を最終取得成功日時の横に出す(モック `#d1-toolbar`)。スイッチの状態は保存しない(再読み込みで既定のオンに戻る。ユーザー設定を持たない)。
- 自動更新の結果は読み上げない(DS 8)。失敗では通知(スナックバー・ダイアログ)を出さず、ページ内の警告に留める(DS 4.7)。
- 自動更新の間隔 30 秒の理由: 死活の確認は即時性が要るが、10 秒ごとでは取得側の負荷が上がり、確認の失敗が連続して通知を増やす。ジョブ詳細(J2。実行中のみ 10 秒)と違い、ダッシュボードは常時開いたままになりやすい。

### 4.2 最終取得成功日時

- ページ見出しの右(または下)に「最終取得成功 2026-11-21 10:48:02」。画面全体の取得(1 回の取得)が成功した最後の日時。コンポーネントごとの確認時刻は、タイルの「確認 hh:mm:ss」。
- 取得失敗が続いても、この日時は最後の成功のまま更新しない。

### 4.3 取得失敗(Admin API に届かない)

| 状況 | 見せ方 |
| --- | --- |
| データなし(初回から失敗) | 概況とタイルの代わりに、エラーブロック(`role="alert"`)「コンポーネントの状態を取得できません」+「Admin API に接続できませんでした。…api コンテナが起動しているかを確認してください。」+試行時刻+「再試行」(`#d1-error`) |
| 前回データあり(stale。導出。ゲート C 承認済み) | ページ上部に warning のアラート(`role="alert"`)「最新の状態を取得できませんでした」+「Admin API に接続できないため、どのコンポーネントの現在の状態も確認できません。前回取得した状態(時刻)を、タイルに添えています。」+「再読み込み」。概況は「現在の状態を確認できません」(`warning`)。**前回の構成と同じ全タイル(必須 5・任意 3)を出し、前回「正常」「異常」だったタイルのタグを「判定不能」に切り替え**、3 行目に「前回の状態: 正常(10:44:30 時点)」を出す。前回「未設定」だったタイルは未設定のまま「前回取得時は、設定されていませんでした」を添える(設定の有無は「正常」と断定する情報ではない)。「任意のコンポーネント」の節も省かない(モック `#d1-stale`)。自動更新は続け、成功したら通常の表示に戻る(`#d1-stale`) |
| 一部のコンポーネントだけ取得失敗 | そのタイルだけ「判定不能」(3.3)。概況は 3.4 の判定不能あり |

- 前回データのまま「正常」を表示し続けない理由: 現在の状態として読まれ、実際には落ちているコンポーネントを見逃させるため(機能設計書 AF-18「取得結果が古いときも正常と断定しない」)。

| 取得失敗(前回データ) | `#d1-stale` | 前回の構成と同じ全 8 タイル。前回「正常」「異常」だったタイルは判定不能、「未設定」は維持 |
| 取得失敗(データなし) | `#d1-error` | エラーブロック |
| 読み込み中 | `#d1-loading` | 概況とタイルのスケルトン。見出し・更新は先に出す。`aria-busy`、視覚的に隠した「…を読み込み中」 |
| 更新の操作(入切・更新中) | `#d1-toolbar` | スイッチの入切、更新中の進行バー |
| 空 | なし | 必須のコンポーネントは常に 5 つあるため、「空」はない(定義表が空になることはない) |

## 6. インタラクション

- ホバー: タイルは変化なし(操作要素ではない)。タイル内のリンクはホバーで下線。
- フォーカス: タブ移動はタイルの順にリンクへ(コンポーネントの定義表の順)。フォーカスリングは DS 2.6。
- 動き: 進行バーとスケルトンのみ(DS 2.6)。状態が変わったときのアニメーションは付けない。

## 8. アクセシビリティ

- 見出し: `h1`「ダッシュボード」、`h2`「コンポーネント」「任意のコンポーネント」「この表示について」、タイルの名前は `h3`。タイルのリストは `<ul aria-label>`。
- 状態は色・形・文言(DS 4.1)。判定不能・未設定も、タグの文言で伝える。異常のタイルの強調(左の帯)は補助。
- 本文内のリンク(タイル末尾の「ジョブの状態を確認」など)の操作領域は高さ 24px 以上(WCAG 2.2 の 2.5.8)。
- 自動更新: 読み上げない。スイッチは DS 4.17 の `AutoRefreshSwitch`(`role="switch"`)・`<label>` つき(「自動更新(30 秒ごと)」)で、キーボードで操作できる。一時停止できることで、自動更新する情報の一時停止・停止の要件(WCAG 2.2.2)に配慮する。非表示のタブでは更新しない。
- 手動更新の直後だけ、視覚的に隠した `role="status"` で結果の要約を伝える(3.4)。
- 取得エラー・古いデータの警告は `role="alert"`。
- コントラスト: タグ・概況・タイルの文字は DS 2.1 の値(4.5:1 以上)。

## 10. データ項目と取得(想定。Admin API は未設計)

| 項目 | 備考 |
| --- | --- |
| コンポーネントごとの状態(正常 / 異常 / 未設定 / 判定不能)、確認時刻、判定不能の理由、最終取得成功日時 | 取得経路は未決(AF-U-1)。Admin API が確認し、状態の値として返す想定 |
| 任意コンポーネントが設定されているか | 設定の有無は Admin API が判断して返す(画面は設定を知らない) |

- 取得経路の制約(機能設計書 3.8): SD §7.3「`api` は `indexer` に接続しない」と、Crawler・Indexer の稼働確認用 API が Admin API の契約外であること(crawler-api §1・§4.7、indexer-api §1)。画面は影響を受けない。
- 「起動状態」の意味: ダッシュボードの死活は「起動が完了して応答できる」ことを意味する(Crawler の `/healthz` は「受付が始まっている」ことだけを示す。機能設計書 3.8)。画面の「この表示について」に意味を書いた。
- データ取得は TanStack Query(`queryKey: ['dashboard']`、`refetchInterval`、`isRefetchError` で前回データ+警告。DS 4.5)。取得失敗時にタイルを判定不能へ切り替える処理は、取得成功時のデータ(`state`)を画面側で降格して表示する(`isRefetchError` が真のとき、前回「正常」「異常」だったタイルの表示状態を判定不能にし、`data` の状態を「前回の状態」として添える。前回「未設定」のタイルは未設定のまま)。

Admin API への申し送り: (1) 取得経路(AF-U-1)と、異常 / 判定不能の境界、(2) コンポーネントごとの最終取得成功日時の保持(判定不能の「最後に確認できた状態」)、(3) 任意コンポーネントの設定の有無、(4) 取得のタイムアウト(30 秒の自動更新より短く)、(5) `api`・`web` 自身の状態の取り扱い(`web` と `api` が同居する場合を含む)。
