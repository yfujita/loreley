## 1. データモデル

> プロダクトデザイン上の位置づけ：共通ドキュメント形式とID設計は、Connector・Indexer・検索・Store層をつなぐ契約である。Store層は、MVPでは専用DBを置かず、OpenSearchをKVSとして使う（プロダクトデザイン v0.8 参照）。

### 1.1 共通ドキュメント形式

ConnectorがIndexerに渡す形式（v0.4 付録A.1）。

| 項目 | 説明 |
| --- | --- |
| `source_id` | データソースの識別子。登録後は変更できない |
| `external_id` | データソース内で一意な識別子（ルートからの相対パス、ページID等）。§1.2の正規化を適用する |
| `title` | タイトル（取得できなければファイル名） |
| `url` / `path` | 原文への参照（表示用） |
| `mime_type` | 文書形式 |
| `raw_content` | 取得済みの原本（MVPでは参照ではなく原本そのものを渡す。「原本または参照」の2通りはやめた）。抽出前のデータであり、検索インデックスの`content`（抽出後の本文）とは別物 |
| `content_hash` | 原本のSHA-256 |
| `source_updated_at` | データソース上の更新日時（ローカルでは`mtime`） |
| `size` | 原本のサイズ（バイト） |
| `fetched_at` | 原本を取得した日時。取得を省略した場合は更新しない |
| `metadata` | Connector固有の追加属性 |

`last_seen_at`は共通ドキュメント形式に含めない。クロールの実行コンテキストとして`crawl_started_at`（クロールの開始時刻）をIndexerに渡し、Indexerが`last_seen_at`に書く。`fetched_at`は「取得した日時」、`last_seen_at`は「列挙で見つかった日時」である。毎回の全文upsertで`last_seen_at`が更新されるほか、取得に失敗してスキップした文書の誤削除を防ぐため、列挙で見つかった時点で`last_seen_at`だけを部分更新する（§2.4、§3.1、§3.2）。

本システム内で`content`の意味は場所ごとに異なる。

| 場所 | 名前 | 意味 |
| --- | --- | --- |
| Connector → Indexer | `raw_content` | 取得済みの原本 |
| Store層 | `text` | 抽出・正規化後のテキスト（サイズ上限で切り詰め後） |
| 検索インデックス | `content` | `text`と同じ内容を検索用に解析したもの |
| `get_document`の応答 | `content` | `text`の指定範囲 |

### 1.2 ID設計

v0.4 付録A.2。

- `document_id` = `SHA-256(source_id + "\0" + external_id)`の16進文字列（小文字）。NUL文字で区切るため、連結で別の組が同じ値にならない。
- `external_id`は、ハッシュの前にUnicode NFCへ正規化し、パス区切りを`/`に統一する（ルートからの相対パス、先頭に`/`を付けない）。大文字小文字は区別したまま扱う。
- 同じ文書を再取得すると同じIDになるため、再実行しても重複しない。検索インデックスとStore層のどちらも、`document_id`を文書IDとして使う。
- `source_id`は登録後に変更できない。変更が必要なときは、新しいデータソースとして登録し直す。
- パスの変更やリネームは「旧IDの削除 + 新IDの追加」として扱う。リネームの追跡は初期要件にしない。
- データソースを削除するときは、その`source_id`の文書をStore層、検索インデックスの順にすべて削除し、そのあとで、そのソースのスキップ記録とロック文書（`lock-{source_id}`）を削除し、最後にデータソース設定を削除する。途中で止まった場合に備え、設定の削除は文書とスキップ記録の削除が終わってから行う。

### 1.3 Store層のデータモデル

v0.4 付録C.1。MVPのStore層はOpenSearchをKVSのように使い、設定・ジョブ・抽出済みテキスト・文書ごとの処理状態を保存する。用途ごとに検索インデックスとは別のインデックスを分け、IDをキーにget/put/deleteする。

| インデックス | 内容 |
| --- | --- |
| `loreley-sources` | データソース設定（`source_id`、種別、ルート、周期、TTL、除外条件など。認証情報は参照名のみ） |
| `loreley-jobs` | ジョブ状態、ソースごとの実行ロック、削除保留、スキップ記録（§3.1） |
| `loreley-texts` | 文書ごとの抽出済みテキストと処理状態 |

`loreley-texts`の項目：`document_id`、`source_id`、`external_id`、`title`、`url`/`path`、`mime_type`、`text`、`truncated`、`content_hash`（確定済み）、`pending_content_hash`、`source_updated_at`、`indexed_at`、`size`、`extractor_version`※、`index_status`、`extract_fail_count`※、`pending_since`（`pending_index`になった日時）、`summary`、`summary_content_hash`（要約の生成元の`content_hash`）、`summary_status`、`summary_model`。

※`extractor_version`・`extract_fail_count`は、差分検知（将来拡張。§3.7）で使う予約項目で、MVPでは使わない（新しい項目ではなく、v0.3からの項目を残している）。v0.1にあった`fetch_fail_count`（恒久失敗の判定用）は、スキップ方針（§3.1）で不要になったため削除した。取得・登録の失敗回数は、`loreley-jobs`のスキップ記録に持つ（新規の文書も含む）。

`pending_content_hash`・`pending_since`・`source_updated_at`・`size`は、MVPでも使う。

**真実の置き場所**：文書の本文・要約・処理状態の正はStore層（`loreley-texts`）。検索インデックスはそこから作る派生物である。ただし`last_seen_at`は検索インデックスだけに持つ。`title`・`url`/`path`・`mime_type`・`indexed_at`もStore層に持つので、§2.5(b)の再構築と`get_document`（§5.4。`title`と`url`/`path`を返す）は、Store層だけで成立する。

### 1.4 マッピング方針

v0.4 付録C.2（Store層のインデックス）。

- `dynamic: strict`にして、未定義のフィールドの混入を防ぐ。
- 検索や集計の対象にしない大きな文字列（`text`など）は、解析も索引化もしない（`index: false`、またはオブジェクトの`enabled: false`）。取得はIDによる`_source`の読み出しで行う。
- 条件で一覧する項目（`source_id`、`index_status`、`summary_status`など）は`keyword`にする。
- MVPは単一ノード前提で、`number_of_shards: 1`、`number_of_replicas: 0`とする。

### 1.5 Repositoryインターフェース

v0.4 4.8（データストア）の実装に関する部分。コード上は検索インデックスとは別の「Store層」として扱い、アプリケーションはRepositoryインターフェースだけを経由して読み書きする。

- バックエンドは設定で差し替えられるようにする。将来、PostgreSQLやSQLiteを追加しても呼び出し側を変えない。
- インターフェースは、IDによる取得・保存・削除、単純な条件での一覧、条件付き更新（楽観的排他制御）に限る。トランザクションと結合には依存しない。
- Connectorの認証情報は、Store層に平文で保存しない。環境変数や秘密情報ファイルで参照する（§6.4）。
- 条件付き更新の方法（`if_seq_no`/`if_primary_term`）と、検索ではなくIDによる取得を使う理由は§3.8に記す。
- Repositoryインターフェースの詳細と、OpenSearch以外のバックエンドに移る条件（件数・更新頻度・排他の要件など）は未決定である（v0.4 9.2 #6。§12.1）。

## 2. 検索インデックス

> プロダクトデザイン上の位置づけ：1文書 = 1検索レコードを基本とし、タイトル・要約・本文をBM25で検索する。日本語を主な対象とし、英語も併せて解析する。チャンク分割・ベクトル検索は、評価結果を見て判断する（プロダクトデザイン v0.8 参照）。

### 2.1 フィールド・Mapping・Analyzer・Shard/Replica

v0.4 付録B.1。1文書 = 1検索レコード。`_id`は`document_id`。

| フィールド | 用途 |
| --- | --- |
| `document_id` | 一意な識別 |
| `source_id` | データソースによる絞り込み |
| `external_id` | データソース内の識別子（突合と、削除対象の特定に使う） |
| `title` | タイトル検索 |
| `summary` | 文書全体の主題による検索 |
| `content` | 細かい語句・識別子による全文検索（抽出・正規化後の本文） |
| `url` / `path` | 原文への参照（表示のみ） |
| `mime_type` | 文書形式による絞り込み |
| `source_updated_at` | 更新日による絞り込み |
| `indexed_at` | インデックスに登録した日時 |
| `content_hash` | 要約の条件付き更新の判定に使う |
| `summary_status` / `summary_model` | 要約の生成状態と、生成に使ったモデル・バージョン |
| `index_status` / `truncated` | 抽出状態と、本文を切り詰めたかどうか |
| `last_seen_at` | 列挙クロールで最後に見つかった日時（期限による削除の判定） |
| `acl` | アクセス制御用の属性（MVPでは使わない。将来に備えて予約） |
| `summary_embedding` | 意味検索用のベクトル（任意） |

`summary` / `summary_status` / `summary_model` / `index_status` / `truncated`は、検索結果の表示と絞り込みのための写しである。**正はStore層**に置く。`last_seen_at`だけは検索インデックスが唯一の保存場所である。

`summary_status`の取りうる値：`disabled`（要約が無効）、`pending`、`generated`、`failed`。`index_status`の取りうる値：`pending_index`（Store層のみ。登録前）、`indexed`、`extract_failed`。

**Mapping・Analyzer・Shard/Replica**：v0.4は検索インデックスのマッピング全体を定義していない。決まっているのは次の方針で、詳細は実装時に確定する。

- アクセスはエイリアス経由とする（§2.3）。
- ハイライトに使うフィールドは`index_options: offsets`でオフセットを保存する（§2.3）。
- アナライザは、日本語を形態素解析（kuromojiまたはSudachi）、英語を標準アナライザとし、識別子・型番の検索漏れを防ぐためにn-gramのサブフィールドの追加を検討する（§2.2）。選定は評価セットのRecall@10・MRRで行う（v0.4 9.2 #1。§12.1）。
- 単一ノード前提のMVPでは、`number_of_shards: 1`、`number_of_replicas: 0`とする。v0.4が明記しているのはStore層のインデックス（§1.4）で、検索インデックスにも同じ前提を置く（推測。実装時に確認する）。同様に、`dynamic: strict`と、絞り込みに使う項目（`source_id`、`mime_type`、`index_status`、`summary_status`）の`keyword`化も、検索インデックスに同じ方針で適用する想定である（推測）。
- 専用プラグインを導入した独自のOpenSearchイメージを使う（§7.4）。

### 2.2 検索クエリ・BM25・日本語解析・辞書

v0.4 付録B.2、4.3。

- 基本はBM25による全文検索とし、タイトル・要約・本文の重みを調整する。
- 日本語は形態素解析（kuromojiまたはSudachi。評価して決める）で解析し、英語は標準アナライザで併せて解析する。識別子や型番の検索漏れを防ぐため、n-gramのサブフィールドの追加も検討する。
- ユーザー辞書・同義語辞書はファイルで管理し、更新したら再インデックスで反映する（§2.5）。
- 将来は、要約Embeddingによるベクトル検索やハイブリッド検索を追加する。
- データソースから消えた文書は、削除されるまで検索結果に残る。検索時に`last_seen_at`で除外はしない（§3.4）。

### 2.3 ハイライトとインデックス運用

v0.4 付録B.3。

- インデックスにはエイリアス経由でアクセスする。マッピングや辞書を変えるときは、新しいインデックスを作ってからエイリアスを切り替える。
- ハイライトに使うフィールド（n-gramなどのサブフィールドを含む）は、`index_options: offsets`でオフセットを保存する。ハイライタはunified（既定）を使う。オフセットがあると、unifiedハイライタは本文を再解析しないため、解析上限（`index.highlight.max_analyzed_offset`、既定は100万文字）は適用されない。この上限を理由に長い文書の本文を切り詰めない。
- plainハイライタは常に再解析し、上限を超えると検索リクエスト全体が失敗するため使わない。
- オフセットの保存でインデックスサイズが増える。増え方は実装時に計測する。本文サイズの上限は、リクエストサイズ・インデックスサイズ・処理時間などの観点で決める（§10.2）。
- 長い文書で検索精度に問題が出た場合は、見出し・セクション単位の補助インデックスを追加できる構成にする。固定長チャンクへの分割は初期要件にしない。

### 2.4 更新処理・競合制御

v0.4 付録B.4。検索インデックスへの書き込みは次の2種類に分ける。MVPは全件更新で、すべての文書を全文upsertする。これに加えて、読めない文書をスキップしても削除されないよう、列挙で見つかった時点の`last_seen_at`の部分更新を行う（§3.1）。

| 種別 | 書くフィールド | 書き込む側 | 競合時の扱い |
| --- | --- | --- | --- |
| 全文upsert | 全フィールド。`last_seen_at`は既存値と`crawl_started_at`の大きい方（スクリプトによるupsert。新規作成時は`crawl_started_at`）、`content_hash`は新しい値。`summary`と`summary_status`は、`content_hash`が既存と同じなら既存の値を保持し、違えば`summary`は書かず`summary_status=pending`（要約が無効なら`disabled`） | Indexer（本文の追加・更新時） | 文書全体を置き換える。本文が変わったときは、旧本文向けの要約を残さない（全件更新で毎回要約を作り直さないよう、本文が同じなら引き継ぐ）。同じデータソースのクロールは1つだけなので、同時の全文upsert同士は起きない。`last_seen_at`は古い値に戻さない（max比較） |
| `last_seen_at`の部分更新 | `last_seen_at`のみ（値は`crawl_started_at`） | Indexer（列挙で文書が見つかった時点。取得より前） | 現在値と比べるスクリプト更新（max比較）。新しい値のときだけ書き、古い値で上書きしない。ほかのフィールドは変更しない。検索インデックスに文書がない場合（404）は何もしない（upsertしない）。取得・抽出・登録が失敗しても更新済みのまま残る |
| 要約の部分更新 | `summary`、`summary_status`、`summary_model`、`summary_embedding` | 要約生成（非同期） | **検索インデックス上の`content_hash`が、要約を生成した本文の`content_hash`と一致するときだけ**書く（条件付き更新）。不一致なら捨てる（本文が更新済みで、新しい要約が生成される）。更新の衝突は再試行する |

**リース切れ後の旧Workerの全文upsert**：全文upsertは文書全体を置き換えるため、古い世代のWorkerが新しい内容を上書きするのを原子的には拒否できない。MVPでは、単一Worker・直列実行を基本とし、リース期限切れだけでは自動で引き継がない（§4.3）ことで、この状況が起きにくくする。実行世代番号を持たせて古い世代の上書きを拒否する完全な分散フェンシングは、複数Worker化の際の将来拡張とする（§4.7）。ここで保証するのは、`last_seen_at`が戻らないことまでである（部分更新もmax比較なので同様に戻らない）。

要約は、生成の完了後にまずStore層へ保存し、そのうえで検索インデックスへ反映する。Store層への保存も、生成元の`content_hash`が一致するときだけ行う（§3.8、§8.4）。

### 2.5 再インデックス

v0.4 付録B.5。マッピングや辞書を変えるとき、またはインデックスを作り直すときは、次の2つの手段を使い分ける。どちらも、**再インデックスの対象のデータソース（インデックス全体を作り直すときはすべて）のクロールと要約の書き込みを止めてから**行い、完了後に再開する。削除も実行しない。

**開始前に、実行中の書き込みが終わったことを確認する**。対象のソースに`running`のクロールと要約生成のジョブがなくなったことを確認し、終わらないときはWorkerを停止してから始める（ロックの取得やフラグだけでは、すでに始まっている書き込みは止まらないため）。単一Worker・直列実行なので、要約の書き込みはクロールと直列に処理される（§4.3）。

止める手段は、対象のソースごとの実行ロック（§4.2）を取得したままにするか、`loreley-jobs`にメンテナンスフラグを立てて、CrawlerとIndexerがフラグを確認して書き込みを控えるか、のどちらかとする。MVPでは手動手順（READMEに記載）とする。画面（Admin View）からの実行は将来拡張とする。

| 手段 | 内容 | `last_seen_at` | 要約 | 使う場面 |
| --- | --- | --- | --- | --- |
| (a) `_reindex`で旧インデックスからコピー | 新しいインデックスを作り、旧インデックスの文書をコピーしてエイリアスを切り替える | 保持される | 保持される | マッピング・辞書・アナライザの変更（通常はこちら） |
| (b) Store層からの再構築 | Store層の抽出済みテキストから、検索インデックスを新しく作る。再クロールは不要 | 再構築時刻に初期化される（TTLの時計が再構築時から始まる） | Store層に保存している要約のうち、生成元の`content_hash`が本文と一致するものだけが保持される。不一致は`pending`に戻す | **旧インデックスを失った場合に限る**。抽出ロジックを変えたときは使わず、全件更新の再クロールで反映する（§3.2。差分検知を導入した場合は`extractor_version`の更新による再クロールで反映する。§3.7） |

READMEに記載する手順（クロールと要約書き込みの停止、実行中の書き込みの終了確認、コピー、エイリアス切り替え、再開）は、§11.6のテストで確認する。

## 3. クロール・削除

> プロダクトデザイン上の位置づけ：MVPは全件更新（差分検知は将来拡張）で、削除は`last_seen_at`とTTLによる期限で判定する。削除の安全性（誤削除の防止）が成功指標の1つである（プロダクトデザイン v0.8 参照）。

### 処理の流れ（概要）

**Connectorと列挙クロール**（v0.4 4.1）：ConnectorはデータソースごとのCrawlerの実装で、Crawlerはその実行・周期・同期状態を管理する。データソースから文書を列挙・取得し、Indexerに共通ドキュメント形式（§1.1）で渡す。

- MVPのConnectorは、ローカルディレクトリ／ファイル共有のみ。HTTPサイト、Confluence、Gitなどは将来の拡張（Webページのスクレイピングも将来）。
- **列挙クロール**：データソース内のすべての文書を列挙するクロール。MVPでは、列挙した文書をすべて取得・抽出して登録する（全件更新。差分検知は将来拡張）。MVPのクロールはすべて列挙クロールである。削除の判定は列挙クロールだけが行う。
- 追加・更新の検知はせず、毎回すべての文書を処理する（§3.2）。削除は期限（`last_seen_at`とTTL）で判定する（§3.3、§3.4）。
- 読めない文書は、設定した回数だけリトライしてもだめなら、その文書だけスキップする。スキップはクロール全体・他の文書の登録・削除に影響させない（§3.1）。
- 接続設定、認証情報の参照名、実行周期、取得状況、エラーはStore層に保存する（§1.3）。

**収集・更新**（v0.4 5.1）：

1. Crawlerがデータソースを列挙する（§3.1）。見つかった文書の`last_seen_at`を、その時点で部分更新する（§2.4）。全文upsertでも更新される。
2. すべての文書を取得し、処理する（全件更新。§3.2）。取得できない文書は、リトライしてもだめならスキップして次の文書へ進む（§3.1）。
3. Indexerが本文を抽出・正規化し、Store層と検索インデックスに登録する。登録が成功してから、処理済みの印（`content_hash`など）を確定する。途中で失敗した文書は、リトライしてもだめならスキップし、次回のクロールで再処理される。
4. 要約生成が有効なら、要約を非同期に生成し、Store層に保存したうえで、本文が変わっていないときだけ検索インデックスに反映する（§2.4、§3.8、§8）。

**Indexerの登録処理**（v0.4 4.2のうち登録に関する部分）：

- 文書形式に応じてテキストを抽出し、正規化する。MVPの対応形式はtxt・Markdown・HTML・PDF。Office文書は次版。文字コードは自動判定し、UTF-8のほかShift_JIS/CP932にも対応する。抽出ライブラリと文字コード判定の方法は未決定（v0.4 9.2 #10。§12.1）。
- 抽出済みテキストをStore層に保存する。原本は保存せず、元システムを参照する。
- 検索インデックスへの登録・更新・削除を行う。書き込みの種類ごとの競合の扱いは§2.4に定める。
- 抽出に失敗した文書は、タイトルとメタデータだけを登録し、抽出失敗として扱う（状態値は§2.1）。Admin Viewに表示する。本文がサイズ上限を超える場合は、上限までを索引化して`truncated=true`にする。
- Embeddingの生成は、ベクトル検索と同じ将来拡張とし、MVPでは行わない（プロダクトデザイン v0.8 §1.5、§8.4）。
- 検索インデックスへの登録に失敗した場合は、§3.1のリトライ設定の回数だけリトライし、それでも失敗したら、その文書をスキップして個別文書の失敗として記録する。クロールは部分成功になるが、削除は行う（§3.3）。ジョブ全体の失敗は、列挙の失敗とOpenSearch全体の異常（判定基準は§3.1）などに限る。

**削除**（v0.4 5.2）：

1. 列挙クロールが最後まで完了し、全体異常（`failed`。§3.3）でないときだけ（読めない文書のスキップがあってもよい）、同じ`source_id`のうち`last_seen_at + TTL < 現在時刻`の文書を削除の対象にする（§3.3）。
2. 削除率が一定を超えるときは、削除を保留して管理者の承認を待つ（§3.5）。保留はAdmin Viewに表示する（通知を兼ねる。メールなどの通知はMVPでは実装しない）。
3. 削除は、**Store層、検索インデックスの順**に行う。途中で止まっても、検索インデックスに残る文書は次回の削除で再度対象になる。Store層と検索インデックスの食い違いは、突合ジョブで検出する。検索インデックスにだけある文書は削除し、Store層にだけある文書は、MVPでは自動削除せず、Admin Viewでの確認と安全な再登録にとどめる（§3.6）。

### 3.1 発見と取得、リトライとスキップ

v0.4 付録D.1、プロダクトデザイン v0.8 の「読めない文書はスキップする」方針。MVPのクロールは、列挙した文書をすべて取得・抽出し、全文upsertする。

**発見と取得の分離**：列挙で文書が見つかった時点で、その文書の`last_seen_at`を部分更新する（§2.4。文書が検索インデックスになければ何もしない）。その後の取得・抽出・登録が失敗しても、`last_seen_at`は更新済みのままである。取得の失敗が「見つからなかった」と区別され、読めない文書がTTLで誤削除されない。取得に失敗した新規文書は登録されず、次回のクロールで再度試みる。部分更新は、見つかったすべての文書に行う（§2.4）。書き込み量の増加は§10.3に記す。部分更新が失敗したとき（OpenSearchへの書き込み不可など）は、その文書をスキップとして扱わず、ジョブを`failed`にして削除しない。部分更新の失敗を放置すると、読めない文書の`last_seen_at`が更新されずに誤削除されうるためである。

**リトライとスキップ**：文書の取得（権限エラー、一時的な読み取りエラーなど）と、検索インデックス・Store層への登録が失敗したときは、次の設定でリトライする。

| 設定 | 既定値（案） | 内容 |
| --- | --- | --- |
| 最大試行回数 | 3回（最初の1回 + リトライ2回） | 文書ごと・処理段階ごと（取得、登録）に数える。権限エラーなど再試行しても直らないエラーも区別せず、同じ回数を試す（実装を単純にするため） |
| バックオフ | 初回1秒、2倍ずつ、上限30秒、ジッタあり | 指数バックオフ |

設定はグローバルな既定値とデータソースごとの上書きができる。値は案で、実装時に調整する（§12.2）。上限回数まで失敗した文書は**スキップ**する。

- スキップした文書は、その文書の処理だけを終えて次の文書へ進む。クロール全体の継続、他の文書の登録、他の文書の削除判定に影響させない。
- 抽出の失敗は、スキップではなく従来どおり`extract_failed`として、タイトルとメタデータを登録する（§3.2。リトライはしない）。
- **全体異常とスキップの判定基準**（登録・部分更新の失敗時）：次はOpenSearch全体の異常とみなし、スキップせずジョブを`failed`にする：接続エラー、タイムアウト、HTTP 429、5xx、`cluster_block_exception`、circuit breaker（`circuit_breaking_exception`）。リトライ設定の回数まで試しても直らなければ`failed`とする。文書固有の4xxの拒否（マッピング違反、文書の内容に起因する拒否など）だけをスキップにする。文書固有の4xxのスキップが連続して20件（案。設定可能）に達したら、設定や状態の異常の疑いとして`failed`にする。
- **列挙中のエラー**：ディレクトリにアクセスできない、列挙の途中で読み取りエラーになるなどは、列挙の失敗として`failed`にする。実装は、列挙時のエラーを握りつぶさない（例：Pythonの`os.walk`は既定でエラーを無視するので、`onerror`でエラーを検出して列挙を失敗させる）。一部のディレクトリを列挙できないまま完了扱いにすると、そこにある文書が「見つからなかった」ことになり、誤削除につながるためである（§3.4）。
- スキップした文書は、次回のクロールで通常どおり再処理される。成功すれば、スキップ記録を削除する。

**スキップ記録**：スキップした文書は、`loreley-jobs`に記録する（Store層の文書がない新規の文書も記録できるよう、`loreley-texts`ではなくここに置く）。ID：`skip-{source_id}-{document_id}`。

| 項目 | 内容 |
| --- | --- |
| `source_id` / `document_id` / `external_id` | 対象の識別 |
| `stage` | 失敗した段階（`fetch` / `index`） |
| `reason` | エラーの種類（権限、読み取り、登録拒否など）と短いメッセージ。本文や秘密情報は含めない |
| `attempts` | 直近のクロールでの試行回数 |
| `consecutive_skips` | 連続してスキップされたクロール数。成功時に記録ごと削除する |
| `first_skipped_at` / `last_skipped_at` | 最初・直近にスキップした日時 |
| `last_job_id` | 直近にスキップしたクロールのジョブID |

記録は、(a)同じ文書が後のクロールで成功したとき、(b)文書が削除されたとき、(c)データソースが削除されたとき、(d)次回以降の列挙クロールで、その文書が列挙で見つからなかったときに消す（(d)がないと、削除された元ファイルの記録がAdmin Viewに残り続ける）。ジョブの結果には`skipped_count`（スキップ件数）を別に持たせる。

**Admin Viewの表示項目**：クロール結果にスキップ件数を表示し、データソースごとに「スキップした文書」の一覧を出す。一覧の項目は、`external_id`（パス）、`stage`、`reason`、`attempts`、`consecutive_skips`、`first_skipped_at`/`last_skipped_at`、既存文書か新規文書か（既存なら古い内容のまま検索に残る）、直近のジョブへのリンクとする。管理者は、アクセス権の修正や除外条件への追加で原因を解消し、再実行する。

**削除との関係**：スキップがあっても、列挙が最後まで完了していれば削除は行う（§3.3）。スキップした文書は`last_seen_at`が更新されているので、削除対象にならない。

### 3.2 全件更新（差分検知はMVP対象外）

v0.4 付録D.2。MVPでは、`mtime`・`size`・`extractor_version`によるスキップ判定をしない。毎回、次の順で全文書を処理する。

1. Connectorが文書を列挙する。
2. 各文書の原本を取得し、`content_hash`を計算する。取得に失敗した文書は、§3.1のリトライとスキップに従う。
3. 抽出・正規化する。取得した`content_hash`が、Store層の確定済みの`content_hash`と**同じ**なら、`pending_index`に遷移せず、全文upsert（`last_seen_at`の更新を含む。要約は引き継ぐ）だけを行う（抽出ロジックを変えた場合に備え、Store層の`text`も抽出し直した内容で更新する）。**変わった（または新規の）場合のみ**、Store層に`text`・`pending_content_hash`・`index_status=pending_index`を書いてから、全文upsertする。これは差分検知ではなく書き込み状態の判定である。変更のない文書で`pending_since`や`index_status`が毎回変わり、§3.6の警告や§5.4の応答が不安定になるのを防ぐ。
4. 全文upsertに成功したら、**最後に**Store層の`content_hash`・`index_status`などを確定し、`pending_index`を解消する。途中で失敗すると確定されないので、次回のクロールで再処理される。
5. 本文が前回と同じ（`content_hash`が同じ）なら、要約を引き継ぐ。違うなら、要約を引き継がず`summary_status=pending`に戻す（§8.5）。

抽出に失敗した文書（`extract_failed`）も、毎回再試行する。回数の上限で止める処理はMVPにはない。そのため、`extract_failed`・`pending_index`の文書は特別な扱いなしに、次のクロールで再処理される。抽出ロジックを変えたときも、次の全件更新で反映される。

**制限**：変更のない文書も毎回処理するため、クロールの時間と書き込みの負荷は文書数に比例する（§10.3）。

### 3.3 クロールの完了状態・異常系

v0.4 付録D.3。

| 状態 | 条件 | 削除 |
| --- | --- | --- |
| 正常完了（`succeeded`） | 列挙が最後まで完了し、スキップした文書がない（抽出失敗は、スキップに含めない）。列挙が0件の場合は、§3.4の条件を満たす | 行う |
| 部分成功（`partially_succeeded`） | 列挙は最後まで完了したが、リトライしてもだめでスキップした文書がある（`skipped_count`が1以上） | **行う**（スキップ以外の文書は通常どおり判定する。スキップした文書は`last_seen_at`が更新済みなので対象にならない） |
| 失敗（`failed`） | 列挙が途中で止まった（アクセスできないディレクトリなど、列挙中のエラーを含む。§3.1）、0件列挙が異常と判定された、OpenSearch全体の異常（判定基準は§3.1）、`last_seen_at`の部分更新の失敗、またはマウント外れなどの全体の異常 | 行わない |
| 取り消し（`cancelled`） | 管理者が実行を取り消した | 行わない |

部分成功のクロールの結果は、Admin Viewにスキップした文書の一覧（§3.1）とあわせて表示する。

**読めない文書**：権限エラーなどで読めない文書があっても、その文書をスキップするだけで、他の文書の処理と削除は止まらない。v0.1にあった「失敗が続く文書があると削除が止まり続ける」制限は廃止した。管理者はAdmin Viewでスキップした文書を確認し、アクセス権の修正や除外条件への追加など、原因を解消して再実行する。

### 3.4 期限による削除

v0.4 付録D.4。

- 削除の対象は、**列挙が最後まで完了したクロール**（`succeeded`、またはスキップのみの`partially_succeeded`）で、同じ`source_id`のうち`last_seen_at + TTL < 現在時刻`の文書である。差分だけを取るクロール（将来のConnector）では削除しない。列挙の失敗、0件列挙、マウント外れなど、クロール全体の異常では削除しない（`failed`）。
- TTLはデータソースごとに指定し、クロールの間隔より長くする。例：日次クロールでTTLが3日なら、3回続けて見つからなかった文書を削除する。
- **0件列挙は異常扱い**：データソースに既存の文書があるのに列挙が0件のとき（マウント外れ、共有の切断など）は、`failed`（理由：空の列挙）にして、削除しない。「既存の文書がある」の判定元は検索インデックスである（当該`source_id`の件数。リフレッシュ後に数える）。
- **実際に全ファイルを消した場合**：0件列挙の`failed`は、Admin Viewに「全件削除の確認待ち」として表示する。承認すると、再度列挙し、なお0件のときだけ、そのデータソースの全文書を削除する（Store層、検索インデックスの順）。却下すると削除しない。
- **0件保護の限界**：0件列挙の保護は、データソース全体が0件のときだけ働く。一部のディレクトリだけがマウント外れなどで消えた場合は防げない。その場合は、削除率のしきい値（§3.5）による保留に頼る。しきい値以下の少数の消失は、通常の削除として扱われる。MVPではこれを制限事項とし、これ以上は作り込まない。
- **二重防御**：削除の対象を決めるとき、今回のジョブのスキップ記録（`last_job_id`が今回のジョブID）の`document_id`を、明示的に削除対象から除外する。`last_seen_at`の更新が万一漏れていても、スキップした文書は消さない。
- 削除対象は検索で抽出するため、抽出前にリフレッシュする。削除は、Store層、検索インデックスの順に行う（上記「削除」の手順3）。
- データソースから消えた文書は、削除されるまで検索結果に残る。検索時に`last_seen_at`で除外はしない。クロールが失敗し続けると、全文書が検索から消えてしまうためである。

### 3.5 削除の保留

v0.4 付録D.5。

- **判定**：削除対象の件数が、削除前の同じ`source_id`の登録文書数（分母）に対して、しきい値（例：20%）を超えるときは、削除を保留する。ただし削除対象の件数が最小件数（例：10件）以下なら、率に関わらず保留しない（少数のソースで1件の削除が高い率になるため）。しきい値と最小件数は、データソースの設定にする。
- **保存先**：保留は`loreley-jobs`に記録する（`source_id`、クロールのジョブID、対象件数、分母、状態：`pending`/`approved`/`rejected`/`superseded`）。
- **保留中のクロール**：保留中のデータソースでも、次のクロールは実行できる。保留中に新しいクロールが完了（`succeeded`または`partially_succeeded`）したら、古い保留は`superseded`にして、新しく判定し直す。
- **承認時**：Admin Viewで承認すると、承認時点で`last_seen_at + TTL < 現在時刻`を満たす文書を検索し直して削除する。承認時に対象件数が保留時より増えているときは、再度保留にする。却下すると削除しない（`rejected`）。
- **古い承認操作との競合**：承認・却下の操作は、画面を開いた時点の保留レコード（ID）を指定する。保留の状態が`pending`のままのときだけ受け付け（条件付き更新）、すでに`superseded`・`approved`・`rejected`になっていれば拒否して、最新の保留を表示し直す。新しいクロールの結果を、古い承認で削除してしまうことを防ぐ。詳細は実装時に決める（v0.4 9.2 #13。§12.2）。
- しきい値、削除保留の最小件数の既定値は未決定（v0.4 9.2 #4。§12.1）。

### 3.6 突合ジョブ

v0.4 付録D.6。検索インデックスとStore層の食い違いを検出し、安全な範囲で直す。Admin Viewから手動で実行する。定期実行は将来（v0.4 9.2 #18。§12.2）。MVPでは、**検出と安全な再登録まで**にとどめる。

**比較する項目**：同じ`document_id`の存在確認に加え、`content_hash`と`index_status`は、次の2つに限って比べる。(1)`pending_index`が`pending_since`から一定期間続いているもの、(2)Store層の`index_status`が`extract_failed`で、検索インデックスの写しが`indexed`である食い違い。更新の途中で通常起きる短時間の不一致は、誤検出しない（検出対象にしない）。

| 食い違い | 対応 |
| --- | --- |
| 検索インデックスにあってStore層にない文書（削除が途中で止まった場合に発生しうる） | 検索インデックスから削除する（Store層が正のため） |
| 同じ`document_id`が両方にあり、上の限定した条件に当てはまる`content_hash`・`index_status`の不一致 | 検出して、Admin Viewに表示する。元ファイルが存在するなら、再索引化（Store層の確定済みの本文からの再登録、または次のクロールでの再処理）を試みる |
| Store層にあって検索インデックスにない文書（`index_status=pending_index`。登録の失敗で発生する） | 次の項目の方針に従う |

**`pending_index`の文書の扱い**：`pending_since`（`pending_index`になった日時。登録に成功して解消するまで更新しない）は、**削除条件にしない**。期限を過ぎたことだけを理由に消すと、一時的な障害で登録できなかっただけの実在文書を誤って消すためである。`pending_since`は異常検知にだけ使う。

| 状況 | 対応 |
| --- | --- |
| `pending_index`が続いている | Admin Viewで警告する（`pending_since`からの経過期間を表示） |
| 元ファイルが存在する | 再索引化を試みる（次のクロールで再処理される。突合ジョブからの手動の再登録も可） |
| 列挙が正常に完了し、元ファイルの不存在を確認できた | 削除候補とする。MVPでは自動削除せず、Admin Viewで確認して手動で削除する（将来の方式は未決定。v0.4 9.2 #17。§12.2） |
| 元ファイルの存在を確認できない（取得エラー、マウント外れなど） | 自動削除しない |

MVPでは、**Store層にだけ存在する文書の自動削除は行わない**。検出、Admin Viewの表示、手動確認（安全な再登録を含む）にとどめる。スキップが続く文書（§3.1）も、Admin Viewで確認して手動で扱う。`pending_index`を警告するまでの期間は未決定（v0.4 9.2 #4。§12.1）。

### 3.7 将来拡張：差分検知と関連機能

v0.4 付録D.7。MVPの全件更新（§3.2）の負荷が問題になったときに導入する設計である。v0.4のレビューで決めた内容を、そのまま残している。これを導入する場合は、あわせて`extractor_version`・`extract_fail_count`（§1.3の予約項目）を使う。`last_seen_at`の部分更新と、読めない文書のスキップ（§3.1）はMVPで導入済みである。導入の条件は未決定（v0.4 9.2 #9。§12.1）。

以下の「旧D.2」「旧B.4」などは、v0.3での節の位置を指す。

**差分検知（旧D.2）**

列挙のたびに、文書ごとに次の順で判定する。

1. **スキップ条件**：次のすべてを満たすときだけ、取得も`content_hash`の計算も省略する（Connectorが列挙時に取得した`mtime`・`size`とStore層の値を比べる。`source_mtime`・`source_size`は列挙時の値、`stored_mtime`・`stored_size`はStore層に保存した`source_updated_at`・`size`に対応する）。

   ```text
   can_skip = (index_status == "indexed"
               or (index_status == "extract_failed"
                   and extract_fail_count >= 上限))
              and source_mtime == stored_mtime
              and source_size == stored_size
              and extractor_version == current_extractor_version
   ```

   `pending_index`の文書、および失敗回数が上限未満の`extract_failed`の文書は、`mtime`・`size`が一致していても**スキップしない**（処理が完了していないため）。上限に達した`extract_failed`は、`mtime`・`size`・`extractor_version`が変わらない限りスキップする（停止中）。
2. スキップしない場合は原本を取得して`content_hash`を計算する。確定済みの`content_hash`と同じで、かつ`extractor_version`も現在と同じで、かつ`index_status=indexed`なら、本文の再処理は省略し、`mtime`/`size`だけを更新する。
3. `content_hash`が違えば、再抽出して全文upsertする。
4. `extractor_version`（抽出ロジックとライブラリのバージョン）が変わった場合は、**`content_hash`が同じでも再抽出する**。`extractor_version`の変更は、ステップ2の`content_hash`の一致より優先する。全件を一度に再処理しないよう、クロールの中で順次処理する。
5. 検索インデックスへの登録に成功してから、**最後に**Store層の`content_hash`・`mtime`・`size`・`extractor_version`をまとめて確定する（`extract_failed`で終わった場合も、`mtime`・`size`・`extractor_version`は確定する。上限到達後のスキップ判定に使うため）。途中で失敗すると確定されないので、次回のクロールで再処理される。登録前の間は`pending_content_hash`と`index_status=pending_index`を持つ。本文を更新した文書は、要約を引き継がず`summary_status=pending`に戻す。

`mtime`と`size`が同じまま内容だけが変わると見逃す。これは既知の限界で、MVPでは許容する。

**抽出失敗の再試行**：`extract_failed`の文書は、連続して失敗した回数（`extract_fail_count`）が上限（例：3回）に達するまで、次のクロールで再処理する（上記のとおりスキップしない）。上限に達したあとは、**`mtime`・`size`・`extractor_version`のいずれかが変わるか、管理者が手動で再試行するまで**、自動では再処理しない。`content_hash`は、`mtime`・`size`が変わって取得し直したあとに、再抽出が必要かを判定するために使うもので、停止の解除条件そのものではない。`extract_fail_count`は、解除条件を満たして再処理を始める時点で0に戻す。上限到達後の文書は、スキップされるのではなく「停止中」としてAdmin Viewに表示する。

**発見と取得の分離（旧D.1）、`last_seen_at`の部分更新（旧B.4）**

MVPに取り込み済み（§3.1、§2.4）。差分検知を導入して、スキップ条件に一致する文書の取得を省くときも、列挙時の`last_seen_at`の部分更新は引き続き必須である（取得しない文書が、TTLで削除されないようにするため）。

**間引き（任意）**：§2.4の部分更新の書き込み量を減らすため、現在の`last_seen_at`がTTLの1/3より新しければ更新しない。判定に必要な現在の`last_seen_at`は、検索インデックスから読む（スクリプト内の比較、または一括取得）。間引くと、判定上のTTLは最大でTTLの1/3だけ短くなる（実効TTLは最短でTTL×2/3）。そのため、TTL×2/3がクロール間隔より長くなるように設定する。

**恒久失敗（旧D.3）**

v0.1では、同じ文書の取得・登録の連続失敗回数（`fetch_fail_count`）が上限に達したら「恒久失敗」として部分成功の判定から除外する設計だった。MVPでは、読めない文書をスキップしても削除が止まらない（§3.1、§3.3）ため、この判定は不要になり、`fetch_fail_count`は廃止した。連続失敗の回数は、スキップ記録の`consecutive_skips`が持つ（新規文書も記録できる）。

将来、差分検知の導入時に、長く読めない文書のリトライ負荷を下げたい場合は、`consecutive_skips`が上限を超えた文書の試行回数を減らす（例：リトライなしの1回だけ試す）拡張を検討する。導入の条件は未決定。

### 3.8 Store層と検索インデックスの整合性・排他

v0.4 付録C.3。

- OpenSearchの検索はリフレッシュ後にしか反映されない（ニアリアルタイム）。状態の確認や排他の判定には、検索ではなくIDによる取得（リアルタイム）を使う。
- 条件付き更新には`if_seq_no`/`if_primary_term`を使う。要約をStore層へ保存するときは、読み出した文書の現在の本文のハッシュ（確定前は`pending_content_hash`、確定後は`content_hash`）が生成元と一致し、かつ`if_seq_no`/`if_primary_term`が一致するときだけ書く。本文が変わるとき（`content_hash`が既存と違うとき）は、Store層の要約を消して`summary_status`を`pending`（要約が無効なら`disabled`）に戻す。
- 初回の作成は、存在しない場合だけ成功する作成（create）を使う。
- Store層と検索インデックスは別のインデックスであり、またがるトランザクションはない。更新の途中では、両者の内容（本文の`content_hash`や`index_status`）が一時的に食い違う。MVPでは短時間の不一致を許容し、検出と復旧は突合ジョブ（§3.6）、読み出し時の扱いは`get_document`（§5.4）に定める。
- ノードが1つなので、データの消失に備えてスナップショットを取る（§9）。

## 4. ジョブ管理

> プロダクトデザイン上の位置づけ：クロール・インデックス・要約生成はジョブとして管理する。MVPは単一Worker・直列実行を基本とし、これ以上の異常系は作り込まない（プロダクトデザイン v0.8 参照）。

### 4.1 状態遷移と基本方針

v0.4 付録E.1、4.7。状態は、実行待ち・実行中・成功・一部成功・失敗・取り消しの6つ。

`queued` → `running` → `succeeded` / `partially_succeeded`（スキップした文書がある。削除は行う）/ `failed` / `cancelled`。

- ジョブの状態はStore層（`loreley-jobs`）に保存する。
- 同じデータソースのクロールは同時に1つだけ実行する。止まったジョブは`failed`として検知する。再実行は、Worker再起動または管理者のロック解放のあとに行う（§4.3）。
- 一時的なエラーは、§3.1のリトライ設定（既定は最大3回試行、指数バックオフ）に従ってリトライする。文書単位の失敗は、リトライしてもだめならその文書をスキップする。ジョブ全体の失敗（OpenSearchへの接続不可など）は、ジョブを`failed`にする。失敗したジョブは、Admin Viewから再実行できる。
- 文書ごとの処理状態（`index_status` / `summary_status`）はジョブとは別に保持する（§2.1）。

### 4.2 排他とリース

v0.4 付録E.2。

- ジョブには、`owner`（実行しているワーカー）、`heartbeat_at`、`lease_expires_at`を持たせる。
- `queued`から`running`への遷移は、`if_seq_no`/`if_primary_term`を使った条件付き更新で行う。成功したワーカーだけがジョブを取得する。
- データソースごとの実行ロックは、`loreley-jobs`のロック用文書（ID：`lock-{source_id}`）で表す。存在しない場合だけ成功する作成（create）でのみ取得する。リース期限切れのロックの引き継ぎは、Worker再起動時と管理者の解放に限る（§4.3）。
- **MVPは単一Worker・直列実行を基本とする**。複数のWorkerを同時に動かす構成はMVPでは対象にしない。

### 4.3 ハートビート・リース切れ・Worker引き継ぎ

- 実行中のワーカーは、リース期間（例：5分）の1/3程度の間隔でハートビートを送り、`lease_expires_at`を延長する。
- `lease_expires_at`を過ぎた`running`のジョブは、`failed`として表示する。ただし、**リース期限切れだけでは、別のWorkerが自動でロックを引き継がない**（前のWorkerが停止したのか、遅いだけなのかを区別できないため）。
- 引き継ぎは次の場合に限る。(1)単一Workerの再起動時（前のインスタンスは停止済みとみなし、自分のものだった期限切れのロックを引き継ぐ）、(2)管理者がAdmin Viewでロックを解放したとき。ロックが保持されている間は、そのソースのジョブを再実行できない。
- 前Workerの停止を確認する方法は実装時に決める（v0.4 9.2 #14。§12.2）。再起動時の引き継ぎは、再起動前後で同じ安定したWorker IDを使うことが前提である（v0.4 9.2 #14）。
- リース期間の既定値は未決定（v0.4 9.2 #4。§12.1）。

### 4.4 要約生成ジョブ

要約生成のジョブも同様にリースを持つ。MVPは単一Worker・直列実行なので、要約の生成と書き込みは同じソースのクロールと直列に処理し、クロールの実行中には書き込まない。要約の書き込み（Store層・検索インデックス）の前には、フェンシングと同様に、対象ソースの実行ロックがメンテナンス（再インデックス）のために保持されていないか、またはメンテナンスフラグが立っていないかを確認し、立っていれば書き込まずに止まる（§2.5）。

### 4.5 リース切れ後の旧ワーカー対策（フェンシング）

検索インデックスやStore層への書き込みの前、および削除の前に、ロック文書をIDで取得し、自分が所有していて期限内であることを確認する。確認できなければ（期限内でなければ）書き込みを中止する。再開はWorkerの再起動か管理者の操作で行う。確認と書き込みの間にはわずかな窓が残るが、`last_seen_at`は全文upsertでも古い値で上書きしない（§2.4）。

### 4.6 ロックの解放

ジョブが`succeeded` / `partially_succeeded` / `failed` / `cancelled`になったとき、所有者が自分のロック文書を条件付きで削除する。ワーカーが落ちた場合は、期限切れだけでは別のワーカーは取得できない。Worker再起動時の引き継ぎか、管理者のAdmin Viewからの解放を待つ。

### 4.7 将来拡張：複数Worker化

完全な分散フェンシングは、MVPでは行わない。複数Workerにするときに、ロックの取得ごとに増える実行世代番号を持たせ、全文upsertを含むすべての書き込みで古い世代の上書きを原子的に拒否する方式を導入する。

## 5. Search API・MCP・文書取得

> プロダクトデザイン上の位置づけ：検索機能はSearch APIとMCPで提供する。MCPはSearch APIを公開するアダプタで、独自の検索ロジックは持たない。認証・認可はMVPでは実装しない（プロダクトデザイン v0.8 参照）。

※エンドポイントとリクエスト形式は実装時に確定する。以下は要点である。

### 5.1 Search API

v0.4 4.4、付録F.1。OpenSearchを使った共通の検索・文書取得インターフェースを提供する。MCP ServerとWeb UIは、原則としてこのAPI（または同じサービス層）を使う。

- ドキュメント検索：クエリ、データソース・文書形式・更新日による絞り込み、件数。
- ドキュメント取得：本文はStore層の抽出済みテキストから返す。AgentやUIを圧迫しないよう、文字オフセットと最大長で範囲を指定して取得できる。
- 検索結果の整形：タイトル、要約、関連箇所、出典、スコア。
- 認証・認可は将来拡張（MVPでは実装しない）。将来は、Search API内で認証・アクセス制御を適用する（§6.6）。

エンドポイントの例：

```text
GET /api/documents/search?q=...&source_ids=...&mime_types=...&updated_after=...&updated_before=...&limit=...
GET /api/documents/{document_id}?offset=...&max_length=...
GET /api/sources
```

検索・取得の流れ（v0.4 5.3）：

1. AgentはMCP Serverを通じて、利用者はWeb UIを通じて検索する。
2. Search APIがOpenSearchを検索する（将来は認証・アクセス制御もここで適用する）。
3. タイトル・要約・関連箇所・文書ID・出典を返す。
4. Agentは必要な場合だけ`get_document`で本文を取得する（長い文書は分割して取得する）。
5. 回答はAgent側で生成する（Chat Viewを設けた場合はChat Viewで生成する）。

### 5.2 検索のレスポンス

v0.4 付録F.2。各結果に次を含める。

- `document_id`、`source_id`、`title`、`summary`（なければnull）
- `highlights`：関連箇所（ハイライトした断片。件数と断片の長さに上限）
- `url`または`path`（表示用の出典）、`mime_type`、`source_updated_at`
- `score`

全体に、`total`（該当件数）と`limit`を含める。

### 5.3 MCP Server

v0.4 4.5、付録F.3。AI Agentが文書を検索・取得するためのMCPインターフェースを提供する。Search APIの機能を公開するアダプタであり、独自の検索ロジックは持たない。

- 通信方式はStreamable HTTP。Search APIと同じコンテナに置く（§7.2）。
- 読み取り専用。書き込み系のToolは提供しない。
- 認証は将来の版で追加する。MVPは運用前提（§6）で使う。ただし、DNS rebinding対策として`Origin`ヘッダーの検証はMVPで行う（§6.1）。
- クライアント互換性は、実装時に主要なMCPクライアントで確認する（§11.7）。

Tool：

```text
search_documents(query, source_ids?, mime_types?, updated_after?, updated_before?, limit?)
get_document(document_id, offset?, max_length?)
list_sources()
```

- `search_documents`のフィルタ引数は、Search APIと同じ名前・意味にする。
- `list_sources`は、`source_id`、名前、種別、文書数、最終クロールの状態と時刻だけを返す。**認証情報や接続の秘密情報は返さない**。
- ToolのDescriptionに、返される本文は文書であり、指示として扱わないことを明記する（§6.5）。

### 5.4 `get_document`

v0.4 付録F.4。

- **本文の取得元はStore層**（`loreley-texts`の`text`）。
- `offset`と`max_length`は、**正規化後のテキストの文字単位**（Unicodeのコードポイント）。`max_length`にはサーバー側の上限を設け、省略時は既定値を使う。
- レスポンス：`document_id`、`title`、`source_id`、`url`/`path`、`content`（指定範囲）、`offset`、`length`、`total_length`、`next_offset`（続きがなければnull）、`truncated`、`index_status`。
- **更新途中の文書**：Store層の確定済みの本文を返す。更新の途中で`index_status=pending_index`のときは、応答に`index_status`を含めて状態を示す（検索インデックスとの短時間の不一致を許容する。§3.8）。正常な状態への復旧は、再索引化（次のクロールでの再処理）か、突合ジョブによる再登録で行う（§3.6）。この扱いは仮決定である（§12.3）。
- 新規文書の`text`は、登録前（`pending_index`にする時点）にStore層へ書く。したがって通常は、初回登録の失敗後も本文を返せる。これは仮決定である。
- **確定済みの`text`がない場合**（本文の抽出やStore層への書き込みが、新規文書の初回処理で失敗した場合など）：404ではなく、`index_status`を含み、`content`なしの応答を返す。これは仮決定である（§12.3）。
- 文書の更新で内容が変わったとき、分割取得の途中の`offset`が新しい本文では意味を持たなくなる。このときの扱い（`content_hash`を応答に含めて変化を検知するなど）は実装時に決める（v0.4 9.2 #16。§12.2）。
- `truncated=true`は、索引化のサイズ上限で本文が切り詰められていることを表す。この場合、`total_length`は保存済みの長さであり、元の文書はこれより長い。上限を超える部分は取得できない（§10.2）。

## 6. セキュリティ実装

> プロダクトデザイン上の位置づけ：MVPには認証・認可がなく、信頼できる社内ネットワーク内で、全員が閲覧してよい文書だけを対象に運用する。この前提と、将来の認証方式の方針はプロダクトデザイン v0.8 に残る。ここでは、その前提を支える実装上の措置を定める。

### 6.1 MCPのOrigin検証

v0.4 6.1。MCPのStreamable HTTP仕様は、DNS rebinding対策としてサーバーにOriginヘッダーの検証を求めている。MVPのMCPエンドポイントは、`Origin`ヘッダーがあり、許可リストにないリクエストを拒否する（HTTP 403）。

- `Origin`ヘッダーのないリクエスト（ブラウザ以外のMCPクライアント）は拒否しない。
- **認証とOrigin検証は別の問題**であり、Origin検証を入れても認証は実装しない（このため、到達できる人は誰でも検索できる前提は変わらない）。
- 設定名、許可リストの書式、ポート指定の扱いは実装時に決める（v0.4 9.2 #15。§12.2）。

### 6.2 許可リスト

v0.4 6.1。許可するOriginは環境変数または設定ファイルで指定する（例：`MCP_ALLOWED_ORIGINS`にカンマ区切りで列挙。名称は例）。

- 既定はlocalhost系（`http://localhost:*`、`http://127.0.0.1:*`）のみ。
- 社内ネットワークへ公開するときは、公開先のOriginを追加する。

### 6.3 バインド先とポート制限

- 既定ではlocalhostだけで待ち受ける。社内ネットワークへ公開するには、バインド先を設定で明示的に変更する。この前提はREADMEと導入手順で明示する。
- **OpenSearchの保護**：OpenSearchとDashboardsのポートはホストの外に公開しない。Search APIだけを公開の窓口にする（§7.3）。

### 6.4 読み取り専用マウント・秘密情報の管理

**読み取り専用マウント（実行環境側の境界）**（v0.4 6.1）：Admin Viewは認証を省く代わりに、読み込めるディレクトリをComposeのマウントで限定する。検索対象のディレクトリは**読み取り専用（`:ro`）**でマウントし、それ以外のホストのパスはコンテナに見せない。Admin Viewは認証なしで任意のローカルパスを登録できるが、コンテナにマウントしたディレクトリ以外は読めない。将来の版で、登録できるルートパスの制限と管理者トークンを追加する。

**秘密情報の管理**（v0.4 6.2、4.8）：

- Connectorの認証情報は、Store層（`loreley-sources`）に平文で保存しない。環境変数や秘密情報ファイルで参照する。設定ファイルにも平文で書かない方法を用意する。
- ログに本文や秘密情報を記録しない。
- `list_sources`は認証情報や接続の秘密情報を返さない（§5.3）。

### 6.5 外部通信・プロンプトインジェクション対策

v0.4 6.2。

- **外部通信**：要約・Embeddingに外部LLMを使う場合は、明示的な設定を必須にする。既定の構成はオフラインで動作する（§8.1）。
- **プロンプトインジェクション**：文書を加工せずに返す。そのうえで、返す内容が「データソースから取得した文書」であることを出典とあわせて明示し、MCPのTool説明で、本文を指示として扱わないようAgentに注意を促す（§5.3）。
- **運用性**：クロール失敗の再実行、同期状態の確認、ログ、ヘルスチェック、バックアップ・リストア手順（§9）を用意する。

### 6.6 将来の認証・認可（実装上の方針）

将来の版で、API/MCPのトークン認証、管理者トークン、登録できるルートパスの制限、データソース単位のアクセス可否、文書単位のACL同期、SSO連携を順に追加する。Search APIとMCPで同じ権限判定を適用する。検索インデックスには、アクセス制御用の`acl`フィールドを予約している（§2.1）。将来の認証方式（トークンの発行・管理方法、データソース単位の権限モデル）は、プロダクトデザイン v0.8 の未決定事項として扱う（v0.4 9.2 #7）。

## 7. コンテナ構成・技術スタック

> プロダクトデザイン上の位置づけ：Docker Composeによるセルフホスト配布を基本とし、外部サービスへの通信を必須としない（プロダクトデザイン v0.8 参照）。

### 7.1 論理構成

v0.4 3章。

```text
[社内ドキュメント / ファイル / Wiki / Git 等]

                    |

        (抽出・正規化・要約生成)
```

## 8. 要約生成

> プロダクトデザイン上の位置づけ：要約は検索用のものである。既定では無効で、LLMを明示的に設定したときだけ有効になる。要約なしでも検索できる（プロダクトデザイン v0.8 参照）。

### 8.1 方針

v0.4 4.2。

- 文書全体の**検索用の要約**を生成する。主題、重要な概念、その文書で答えられる質問を表現する。
- 既定では無効で、LLMを明示的に設定したときだけ有効になる。外部LLMを使う場合は明示的な設定を必須にする（§6.5）。既定の構成はオフラインで動作する。
- Embeddingの生成は、ベクトル検索と同じ将来拡張とし、MVPでは行わない（プロダクトデザイン v0.8 §1.5、§8.4）。

### 8.2 非同期処理

- 要約の失敗・遅延では、要約なしで先に登録し、後から非同期に生成する。
- 要約生成のジョブはリースを持ち、MVPでは同じソースのクロールと直列に処理する。クロールの実行中には書き込まない（§4.4）。
- 要約の書き込みの前に、対象ソースの実行ロックがメンテナンスのために保持されていないか、メンテナンスフラグが立っていないかを確認する（§4.4、§2.5）。

### 8.3 生成状態

- 要約の生成状態とモデル名・バージョンを保持し、後から再生成できるようにする。
- `summary_status`：`disabled`（要約が無効）、`pending`、`generated`、`failed`。`summary_model`にモデル名・バージョンを持つ（§2.1）。

### 8.4 保存先と書き込みの整合

- 要約はStore層にも保存し、再インデックスで失わないようにする。Store層の要約には、生成元の`content_hash`（`summary_content_hash`）を持たせる（§1.3）。
- 要約は、生成の完了後にまずStore層へ保存し、そのうえで検索インデックスへ反映する。
- Store層への保存は、生成元の`content_hash`が、現在の本文のハッシュ（確定前は`pending_content_hash`、確定後は`content_hash`）と一致し、かつ`if_seq_no`/`if_primary_term`が一致するときだけ行う（§3.8）。
- 検索インデックスへの反映は、検索インデックス上の`content_hash`が生成元と一致するときだけ行う。不一致なら捨てる（本文が更新済みで、新しい要約が生成される）。更新の衝突は再試行する（§2.4）。

### 8.5 再生成・本文更新との整合

- 本文が変わるとき（`content_hash`が既存と違うとき）は、Store層の要約を消して`summary_status`を`pending`（要約が無効なら`disabled`）に戻す（§3.8）。検索インデックスの全文upsertでも、`summary`は書かず`summary_status=pending`（無効なら`disabled`）にする（§2.4）。
- 本文が同じ（`content_hash`が同じ）なら、要約を引き継ぐ。MVPは全件更新で毎回すべての文書を処理するため、毎回の要約の再生成を避けるのがこの引き継ぎの目的である（§3.2）。
- Store層からの再構築（§2.5(b)）では、Store層の要約のうち、生成元の`content_hash`が本文と一致するものだけが保持される。不一致は`pending`に戻す。

### 8.6 モデル選定

要約生成に使うモデル、コスト、生成にかかる時間は未決定（v0.4 9.2 #3。§12.1）。要約の品質・コストは、測定して決める（§10.4）。

## 9. バックアップ・リストア

> プロダクトデザイン上の位置づけ：運用性の要件として、バックアップ・リストア手順を用意する。MVPの受け入れ基準に、スナップショットによるバックアップとリストアの手順をREADMEに記載することを含む（プロダクトデザイン v0.8 参照）。

v0.4は、バックアップの対象と再構築の方針を定め、手順の細部は「READMEに記載する」としている。手順の中身（コマンド、保存先、周期）はv0.4に記述がなく、実装時に決める（§12.2への追加項目として扱う）。

### 9.1 バックアップの対象

v0.4 6.2。MVPではStore層もOpenSearchにあるため、**OpenSearchのスナップショットと設定ファイル**をバックアップの対象とする。

### 9.2 スナップショット

v0.4 付録C.3、6.2。ノードが1つなので、データの消失に備えてスナップショットを取る（§3.8）。ノード障害時のデータ消失は、OpenSearchをKVSにすることのリスクである（プロダクトデザイン v0.8 参照）。

### 9.3 リストア手順

OpenSearchのスナップショットによるバックアップとリストアの手順を、READMEに記載する（v0.4 8.2の受け入れ基準）。手順の中身は未決定である。

### 9.4 障害時の再構築

v0.4 6.2、付録B.5。

| 状況 | 対応 |
| --- | --- |
| マッピング・辞書・アナライザを変更する | 新しいインデックスを作り、旧インデックスからコピー（`_reindex`）してエイリアスを切り替える（§2.5(a)）。通常はこちらを使う |
| 旧の検索インデックスを失った（Store層は残っている） | Store層の抽出済みテキストから、検索インデックスを再構築する（§2.5(b)）。このとき`last_seen_at`は再構築時刻に初期化される。要約は、生成元の`content_hash`が本文と一致するものだけが保持される |
| 検索インデックスとStore層の両方を失った | 再クロールが必要である |
| 抽出ロジックを変えた | Store層からの再構築は使わず、全件更新の再クロールで反映する（§3.2） |

検索インデックスは、通常は旧インデックスからのコピーで作り直す。旧インデックスを失った場合に限り、Store層から再構築する。

## 10. 非機能設計

> プロダクトデザイン上の位置づけ：非機能要件（文書数・レイテンシ・同時利用数など）は、設計段階では目標値を置かず、実装後に実測して決める。規模は1万〜10万文書を想定するが、目標値ではない（プロダクトデザイン v0.8 参照）。

### 10.1 想定規模

- 最初のデータソースはローカルディレクトリ／ファイル共有で、規模は1万〜10万文書を想定する（目標値ではない。v0.4 9.1。要確認）。
- 数十万件を超える規模や、高可用構成は対象外である。単一ホスト、単一ノードのOpenSearchを前提とする。

### 10.2 文書サイズ上限

- 文書の最大サイズ（索引化の上限）と、長い文書に対する検索品質は未決定（v0.4 9.2 #2。§12.1）。上限は、リクエストサイズ・インデックスサイズ・処理時間などの観点で決める（§2.3）。
- 本文がサイズ上限を超える場合は、上限までを索引化して`truncated=true`にする（§3、Indexerの登録処理）。Store層の`text`は、サイズ上限で切り詰めた後のテキストである（§1.1）。`get_document`の`total_length`は保存済みの長さで、上限を超える部分は取得できない（§5.4）。
- ハイライトの解析上限（`index.highlight.max_analyzed_offset`）を理由に、本文を切り詰めない（§2.3）。
- オフセット保存（`index_options: offsets`）による索引の増加量と、上限値は実測して決める。
- 長い文書で検索精度に問題が出た場合は、見出し・セクション単位の補助インデックスを追加できる構成にする（§2.3）。

### 10.3 書き込み負荷

- MVPは差分検知をせず、毎回すべての文書を取得・抽出し、全文upsert（`last_seen_at`の更新を含む）する。列挙時の`last_seen_at`の部分更新（§3.1）も加わり、文書ごとの書き込みが増える（全文upsertが成功する文書にも行う。§2.4）。文書数に比例して、クロール時間、OpenSearchの書き込み量とセグメントのマージ負荷、Store層の書き込みが増える。1万〜10万文書の想定でも、クロール間隔内に完了するかは未検証である。
- 緩和策：クロール間隔は所要時間より長く設定する。本文が変わらない文書の要約は引き継ぎ、要約の再生成を避ける（§2.4、§8.5）。負荷が問題になれば、差分検知（§3.7）を導入する。
- `last_seen_at`は検索インデックスの文書に持つため、その書き込み負荷はリスクとして扱う。負荷の実測方針は維持する。
- 全件更新の負荷の実測と、差分検知を導入する条件は未決定（v0.4 9.2 #9。§12.1）。

### 10.4 性能測定

実装時に、次を実測する。

- 代表的な規模で、クロール所要時間と、書き込み量・インデックスの増加を測る（全件更新の負荷。§10.3）。
- オフセット保存による増加量と、本文サイズの上限値を測る（§10.2）。
- 要約モデルの選定のため、生成時間・コストを測る（§8.6）。
- 検索レイテンシ、同時利用数、ホスト要件などの非機能要件は、設計段階では目標値を置かず、実測して決める（v0.4 9.2 #8。§12.1）。
- 検索品質（Recall@10、MRR）は評価セットで測る。これは検索方式の評価であり、プロダクトデザイン v0.8 の評価方法に従う。

### 10.5 リソース要件

ホスト要件（CPU、メモリ、ディスク）は未決定である（v0.4 9.2 #8）。v0.4は数値を置いていない。制約として、次を前提にする。

- 単一ホストにDocker Composeで導入する。外部サービスへの通信を必須としない。
- OpenSearchは単一ノード（`number_of_shards: 1`、`number_of_replicas: 0`）で、ノード障害時のデータ消失に備えてスナップショットを取る（§9）。
- ローカルの要約・Embeddingモデル（`embedding` / `llm`）を使う場合は、別途リソースが必要になる（任意。§7.2）。

## 11. テスト設計

> プロダクトデザイン上の位置づけ：MVPの受け入れ基準（完成の定義）はプロダクトデザイン v0.8 に残る。本章は、その基準を満たすための詳細なテストケースを、異常系、競合、削除保留、リース切れ、再インデックスに分けて定める。

**導出元**：v0.4の8.2（受け入れ基準）と2章（検証項目）に加え、付録B〜Fの仕様から、テストする観点を導いた（導出であり、v0.4に列挙されていたものではない）。ケースの粒度は実装時に調整する。

### 11.1 方針

- 異常系の試験は、MVPで保証する範囲（単一Worker・直列実行、削除の安全性）に限る。これ以上の異常系は作り込まない。
- 排他とリース切れの動作は、実装時に試験する（v0.4の2章の検証項目）。
- 各ケースの根拠として、対応する章を示す。

## 13. 用語

> プロダクトデザイン上の位置づけ：プロダクトデザイン v0.8 §10 の用語集に残らない実装用語を定義する。v0.4 §10 の用語集のうち、v0.8 に残していないものを移した。

| 用語 | 意味 |
| --- | --- |
| `source_id` | データソースの識別子。登録後は変更できない（§1.1、§1.2） |
| `document_id` | 文書の一意なID。`source_id`と`external_id`から決定的に生成する（v0.4 付録A.2。§1.2） |
| `content_hash` | 文書の内容のハッシュ（SHA-256）。要約の書き込みの整合確認と、本文が変わったかの判定に使う（差分検知は将来拡張）（§1.1、§2.4） |
| `last_seen_at` | 列挙クロールで最後に見つかった日時（クロール開始時刻）。検索インデックスの文書に持つ。期限による削除の基準。全文upsertのほか、列挙で見つかった時点の部分更新でも更新する（§1.3、§2.4、§3.4） |
| `crawl_started_at` | クロールの開始時刻。実行コンテキストとしてIndexerに渡し、`last_seen_at`に書く（§1.1） |
| `extractor_version` | 抽出ロジックとライブラリのバージョン。差分検知（将来拡張）で、変わると再抽出の対象にする（v0.4 付録D.7。§3.7） |
| リース | ジョブやロックの所有を、期限付きで主張する仕組み。MVPでは、期限が切れただけでは自動で引き継がない（v0.4 付録E.2。§4.3） |
| スキップ | リトライ設定の回数まで取得・登録に失敗した文書を、その文書だけ処理から外すこと。スキップ記録を`loreley-jobs`に残し、Admin Viewで確認できる。クロール全体と他の文書の削除には影響しない（§3.1） |
| 削除保留 | 削除対象が多いときに、削除を止めて管理者の承認を待つ状態（v0.4 付録D.5。§3.5） |
| 突合ジョブ | 検索インデックスとStore層の食い違いを検出し、安全な範囲で直すジョブ（v0.4 付録D.6。§3.6） |
