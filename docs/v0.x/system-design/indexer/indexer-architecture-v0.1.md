## 1. 位置づけと前提

### 1.1 MVP の前提

- 単一ホスト、単一 Crawler・単一 Indexer・直列実行、認証なし、OpenSearch を Store 層のバックエンドにする(プロダクトデザインで決まった前提)。
- Crawler と Indexer は別コンテナで、メッセージブローカーを介さず HTTP で直接通信する(確定。ユーザー指示)。

### 1.2 本書の範囲

本書が扱うもの: Indexer の責務と境界、登録処理、書き込みの競合制御、整合性、要約生成、フェンシング、Deletion Manager(削除の判断・実行)、突合ジョブ、再インデックス時の停止手順、障害と再起動、将来拡張、バックアップ、非機能(Indexer 関連)、テスト観点。

本書が扱わないもの(境界として必要な箇所だけ触れる):

- **Crawler 領域**: ジョブ、ロック、リース、ハートビート、スキップ記録、リトライ・スキップの判断、クロールの完了状態、登録結果の集計、確認結果の区分(`confirmed` / `unconfirmed` / `unknown`)、ジョブの起動。Crawler 設計書は本作業の対象外。
- Search API・MCP Server、Admin API・Admin View、セキュリティ全般、コンテナ構成。
- Crawler -> Indexer の契約の詳細(`indexer-api-v0.1.md`)、各インデックスのスキーマ(`opensearch/schema/` 配下の3文書)。

### 1.3 用語(Indexer 関連)

| 用語 | 意味 |
| --- | --- |
| `source_id` | データソースの識別子。登録後は変更できない |
| `document_id` | `SHA-256(source_id + "\0" + external_id)` の16進文字列(小文字)。検索インデックスと Store 層の文書 ID(3.2) |
| `content_hash` | 原本の SHA-256 |
| `last_seen_at` | 列挙クロールで最後に見つかった日時(クロール開始時刻)。検索インデックスの文書に持つ。期限による削除の基準。全文 upsert のほか、列挙で見つかった時点の部分更新でも更新する |
| `crawl_started_at` | クロールの開始時刻。実行コンテキストとして Indexer に渡し、`last_seen_at` に書く |
| `extractor_version` | 抽出ロジックとライブラリのバージョン。MVP では使わない予約項目(13.1) |
| Indexer | 文書の登録・更新・削除を担当するサービス(別コンテナ)。抽出・正規化、検索インデックス・`loreley-texts`・`loreley-deletions` への書き込み、要約生成、削除の判断と実行(Deletion Manager)を担う。これらへの書き込みの唯一の役割 |
| Deletion Manager | Indexer の内部モジュール(独立コンテナではない)。開始・終了通知の受理、世代の管理、同じソースの削除の直列化、件数照合、削除対象の決定、割合ルール、削除の実行、`loreley-deletions` への記録を担う |
| `crawl_id` / 世代 | `crawl_id` はクロール1回の識別子で、Crawler のジョブ ID をそのまま使う。世代は、ソースごとに最後に受理した開始通知の `crawl_id`。新しい開始通知は、終了通知が届かなかった旧い世代の結果を `superseded` にする。`superseded` の結果に遅れて届いた終了通知は何もしない(202)。記録済みの終了通知の再送は、世代を見ず冪等。開始通知を受けていない未知の `crawl_id` は、記録せず破棄する |
| 削除の記録 | `loreley-deletions` 内の `deletion-*`(ソースごとの現行世代)と `deletion_result-*`(削除結果)の総称 |
| 削除結果 | クロール1回分の削除の判断・実行の結果。`deletion_result-{crawl_id}` に持つ。状態は `running` / `deleted` / `skipped_by_ratio` / `validation_failed` / `discarded` / `failed`(9.10) |
| 削除の直列化・待機中 | 同じソースの削除は、前の削除が終端状態になるまで、後の削除の判定・実行を始めない。待機中は、終了通知を受理済みで、先行する削除結果が終端状態でないため判定を始めていない削除結果(状態は `running`) |
| 割合ルール | 削除対象÷削除前の登録文書数がしきい値以下なら削除し、超えれば削除しない自動判断。削除対象が最小件数以下なら割合に関わらず削除する。しきい値は 0% 以上 100% 未満で、範囲の検証は Admin API だけが行う。承認はない |
| 強制削除モード | 割合ルールと最小件数ルールだけを無視して削除するモード。手動実行のクロールの起動時にのみ指定でき、削除結果に記録される |
| 突合ジョブ | 検索インデックスと Store 層の食い違いを検出し、安全な範囲で直すジョブ(10章) |
| Status API | Indexer が削除結果を返す読み取りの API(`GET /crawls/{crawl_id}`、案)。Crawler がポーリングして終端状態を確認する。返すのは削除結果のみ(用語集の記述に食い違いあり。19章 X1) |

## 2. 責務と境界

### 2.1 論理構成(Indexer 視点)

```text
Crawler / Connector(別コンテナ。ジョブ・ロックを管理)
        |  HTTP(同期バッチ登録、last_seen_at 部分更新、開始通知・終了通知、Status API)
Indexer(別コンテナ)
 抽出・正規化 / 登録 / 要約生成 / 削除の判断と実行[Deletion Manager]
 検索インデックスと Store 層の書き込み役
        |                        |
 検索インデックス        Store 層(loreley-texts / loreley-deletions(仮名)ほか。バックエンド差し替え可)
        \                        /
                 OpenSearch
```

- Admin API は `loreley-jobs` と `loreley-deletions` を読み取りのみで直接読んで表示する。`api` から `indexer` への通信は置かない(案)。
- 削除の判断と実行は Indexer の内部モジュール Deletion Manager が行い、削除の記録を `loreley-deletions` に持つ。独立したコンテナにはしない(確定)。

### 2.2 責務分担

SD v0.8 の2つの責務表(削除管理の表、コンポーネント間通信の責務表)を1つにまとめた。

| 責務 | 担当 |
| --- | --- |
| ジョブ(状態、起動の受付、直列実行)、ロック、リース、ハートビート | Crawler |
| `loreley-jobs` への書き込み(ジョブ、ロック、スキップ記録、削除結果の要約、確認結果の区分、登録結果) | Crawler(唯一)。Admin API は書かない。例外はメンテナンスフラグ(運用者の手動手順。案) |
| `loreley-deletions` への書き込み(現行世代、削除結果) | Indexer(Deletion Manager。唯一)。Crawler も Admin API も書かない |
| データソースの列挙、原本の取得、定期実行 | Crawler |
| リトライ・スキップの判断 | Crawler。Indexer は文書単位の失敗種別を返す |
| 開始通知・終了通知の送信、Status API のポーリング、結果の要約と確認結果の区分のジョブ記録、Indexer のバッチ応答の集計と登録結果の記録 | Crawler。Crawler は確認結果の区分を残したあとに再確認しない |
| 列挙の完了とスキップの確定 | Crawler |
| 削除の判断(対象の決定、割合ルール、最小件数ルール、全件削除するかの判定)、世代の管理、件数照合、削除の実行、同じソースの削除の直列化 | Indexer(Deletion Manager)。Crawler は検索インデックスを直接読まない |
| 抽出・正規化 | Indexer |
| 検索インデックスと `loreley-texts` への書き込み(全文 upsert、`last_seen_at` の部分更新、削除) | Indexer(唯一)。期限による削除は Deletion Manager が決めた対象だけで、Crawler は要請しない(ソース削除のジョブ(9.14)と突合ジョブ(10章)での削除要請は従来どおり。案) |
| 要約の生成と書き込み | Indexer 内部(Crawler からは呼ばない) |
| 書き込み前のロック所有確認(登録、`last_seen_at` の更新) | Indexer(Crawler が `owner` と `job_id` を渡す) |
| 削除前の確認 | Indexer。終了通知の受理時の世代の判定(記録済みの終了通知の再送は世代を見ず冪等)と、メンテナンスフラグ・自分の削除結果の状態の確認。ロック所有の確認は行わない(8章) |
| 突合ジョブ | 実処理は Indexer。ジョブとしての起動・管理は Crawler(案) |
| ジョブ状態と登録結果の表示 | Admin API。`loreley-jobs` を読み取りのみで直接読む(登録結果と確認結果の区分を含む。Status API は登録結果を返さない) |
| 削除結果の表示 | Admin API。`loreley-deletions` を読み取りのみで直接読む。Admin View は、確認結果の区分(`loreley-jobs`)と `loreley-deletions` の現在値を併記し、「結果未確認」「結果不明」を表示する |
| しきい値の範囲の検証 | Admin API(固定経路。データソースの設定の登録・更新を Crawler に中継する前に検証する)。Crawler と Indexer は検証しない |
| クロールの起動(強制削除モードの指定を含む)、取り消し、ロック解放、突合の起動 | Admin API が Crawler に HTTP で中継する(固定の経路のみ)。削除の承認・却下・全件削除の確認は、承認の廃止により存在しない |

検索・文書取得(Search API、MCP)は読み取りのみ。

### 2.3 インデックスごとの書き込み役と読み取り

SD v0.8 の記述を、書く側・読む側ごとにまとめた表(SD 内では記述が分散している。19章 X6)。

| インデックス | 内容 | 書く | Indexer が読むか |
| --- | --- | --- | --- |
| 検索インデックス | 1文書 = 1検索レコード(`search-index-v0.1.md`) | Indexer のみ | 読む(削除対象の抽出、件数照合、削除直前の `last_seen_at` の読み直し) |
| `loreley-texts` | 文書ごとの抽出済みテキストと処理状態(`loreley-texts-v0.1.md`) | Indexer のみ | 読む |
| `loreley-deletions`(仮名) | 削除の判断・実行の記録(`loreley-deletions-v0.1.md`)。Indexer 専用 | Indexer のみ(Crawler も Admin API も書かない) | 読む |
| `loreley-jobs` | ジョブ状態、ソースごとの実行ロック(`lock-{source_id}`)、スキップ記録。各ジョブに削除結果の要約・確認結果の区分・登録結果を残す。Crawler 領域 | Crawler のみ(例外: メンテナンスフラグ。運用者の手動手順で書く(案)。または Crawler の固定経路を経由する) | **ロック文書(書き込み前の所有確認)とメンテナンスフラグを読む**。スキップ記録は読まない |
| `loreley-sources` | データソース設定(`source_id`、種別、ルート、周期、TTL、削除率のしきい値、削除の最小件数、除外条件など。認証情報は参照名のみ)。Crawler 領域 | Crawler(Admin API は固定の経路で中継(案)) | **読まない**(TTL などは開始通知で渡される) |

Admin API は `loreley-jobs` と `loreley-deletions` を読み取りのみで読む。

### 2.4 コンポーネント間通信の方針

- メッセージブローカー(キュー)は使わず、コンポーネント間は HTTP で直接通信する。
- Crawler と Indexer は別コンテナ(`crawler`、`indexer`)。ジョブの起動も HTTP で行う。
- 内部通信は Compose の内部ネットワークだけで行い、ホストに公開しない(案)。検索対象ディレクトリの読み取り専用(`:ro`)マウントは `crawler` だけで、`indexer` には不要(案)。
- 単一ホスト、単一 Crawler、単一 Indexer、直列実行、認証なし、OpenSearch を Store 層とする前提は維持する。
- 契約を明確にし、将来キューが必要になったとき、HTTP 部分をメッセージングに置き換えられるようにする(13.3)。
- Indexer は削除の判断・実行を担う内部モジュール(Deletion Manager)を持つ。Crawler は開始通知・終了通知を HTTP で送り、結果を Indexer の Status API で確認する。
- 認証なしの前提は変えないため、内部ネットワークに届く範囲が境界になる。
- ログに本文や秘密情報を記録しない。要約・Embedding に外部 LLM を使う場合は明示的な設定を必須にし、既定の構成はオフラインで動作する。
- `indexer` コンテナは、`loreley-deletions` に書く唯一のコンテナである。
- 起動順や稼働確認(healthcheck など)の方法は未決(18章)。
- 技術スタック: バックエンドは Python。各文書形式の抽出ライブラリと文字コード判定の方法は未決(18章)。Store 層のバックエンドは MVP では OpenSearch。

### 2.5 時刻の前提

`crawl_started_at`、`last_seen_at`、TTL の判定は、Crawler と Indexer が同じホストの時計で動く前提(時刻ずれは想定しない)。

## 3. データモデルと識別子(Indexer 観点)

共通ドキュメント形式の項目定義は `indexer-api-v0.1.md` が持つ。

### 3.1 `content` の意味

本システム内で `content` の意味は場所ごとに異なる。

| 場所 | 名前 | 意味 |
| --- | --- | --- |
| Connector -> Indexer | `raw_content` | 取得済みの原本(抽出前) |
| Store 層 | `text` | 抽出・正規化後のテキスト(サイズ上限で切り詰め後) |
| 検索インデックス | `content` | `text` と同じ内容を検索用に解析したもの |
| `get_document` の応答(Search API 側) | `content` | `text` の指定範囲 |

### 3.2 `document_id` と `external_id`

- `document_id` = `SHA-256(source_id + "\0" + external_id)` の16進文字列(小文字)。NUL 文字で区切るため、連結で別の組が同じ値にならない。
- `external_id` は、ハッシュの前に Unicode NFC へ正規化し、パス区切りを `/` に統一する(ルートからの相対パス、先頭に `/` を付けない)。大文字小文字は区別したまま扱う。
- 同じ文書を再取得すると同じ ID になるため、再実行しても重複しない。検索インデックスと Store 層のどちらも、`document_id` を文書 ID(`_id`)として使う。
- `source_id` は登録後に変更できない。変更が必要なときは、新しいデータソースとして登録し直す。
- パスの変更やリネームは「旧 ID の削除 + 新 ID の追加」として扱う。リネームの追跡は初期要件にしない。

### 3.3 `last_seen_at` と `crawl_started_at`

- `last_seen_at` は共通ドキュメント形式に含めない。クロールの実行コンテキストとして `crawl_started_at` を Indexer に渡し、Indexer が `last_seen_at` に書く。確定。`last_seen_at` は検索インデックスの文書に持つ(負荷はリスクとして扱う。15.3)。
- `fetched_at` は「取得した日時」、`last_seen_at` は「列挙で見つかった日時」である。
- 毎回の全文 upsert で `last_seen_at` が更新されるほか、取得に失敗してスキップした文書の誤削除を防ぐため、列挙で見つかった時点で `last_seen_at` だけを部分更新する(5章)。
- `crawl_started_at` は開始通知でも `loreley-deletions` に渡され(9.5)、削除前の件数照合は `last_seen_at >= crawl_started_at` の件数を使う(9.6)。
- `fetched_at` と `metadata` の保存先が書かれていない(19章 X7)。

### 3.4 真実の置き場所

文書の本文・要約・処理状態の正は Store 層(`loreley-texts`)。検索インデックスはそこから作る派生物である。ただし `last_seen_at` は検索インデックスだけに持つ。`title`・`url`/`path`・`mime_type`・`indexed_at` も Store 層に持つので、Store 層からの再構築(11章)と `get_document`(`title` と `url`/`path` を返す。Search API 側)は、Store 層だけで成立する。

`text` は、登録前(`pending_index` にする時点)に書く(`get_document` の仮決定が前提とする条件)。

### 3.5 Store 層と Repository インターフェース

- MVP の Store 層は OpenSearch を KVS のように使い、設定・ジョブ・抽出済みテキスト・文書ごとの処理状態を保存する。用途ごとに検索インデックスとは別のインデックスを分け、ID をキーに get/put/delete する。
- コード上は検索インデックスとは別の「Store 層」として扱い、アプリケーションは Repository インターフェースだけを経由して読み書きする。
- バックエンドは設定で差し替えられるようにする。将来、PostgreSQL や SQLite を追加しても呼び出し側を変えない。
- インターフェースは、ID による取得・保存・削除、単純な条件での一覧、条件付き更新(楽観的排他制御)に限る。トランザクションと結合には依存しない。
- 書き込みを担当するコンポーネントは分けてある(2.2)。Repository インターフェースは、各コンポーネントが共通で使う。
- Connector の認証情報は、Store 層に平文で保存しない。環境変数や秘密情報ファイルで参照する。
- 条件付き更新の方法(`if_seq_no`/`if_primary_term`)と、検索ではなく ID による取得を使う理由は6章。
- Repository インターフェースの詳細と、OpenSearch 以外のバックエンドに移る条件(件数・更新頻度・排他の要件など)は未決(18章)。
- Store 層のマッピング方針(`dynamic: strict` など)は `loreley-texts-v0.1.md` を参照。

## 4. 登録処理

### 4.1 Indexer の位置づけ(クロール全体の流れの中で)

クロール全体の手順(Crawler 領域)のうち、Indexer が関わる部分は次のとおり。

1. Crawler がソースのロックを取得したあと、列挙の前に、Indexer へ開始通知を送る(9.5)。
2. Crawler が列挙し、見つかった文書の `last_seen_at` を、その時点で部分更新する(書き込みは Indexer が行い、Crawler が要請する。5章)。全文 upsert でも更新される。
3. すべての文書を取得し、処理する(全件更新。4.3)。
4. Indexer が本文を抽出・正規化し、Store 層と検索インデックスに登録する。登録が成功してから、処理済みの印(`content_hash` など)を確定する。途中で失敗した文書は、Indexer が文書単位の失敗として返し、Crawler がリトライしてもだめならスキップを判断する。スキップした文書は次回のクロールで再処理される。
5. 要約生成が有効なら、Indexer が内部で要約を非同期に生成し、Store 層に保存したうえで、本文が変わっていないときだけ検索インデックスに反映する(7章)。
6. Crawler は、全バッチの登録の応答を確認したら、終了通知を送る(202 で受理される)。そのあと Status API をポーリングして削除結果を確認する(9.11)。

### 4.2 抽出・正規化と登録

- 文書形式に応じてテキストを抽出し、正規化する。MVP の対応形式は txt・Markdown・HTML・PDF。Office 文書は次版。文字コードは自動判定し、UTF-8 のほか Shift_JIS/CP932 にも対応する。抽出ライブラリと文字コード判定の方法は未決(18章)。
- 抽出済みテキストを Store 層に保存する。原本は保存せず、元システムを参照する。
- 検索インデックスへの登録・更新・削除を行う。書き込みの種類ごとの競合の扱いは5章に定める。
- 抽出に失敗した文書は、タイトルとメタデータだけを登録し、抽出失敗(`index_status=extract_failed`)として扱う。Admin View に表示する。
- 本文がサイズ上限を超える場合は、上限までを索引化して `truncated=true` にする(15.2)。
- Embedding の生成は、ベクトル検索と同じ将来拡張とし、MVP では行わない。

### 4.3 全件更新の処理手順(差分検知は MVP 対象外)

MVP では、`mtime`・`size`・`extractor_version` によるスキップ判定をしない。毎回、次の順で全文書を処理する(手順1・2は Crawler)。

1. Connector が文書を列挙する。
2. 各文書の原本を取得し、`content_hash` を計算する。取得に失敗した文書は、Crawler のリトライとスキップに従う。
3. 抽出・正規化する。取得した `content_hash` が、Store 層の確定済みの `content_hash` と**同じ**なら、`pending_index` に遷移せず、全文 upsert(`last_seen_at` の更新を含む。要約は引き継ぐ)だけを行う(抽出ロジックを変えた場合に備え、Store 層の `text` も抽出し直した内容で更新する)。**変わった(または新規の)場合のみ**、Store 層に `text`・`pending_content_hash`・`index_status=pending_index` を書いてから、全文 upsert する。これは差分検知ではなく書き込み状態の判定である。変更のない文書で `pending_since` や `index_status` が毎回変わり、`pending_index` の警告(10章)や `get_document` の応答が不安定になるのを防ぐ。
4. 全文 upsert に成功したら、**最後に** Store 層の `content_hash`・`index_status` などを確定し、`pending_index` を解消する。途中で失敗すると確定されないので、次回のクロールで再処理される。
5. 本文が前回と同じ(`content_hash` が同じ)なら、要約を引き継ぐ。違うなら、要約を引き継がず `summary_status=pending` に戻す(7.5)。

- 手順3〜4の Store 層・検索インデックスへの書き込みと確定は、Indexer が文書ごとに行う(Crawler が原本とメタデータを渡す)。
- 抽出に失敗した文書(`extract_failed`)も、毎回再試行する。回数の上限で止める処理は MVP にはない。そのため、`extract_failed`・`pending_index` の文書は特別な扱いなしに、次のクロールで再処理される。抽出ロジックを変えたときも、次の全件更新で反映される。
- **手順3の注記(推測)**: 「同じ `content_hash` のとき Store 層の `text` を抽出し直して更新し、この更新は `pending_index` を経由しない」は、SD の元になった版の作成時に、指示外で補われた点である。Store 層と検索インデックスの本文が食い違う余地があり、要否は未確認(17章、19章)。
- **制限**: 変更のない文書も毎回処理するため、クロールの時間と書き込みの負荷は文書数に比例する(15.3)。

### 4.4 登録失敗時の分担と Indexer の異常

(リトライ・スキップの判断は Crawler 領域。ここでは Indexer が関わる境界だけを示す。)

- 検索インデックスへの登録に失敗した場合は、Indexer が文書単位の失敗種別を返し、Crawler がリトライ設定の回数だけリトライする。それでも失敗したら、Crawler がその文書をスキップして個別文書の失敗として記録する。クロールは部分成功になるが、削除は行う。ジョブ全体の失敗は、列挙の失敗、OpenSearch 全体の異常、Indexer の異常などに限る。失敗種別の具体名は未決(18章)。
- リトライの既定値(案): 最大試行回数 3 回(最初の1回 + リトライ2回)、バックオフは初回 1 秒、2 倍ずつ、上限 30 秒、ジッタあり。文書ごと・処理段階ごと(取得、登録)に数える。設定はグローバルな既定値とデータソースごとの上書きができる。値は案で、実装時に調整する。Indexer 側の削除エラーのリトライもこの設定を共有する(9.8)。
- **全体異常とスキップの判定基準**(登録・部分更新の失敗時。案): 次は OpenSearch 全体の異常とみなし、スキップせずジョブを `failed` にする: 接続エラー、タイムアウト、HTTP 429、5xx、`cluster_block_exception`、circuit breaker(`circuit_breaking_exception`)。リトライ設定の回数まで試しても直らなければ `failed` とする。文書固有の 4xx の拒否(マッピング違反、文書の内容に起因する拒否など)だけをスキップにする。文書固有の 4xx のスキップが連続して 20 件(案。設定可能)に達したら、設定や状態の異常の疑いとして `failed` にする。
- **Indexer の異常**: Indexer に接続できない、タイムアウト、サーバ側エラー(HTTP 5xx 等)は、OpenSearch 全体の異常と同様に扱う。
  - 「Indexer・Store 層の障害でクロールが失敗扱いになったときは削除しない。個別文書の失敗(スキップ)とは区別する」は、ユーザー確認済み(確定)。
  - 以下の細部(リトライ回数、連続 20 件、エラー種別、ジョブ `failed` にする対象の範囲)は案のまま。リトライ設定の回数まで試しても直らなければ、スキップにせずジョブを `failed` にして、削除しない。スキップの対象は文書固有の拒否だけで、連続 20 件(案)で `failed` にする既存のルールも維持する。
  - この「Indexer の異常はジョブ `failed`」の扱いの対象は、開始通知、登録、`last_seen_at` の部分更新、終了通知の失敗に限る。Status API のポーリングの失敗は警告のみで、ジョブの status は変えない。
  - ロック所有の確認(8章)に失敗した場合は、スキップ・リトライの対象にせず、ジョブを `failed` にして削除しない(案)。
- `last_seen_at` の部分更新が失敗したとき(OpenSearch への書き込み不可など)は、その文書をスキップとして扱わず、ジョブを `failed` にして削除しない。部分更新の失敗を放置すると、読めない文書の `last_seen_at` が更新されずに誤削除されうるためである。「存在確認日時(`last_seen_at`)を保存できなければ、クロールを完了扱いにしない(削除もしない)」は、プロダクト側の文書に記載されているが、ユーザーの確認済みリストには含まれない(案。ユーザー確認は未確認)。
- 登録・部分更新の失敗は、文書固有の拒否を除き、Indexer が返す文書単位の失敗種別で Crawler に伝わる。書き込み(登録・部分更新)の応答の形は `indexer-api-v0.1.md`。

## 5. 書き込み種別と競合制御

検索インデックスへの書き込みは、Indexer だけが行う。書き込みは次の3種類に分ける。MVP は全件更新で、すべての文書を全文 upsert する。これに加えて、読めない文書をスキップしても削除されないよう、列挙で見つかった時点の `last_seen_at` の部分更新を行う。

| 種別 | 書くフィールド | 書き込む側 | 競合時の扱い |
| --- | --- | --- | --- |
| 全文 upsert | 全フィールド。`last_seen_at` は既存値と `crawl_started_at` の大きい方(スクリプトによる upsert。新規作成時は `crawl_started_at`)、`content_hash` は新しい値。`summary` と `summary_status` は、`content_hash` が既存と同じなら既存の値を保持し、違えば `summary` は書かず `summary_status=pending`(要約が無効なら `disabled`) | Indexer(本文の追加・更新時) | 文書全体を置き換える。本文が変わったときは、旧本文向けの要約を残さない(全件更新で毎回要約を作り直さないよう、本文が同じなら引き継ぐ)。同じデータソースのクロールは1つだけなので、同時の全文 upsert 同士は起きない。`last_seen_at` は古い値に戻さない(max 比較) |
| `last_seen_at` の部分更新 | `last_seen_at` のみ(値は `crawl_started_at`) | Indexer(列挙で文書が見つかった時点。取得より前。Crawler の要請を受けて書く) | 現在値と比べるスクリプト更新(max 比較)。新しい値のときだけ書き、古い値で上書きしない。ほかのフィールドは変更しない。検索インデックスに文書がない場合(404)は何もしない(upsert しない)。取得・抽出・登録が失敗しても更新済みのまま残る |
| 要約の部分更新 | `summary`、`summary_status`、`summary_model`、`summary_embedding` | Indexer 内部の要約生成(非同期) | **検索インデックス上の `content_hash` が、要約を生成した本文の `content_hash` と一致するときだけ**書く(条件付き更新)。不一致なら捨てる(本文が更新済みで、新しい要約が生成される)。更新の衝突は再試行する。要約生成はクロールと並行しうるため、この条件で正しさを保つ(7章) |

**リース切れ後の旧 Crawler の全文 upsert**: 全文 upsert は文書全体を置き換えるため、古い世代の Crawler(からの登録要請)が新しい内容を上書きするのを原子的には拒否できない。MVP では、単一 Crawler・直列実行を基本とし、リース期限切れだけでは自動で引き継がない(Crawler 領域)ことで、この状況が起きにくくする。実行世代番号を持たせて古い世代の上書きを拒否する完全な分散フェンシングは、複数 Crawler 化の際の将来拡張とする(13.2)。ここで保証するのは、`last_seen_at` が戻らないことまでである(部分更新も max 比較なので同様に戻らない)。Crawler と Indexer が別コンテナになっても、この保証は変わらない。ロック所有の確認(8章)から書き込みまでの窓は Indexer 側にも広がるが、max 比較により `last_seen_at` は戻らない。

要約は、生成の完了後にまず Store 層へ保存し、そのうえで検索インデックスへ反映する。Store 層への保存も、生成元の `content_hash` が一致するときだけ行う(6章、7.4)。

フィールドの定義は `search-index-v0.1.md`、操作の契約は `indexer-api-v0.1.md` を参照。

## 6. Store 層と検索インデックスの整合性・排他

- OpenSearch の検索はリフレッシュ後にしか反映されない(ニアリアルタイム)。状態の確認や排他の判定には、検索ではなく ID による取得(リアルタイム)を使う。
- 条件付き更新には `if_seq_no`/`if_primary_term` を使う。要約を Store 層へ保存するときは、読み出した文書の現在の本文のハッシュ(確定前は `pending_content_hash`、確定後は `content_hash`)が生成元と一致し、かつ `if_seq_no`/`if_primary_term` が一致するときだけ書く。本文が変わるとき(`content_hash` が既存と違うとき)は、Store 層の要約を消して `summary_status` を `pending`(要約が無効なら `disabled`)に戻す。
- 初回の作成は、存在しない場合だけ成功する作成(create)を使う。
- Store 層と検索インデックスは別のインデックスであり、またがるトランザクションはない。更新の途中では、両者の内容(本文の `content_hash` や `index_status`)が一時的に食い違う。MVP では短時間の不一致を許容し、検出と復旧は突合ジョブ(10章)、読み出し時の扱いは `get_document`(Search API 側)に定める。
- ノードが1つなので、データの消失に備えてスナップショットを取る(14章)。

## 7. 要約生成

### 7.1 方針

- 文書全体の**検索用の要約**を生成する。主題、重要な概念、その文書で答えられる質問を表現する。要約の生成と書き込みは、Indexer が内部で行う。
- 既定では無効で、LLM を明示的に設定したときだけ有効になる。外部 LLM を使う場合は明示的な設定を必須にする。既定の構成はオフラインで動作する。
- Embedding の生成は、ベクトル検索と同じ将来拡張とし、MVP では行わない。

### 7.2 非同期処理とジョブ対象外

- 要約の失敗・遅延では、要約なしで先に登録し、後から非同期に生成する。
- 要約生成は Indexer 内部の非同期処理であり、`loreley-jobs` のジョブ・ロック・リースの対象にしない(`loreley-jobs` に書くのは Crawler だけのため。要約の状態は `summary_status` で持つ)。
- Crawler と Indexer が別コンテナになるため、要約の書き込みがクロールと並行する場合がありうる。**厳密な直列は保証せず、`content_hash` の条件付き更新で正しさを保つ**(旧設計の「クロールの実行中には要約を書かない」を緩和。確定。ユーザー確認済み)。要約を検索インデックスと Store 層に書くときは、生成元の `content_hash` が現在の本文と一致するときだけ書き、不一致なら捨てる(5章、6章、7.4)。
- メンテナンス(再インデックス)のために `loreley-jobs` のメンテナンスフラグが立っている場合、Indexer は書き込み前にそれを確認し、書き込まずに止まる(11章)。実行ロックは、クロール用のロックと区別できないため判別に使わない。確認の詳細は未決(18章)。
- **要約生成の再開**(案): 要約生成はジョブ記録を持たない。Indexer の再起動後は、`summary_status=pending` の文書(正は Store 層)を再走査して再開する。したがって、要約生成の終了確認(11章)は、Indexer の停止が確実な手段である。再開・リトライ・負荷制御の方法は未決(18章)。

### 7.3 生成状態

- 要約の生成状態とモデル名・バージョンを保持し、後から再生成できるようにする。
- `summary_status`: `disabled`(要約が無効)、`pending`、`generated`、`failed`。`summary_model` にモデル名・バージョンを持つ(値域は `search-index-v0.1.md` と `loreley-texts-v0.1.md`)。

### 7.4 保存先と書き込みの整合

- 要約は Store 層にも保存し、再インデックスで失わないようにする。Store 層の要約には、生成元の `content_hash`(`summary_content_hash`)を持たせる。
- 要約は、生成の完了後にまず Store 層へ保存し、そのうえで検索インデックスへ反映する。
- Store 層への保存は、生成元の `content_hash` が、現在の本文のハッシュ(確定前は `pending_content_hash`、確定後は `content_hash`)と一致し、かつ `if_seq_no`/`if_primary_term` が一致するときだけ行う(6章)。
- 検索インデックスへの反映は、検索インデックス上の `content_hash` が生成元と一致するときだけ行う。不一致なら捨てる(本文が更新済みで、新しい要約が生成される)。更新の衝突は再試行する(5章)。

### 7.5 再生成・本文更新との整合

- 本文が変わるとき(`content_hash` が既存と違うとき)は、Store 層の要約を消して `summary_status` を `pending`(要約が無効なら `disabled`)に戻す。検索インデックスの全文 upsert でも、`summary` は書かず `summary_status=pending`(無効なら `disabled`)にする(5章)。
- 本文が同じ(`content_hash` が同じ)なら、要約を引き継ぐ。MVP は全件更新で毎回すべての文書を処理するため、毎回の要約の再生成を避けるのがこの引き継ぎの目的である(4.3)。
- Store 層からの再構築(11章)では、Store 層の要約のうち、生成元の `content_hash` が本文と一致するものだけが保持される。不一致は `pending` に戻す。

### 7.6 モデル選定

要約生成に使うモデル、コスト、生成にかかる時間は未決(18章)。要約の品質・コストは、測定して決める(15.4)。

## 8. フェンシング(書き込み前のロック所有確認)

- 検索インデックスや Store 層への書き込み(登録、`last_seen_at` の更新)の前に、**Indexer が**ロック文書(`loreley-jobs` の `lock-{source_id}`)を ID で取得し、書き込みを要請したジョブの所有者であり期限内であることを確認する。確認に必要な情報(`owner` と `job_id`)は、Crawler が書き込み要請に添えて渡す(形は未決。18章)。確認できなければ(期限内でなければ)書き込みを中止する。再開は Crawler の再起動か管理者の操作で行う。確認と書き込みの間にはわずかな窓が残る(窓は Indexer 側にも広がる)が、`last_seen_at` は全文 upsert でも古い値で上書きしない(5章)。
- **削除の前**: Indexer が削除の判断と実行を非同期に行い、Crawler のロックは削除結果の確認後(またはタイムアウト後)に解放されるため、ロックの所有は削除の条件にならない。代わりに、Indexer が**世代の判定**(終了通知の受理時に1回だけ。新しい開始通知で整理済み(`superseded`)の結果への遅れた終了通知は何もしない。記録済みの終了通知の再送は世代を見ず冪等。バッチごとの確認は行わない)と**メンテナンスフラグの確認**(判定の前と削除のバッチごと)を行う(9章)。立っていれば `failed`(`maintenance`)にして止める。新しいクロールが始まっても、受理済みの旧い削除は止めない。
- 確認の対象は、要請に由来する書き込み(登録、`last_seen_at` の更新)である。要約の書き込みは、この確認ではなく、7.4 の条件付き更新とメンテナンスフラグの確認で守る。
- Crawler がタイムアウトした後も Indexer の処理が続く窓と旧要請の扱いについては、Indexer は要請を直列に処理し(単一 Indexer の前提)、所有確認を文書ごとに行う(案)。それでも残る窓は、MVP では既知の制限として許容し、完全なフェンシングは 13.2 とする。

## 9. Deletion Manager(削除の判断・実行)

### 9.1 位置づけ

削除の判断と実行を担う、Indexer の**内部モジュール**(独立コンテナにしない。確定)。Indexer は、クロール1回ごとの削除の判断・実行を、削除結果として記録する。Crawler からの通知を受けて、記録、検証、判断、削除を行う。Crawler は検索インデックスを読まず、削除の判断にも関わらない。通知や応答の形は案で、細部は未決(18章)。

新しいクロールの開始による削除の「中断」は廃止し(仕様変更。確定)、同じソースの削除を直列にした。旧い削除は、止められることなく終端状態まで走る。後の削除は、前の削除が終端状態になってから始める(9.9)。

責務分担は 2.2。`crawl_id` はジョブ ID をそのまま使う(新しい ID を採番しない)。現行世代は、そのソースで最後に受理した開始通知の `crawl_id`である。実行中のクロールは通常1つだが、削除結果は、旧い削除の待機・判定・実行と重なって複数ありうる(直列に処理する。9.9)。

### 9.2 期限による削除

削除の流れ(概要):

1. Indexer(Deletion Manager)が終了通知を受ける(受理時に、削除結果が `superseded` などの終端状態になっていないことを1回確認する。なっていれば何もしない)。同じソースの先行する削除が終端状態になるのを待ってから、メンテナンスフラグがないこと、件数照合が成立することを確認する。列挙クロールが最後まで完了し(`outcome=enumeration_completed`)、これらを満たすときだけ、同じ `source_id` のうち `last_seen_at + TTL < 現在時刻` で、今回スキップした文書でない文書を削除の対象にする。読めない文書のスキップがあってもよい。
2. 割合ルール(9.3)で、削除するかを決める。削除対象÷削除前の登録文書数がしきい値以下、または対象が最小件数以下なら削除し、超えれば削除せず、削除結果に理由を記録する。承認待ちはない。手動実行で強制削除モードを指定したときだけ、割合ルールと最小件数ルールを無視する。
3. 削除は Indexer が、**Store 層、検索インデックスの順**に、バッチごとに再抽出しながら行う(9.8)。新しいクロールが始まっても、実行中の削除は止めない。同じソースの削除は直列に行う(9.9)。途中で止まっても、検索インデックスに残る文書は次回の削除で再度対象になる。Store 層と検索インデックスの食い違いは、突合ジョブで検出する(10章)。

規則:

- 削除の対象は、**列挙が最後まで完了したクロール**(`succeeded`、またはスキップのみの `partially_succeeded`)の終了通知(`outcome=enumeration_completed`)を受理し(受理時の世代の確認)、メンテナンスフラグの確認、件数照合に通ったクロールで、同じ `source_id` のうち `last_seen_at + TTL < 現在時刻` の文書である。差分だけを取るクロール(将来の Connector)は、`enumeration_completed` として通知しないので、削除されない。列挙の失敗、マウント外れなど、クロール全体の異常では、Crawler は `outcome=failed` を通知するか通知できず、いずれも削除しない。
- **TTL**: データソースごとに指定し、クロールの間隔より長くする。例: 日次クロールで TTL が 3 日なら、3 回続けて見つからなかった文書を削除する。Indexer は、開始通知のスナップショットに載った TTL(削除結果に複写した値。案)を使う。
- **0件列挙**: アクセスできていて最後まで完了した 0 件列挙は、列挙の完了であり、ジョブは `succeeded` になる。削除するかは、件数照合(`0 = N_seen + E_missing`)を通したうえで、割合ルールが決める。`last_seen_at + TTL` が過ぎていない文書は、対象にならない。TTL が過ぎて対象が分母に近づくと、割合ルールが働いて削除されない。これが、マウント外れや共有の切断による全件削除の保護になる。
- **実際に全ファイルを消した場合(強制削除モード)**: 割合ルールでは、全件(100%)の削除は通常行われない。全ファイルを実際に消したときは、管理者が**手動実行のクロールの起動時に**強制削除モードを指定する。このモードは、**割合ルールと最小件数ルールだけ**を無視し、`last_seen_at + TTL < 現在時刻` の文書をすべて削除する。0件列挙でも全件を削除する。次は無視しない: 列挙が最後まで完了していること、世代が現行であること、件数照合が成立すること、メンテナンスフラグがないこと、スキップした文書の除外、各文書の TTL の経過(したがって、全件削除は最後に見つかってから TTL が過ぎた後になる)。TTL を過ぎていない文書は、強制削除モードで実行しても対象外で残る。全件を削除したいときは、TTL の経過後に実行する。定期実行からは指定できない。削除結果に、強制削除モードで実行したことを記録する(`forced`)。開始通知の `force_delete` で渡し、`deletion-{source_id}` と `deletion_result-{crawl_id}`(複写)に記録する。9.7 の順5の割合ルールと最小件数ルールだけを無視する。受理時の世代の判定、順1〜3、順4(TTL とスキップ文書の除外)、列挙の完了は無視しない。
- **0件保護の限界**: 専用の0件保護はなくなり、割合ルールに一本化した。次は防げない制限事項として残す: (1)一部のディレクトリだけがマウント外れなどで消えた場合、しきい値以下の少数の消失は通常の削除として扱われる。(2)削除対象が最小件数以下の小さなソースでは、0件列挙(マウント外れの空ディレクトリなど)でも、TTL が過ぎた文書は削除される。MVP ではこれ以上は作り込まない。
- **二重防御**: 削除の対象を決めるとき、今回のスキップした文書の ID(終了通知で渡された `skipped_document_ids`)を、明示的に削除対象から除外する。`last_seen_at` の更新が万一漏れていても、スキップした文書は消さない。スキップ記録そのものは `loreley-jobs` に残り、Indexer は読まない。
- 削除対象は検索で抽出するため、抽出前にリフレッシュする。抽出と削除は Indexer が行い、Crawler は検索インデックスを直接読まない。削除は、Store 層、検索インデックスの順に行い、バッチごとに再抽出する。削除前のロック所有確認は行わず、代わりに終了通知の受理時の世代判定と、バッチごとのメンテナンスフラグ・自分の削除結果の状態の確認を行う(8章、9.8)。
- データソースから消えた文書は、削除されるまで検索結果に残る。検索時に `last_seen_at` で除外はしない。クロールが失敗し続けると、全文書が検索から消えてしまうためである。
- ジョブの status と削除結果は切り離されている。削除結果の `failed` はジョブの status を変えない(Crawler 領域)。

### 9.3 割合ルール

- **判定**: 削除対象の件数 T、削除前の同じ `source_id` の登録文書数(分母)D(検索インデックスの件数。リフレッシュ後に数える。登録済みのスキップ文書も含む)として、次の順で判定する(以下を「割合ルールの判定1〜3」と呼ぶ。9.7 の判定表の「順1〜6」とは別の番号体系。19章 X5)。
  1. T が最小件数以下なら、率に関わらず削除する(少数のソースで 1 件の削除が高い率になるため)。
  2. そうでなければ、T ÷ D がしきい値以下なら削除する。超えるなら削除しない(削除結果の状態は `skipped_by_ratio`。T、D、しきい値、理由を記録する)。
  3. 強制削除モード(9.2)では、1 と 2 を行わず、削除する。
- **分母 D=0 のとき**: T は D の内数なので、T=0 である。9.7 の判定表では、順4(削除対象が 0 件なら `deleted`。`deleted_count=0`)が順5(割合ルール・最小件数ルール)より前にあるので、D=0 なら、順1〜3(先行削除の待機、`maintenance`、`validation_failed`)を通過すれば順4で `deleted` となる。いずれも除算せず、最小件数の値(正常値でも不正値でも)に依存しない。除算に進むのは T>0 のときだけで、このとき D≧T>0 である。最小件数が欠損・負・NaN・数値以外のときに未定義なのは、T>0 のときの割合ルールの判定1(最小件数ルール)の結果であり、D=0 とは関係しない(9.13 の受容事項(9)、18章)。
- **設定**: しきい値と最小件数は、データソースの設定にする(`loreley-sources`)。開始通知のスナップショットで Indexer に渡し、削除結果に複写して(案)、そのクロールの削除の判断に使う。しきい値の既定値は未決(18章)。最小件数の既定値は未決(例: 10 件)。
- **しきい値の入力検証**(確定。範囲の根拠): 範囲は 0% 以上 100% 未満である(割合で表すなら 0 以上 1 未満)。100% 以上を許さないのは、T が分母 D の内数で T÷D が 1 を超えないため、しきい値が 100% 以上だと割合ルールが働かず、全件削除を防げないからである(全件削除したい場合は強制削除モードを使う)。検証は**Admin API(固定経路)だけ**で行う。
  - 範囲外の値(100% 以上、負の値)の拒否は確定。数値でない値(NaN を含む)の拒否と、拒否したときに Crawler へ中継せず保存済みの設定を変えない動作は案。0% と 99.9% は受け付ける(0% は、最小件数を超える削除を自動では実行しない設定)。
  - 拒否応答(案): HTTP 400。エラーコード(例: `invalid_ratio_threshold`)、項目名、許容範囲を含める。具体名と形式は未決(18章)。
  - **Crawler と Indexer は検証しない**(確定)。開始通知のスナップショットで受け取った値を、そのまま判定に使う。Admin API を経由しない経路で範囲外の値が入った場合の挙動は、既知の制限として 9.13 の受容事項(9)に書く。
  - 未指定(欠損)の扱い(必須にするか、既定値を使うか)は、既定値が未決のため未決。Admin API の更新で値が省略された場合に、保存済みの値を保つか欠損とするかも未決。入力の単位(% の数値か、0〜1 の割合か)も未決(いずれも 18章)。最小件数と TTL の範囲検証は Admin API も定めない(不正値の挙動は未定義。9.13 の受容事項(9))。
- **承認はない**: 削除の保留、承認、却下の状態やレコードは持たない。割合を超えたクロールは、削除しないで終わる。状態は引き継がず、次のクロールのたびに新しく判定する。管理者は、Admin View で削除結果(`skipped_by_ratio` と、T、D、しきい値)を確認する。大量の削除が意図したものなら、強制削除モードを指定して手動でクロールを実行する。しきい値を変えたときは、次の開始通知から反映される。
- 割合ルールで削除しなかったことは、ジョブの status に影響しない。

### 9.4 `loreley-deletions` の記録と設定スナップショット

インデックス名は仮名。スキーマの詳細は `loreley-deletions-v0.1.md`。

| ID | 内容 |
| --- | --- |
| `deletion-{source_id}` | ソースごとの現行世代: `crawl_id`、`crawl_started_at`、設定スナップショット(TTL、しきい値、最小件数)、`force_delete`、更新日時。開始通知で更新する。直近の開始通知の内容であり、削除の判断・実行には使わない(使うのは、下の複写した値)。ソース削除の停止にも使わない(停止は自分の削除結果を読んで行う。9.8、9.14) |
| `deletion_result-{crawl_id}` | 削除結果: `source_id`、`status`、`reason`、`outcome`、`enumerated_count`、`n_seen`、`e_missing`、`target_count`(T)、`denominator`(D)、`deleted_count`、`forced`(強制削除モードで実行したか。複写した `force_delete` そのもので、別の項目を重ねて持たない)、設定スナップショットの複写(`ttl`、`ratio_threshold`、`min_delete_count`と、`forced` として持つ `force_delete`。案)、`finish_received_at`、`deletion_started_at`、開始・終了日時。ソースごとに、**終端状態の結果を**直近 N 件保持し、古いものは Indexer が消す(N は未決。18章)。整理の対象は終端状態の結果だけで、`running`(待機中を含む)は数えず、消さない |

**設定スナップショットの複写**(案。旧い削除が、あとから届いた新しい世代の設定で動かないようにするために必要): 開始通知を受理するとき、通知の `ttl`、`ratio_threshold`、`min_delete_count`、`force_delete` を `deletion_result-{crawl_id}` に複写する。判定と実行は、常にこの複写した値を使い、`deletion-{source_id}`(新しい開始通知で上書きされる)からは読まない。旧い削除は、待機中や実行中に新しい開始通知が来て設定が変わっても(強制削除モードの指定の有無を含む)、自分のクロールの設定で最後まで動く。

`deletion-{source_id}` の用途は SD の記述上、削除の判断・実行・ソース削除の停止には使わないとされ、使う場面として読み取れるのは開始通知の世代判定(古い `crawl_started_at` の拒否。9.5)のみ(19章 X14。推測)。

### 9.5 開始通知・終了通知・Status API の受理(Indexer の動作)

契約(エンドポイント、リクエスト/レスポンス)は `indexer-api-v0.1.md`。ここでは Indexer の動作を示す。エンドポイント形・応答コードは案。

**開始通知**(`POST /crawls/start`。案)

- Crawler が送るタイミング: ロック取得後、列挙の前。
- 内容: `crawl_id`、`source_id`、`crawl_started_at`、設定スナップショット(`ttl`、`ratio_threshold`、`min_delete_count`)、`force_delete`(既定は `false`)。
- 判定の順序と拒否(409。案): 次の順で判定する。(1)`deletion_result-{crawl_id}` がすでに終端状態なら、409 で拒否する(終了したクロールの通知が再送されても、`running` に戻さない)。(2)同じ `crawl_id` で削除結果が `running` なら、状態を変えずに成功を返す(再送)。(3)`crawl_started_at` が現行世代の `crawl_started_at` より古ければ、409 で拒否する(遅れて届いた古い通知で、世代が巻き戻らないようにする)。Crawler は、409 をジョブ `failed` として扱う。
- 即時の受理: 開始通知は、旧い削除が待機中・判定中・実行中でも待たせず、すぐに受理する。
- Indexer の動作(上の判定を通ったとき): `deletion-{source_id}` の現行世代を更新し、`deletion_result-{crawl_id}` を設定スナップショットの複写つきで `running` で作る。同じソースに、`finish_received_at` の無い `running` の旧い削除結果(終了通知が届かなかった世代)があれば、`discarded`(理由: `superseded`)にする。これは終了通知が届かなかった世代の整理であり、実行中の削除を止めるものではない。`finish_received_at` のある結果(待機中、判定中、実行中)には何もしない。
- 通知の失敗(リトライ設定の回数まで試しても直らない場合)は、Crawler がジョブを `failed` にする。開始通知の失敗と、終了通知が Indexer に届かなかった場合は、削除は行われないだけで、安全である。ただし、終了通知の応答が失われただけの場合は、Indexer が受理済みで `finish_received_at` が記録され、削除が進みうる(Crawler からは、届かなかった場合と区別できない)。その結果は削除結果に残り、Admin View の削除結果で確認できる場合がある(ジョブ記録に確認結果の区分は付かない)。この場合を含め、「安全」の根拠は、前提(列挙の完了、全バッチの登録の確認)は終了通知の送信前に確認済みで、実行時は各文書の削除直前の TTL 再確認で守られることである(9.8)。(案。既存の仕様からの帰結を明記したもの)

**終了通知**(`POST /crawls/{crawl_id}/finish`。案)

- Crawler が送るタイミング: すべてのバッチ登録(と `last_seen_at` の部分更新)の応答を確認したあと。列挙の失敗・取り消しの場合は、`outcome=failed` または `cancelled` を可能なら送る(届かなくても、削除されないので安全)。取り消しが有効なのは、終了通知を送る前だけである。終了通知を送ったあとに取り消しても、削除処理は止まらない(9.11)。
- 内容: `source_id`、`outcome`(`enumeration_completed` / `failed` / `cancelled`)、`enumerated_count`(Crawler が `document_id` で重複を除いて数えた、列挙で見つかった文書の数。スキップ・抽出失敗の文書を含む)、`skipped_document_ids[]`、`skipped_count`、`finished_at`。
- 応答は**202のみ**(受理。判断は非同期)。判断の結果は応答に含めない。Crawler は、Status API で確認する。`enumeration_completed` の受理では、Indexer は `finish_received_at` を `loreley-deletions` に永続化してから 202 を返す(202 のあとに再起動しても、受理した事実が残り、再起動時に `failed`(理由: `indexer_restart`)にできる)。`failed`・`cancelled` の受理では `finish_received_at` を記録せず、削除結果を `failed` にしてから 202 を返す。(内容が異なる再送は 409 になる(次項)ため、「202 のみ」は通常の応答を指す。19章 X3)
- 再送は冪等である(受理時の分岐の**先頭**で判定する)。記録済みの終了通知(`finish_received_at` が記録済み、または結果が `failed` など終端状態)の再送は、世代を見ずに、再処理せず 202 を返す。内容が最初と異なる再送は、`finish_received_at` が記録済みのものに限り、409 で拒否する(案)。受理済みの旧い削除(待機中、判定中、実行中)は、新しい開始通知のあとに終了通知が再送されても、`discarded` にならず、止まらない。
- 受理時の分岐(上の再送の判定のあと。「世代の判定」は、**この受理時に1回だけ**行う確認で、結果が新しい開始通知で整理済み(`superseded` など)でないかを見る。受理後の待機中、判定中、バッチの間には再確認しない):
  1. `finish_received_at` が未記録で、その `crawl_id` の削除結果がすでに終端状態の場合(終了通知が届かないまま新しい開始通知で `superseded` になった旧世代への、遅れた終了通知など): 何もしない。状態を変えず、削除しない。
  2. 開始通知を受けていない未知の `crawl_id`: 削除結果を作らず(記録しない)、ログに残すだけ。どちらも応答は 202。
  3. `outcome` が `failed` または `cancelled` なら、待たずに `failed`(理由: `outcome_failed` または `outcome_cancelled`)を記録して削除しない(`finish_received_at` は記録しない)。
  4. `enumeration_completed` なら、`finish_received_at` を記録し、ソースごとの待ち行列に入れる(9.9)。先行する削除結果が終端状態になってから、9.7 の判定に進む。

**Status API**(`GET /crawls/{crawl_id}`。案): 削除結果を読み取りで返す。内容は、`status`、`reason`(`failed` の理由コードを含む)、`forced`、`target_count`、`denominator`、しきい値、`deleted_count`、`enumerated_count` と `n_seen`・`e_missing`(検証の数値)、時刻である。待機中は、任意項目 `waiting_for`(先行する削除結果の `crawl_id`。案)も返しうる。保持件数を超えて消えた `crawl_id`、開始通知を受けていない `crawl_id`、`loreley-deletions` を失った場合は 404 を返す(案。19章 X11)。Admin View の表示は、同じ内容を Admin API が `loreley-deletions` から直接読む。Status API は削除結果のみを返し、登録結果と確認結果の区分は含まない(確定)。

### 9.6 検証(件数照合)

状態を持たない。次が成立するときだけ、削除の判断に進む。

```text
enumerated_count == N_seen + E_missing
  N_seen    = 当該source_idで last_seen_at >= crawl_started_at の件数（リフレッシュ後の検索インデックス）
  E_missing = skipped_document_ids のうち、検索インデックスにないものの件数
```

- スキップした既存文書は、列挙時の `last_seen_at` の部分更新で `N_seen` に数えられる。スキップした新規文書(検索インデックスにない)は `E_missing` に数える。不一致なら削除せず、`validation_failed` として、3つの数値と `enumerated_count` を記録する。許容差は設けない(案)。`skipped_document_ids` が上限(未決。18章)を超えるときも、削除せず `validation_failed` にする(案)。
- **件数の数え方**(案): 上限を超えた原本の扱い(未決。15.2、19章 X10)が決まるまで、新規の超過文書は `E_missing` に入らず、件数照合が不一致になりうる。その場合は削除しない(安全側。そのソースの削除が止まり続けるため、早めに決める)。`enumerated_count` は、Crawler が `document_id` で重複を除いて数える(列挙が同じ文書を 2 回返しても 1 と数える)。抽出に失敗した文書(`extract_failed`)は、タイトルとメタデータが登録されて検索インデックスにあるので、`N_seen` に数えられる。`N_seen` は、列挙以外の書き込みでも増えうる(例: 突合ジョブの再登録)。その場合は不一致になり、削除しない(安全側)。突合ジョブは、同じソースのロックを取るジョブとして、クロールと同時には動かさない前提とする。
- **旧い削除の件数照合**(案。許容する): 件数照合は、順番が来た時点で行う。旧い削除が待機している間に、新しいクロールが `last_seen_at` を更新したり、新しい文書を登録したりすると、`N_seen` が `enumerated_count` と合わなくなりうる。この場合は `validation_failed` になり、削除しない側に倒れるだけなので、許容する。削除が遅れるだけで、TTL 方式のため安全である。

### 9.7 判定の順序

`enumeration_completed` の終了通知を受けたとき。待機中も判定中も、削除結果は `running` である。

| 順 | 確認 | 満たさないとき |
| --- | --- | --- |
| 受理時(1回のみ。`finish_received_at` が未記録の結果だけ) | 削除結果が終端状態でない(`superseded` などで整理済みでない。世代の判定) | 何もしない(202。終端状態のまま。削除しない) |
| 1 | 先行する削除結果(定義は 9.9)が、すべて終端状態 | 待機する(`running` のまま。先行が終端状態になるまで次へ進まない) |
| 2 | メンテナンスフラグ(`loreley-jobs`)がない | `failed`(理由: `maintenance`) |
| 3 | 件数照合が成立(9.6) | `validation_failed` |
| 4 | 削除対象の決定(`last_seen_at + TTL < 現在時刻`、スキップ文書を除外。TTL は複写した値) | 対象が 0 件なら、`deleted`(`deleted_count=0`) |
| 5 | 割合ルール・最小件数ルール(9.3。しきい値と最小件数は複写した値)。強制削除モードは無視 | `skipped_by_ratio` |
| 6 | 削除の実行(バッチごとに、実行の直前にメンテナンスフラグと自分の削除結果の状態を確認する。最初のバッチの前も含む) | フラグがあれば、そのバッチを実行せず `failed`(理由: `maintenance`)。自分の削除結果が終端状態(ソース削除で `discarded`(`source_deleted`)になった場合)なら、結果を書き換えずに止まる |

- 世代の判定は、順6のバッチごとの確認から外してある(バッチごとの世代確認は行わない)。新しい開始通知が来ても、受理済みの旧い削除は止まらない。
- 順2〜6では、結果を書く前(状態遷移の書き込みの前)に、自分の削除結果を読み、終端状態(ソース削除の `discarded`)なら、書き換えずに止まる確認が入る。自分の削除結果が読めない(404)場合、条件付き更新が失敗した場合も同じである。待機から判定への遷移では、`deletion_started_at` を `if_seq_no` の条件付き更新で書く(案)。

### 9.8 削除の実行

- **バッチの流れ**: (1)対象を再抽出する(リフレッシュ後。バッチ件数は未決。18章)。(2)**バッチの実行の直前に**、メンテナンスフラグと、自分の削除結果(`deletion_result-{crawl_id}`)の状態を確認する。最初のバッチの前も含む。フラグがあれば、そのバッチは実行せず、`failed`(理由: `maintenance`)にして止める。自分の削除結果が終端状態なら(ソース削除で `discarded`(理由: `source_deleted`)になった場合。9.14。案)、そのバッチは実行せず、結果は書き換えずに止める。世代は確認しない。(3)バッチの各文書について、削除の直前に、検索インデックスから現在の `last_seen_at` を ID で読み直し、`last_seen_at + TTL < 現在時刻`(TTL は複写した値)を再確認する。満たす文書だけ、Store 層、検索インデックスの順に削除する。満たさない文書(抽出のあとに更新された文書)は削除しない。実行中のバッチは、途中でフラグが立っても止まらず(止まるのはバッチの単位)、次のバッチの前の確認で止まる。**新しいクロールが始まっても、旧い削除は止めない。** その間に新しいクロールが更新した文書は、(3)の TTL の再確認で消えない。これが、旧い削除を終端まで走らせてよい根拠である。
- **順序と窓**: Store 層(`loreley-texts`)、検索インデックスの順に削除する。検索インデックスの削除にも同じ条件を付ける(条件付きの削除)。再確認から Store 層の削除までの極小の窓で `last_seen_at` が更新された場合や、Store 層の削除の後に止まった場合は、Store 層だけが消えて検索インデックスに文書が残る。この文書は、次の全件更新で全文 upsert され、Store 層も復旧する(自己修復)。突合ジョブ(10章)が先に走ると、検索インデックスの文書は削除され、次の全件更新で再登録される。この窓は、`loreley-texts` を廃止すると消える(SD は「廃止を予定する版で消える」と書くが、廃止自体は未決。19章 X2)。
- **ソース削除での停止**(案): バッチ前の確認に加え、削除結果の各状態遷移の書き込み(待機から判定への遷移で `deletion_started_at` を書くとき、`deleted` などの終端状態の記録)の前にも、自分の削除結果を読む。書き込みは `if_seq_no` の条件付き更新にして、終端状態(ソース削除の `discarded`)を上書きしない。条件が外れたら、その削除結果は変えずに止まる。自分の削除結果が読めない(404。記録ごと削除された場合)ときも、書き換えずに止まる。待機中のものも、順番が来て判定に進む前に同じ確認を行う。逆に、ソース削除側の `discarded` の書き込みが衝突したときは、読み直して再試行し、終端状態になるか `discarded` にできるまで繰り返す(細部は未決。18章)。
- Indexer が待機中、判定中、または削除の実行中に再起動した場合は、その削除結果を `failed`(理由: `indexer_restart`)にし、再開しない。起動時に、`finish_received_at` があって終端状態でない削除結果(待機中のものを含む)をすべて対象にする。残りの削除は、次のクロールに委ねる(TTL 方式のため、削除が遅れるだけである)。再起動時の整理の細部(待機中を含む対象判定)は未決(18章)。
- Indexer 側の削除のエラーは、リトライ設定(4.4)の回数まで試し、直らなければ `failed`(理由: `delete_error`。エラーの種類も記録)にして止める。それまでの削除件数は記録する。

### 9.9 削除の直列化

方式はユーザー承認(確定)。待ち行列の持ち方などの細部は案。

同じソースの削除は、前の削除が終端状態になるまで、後の削除の判定も実行も始めない。旧い削除と新しい削除は重ならない。方式は、Deletion Manager がソースごとに判定・実行を直列に処理する形である。

1. 開始通知は、即時に受理する(現行世代の更新、`deletion_result-{crawl_id}` を `running` で作成、409 の規則は変えない)。旧い削除が進行中でも待たせない。
2. 受理した終了通知(`enumeration_completed`)は、ソースごとの先入れ先出し(FIFO。受理した順)の待ち行列に入れる。先行する削除結果が終端状態になってから、判定(9.7)と実行を始める。待機中も削除結果は `running` である。先行が `failed` などで終わっても、後続はそのまま順番に進む。
3. 待ち行列は、`loreley-deletions` の状態(`finish_received_at` があって終端状態でない削除結果。`finish_received_at` の順)から導き、専用の待ち行列を別に持たない(案)。Indexer の再起動では待機中のものも `failed`(`indexer_restart`)になるので、待ち行列を復元する必要はない。
4. 新しい開始通知が `discarded`(理由: `superseded`)にするのは、`finish_received_at` の無い旧い結果だけである(終了通知が届かなかった世代の整理)。受理済みの結果には何もしない。この開始通知の `superseded` 化と、終了通知の受理(`finish_received_at` の記録)が競合しないよう、Deletion Manager はソースごとに、開始通知と終了通知の受理を直列に処理する(案。代わりに、`superseded` 化を「`finish_received_at` が無い」ことを条件にした条件付き更新にしてもよい)。
5. 遅れて届いた旧世代の終了通知(その結果は、新しい開始通知で `discarded`(理由: `superseded`)になっている)の確認は、終了通知の受理時に1回だけ行い、何もしない(202)。受理後は、待機中、判定中、バッチの間に世代を再確認しない。メンテナンスフラグの確認は、判定の前とバッチごとに残す。
6. **先行する削除結果**(案): 同じ `source_id` で、`finish_received_at` が自分より前(同値なら `crawl_id` の辞書順など、決定的な規則)かつ終端状態でない削除結果。`finish_received_at` の無い `running`(終了通知が届いていない世代)は先行にならず、待たない。
7. **古い世代でも削除してよい根拠**: 受理済み・待機中の削除結果は、順番が来た時点で現行世代でなくなっていても、削除してよい。削除は各文書の直前に TTL を再確認し、対象は順番が来た時点で再抽出するので、受理時の古い対象リストでは動かない。設定スナップショットは、その世代の複写を使う。

例(3世代が続く場合。ポーリングのタイムアウト、または終了通知後の取り消しでロックが解放された場合が前提): クロール A、B、C が同じソースで続き、A の削除が実行中に B が終了通知を送り、続けて C が開始通知・終了通知を送る。A の削除は、B の開始通知にも、C の開始通知にも止められず、終端状態まで走る。B の削除結果は、受理後、A が終端状態になるまで `running`(待機中)である。C の削除結果は、B が終端状態になるまで `running`(待機中)である。判定・実行の順は、A、B、C になる。各削除は、自分の設定スナップショット(複写)で動く。

- **Status API での待機中の見え方**: 状態は増やさず、`running` のままである。先行する削除結果が終端状態でない間は、任意項目 `waiting_for`(先行する削除結果の `crawl_id`)を返してよい(案)。
- **Crawler のロック**: 変更しない。待機が長引き、Crawler のポーリングが上限時間を超えたときは、従来のタイムアウトの経路(警告と区分を残す、ジョブの status は変えない、ロックを解放する。Crawler 領域)を使う。ロックが解放されたあとに次のクロールが始まっても、その削除は旧い削除の後ろに並ぶだけである。
- **旧い削除が終わらない場合**: 強制終了のタイムアウトやハング検知は設けない(ユーザー決定)。Indexer の停止は再起動時の `failed`(`indexer_restart`)、メンテナンスはフラグによる `failed`(`maintenance`)、削除のエラーはリトライのあとの `failed`(`delete_error`)で、それぞれ終端状態になる前提である。それ以外の原因で終わらない場合、後の削除は待ち続ける。新しい削除が遅れるだけで、TTL 方式のため安全である(受容事項)。
- 待機中を進める契機(イベントか定期走査か)、同時刻時の順序(`crawl_id` の辞書順は案)、ソースが異なる削除の並行度は未決(18章)。

### 9.10 削除結果の状態と理由コード

状態名・項目の定義は `loreley-deletions-v0.1.md` が持つ。判断に必要な範囲を示す。

| 状態(`status`) | 意味 |
| --- | --- |
| `running` | 開始通知を受けてから終端状態になるまで(終了通知待ち、待機中、判定中、削除中を含む) |
| `deleted` | 判断を通り、削除を完了した(対象が 0 件の場合を含む)。`deleted_count` を記録する。強制削除モードなら `forced=true` |
| `skipped_by_ratio` | 割合ルールで削除しなかった。T、D、しきい値を記録する |
| `validation_failed` | 件数照合の不一致、またはスキップ文書 ID の上限超過。数値を記録する |
| `discarded` | 終了通知が届かなかった旧い世代の整理(新しい開始通知による。`superseded`。`finish_received_at` の無いものに限る)、ソース削除で破棄された(`source_deleted`)。`reason` に区別を記録する(理由は2つ)。`superseded` の結果に遅れて届いた終了通知は、何もしない。未知の `crawl_id` は記録しない |
| `failed` | 削除が完了しなかった、または行わなかった。理由コードを `reason` に記録する(下の表)。再開しない。削除結果の状態であり、ジョブの status は変えない |

`running` 以外が終端状態である。

**`failed` の理由コード**(案。コードの名称は実装時に調整する)

| 理由コード | 場面 |
| --- | --- |
| `outcome_failed` / `outcome_cancelled` | 終了通知の `outcome` が `failed` / `cancelled`(列挙の失敗、取り消し)。削除しない |
| `maintenance` | メンテナンスフラグが立っていた(判定の前、バッチの前。待機中だったものが順番が来た時点で立っていた場合を含む) |
| `indexer_restart` | 待機中、判定中、削除の実行中に Indexer が再起動した |
| `delete_error` | 削除のエラーが、リトライ設定の回数まで試しても直らなかった(エラーの種類も記録する) |

### 9.11 Crawler の手順との境界

Crawler の手順(Crawler 領域)のうち、Indexer の動作と接する点を示す。

1. ソースのロックを取得する。
2. 開始通知を送る。
3. 列挙、`last_seen_at` の部分更新、バッチ登録を行う。
4. 全バッチ登録の応答を確認する。
5. 終了通知を送り、202 を確認する(これより前なら、取り消しで `outcome=cancelled` を送って終えられる)。
6. Status API をポーリングして、削除結果が終端状態になるのを待つ。間隔と上限時間は未決(18章)。
7. 削除結果の要約と確認結果の区分(案)をジョブ記録に残し、ジョブの最終状態を記録する。
8. ロックを解放する。

- ロックは、削除結果が終端状態になるまで保持する(次のクロールとの競合を減らす)。ポーリングの失敗(リクエストのタイムアウト、接続エラー・5xx、404)が連続でリトライ設定の回数まで続いた場合、またはポーリング全体の上限時間を超えた場合は、警告と確認結果の区分をジョブ記録に残すだけで、ジョブの status は変えない。Crawler は、区分を残したあとに再確認しない(確定)。区分の名称と規則(`confirmed` / `unconfirmed` / `unknown`)は案で、Crawler 領域。
- ポーリング中もジョブは `running` で、ハートビートを続ける。列挙が失敗または取り消しになったときは、ポーリングせず、ジョブを終えてロックを解放する。
- **終了通知を送ったあとの取り消し**は、削除処理を止めない。ジョブは `cancelled` になり、Crawler はポーリングを打ち切って(確認結果の区分は `unconfirmed`。案)ロックを解放するが、Indexer は判断と削除を続け、結果は削除結果に残る(削除結果とジョブの status は切り離されている)。
- ポーリング中に Crawler が停止、またはリース切れとなり、回復でジョブが `failed` になった場合は、区分を残さない(案。回復時に区分を書くかは未決)。
- Status API の 404 は、保持件数の超過、または `loreley-deletions` の喪失を意味する(Crawler 側では区別できない)。

### 9.12 競合と失敗の扱い

| 状況 | 扱い |
| --- | --- |
| 旧い削除(終了通知を受理済み。待機中、判定中、実行中)があるときに、新しいクロールの開始通知が来る | 開始通知は即時に受理し、現行世代を更新する。旧い削除は止まらず、終端状態まで続く(バッチの途中でも、次のバッチの前でも、最初のバッチの前でも止まらない)。新しい削除は、終了通知の受理後、旧い削除が終端状態になってから判定・実行する |
| 終了通知が届いていない旧い結果(`running`)があるときに、新しい開始通知が来る | `discarded`(理由: `superseded`)にする。新しい世代の終了通知で改めて判断する |
| 古い `crawl_started_at` の開始通知(遅れて届いた、再送)、終端状態の `crawl_id` の開始通知 | 409 で拒否する。世代は変わらない。ジョブは `failed` |
| 終了通知の重複 | 冪等(受理時の分岐の先頭。記録済みの再送は世代を見ない)。再処理しない |
| 終了通知が届かない(Crawler の停止、通信失敗) | 削除結果は `running` のまま。削除されない。次の開始通知で `discarded`(`superseded`)になる |
| 開始通知なしの終了通知、未知の `crawl_id` | 削除結果を作らず(記録しない)、202 を返す。削除しない |
| 旧世代の遅れた終了通知 | `finish_received_at` が記録済みの再送なら、世代を見ずに冪等(何もしない。受理済みの旧い削除は止まらない)。未記録で、結果が `superseded` などの終端状態なら、何もしない(202。状態は変えない)。未知の `crawl_id` は記録せず破棄する。削除しない。受理後の再判定はしない |
| 終了通知を送ったあとの取り消し | 削除処理は止まらない。ジョブは `cancelled`、結果は削除結果に残る |
| Status API のポーリングの失敗、待機中のままのポーリング全体の上限時間の超過 | 警告と確認結果の区分(`unconfirmed` / `unknown`。案。Crawler 領域)をジョブ記録に残すのみ。ジョブの status は変えない。ロックを解放する。待機中のまま上限時間を超えた場合、削除結果は `running` のまま待機を続ける。Crawler は再確認しない。Admin View が「結果未確認」「結果不明」と現在値を表示する |
| メンテナンスフラグ | 判定の前と各バッチの実行の前に確認し、立っていれば止める(`failed`、理由: `maintenance`)。待機中のものは、順番が来た時点で立っていれば判定に進まず `failed` にする。削除の実行も、メンテナンス停止の対象である(11章) |
| Indexer の再起動 | 待機中、判定中、実行中の削除結果をすべて `failed`(理由: `indexer_restart`)にする。再開しない |
| ソース削除(9.14)のときに削除結果が `running` | 終端状態でない削除結果を、`if_seq_no` の条件付き更新で `discarded`(理由: `source_deleted`)にする。そのあとで記録を削除する。待機中・判定中・実行中の削除は、バッチ前と各状態遷移の書き込みの前に自分の削除結果を読み、終端状態なら止まる。読めない(404)、または条件付き更新が失敗した場合も、書き換えずに止まる。ソース削除側の `discarded` の書き込みが衝突したら、読み直して再試行し、終端状態になるか `discarded` にできるまで繰り返す(案。細部は未決) |
| 時刻 | `crawl_started_at`、`last_seen_at`、TTL の判定は、Crawler と Indexer が同じホストの時計で動く前提(時刻ずれは想定しない) |

### 9.13 受容事項

(1)新しいクロールが始まっても、終了通知を受理済みの旧い削除は破棄も中断もされず、終端状態まで走る(各文書の削除直前の TTL 再確認があるので、新しいクロールが更新した文書は消えない)。終了通知が届かなかった旧い世代だけが、`discarded`(`superseded`)になる。

(2)新しいクロールが失敗し続けると、削除は遅れるだけである(TTL 方式のため安全)。

(3)登録・`last_seen_at` の更新は世代を確認しない(所有確認のみ。8章、13.2)。件数照合は、遅れた登録の取りこぼしがあれば不一致になり、削除を止める。

(4)ポーリングのタイムアウト後、または終了通知後の取り消し後は、ロックが解放されるので、突合ジョブや次のクロールが旧クロールの削除と重なりうる。次のクロールの削除は旧い削除の後ろに並ぶ。件数照合の不一致なら削除されず、削除の実行中は各削除の直前の TTL 再確認が働くので、安全側に倒れる。

(5)旧い削除がハングした場合の保護は設けない。再起動、メンテナンス、エラーで終端状態になる前提で、それ以外の原因で終わらなければ、新しい削除は待ち続ける。遅れるだけで、TTL 方式のため安全である。

(6)旧い削除の件数照合は、待機中の新しいクロールの更新で不一致になりうる。削除しない側に倒れるだけなので許容する(案)。

(7)待機中の削除も、開始通知を受理した時点の設定(複写した値)で動く。待機の間に管理者が設定を変えても、その削除には反映されず、次のクロールから反映される(案)。

(8)旧い削除の待機時間が、後続クロールのポーリングの上限時間を消費し、警告(確認結果の区分 `unconfirmed`。Admin View の「結果未確認」の表示に当たる)が増えうる。削除結果自体は、ロック解放後も待機を続けて終端状態になる。Admin View は「結果未確認」に `loreley-deletions` の現在値(待機を終えた終端状態)を併記するので、管理者は最終状態を確認できる。

(9)**しきい値の範囲外の値**(既知の制限): 範囲(0% 以上 100% 未満)の検証は Admin API だけで行い、Crawler と Indexer は検証しない(確定)。最小件数と TTL は、Admin API も範囲を検証しない(定めない)。Admin API を経由しない経路は次のとおりで、いずれも範囲外・不正な値が入りうる: (i)Crawler の設定受付への直接入力、(ii)Indexer の開始通知への直接呼び出し(受け取ったスナップショットの値をそのまま使う)、(iii)`loreley-sources` への直接書き込み、バックアップからの復元、(iv)旧版の SD で保存された値。(i)と(ii)は、内部通信が内部ネットワークだけで行われ、ホストに公開されない前提の中で、呼び出し元を信頼するものとして受容し、防御は足さない(案)。Admin API の更新で値が省略された場合に、保存済みの値を保つか欠損とするかは未決(18章)。範囲外の値が入った場合、割合ルールは次のように動く。
- (a)100% 以上: T÷D は 1 を超えないので、必ず「しきい値以下」になり、割合ルールが働かない。最小件数を超える大量の削除でも止まらず、TTL が経過した対象の全件が削除されうる(強制削除モードと同じ結果になる。ただし、列挙の完了、件数照合、各文書の TTL の再確認は働く)。
- (b)負の値: T÷D は 0 以上なので、必ず「しきい値を超える」になり、割合ルールで削除されない側に倒れる(`skipped_by_ratio`)。ただし、T が最小件数以下なら、先に最小件数ルールで削除される。
- (c)しきい値の欠損・NaN・数値以外、および最小件数の欠損・負・NaN・数値以外の場合の挙動は、定義がない。新しい仕様は置かず、挙動は不定とする(未決)。分母 D=0 は(c)に含まれない。(c)に含まれるのは最小件数の不正値であり、D=0 ではない。D=0 なら T=0 で、9.7 の順1〜3 を通過すれば、順4(削除対象が 0 件)で `deleted` となる。いずれも除算せず、最小件数の値に依存しない。最小件数の不正値で未定義なのは、T>0 のときの割合ルールの判定1(最小件数ルール)の結果である。したがって、Admin API 以外の経路での設定は運用で避ける。

### 9.14 データソースの削除(Indexer に要請される部分)

データソースを削除するときは、次の手順を取る(実行は Crawler のジョブ。案)。

1. そのソースの終端状態でない削除結果(終了通知待ち、待機中、判定中、削除の実行中の `running`)を `discarded`、理由 `source_deleted` にする(Indexer が行う。結果の書き込みは `if_seq_no` の条件付き更新で、すでに終端状態の結果は上書きしない)。
   - 待機中・判定中・削除の実行中のものは、バッチの前と各状態遷移の書き込みの前に自分の削除結果を読み、終端状態なら止まる。自分の削除結果が読めない(404)場合、または条件付き更新が失敗した場合も、書き換えずに止まる。
   - ソース削除側の `discarded` の書き込みが衝突したときは、読み直して再試行し、終端状態になるか `discarded` にできるまで繰り返す(細部は未決。案)。
   - ポーリングのタイムアウト後にロックが解放された場合などで、ソース削除の時点で削除結果が `running`(待機中を含む)でありうるため、削除結果の破棄を先に行う。
2. その `source_id` の文書を Store 層、検索インデックスの順にすべて削除する(Indexer)。
3. そのソースのスキップ記録とロック文書(`lock-{source_id}`)を削除する(Crawler。案)。
4. 削除の記録(`loreley-deletions` のそのソースの `deletion-{source_id}` と `deletion_result-*`)を削除する(Indexer)。
5. 最後にデータソース設定を削除する。途中で止まった場合に備え、設定の削除は文書、スキップ記録、削除の記録の削除が終わってから行う。

- 削除結果の破棄、文書の削除、削除の記録の削除は Indexer に要請し(`loreley-deletions` に書くのは Indexer だけ)、スキップ記録とロック文書は Crawler が削除する(案。細部は未決)。この Indexer 呼び出しの形は SD に定義がない(18章)。
- この削除は、期限による削除の判断(9.2)を通らない(ソース全体の削除であり、割合ルールの対象外)。
- ソース削除のジョブは、自分のロック文書をこの手順の中で先に削除してからジョブを終了する(案)。

## 10. 突合ジョブ

検索インデックスと Store 層の食い違いを検出し、安全な範囲で直す。Admin View から手動で実行する。ジョブとしての起動・管理は Crawler、検索インデックスと Store 層の実際の読み書きは Indexer が担う(案。細部は未決)。突合ジョブはソースごとの実行ロックを取り、同じソースのクロールと同時には動かさない(案)。定期実行は将来(要否と周期は未決。18章)。MVP では、**検出と安全な再登録まで**にとどめる。

**比較する項目**: 同じ `document_id` の存在確認に加え、`content_hash` と `index_status` は、次の2つに限って比べる。(1)`pending_index` が `pending_since` から一定期間続いているもの、(2)Store 層の `index_status` が `extract_failed` で、検索インデックスの写しが `indexed` である食い違い。更新の途中で通常起きる短時間の不一致は、誤検出しない(検出対象にしない)。

| 食い違い | 対応 |
| --- | --- |
| 検索インデックスにあって Store 層にない文書(削除が途中で止まった場合に発生しうる) | 検索インデックスから削除する(Store 層が正のため) |
| 同じ `document_id` が両方にあり、上の限定した条件に当てはまる `content_hash`・`index_status` の不一致 | 検出して、Admin View に表示する。元ファイルが存在するなら、再索引化(Store 層の確定済みの本文からの再登録、または次のクロールでの再処理)を試みる |
| Store 層にあって検索インデックスにない文書(`index_status=pending_index`。登録の失敗で発生する) | 次の項目の方針に従う |

**`pending_index` の文書の扱い**: `pending_since`(`pending_index` になった日時。登録に成功して解消するまで更新しない)は、**削除条件にしない**。期限を過ぎたことだけを理由に消すと、一時的な障害で登録できなかっただけの実在文書を誤って消すためである。`pending_since` は異常検知にだけ使う(案。ユーザー未確認)。

| 状況 | 対応 |
| --- | --- |
| `pending_index` が続いている | Admin View で警告する(`pending_since` からの経過期間を表示) |
| 元ファイルが存在する | 再索引化を試みる(次のクロールで再処理される。突合ジョブからの手動の再登録も可) |
| 列挙が正常に完了し、元ファイルの不存在を確認できた | 削除候補とする。MVP では自動削除せず、Admin View で確認して手動で削除する(将来の方式は未決。18章) |
| 元ファイルの存在を確認できない(取得エラー、マウント外れなど) | 自動削除しない |

MVP では、**Store 層にだけ存在する文書の自動削除は行わない**。検出、Admin View の表示、手動確認(安全な再登録を含む)にとどめる。スキップが続く文書も、Admin View で確認して手動で扱う。`pending_index` を警告するまでの期間は未決(18章)。

## 11. 再インデックスとメンテナンス停止

マッピングや辞書を変えるとき、またはインデックスを作り直すときの手段((a)`_reindex`、(b)Store 層からの再構築)は `search-index-v0.1.md` を参照。ここでは、Indexer に関わる停止手順を示す。どちらの手段でも、**再インデックスの対象のデータソース(インデックス全体を作り直すときはすべて)のクロールと要約の書き込みを止めてから**行い、完了後に再開する。削除(Deletion Manager による削除の実行)も実行しない。

**開始前に、実行中の書き込みが終わったことを確認する**: 対象のソースに `running` のクロールがなくなり、`loreley-deletions` に待機中・判定中・削除の実行中の削除結果(`running` で `finish_received_at` があるもの)がなく、Indexer で実行中の要約生成も終わったことを確認する。終わらないときは Crawler と Indexer を停止してから始める(フラグを立てるだけでは、すでに始まっている書き込みは止まらないため)。要約生成はジョブ記録を持たないため、終了の確認は Indexer の停止が確実な手段である。クロールは単一 Crawler・直列実行だが、要約の書き込みはクロールと並行しうる(別コンテナ)ため、Indexer 側の終了も確認する。

**止める手段**: `loreley-jobs` のメンテナンスフラグに一本化する(案)。Crawler と Indexer がフラグを確認して書き込みを控える。実行ロックは、受付時に作られ、クロールの待機・実行中は常に存在するため、メンテナンス用のロックと区別できない。そのため、メンテナンスには使わない。書き込み停止の対象は Crawler と Indexer の**両方**で、Indexer では要約の書き込みに加え、Deletion Manager の削除の判定と、削除のバッチごとの実行も止まる。待機中の削除結果は、順番が来た時点でフラグが立っていれば判定に進まず、`failed`(理由 `maintenance`)になる(9.10)。フラグの確認のタイミングや停止中の応答の扱いなど、細部は未決(18章)。MVP では手動手順(README に記載)とする。画面(Admin View)からの実行は将来拡張とする。メンテナンスフラグの書き込み方法(運用者の手動手順か、Crawler の固定経路)は案(18章)。

README に記載する手順(クロールと要約書き込みの停止、実行中の書き込みの終了確認、コピー、エイリアス切り替え、再開)は、16.6 のテストで確認する。

## 12. 障害と再起動

- **Indexer のダウン・遅延**(接続不可、タイムアウト、サーバ側エラー(HTTP 5xx 等)): OpenSearch 全体の異常と同様に扱う。Indexer が停止している間は、開始通知・登録・終了通知が失敗してクロールが失敗扱いになり、削除されない(E-31)。リトライして直らなければジョブを `failed` にし、削除しない。スキップにはしない。開始通知・終了通知の失敗(開始通知の 409 を含む)も同様に、ジョブを `failed` にする(開始通知の失敗と、終了通知が届かなかった場合は、削除されないだけで安全)。ただし、終了通知の応答が失われただけの場合は、Indexer が受理済みで削除が進みうる。その結果は削除結果に残り、Admin View の削除結果で確認できる場合がある(区分は付かない)。「安全」の根拠は、前提(列挙の完了、全バッチの登録の確認)は終了通知の送信前に確認済みで、実行時は各文書の削除直前の TTL 再確認で守られることである(9.8)。この扱いの対象は、開始通知、登録、`last_seen_at` の部分更新、終了通知の失敗に限る。Status API のポーリングの失敗は含まない(下記)。
- **文書固有の拒否**だけをスキップの対象とする。ロック所有の確認に失敗した場合は、スキップにせずジョブを `failed` にする(案。4.4)。
- **タイムアウト後の Indexer の処理**: Crawler がタイムアウトした後も、Indexer の処理が続く窓がありうる。Indexer は要請を直列に処理し、所有確認を文書ごとに行う(案)。残る窓は既知の制限である(8章)。
- **削除結果の確認(Status API のポーリング)の失敗**: ポーリングの失敗(リクエストのタイムアウト、接続エラー・5xx、404[保持件数の超過、または `loreley-deletions` の喪失])が、連続でリトライの上限まで続いた場合、またはポーリング全体の上限時間を超えた場合も、警告と確認結果の区分(404 のみなら `unknown`、混在を含むそれ以外は `unconfirmed`。案)をジョブ記録に残すだけで、ジョブの status は変えない。Crawler は再確認せず、Admin View が「結果未確認」「結果不明」を表示する(Crawler 領域)。
- **終了通知を送ったあとの取り消し**: 削除処理は止まらない。ジョブは `cancelled` になり、結果は削除結果に残る。取り消しが有効なのは、終了通知を送る前だけである。
- **Indexer の再起動**: 待機中、判定中、削除の実行中だった削除結果は、`failed`(理由 `indexer_restart`)にして再開しない。削除は次のクロールに委ねる。要約生成は `summary_status=pending` の再走査で再開する(案。7.2)。
- **旧い削除が終わらない場合**: 強制終了のタイムアウトやハング検知は設けない。再起動、メンテナンス、エラーのいずれかで終端状態になる前提で、それ以外で終わらなければ、同じソースの新しい削除は待ち続ける。新しい削除が遅れるだけで、TTL 方式のため安全である。
- **待機中の削除**: 新しいクロールが始まっても、旧い削除は止まらない。新しい削除は、旧い削除が終端状態になってから判定・実行する。待機中も Status API は `running` を返す。
- **Crawler の停止**: リース切れで `failed` と表示し、再起動時に回復する(Crawler 領域)。登録中の停止では、登録結果は最後に記録した集計値が「途中」のまま残る。ポーリング中の停止では、登録結果は確定済みで、確認結果の区分は記録されない(案。回復時に区分を書くかは未決)。終了通知が届かない削除結果は、削除されないまま、次の開始通知で `discarded` になる。
- **Admin API から Crawler に届かない場合**: 起動や操作はできないが、ジョブ状態と削除結果の表示は `loreley-jobs`・`loreley-deletions` の読み取りなので続けられる(推測。細部は実装時に確認する)。
- **メンテナンス**: 書き込み停止の対象は Crawler と Indexer の両方で、Indexer の削除の実行も含む。待機中の削除は、順番が来た時点でフラグが立っていれば `failed`(`maintenance`)になる(11章)。細部は未決。
- 同期 HTTP では、遅い Indexer がクロール全体の所要時間を決める。MVP では許容する(15.3)。

## 13. 将来拡張

### 13.1 差分検知と関連機能

MVP の全件更新(4.3)の負荷が問題になったときに導入する設計である。元の記述をほぼそのまま移している(この冒頭の文面は、元の意図を推測して直したものである。推測)。これを導入する場合は、あわせて `extractor_version`・`extract_fail_count`(`loreley-texts` の予約項目)を使う。`last_seen_at` の部分更新と、読めない文書のスキップは MVP で導入済みである。導入の条件は未決(18章)。

**差分検知**

列挙のたびに、文書ごとに次の順で判定する。

1. **スキップ条件**: 次のすべてを満たすときだけ、取得も `content_hash` の計算も省略する(Connector が列挙時に取得した `mtime`・`size` と Store 層の値を比べる。`source_mtime`・`source_size` は列挙時の値、`stored_mtime`・`stored_size` は Store 層に保存した `source_updated_at`・`size` に対応する)。

   ```text
   can_skip = (index_status == "indexed"
               or (index_status == "extract_failed"
                   and extract_fail_count >= 上限))
              and source_mtime == stored_mtime
              and source_size == stored_size
              and extractor_version == current_extractor_version
   ```

   `pending_index` の文書、および失敗回数が上限未満の `extract_failed` の文書は、`mtime`・`size` が一致していても**スキップしない**(処理が完了していないため)。上限に達した `extract_failed` は、`mtime`・`size`・`extractor_version` が変わらない限りスキップする(停止中)。
2. スキップしない場合は原本を取得して `content_hash` を計算する。確定済みの `content_hash` と同じで、かつ `extractor_version` も現在と同じで、かつ `index_status=indexed` なら、本文の再処理は省略し、`mtime`/`size` だけを更新する。
3. `content_hash` が違えば、再抽出して全文 upsert する。
4. `extractor_version`(抽出ロジックとライブラリのバージョン)が変わった場合は、**`content_hash` が同じでも再抽出する**。`extractor_version` の変更は、ステップ2の `content_hash` の一致より優先する。全件を一度に再処理しないよう、クロールの中で順次処理する。
5. 検索インデックスへの登録に成功してから、**最後に** Store 層の `content_hash`・`mtime`・`size`・`extractor_version` をまとめて確定する(`extract_failed` で終わった場合も、`mtime`・`size`・`extractor_version` は確定する。上限到達後のスキップ判定に使うため)。途中で失敗すると確定されないので、次回のクロールで再処理される。登録前の間は `pending_content_hash` と `index_status=pending_index` を持つ。本文を更新した文書は、要約を引き継がず `summary_status=pending` に戻す。

`mtime` と `size` が同じまま内容だけが変わると見逃す。これは既知の限界で、MVP では許容する。

**抽出失敗の再試行**: `extract_failed` の文書は、連続して失敗した回数(`extract_fail_count`)が上限(例: 3 回)に達するまで、次のクロールで再処理する(上記のとおりスキップしない)。上限に達したあとは、**`mtime`・`size`・`extractor_version` のいずれかが変わるか、管理者が手動で再試行するまで**、自動では再処理しない。`content_hash` は、`mtime`・`size` が変わって取得し直したあとに、再抽出が必要かを判定するために使うもので、停止の解除条件そのものではない。`extract_fail_count` は、解除条件を満たして再処理を始める時点で 0 に戻す。上限到達後の文書は、スキップされるのではなく「停止中」として Admin View に表示する。

**発見と取得の分離、`last_seen_at` の部分更新**: MVP に取り込み済み。差分検知を導入して、スキップ条件に一致する文書の取得を省くときも、列挙時の `last_seen_at` の部分更新は引き続き必須である(取得しない文書が、TTL で削除されないようにするため)。

**間引き(任意)**: 5章の部分更新の書き込み量を減らすため、現在の `last_seen_at` が TTL の 1/3 より新しければ更新しない。判定に必要な現在の `last_seen_at` は、検索インデックスから読む(スクリプト内の比較、または一括取得)。間引くと、判定上の TTL は最大で TTL の 1/3 だけ短くなる(実効 TTL は最短で TTL×2/3)。そのため、TTL×2/3 がクロール間隔より長くなるように設定する。

**恒久失敗**: 初期の設計では、同じ文書の取得・登録の連続失敗回数(`fetch_fail_count`)が上限に達したら「恒久失敗」として部分成功の判定から除外する設計だった。MVP では、読めない文書をスキップしても削除が止まらないため、この判定は不要になり、`fetch_fail_count` は廃止した。連続失敗の回数は、スキップ記録の `consecutive_skips` が持つ(新規文書も記録できる)。将来、差分検知の導入時に、長く読めない文書のリトライ負荷を下げたい場合は、`consecutive_skips` が上限を超えた文書の試行回数を減らす(例: リトライなしの 1 回だけ試す)拡張を検討する。導入の条件は未決。

### 13.2 複数 Crawler 化(完全な分散フェンシング)

完全な分散フェンシングは、MVP では行わない。複数 Crawler にするときに、ロックの取得ごとに増える実行世代番号を持たせ、全文 upsert を含むすべての書き込みで古い世代の上書きを原子的に拒否する方式を導入する。

削除については `crawl_id` による世代制御を導入済みで、世代の判定は終了通知の受理時の1回に限る(9章)。登録・`last_seen_at` の更新を含むすべての書き込みへ、世代の確認を広げ、古い世代の書き込みを拒否することは、複数 Crawler 化とあわせた将来拡張とする(現状は所有確認のみ。8章)。

### 13.3 メッセージングへの移行の前提

将来キューが必要になったとき、HTTP 部分をメッセージングに置き換えられるよう、契約は次を満たす。ブローカーの選定は本書の対象外。置き換えても、責務の分担(2.2)は変えない。

- **少なくとも1回配送でも安全**: 登録、`last_seen_at` の部分更新は、重複して届いても結果が変わらない(`document_id` と `content_hash`、max 比較、条件付き更新による)。開始通知・終了通知も、`crawl_id` で冪等である(同じ `crawl_id` の再送は再処理しない(記録済みの終了通知の再送は世代を見ない)。`superseded` の結果に遅れて届いた終了通知は何もせず、未知の `crawl_id` は破棄する。開始通知は、古い `crawl_started_at` か終端状態の `crawl_id` なら 409 で拒否するので、遅れて届いた古い通知で世代が巻き戻らない)。削除は、各文書の「その時点でも TTL を過ぎている」条件により、重複して実行されても結果が変わらない。
- **文書単位の結果が互いに依存しない**: 文書単位の処理結果は、互いの順序に依存しない。ただし、遅れて届く旧要請への完全な対策はフェンシング(13.2)の対象である。終了通知を、全登録の応答確認のあとに送ることは、Crawler の進行制御で保つ。キューに置き換えて、終了通知が登録より先に処理される可能性が出ても、件数照合が不一致になり、削除を止める(9.6)。
- **同期応答は結果イベントに置換可能**: 登録の応答で返す文書単位の結果は、後から届く結果イベントとしても扱える形にする。Status API による削除結果の確認は、結果イベントの購読に置き換えられる。
- ジョブの状態は `loreley-jobs`、削除の状態は `loreley-deletions` にあり、Crawler・Indexer の起動時に回復できる。メッセージが失われても、再実行で復旧できる(推測を含む)。

### 13.4 その他の将来・MVP 方針の整理

- 差分検知の導入条件(全件更新の負荷の実測と条件)、Store 層だけにある文書を期限で削除する方式(そのような文書は検索インデックスに `last_seen_at` がないため、既存の TTL 削除にそのまま合流できない)、突合ジョブの定期実行は、いずれも未決(18章)。
- 長い文書で検索精度に問題が出た場合の見出し・セクション単位の補助インデックスは `search-index-v0.1.md` を参照。

## 14. バックアップ・リストア

導出: バックアップの構成は SD での導出で、プロダクト側の文書に手順の記述はない。手順の中身(コマンド、保存先、周期)は未決で、実装時に決める。

### 14.1 バックアップの対象

MVP では Store 層も OpenSearch にあるため、**OpenSearch のスナップショットと設定ファイル**をバックアップの対象とする。OpenSearch のスナップショットには、`loreley-deletions` も含める(Store 層のインデックスをすべて対象にする)。

### 14.2 スナップショット

ノードが 1 つなので、データの消失に備えてスナップショットを取る。ノード障害時のデータ消失は、OpenSearch を KVS にすることのリスクである。

### 14.3 リストア手順

OpenSearch のスナップショットによるバックアップとリストアの手順を、README に記載する(MVP の受け入れ基準)。手順の中身は未決(18章)。

### 14.4 障害時の再構築

| 状況 | 対応 |
| --- | --- |
| マッピング・辞書・アナライザを変更する | 新しいインデックスを作り、旧インデックスからコピー(`_reindex`)してエイリアスを切り替える。通常はこちらを使う |
| 旧の検索インデックスを失った(Store 層は残っている) | Store 層の抽出済みテキストから、検索インデックスを再構築する。このとき `last_seen_at` は再構築時刻に初期化される。要約は、生成元の `content_hash` が本文と一致するものだけが保持される |
| 検索インデックスと Store 層の両方を失った | 再クロールが必要である |
| `loreley-deletions` を失った(復元できない) | 次のクロールの開始通知で、現行世代が作り直される。それまでに届く終了通知は未知の `crawl_id` として破棄され、削除は行われない。削除結果の履歴は失われる。削除が遅れるだけで安全である(9章) |
| 抽出ロジックを変えた | Store 層からの再構築は使わず、全件更新の再クロールで反映する(4.3) |

検索インデックスは、通常は旧インデックスからのコピーで作り直す。旧インデックスを失った場合に限り、Store 層から再構築する。

## 15. 非機能(Indexer 関連)

非機能要件(文書数・レイテンシ・同時利用数など)は、設計段階では目標値を置かず、実装後に実測して決める。

### 15.1 想定規模

最初のデータソースはローカルディレクトリ／ファイル共有で、規模は 1万〜10万文書を想定する(目標値ではない。要確認)。数十万件を超える規模や、高可用構成は対象外である。単一ホスト、単一ノードの OpenSearch を前提とする。

### 15.2 文書サイズ上限

- 文書の最大サイズ(索引化の上限)と、長い文書に対する検索品質は未決(18章)。上限は、リクエストサイズ・インデックスサイズ・処理時間などの観点で決める。
- Crawler -> Indexer の登録では、大きな原本に上限を設ける。値と形式は未決(18章。`indexer-api-v0.1.md`)。
- **上限を超えた原本の扱い**(ユーザー決定。決定済みの範囲): 取り込まず、原本サイズ超過として文書単位のエラーに記録し、Admin View で確認できる。スキップではなく、リトライもしない。`last_seen_at` は列挙時に更新済みで、削除対象にならない。
  - 未決: エラーの記録先・項目、件数照合での数え方(新規文書が索引にないとき)、ジョブの status への影響(案で、未決)。すでに索引にある同じ文書のデータを残すか、利用者への表示方法も未決。
  - 判定主体(Crawler が送信前に弾くのか、Indexer が拒否するのか)は SD に書かれていない(19章 X10)。
- 本文がサイズ上限を超える場合は、上限までを索引化して `truncated=true` にする。Store 層の `text` は、サイズ上限で切り詰めた後のテキストである。`get_document` の `total_length` は保存済みの長さで、上限を超える部分は取得できない(Search API 側)。
- ハイライトの解析上限(`index.highlight.max_analyzed_offset`)を理由に、本文を切り詰めない。
- オフセット保存(`index_options: offsets`)による索引の増加量と、上限値は実測して決める。
- 長い文書で検索精度に問題が出た場合は、見出し・セクション単位の補助インデックスを追加できる構成にする(`search-index-v0.1.md`)。

### 15.3 書き込み負荷

- MVP は差分検知をせず、毎回すべての文書を取得・抽出し、全文 upsert(`last_seen_at` の更新を含む)する。列挙時の `last_seen_at` の部分更新も加わり、文書ごとの書き込みが増える(全文 upsert が成功する文書にも行う)。文書数に比例して、クロール時間、OpenSearch の書き込み量とセグメントのマージ負荷、Store 層の書き込みが増える。1万〜10万文書の想定でも、クロール間隔内に完了するかは未検証である。
- 緩和策: クロール間隔は所要時間より長く設定する。本文が変わらない文書の要約は引き継ぎ、要約の再生成を避ける(5章、7.5)。負荷が問題になれば、差分検知(13.1)を導入する。
- `last_seen_at` は検索インデックスの文書に持つため、その書き込み負荷はリスクとして扱う。負荷の実測方針は維持する。
- Crawler -> Indexer は同期 HTTP で完了を確認しながら進めるため、Indexer が遅いとクロール全体の所要時間が延びる。MVP では許容する。バッチの大きさやタイムアウトなどの数値は未決(18章)。
- 全件更新の負荷の実測と、差分検知を導入する条件は未決(18章)。

### 15.4 性能測定(Indexer に関わるもの)

実装時に、次を実測する。

- 代表的な規模で、クロール所要時間と、書き込み量・インデックスの増加を測る(全件更新の負荷。15.3)。
- オフセット保存による増加量と、本文サイズの上限値を測る(15.2)。
- 要約モデルの選定のため、生成時間・コストを測る(7.6)。

検索レイテンシ、同時利用数、ホスト要件などの非機能要件と、検索品質(Recall@10、MRR)の評価は、設計段階では目標値を置かず、実測して決める(検索側。`search-index-v0.1.md`)。

### 15.5 リソース要件(Indexer 関連)

ホスト要件(CPU、メモリ、ディスク)は未決。制約として、単一ホストに Docker Compose で導入し、OpenSearch は単一ノード(`number_of_shards: 1`、`number_of_replicas: 0`)で、ノード障害時のデータ消失に備えてスナップショットを取る(14章)。

## 16. テスト観点

### 16.1 導出元・方針

導出: プロダクト側の受け入れ基準と検証項目に加え、仕様から、テストする観点を導いた。導出であり、プロダクト側の文書に列挙されていたものではない。ケースの粒度は実装時に調整する。

- 異常系の試験は、MVP で保証する範囲(単一 Crawler・直列実行、削除の安全性)に限る。これ以上の異常系は作り込まない。
- 排他とリース切れの動作は、実装時に試験する。
- 各ケースの根拠として、対応する本書の章を示す。「Crawler 領域」は本書の対象外の仕様を指す。
- ID は SD v0.8 の ID を引き継ぐ。ケース内で他の ID(本書に転記していないもの)に触れている箇所は、SD v0.8 の ID のまま(16.8 に一覧)。**D-18 は欠番**(旧案「全件削除の承認の期限と消費」は、承認の廃止により不要になった。ほかの ID を詰め直さないため、番号は空けてある。19章 X12)。

### 16.2 異常系(E-*)

Indexer・削除に関わるものを転記する。Crawler 領域・対象外のものは 16.8。

| ID | 条件 | 期待結果 | 根拠 |
| --- | --- | --- | --- |
| E-1 | 既存文書があるデータソースで、アクセスはできるが列挙が 0 件になる(強制削除モードなし) | 列挙は完了しており、ジョブは `succeeded` になる。件数照合(`0 = 0 + E_missing`)が通れば、割合ルールで判断する。TTL が過ぎていない文書は対象にならない。TTL が過ぎて対象が分母に近づくと、削除結果は `skipped_by_ratio` になり、文書は削除されない。ジョブの status には反映されない。列挙自体がエラーになる場合(マウント外れなど)は E-22 | Crawler 領域(クロール完了状態)、9.2、9.3 |
| E-3 | 検索インデックスへの登録が、リトライ後も失敗する(文書単位の拒否など)(Crawler 領域が主) | その文書がスキップされ、スキップ記録が残る。クロールは部分成功になるが、削除は行われる。Store 層の `index_status` は `pending_index` のまま残る | 4.2、4.4、Crawler 領域 |
| E-4 | OpenSearch 全体に接続できない(Crawler 領域が主) | ジョブは `failed` になり、削除は行われない(終了通知は `outcome=failed` で送るか、届かない。削除結果は `failed`、または `running` のまま次の開始通知で `discarded` になる) | Crawler 領域、9章 |
| E-5 | 文書の抽出に失敗する | タイトルとメタデータだけが登録され、`index_status=extract_failed` になる。Admin View で確認できる。次のクロールで再試行される(回数の上限はない) | 4.2、4.3 |
