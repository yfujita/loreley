## 1. 前提

- Crawler と Indexer は別コンテナ。コンポーネント間はメッセージブローカーを使わず HTTP で直接通信する。内部通信は内部ネットワークだけで行い、ホストに公開しない。単一ホスト、単一 Crawler、単一 Indexer、直列実行、認証なし。(出典: SD v0.8 L1752-1755)
- 契約は、将来 HTTP 部分をメッセージングに置き換えられるよう明確にする(「6.1 冪等性」参照)。(L1756)
- 書き込み役: 検索インデックスと `loreley-texts` に書くのは Indexer だけ。`loreley-deletions`(仮名)に書くのも Indexer(Deletion Manager)だけ。`loreley-jobs` に書くのは Crawler だけ。Admin API は書かず、読み取りのみで直接読む。(L278, L1764-1765)
- Status API の利用者: 本文(L786, L1038, L1059, L1777)は Crawler のみ。**ただし SD v0.8 の用語集(L1736)は「Crawler と Admin View」と書く**(食い違い X1。第 11 章)。
- 時刻: `crawl_started_at`、`last_seen_at`、TTL の判定は、Crawler と Indexer が同じホストの時計で動く前提。(L817)

## 2. 通信の流れ

Crawler がソースのロックを取得してから、次の順に Indexer を呼ぶ。(L1783-1796, L790-799)

| 順 | 呼び出し | 形 | 本書の章 |
| --- | --- | --- | --- |
| ① | 開始通知(ロック取得後・列挙前) | `POST /crawls/start`(案) | 4 |
| ② | 見つかった文書の `last_seen_at` 部分更新の要請 | **未定義(N-4)** | 6 |
| ③ | 文書のバッチ登録(同期。文書単位の結果が返る) | **未定義(N-4)** | 5 |
| ④ | 終了通知(202 で受理) | `POST /crawls/{crawl_id}/finish`(案) | 7 |
| ⑤ | 削除結果の確認(ポーリング) | `GET /crawls/{crawl_id}`(案) | 8 |

- 削除の判断・実行は終了通知を受けた Indexer が非同期に行う。期限による削除を Crawler は要請しない。(L1795, L1801)
- ソース削除と突合ジョブでの削除要請だけは Crawler が Indexer に要請する(第 9 章)。(L1801)
- 終了通知は、すべてのバッチ登録と `last_seen_at` 部分更新の応答を確認してから送る。(L700, L793-794)
- 同期 HTTP では遅い Indexer がクロール全体の所要時間を決める。MVP では許容する。(L1826)

## 3. 共通ドキュメント形式と ID

### 3.1 共通ドキュメント形式

Connector(Crawler)が Indexer に渡す形式。(出典: SD v0.8 L229-243)

| 項目 | 説明 |
| --- | --- |
| `source_id` | データソースの識別子。登録後は変更できない |
| `external_id` | データソース内で一意な識別子(ルートからの相対パス、ページ ID 等)。3.2 の正規化を適用する |
| `title` | タイトル(取得できなければファイル名) |
| `url` / `path` | 原文への参照(表示用) |
| `mime_type` | 文書形式 |
| `raw_content` | 取得済みの原本(MVP では参照ではなく原本そのものを渡す)。抽出前のデータで、検索インデックスの `content`(抽出後の本文)とは別物 |
| `content_hash` | 原本の SHA-256 |
| `source_updated_at` | データソース上の更新日時(ローカルでは `mtime`) |
| `size` | 原本のサイズ(バイト) |
| `fetched_at` | 原本を取得した日時。取得を省略した場合は更新しない |
| `metadata` | Connector 固有の追加属性 |

注記:

- `url` / `path` が 1 項目か 2 項目かは SD v0.8 に明記がない(食い違い X8)。表記は SD のまま。
- `fetched_at` と `metadata` の保存先は SD v0.8 に書かれていない(X7)。`fetched_at` は「取得を省略した場合は更新しない」と書かれるが、MVP は全件取得で省略しない。
- `last_seen_at` は共通ドキュメント形式に含めない。Crawler は実行コンテキストとして `crawl_started_at`(クロールの開始時刻)を渡し、Indexer が `last_seen_at` に書く。`fetched_at` は「取得した日時」、`last_seen_at` は「列挙で見つかった日時」。(L245)
- `content` の意味は場所ごとに異なる。(L247-254)

| 場所 | 名前 | 意味 |
| --- | --- | --- |
| Connector → Indexer | `raw_content` | 取得済みの原本 |
| Store 層 | `text` | 抽出・正規化後のテキスト(サイズ上限で切り詰め後) |
| 検索インデックス | `content` | `text` と同じ内容を検索用に解析したもの |

(SD v0.8 にはこの表に `get_document` 応答の `content`(`text` の指定範囲)の行があるが、Search API 側の話のため省略した。)

### 3.2 ID

(出典: SD v0.8 L260-264)

- `document_id` = `SHA-256(source_id + "\0" + external_id)` の 16 進文字列(小文字)。NUL 文字で区切る。
- `external_id` は、ハッシュの前に Unicode NFC へ正規化し、パス区切りを `/` に統一する(ルートからの相対パス、先頭に `/` を付けない)。大文字小文字は区別したまま扱う。
- 同じ文書を再取得すると同じ ID になるため、再実行しても重複しない。検索インデックスと Store 層のどちらも `document_id` を文書 ID として使う。
- `source_id` は登録後に変更できない。変更は新しいデータソースとして登録し直す。
- パスの変更・リネームは「旧 ID の削除 + 新 ID の追加」として扱う。リネームの追跡は初期要件にしない。

## 4. 開始通知

`POST /crawls/start`(案)。(出典: SD v0.8 L689-696, L685, L687)

- **送るタイミング**: ロック取得後、列挙の前。
- **内容**: `crawl_id`、`source_id`、`crawl_started_at`、設定スナップショット(`ttl`、`ratio_threshold`、`min_delete_count`)、`force_delete`(既定は `false`)。
- `crawl_id` は Crawler のジョブ ID をそのまま使う(新しい ID を採番しない)。現行世代は、そのソースで最後に受理した開始通知の `crawl_id`。
- **判定の順序と拒否**(409。案)。次の順で判定する。
  1. `deletion_result-{crawl_id}` がすでに終端状態なら 409 で拒否する(終了したクロールの通知が再送されても `running` に戻さない)。
  2. 同じ `crawl_id` で削除結果が `running` なら、状態を変えずに成功を返す(再送)。
  3. `crawl_started_at` が現行世代の `crawl_started_at` より古ければ 409 で拒否する(世代の巻き戻り防止)。
  - Crawler は 409 をジョブ `failed` として扱う。
- **即時の受理**: 旧い削除が待機中・判定中・実行中でも待たせず、すぐに受理する。
- **Indexer の動作**(上の判定を通ったとき): `deletion-{source_id}` の現行世代を更新し、`deletion_result-{crawl_id}` を設定スナップショットの複写つきで `running` で作る(複写は案)。同じソースに、`finish_received_at` の無い `running` の旧い削除結果(終了通知が届かなかった世代)があれば `discarded`(理由 `superseded`)にする。`finish_received_at` のある結果(待機中・判定中・実行中)には何もしない。
- **通知の失敗**(リトライ設定の回数まで試しても直らない場合)はジョブ `failed`。開始通知の失敗は、削除が行われないだけで安全。
- 設定スナップショットの項目名・複写の項目名は案(食い違い X4。第 11 章)。判定と実行は、複写した値を使い `deletion-{source_id}` からは読まない。構造の詳細は `loreley-deletions-v0.1.md` を参照。

リクエスト/レスポンスの本文形式、成功時の応答コードとボディ、エラーコード名: **SD v0.8 では未定義(N-4)**。

## 5. バッチ登録

(出典: SD v0.8 L1798-1800, L415, L426, L1696)

エンドポイント、リクエスト/レスポンスの形式、エラーコード: **SD v0.8 では未定義(N-4)**。SD が決めているのは次の方針だけである。

- Crawler → Indexer の文書の登録は**同期 HTTP のバッチ登録**。完了を確認しながら進める。
- 応答は**文書単位**に結果を返す。失敗した文書だけを再送でき、再送しても登録の状態が変わらない(冪等。`document_id` と `content_hash` で判定)。
- 登録結果の集計のため、文書単位の応答には**新規か更新かも含める**(案。項目の形は未決)。Crawler が応答を集計して `loreley-jobs` に記録する(集計は Crawler の領域。第 8 章末の注記)。
- 大きな原本には上限を設ける。値と形式は未決(N-3, N-5)。
- 数値(バッチの件数と合計サイズ、タイムアウト、並列度): 未決(N-3)。リトライ回数は Crawler 側の既定値(最大試行 3 回、バックオフは初回 1 秒・2 倍ずつ・上限 30 秒・ジッタあり。いずれも案)を維持する。(L1679, L442-447)

Indexer 側の登録処理の挙動(抽出、Store 層・検索インデックスへの書き込み順、競合時の扱い)は `indexer-architecture-v0.1.md` を参照。

### 5.1 失敗の返し方

(出典: SD v0.8 L426, L440, L449-452, L1816-1817)

- 検索インデックスへの登録に失敗した場合、Indexer は**文書単位の失敗種別**を返し、Crawler が最大試行回数までリトライして、それでも失敗したらその文書をスキップする。失敗種別の具体名は未決(N-4)。
- スキップの対象は**文書固有の拒否**(マッピング違反、文書の内容に起因する 4xx など)だけ。文書固有の 4xx のスキップが連続して 20 件(案。設定可能)に達したら `failed`。
- 次は OpenSearch 全体の異常として、スキップせずジョブ `failed` にする: 接続エラー、タイムアウト、HTTP 429、5xx、`cluster_block_exception`、circuit breaker。
- Indexer の異常(接続不可、タイムアウト、HTTP 5xx 等)も同様に扱い、リトライしても直らなければジョブ `failed`、削除しない。「Indexer・Store 層の障害でクロールが失敗扱いのときは削除しない」はユーザー確認済み(確定)。リトライ回数・連続 20 件・エラー種別・ジョブ `failed` の対象範囲の細部は案。
- ジョブ `failed` の扱いの対象は、開始通知、登録、`last_seen_at` の部分更新、終了通知の失敗に限る。Status API のポーリングの失敗は含まない(8 章)。
- 抽出の失敗はスキップではなく `extract_failed`(タイトルとメタデータを登録)として扱い、リトライしない。

### 5.2 原本サイズ超過

(出典: SD v0.8 L1172, L1680)

- 確定(ユーザー決定)の範囲: 上限を超えた原本は取り込まず、原本サイズ超過として文書単位のエラーに記録する。スキップではなく、リトライもしない。`last_seen_at` は列挙時に更新済みで、削除対象にならない。
- **未決**: 上限の値と形式。誰が拒否するか(Crawler が送信前に弾くのか、Indexer が拒否するのか。SD に記載なし。X10)。エラーの記録先・項目。新規文書が索引にないときの件数照合での数え方(`skipped_document_ids` に含めるか別項目か。含めないと `enumerated_count` と `N_seen + E_missing` が合わない)。ジョブ status への影響。既存の索引データを残すか。

## 6. `last_seen_at` の部分更新

(出典: SD v0.8 L374, L413, L438, L1681)

エンドポイント、リクエスト/レスポンスの形式、要請する単位、結果の返し方: **SD v0.8 では未定義(N-4)**。SD が決めているのは次のとおり。

- Crawler が列挙で文書を見つけた時点で、見つかったすべての文書について、Indexer に `last_seen_at` の部分更新を要請する。書き込むのは Indexer。取得より前に行う。値は `crawl_started_at`。
- 更新は検索インデックスの現在値との max 比較(スクリプト更新)。新しい値のときだけ書き、古い値で上書きしない。ほかのフィールドは変更しない。
- 検索インデックスに文書がない場合(404)は何もしない(upsert しない)。
- 取得・抽出・登録が失敗しても更新済みのまま残る。これにより、取得に失敗してスキップした文書が TTL で誤削除されない。
- 部分更新が失敗したとき(OpenSearch への書き込み不可など)は、その文書をスキップとして扱わず、ジョブを `failed` にして削除しない。(「`last_seen_at` を保存できなければクロールを完了扱いにしない」は、案。ユーザー未確認)
- 重複して届いても結果が変わらない(max 比較による)。

## 7. 書き込み要請に添えるロック所有情報

(出典: SD v0.8 L870, L874, L1691)

- 登録と `last_seen_at` の更新の前に、**Indexer が**ロック文書(`loreley-jobs` の `lock-{source_id}`)を ID で取得し、要請したジョブの所有者であり期限内であることを確認する。
- 確認に必要な情報(`owner` と `job_id`)は、Crawler が書き込み要請に添えて渡す。**情報の形は未決(N-4)**。
- 確認できなければ書き込みを中止する。確認に失敗した場合は、スキップ・リトライの対象にせず、ジョブ `failed` にして削除しない(案)。
- Indexer は要請を直列に処理し(単一 Indexer の前提)、所有確認を文書ごとに行う(案)。確認と書き込みの間の窓は MVP では既知の制限として許容する。
- 確認の対象は要請に由来する書き込み(登録、`last_seen_at` の更新)。要約の書き込みは対象外。削除の実行にもロック所有の確認は行わない(`indexer-architecture-v0.1.md` 参照)。

## 8. 終了通知

`POST /crawls/{crawl_id}/finish`(案)。(出典: SD v0.8 L698-704)

- **送るタイミング**: すべてのバッチ登録(と `last_seen_at` の部分更新)の応答を確認したあと。列挙の失敗・取り消しの場合は、`outcome=failed` または `cancelled` を可能なら送る(届かなくても削除されないので安全)。取り消しが有効なのは、終了通知を送る前だけ。送ったあとに取り消しても削除処理は止まらない(ジョブは `cancelled` になり、結果は削除結果に残る)。
- **内容**: `source_id`、`outcome`(`enumeration_completed` / `failed` / `cancelled`)、`enumerated_count`(Crawler が `document_id` で重複を除いて数えた列挙件数。スキップ・抽出失敗の文書を含む)、`skipped_document_ids[]`、`skipped_count`、`finished_at`。
- **応答**: 通常は **202**(受理。判断は非同期)。判断の結果は応答に含めない。Crawler は Status API で確認する。
  - `enumeration_completed` の受理では、Indexer は `finish_received_at` を `loreley-deletions` に永続化してから 202 を返す(202 のあとに再起動しても、受理した事実が残り、再起動時に `failed`(`indexer_restart`)にできる)。
  - `failed`・`cancelled` の受理では `finish_received_at` を記録せず、削除結果を `failed` にしてから 202 を返す。
- **再送は冪等**(受理時の分岐の先頭で判定)。記録済み(`finish_received_at` が記録済み、または結果が `failed` など終端状態)の終了通知の再送は、世代を見ずに再処理せず 202 を返す。
- **内容が最初と異なる再送**は、`finish_received_at` が記録済みのものに限り **409** で拒否する(案)。
  - SD v0.8 は「応答は 202 のみ」(L702)と「内容が異なる再送は 409(案)」(L703)を併記している(食い違い X3。第 11 章)。ここでは SD の記述どおり両方を残す。
- **受理時の分岐**(再送の判定のあと。世代の判定はこの受理時に 1 回だけ行う):
  1. `finish_received_at` が未記録で、その `crawl_id` の削除結果がすでに終端状態(終了通知が届かないまま新しい開始通知で `superseded` になった旧世代への遅れた終了通知など): 何もしない。状態を変えず、削除しない。
  2. 開始通知を受けていない未知の `crawl_id`: 削除結果を作らず(記録せず)、ログに残すだけ。(1)(2) とも応答は 202。未知の `crawl_id` を記録しない扱いは案(任意の ID で削除結果が増えるのを避けるため。記録する場合は件数の上限を設ける)。
  3. `outcome` が `failed` または `cancelled`: 待たずに `failed`(理由 `outcome_failed` または `outcome_cancelled`)を記録して削除しない(`finish_received_at` は記録しない)。
  4. `enumeration_completed`: `finish_received_at` を記録し、ソースごとの待ち行列に入れる。先行する削除結果が終端状態になってから判定に進む。判定の順序と実行は `indexer-architecture-v0.1.md` を参照。
- **通知の失敗**(リトライ設定の回数まで試しても直らない場合)はジョブ `failed`。終了通知が Indexer に届かなかった場合は、削除が行われないだけで安全。
- **応答が失われた場合**(案。SD は「既存の仕様からの帰結を明記したもの」とする): 終了通知の応答が失われただけの場合は、Indexer が受理済みで `finish_received_at` が記録され、削除が進みうる(Crawler からは届かなかった場合と区別できない)。結果は削除結果に残る。ジョブ記録に確認結果の区分は付かない。「安全」の根拠は、前提(列挙の完了、全バッチの登録の確認)が終了通知の送信前に確認済みであること、実行時の各文書の削除直前の TTL 再確認。

### 8.1 件数照合に使う項目(終了通知の値の定義)

(出典: SD v0.8 L706-716)

Indexer は次が成立するときだけ削除の判断に進む。不一致なら削除せず `validation_failed` として記録する(許容差なし。案)。

```text
enumerated_count == N_seen + E_missing
  N_seen    = 当該 source_id で last_seen_at >= crawl_started_at の件数(リフレッシュ後の検索インデックス)
  E_missing = skipped_document_ids のうち、検索インデックスにないものの件数
```

- `skipped_document_ids` が上限を超えるときも、削除せず `validation_failed`(案)。**上限の値は未決(N-2)。送り方(エンコード、分割など)も未決(N-4)**。
- 抽出に失敗した文書(`extract_failed`)は検索インデックスにあるので `N_seen` に数えられる。突合ジョブの再登録など、列挙以外の書き込みで `N_seen` が増えると不一致になり、削除しない(安全側)。
- 旧い削除が待機している間に新しいクロールが `last_seen_at` を更新すると不一致になりうる。削除しない側に倒れるだけなので許容(案)。

## 9. Status API

`GET /crawls/{crawl_id}`(案)。削除結果を読み取りで返す。(出典: SD v0.8 L786, L760)

- **返す内容**: `status`、`reason`(`failed` の理由コードを含む)、`forced`、`target_count`、`denominator`、しきい値、`deleted_count`、`enumerated_count` と `n_seen`・`e_missing`(検証の数値)、時刻。待機中は任意項目 `waiting_for`(先行する削除結果の `crawl_id`)も返しうる(案。要否は未決)。項目名は SD の記述のままで、正式なレスポンススキーマは**未定義(N-4)**。「しきい値」を指す項目名は未定(X4)。
- **`status` の値**: `running`(終了通知待ち・待機中・判定中・削除中を含む) / `deleted` / `skipped_by_ratio` / `validation_failed` / `discarded` / `failed`。`running` 以外が終端状態。待機中も `running` のままで、状態は増やさない。
- **`failed` の理由コード**(案。名称は実装時に調整): `outcome_failed` / `outcome_cancelled` / `maintenance` / `indexer_restart` / `delete_error`。
- **`discarded` の理由**: `superseded`(終了通知が届かなかった旧世代の整理)、`source_deleted`(ソース削除による破棄)。
- **404 を返す場合**(案): 保持件数を超えて消えた `crawl_id`、開始通知を受けていない `crawl_id`、`loreley-deletions` を失った場合。保持件数 N の値は未決(N-2)。404 の条件の具体は未決(X11。第 11 章)。
- **返すのは削除結果のみ**。登録結果と確認結果の区分は含まない(確定)。
- 各状態の意味と記録項目は `loreley-deletions-v0.1.md` を参照。
- 利用者は Crawler。Admin View への提供は X1(第 11 章)参照。

### 9.1 Crawler 側のポーリング規約(Indexer が前提とする部分)

(出典: SD v0.8 L795-799。Crawler の領域なので要点のみ)

- Crawler は終了通知の 202 を確認したあと、Status API をポーリングして削除結果が終端状態になるのを待つ。間隔・上限時間・リトライ回数は未決(N-2)。
- ポーリングの失敗(リクエストのタイムアウト、接続エラー・5xx、404)が連続でリトライ回数まで続いた場合、またはポーリング全体の上限時間を超えた場合は、警告と確認結果の区分をジョブ記録に残すだけで、ジョブの status は変えない(確定)。区分の名称・対応は案で、Crawler の領域(404 のみが続けば `unknown`、それ以外は `unconfirmed`。案)。Crawler は区分を残したあとに再確認しない(確定)。
- ロックは削除結果が終端状態になるまで保持する。ポーリングの失敗・上限時間の超過のあとはロックを解放する(案)。待機中のまま上限を超えた場合も同じ経路で、削除結果は `running` のまま待機を続ける。
- 登録結果(`enumerated_count` / `created_count` / `updated_count` / `skipped_count` / `oversize_count` / `error_count` / `partial`。名称は案)は、Crawler がバッチ応答を集計して `loreley-jobs` に持つ。Indexer が返すのは、そのための文書単位の応答(新規か更新か。5 章)のみ。

## 10. ソース削除・突合ジョブでの Indexer 呼び出し

### 10.1 ソース削除

(出典: SD v0.8 L265, L1689, L1771, L1801)

呼び出しの形(エンドポイント、リクエスト/レスポンス): **SD v0.8 では完全に未定義(N-4)**。SD が決めているのは次の分担と順序(案を含む)だけである。

- ソース削除は Crawler のジョブとして実行する。期限による削除の判断(割合ルール)は通らない。
- 順序: そのソースの終端状態でない削除結果を `discarded`(理由 `source_deleted`)にする → そのソースの文書を Store 層、検索インデックスの順にすべて削除 → スキップ記録・ロック文書 `lock-{source_id}` と、削除の記録(`loreley-deletions` の `deletion-{source_id}` と `deletion_result-*`)を削除 → 最後にデータソース設定を削除する。
- Indexer に要請するもの: 削除結果の破棄、文書の削除、削除の記録の削除(`loreley-deletions` に書くのは Indexer だけ)。スキップ記録とロック文書は Crawler が削除する(案。細部は未決)。
- 削除結果の `discarded` の書き込みは `if_seq_no` の条件付き更新で、すでに終端状態の結果は上書きしない。衝突したら読み直して再試行し、終端状態になるか `discarded` にできるまで繰り返す(案。回数・間隔は未決)。
- 実行中の削除側の停止確認(自分の削除結果を読み、終端状態や 404 なら書き換えずに止まる)は `indexer-architecture-v0.1.md` を参照。

### 10.2 突合ジョブ

(出典: SD v0.8 L1689, L1775)

- 実処理は Indexer、ジョブとしての起動・管理は Crawler(案)。同じソースのロックを取る。クロールと同時には動かさない前提。
- 呼び出しの形: **SD v0.8 では完全に未定義(N-4)**。比較・修復の内容は `indexer-architecture-v0.1.md` を参照。
