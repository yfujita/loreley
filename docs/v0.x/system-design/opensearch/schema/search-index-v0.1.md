# 検索インデックス Schema 設計書 v0.1

## 0. この文書について

- 対象: 1文書 = 1検索レコードで全文検索に使う OpenSearch インデックス(以下「検索インデックス」)の Schema。
- 版: v0.1。`docs/v0.x/system-design/system-design-v0.8.md`(以下 SD v0.8)から該当部分を抽出したもの。仕様・数値は変えていない。SD 内の「案」「推測」「未決」は、そのまま残している。
- 食い違い・要確認の点は解消せず、「要確認」として明記した(解消は v0.2 で行う)。
- 関連文書(同じ v0.1 の抽出版):
  - `docs/v0.x/system-design/indexer/indexer-architecture-v0.1.md` — 書き込み種別と競合制御、再インデックス前の停止手順、要約生成の整合。
  - `docs/v0.x/system-design/indexer/indexer-api-v0.1.md` — Crawler から Indexer への登録・部分更新の契約。
  - `docs/v0.x/system-design/opensearch/schema/loreley-texts-v0.1.md` — 正の保存先(Store 層)。
- 検索クエリ自体(Search API、MCP)はこの文書の対象外。

## 1. 位置づけ

- 1文書 = 1検索レコードを基本とし、タイトル・要約・本文を BM25 で検索する。日本語を主な対象とし、英語も併せて解析する。
- チャンク分割・ベクトル検索は、評価結果を見て判断する(プロダクト側の判断)。
- 検索インデックスへの書き込みは Indexer だけが行う。
- 文書の本文・要約・処理状態の**正は Store 層**(`loreley-texts`)で、検索インデックスはそこから作る派生物である。ただし `last_seen_at` だけは検索インデックスが唯一の保存場所である。

## 2. フィールド一覧

`_id` は `document_id`(SHA-256 の16進文字列、小文字。`SHA-256(source_id + "\0" + external_id)`。生成規則は `indexer-architecture-v0.1.md` を参照)。

| フィールド | 用途 |
| --- | --- |
| `document_id` | 一意な識別 |
| `source_id` | データソースによる絞り込み |
| `external_id` | データソース内の識別子(突合と、削除対象の特定に使う) |
| `title` | タイトル検索 |
| `summary` | 文書全体の主題による検索 |
| `content` | 細かい語句・識別子による全文検索(抽出・正規化後の本文) |
| `url` / `path` | 原文への参照(表示のみ) |
| `mime_type` | 文書形式による絞り込み |
| `source_updated_at` | 更新日による絞り込み |
| `indexed_at` | インデックスに登録した日時 |
| `content_hash` | 要約の条件付き更新の判定に使う |
| `summary_status` / `summary_model` | 要約の生成状態と、生成に使ったモデル・バージョン |
| `index_status` / `truncated` | 抽出状態と、本文を切り詰めたかどうか |
| `last_seen_at` | 列挙クロールで最後に見つかった日時(期限による削除の判定) |
| `acl` | アクセス制御用の属性(MVP では使わない。将来に備えて予約) |
| `summary_embedding` | 意味検索用のベクトル(任意) |

要確認(SD v0.8 内の食い違い・未記載。v0.1 では SD の表記のまま):

- **`url` / `path`(X8)**: SD は「`url` / `path`」と書き、1項目か2項目かを定めていない。「どちらか一方が入る1項目」か「2項目」かは未決。マッピング化の際に決める必要がある。
- **`summary_embedding`(X9)**: 任意項目として挙がっているが、Embedding 生成は MVP で行わない(SD v0.8 の要約生成の方針)。`acl` は「予約」と明記されているが、`summary_embedding` は予約と明記されていない。位置づけ(MVP では未使用の予約項目かどうか)は v0.2 で整理する。
- **`fetched_at` / `metadata`(X7)**: Crawler から渡される共通ドキュメント形式にあるが、この表にも `loreley-texts` の項目にもなく、保存先が書かれていない。保存するか、受け取るだけで保存しないかは未決(ユーザー判断)。

### 2.1 `last_seen_at` の意味

- 共通ドキュメント形式には含めない。クロールの実行コンテキストとして `crawl_started_at`(クロールの開始時刻)が Indexer に渡され、Indexer が `last_seen_at` に書く(渡し方は `indexer-api-v0.1.md`)。
- `fetched_at`(原本を取得した日時)とは別物で、`last_seen_at` は「列挙で見つかった日時」である。
- 毎回の全文 upsert で更新されるほか、取得に失敗してスキップした文書の誤削除を防ぐため、列挙で見つかった時点で `last_seen_at` だけを部分更新する(MVP は全件更新で、差分検知は将来拡張)。
- 期限による削除の判定(`last_seen_at + TTL < 現在時刻`)と、削除前の件数照合(`last_seen_at >= crawl_started_at` の件数)に使う。詳細は `indexer-architecture-v0.1.md`。
- 消えた文書は、削除されるまで検索結果に残る。検索時に `last_seen_at` で除外はしない。

### 2.2 写しと正

`summary` / `summary_status` / `summary_model` / `index_status` / `truncated` は、検索結果の表示と絞り込みのための**写し**である。正は Store 層(`loreley-texts`)に置く。

### 2.3 状態値

- `summary_status`: `disabled`(要約が無効)、`pending`、`generated`、`failed`。
- `index_status`: `pending_index`(**Store 層のみ**。登録前)、`indexed`、`extract_failed`。検索インデックスに現れる値は `indexed` と `extract_failed`。

## 3. 書き込み種別とフィールド

検索インデックスへの書き込みは、Indexer が次の3種類で行う(競合時の扱いの詳細は `indexer-architecture-v0.1.md`)。

| 種別 | 書くフィールド | 備考 |
| --- | --- | --- |
| 全文 upsert | 全フィールド。`last_seen_at` は既存値と `crawl_started_at` の大きい方(新規作成時は `crawl_started_at`)、`content_hash` は新しい値。`summary` と `summary_status` は、`content_hash` が既存と同じなら既存の値を保持し、違えば `summary` は書かず `summary_status=pending`(要約が無効なら `disabled`) | MVP は全件更新で、すべての文書を全文 upsert する |
| `last_seen_at` の部分更新 | `last_seen_at` のみ(値は `crawl_started_at`) | max 比較。検索インデックスに文書がなければ(404)何もしない(upsert しない) |
| 要約の部分更新 | `summary`、`summary_status`、`summary_model`、`summary_embedding` | 検索インデックス上の `content_hash` が生成元と一致するときだけ書く |

保証の範囲(SD v0.8 §2.4 由来): リース切れ後の旧 Crawler による全文 upsert は原子的には拒否できず、保証するのは `last_seen_at` が古い値に戻らないことまでである。完全な分散フェンシングは複数 Crawler 化の際の将来拡張。

## 4. Mapping・Analyzer・Shard/Replica

検索インデックスのマッピング全体は**未決**(SD v0.8 も定義していない)。決まっているのは次の方針で、詳細は実装時に確定する。

- アクセスはエイリアス経由とする(第5章)。
- ハイライトに使うフィールド(n-gram などのサブフィールドを含む)は `index_options: offsets` でオフセットを保存する(第5章)。
- アナライザは、日本語を形態素解析(kuromoji または Sudachi)、英語を標準アナライザとし、識別子・型番の検索漏れを防ぐために n-gram のサブフィールドの追加を検討する。選定は評価セットの Recall@10・MRR で行う(未決)。
- 単一ノード前提の MVP では `number_of_shards: 1`、`number_of_replicas: 0` とする。ただし、SD が明記しているのは Store 層のインデックスで、検索インデックスにも同じ前提を置くのは**推測**(実装時に確認する)。同様に、`dynamic: strict` と、絞り込みに使う項目(`source_id`、`mime_type`、`index_status`、`summary_status`)の `keyword` 化も、検索インデックスに同じ方針で適用する想定である(**推測**)。
- 専用プラグインを導入した独自の OpenSearch イメージを使う(第7章)。

## 5. 検索方式とインデックス運用

### 5.1 検索方式(Schema に関わる範囲)

- 基本は BM25 による全文検索とし、タイトル・要約・本文の重みを調整する(重みの値は SD に記載なし)。
- 日本語は形態素解析(kuromoji または Sudachi。評価して決める)で解析し、英語は標準アナライザで併せて解析する。n-gram のサブフィールドの追加も検討する。
- ユーザー辞書・同義語辞書はファイルで管理し、更新したら再インデックスで反映する(第6章)。
- 将来は、要約 Embedding によるベクトル検索やハイブリッド検索を追加する。

### 5.2 エイリアス・ハイライト・補助インデックス

- インデックスにはエイリアス経由でアクセスする。マッピングや辞書を変えるときは、新しいインデックスを作ってからエイリアスを切り替える。
- ハイライトに使うフィールド(サブフィールドを含む)は `index_options: offsets` でオフセットを保存する。ハイライタは unified(既定)を使う。オフセットがあると unified ハイライタは本文を再解析しないため、解析上限(`index.highlight.max_analyzed_offset`、既定は100万文字)は適用されない。**この上限を理由に長い文書の本文を切り詰めない**。
- plain ハイライタは常に再解析し、上限を超えると検索リクエスト全体が失敗するため使わない。
- オフセットの保存でインデックスサイズが増える。増え方は実装時に計測する(未決)。本文サイズの上限(索引化の上限)は、リクエストサイズ・インデックスサイズ・処理時間などの観点で決める(未決)。
- 本文がサイズ上限を超える場合は、上限までを索引化して `truncated=true` にする。
- 長い文書で検索精度に問題が出た場合は、見出し・セクション単位の補助インデックスを追加できる構成にする。固定長チャンクへの分割は初期要件にしない。

## 6. 再インデックス

マッピングや辞書を変えるとき、またはインデックスを作り直すときは、次の2つの手段を使い分ける。どちらも、対象のデータソース(インデックス全体を作り直すときはすべて)のクロールと要約の書き込み(および削除の実行)を止めてから行う。停止の方法・実行中の書き込みの終了確認(メンテナンスフラグ。案)は `indexer-architecture-v0.1.md` を参照。

| 手段 | 内容 | `last_seen_at` | 要約 | 使う場面 |
| --- | --- | --- | --- | --- |
| (a) `_reindex` で旧インデックスからコピー | 新しいインデックスを作り、旧インデックスの文書をコピーしてエイリアスを切り替える | 保持される | 保持される | マッピング・辞書・アナライザの変更(通常はこちら) |
| (b) Store 層からの再構築 | Store 層の抽出済みテキストから、検索インデックスを新しく作る。再クロールは不要 | 再構築時刻に初期化される(TTL の時計が再構築時から始まる) | Store 層に保存している要約のうち、生成元の `content_hash` が本文と一致するものだけが保持される。不一致は `pending` に戻す | **旧インデックスを失った場合に限る**。抽出ロジックを変えたときは使わず、全件更新の再クロールで反映する |

障害時の再構築(検索インデックスに関わる行):

| 状況 | 対応 |
| --- | --- |
| マッピング・辞書・アナライザを変更する | 新しいインデックスを作り、旧インデックスからコピー(`_reindex`)してエイリアスを切り替える。通常はこちら |
| 旧の検索インデックスを失った(Store 層は残っている) | Store 層の抽出済みテキストから再構築する。`last_seen_at` は再構築時刻に初期化され、要約は生成元の `content_hash` が本文と一致するものだけが保持される |
| 抽出ロジックを変えた | Store 層からの再構築は使わず、全件更新の再クロールで反映する |

(検索インデックスと Store 層の両方を失った場合は再クロールが必要。`loreley-deletions` を失った場合は `loreley-deletions-v0.1.md` を参照。)

## 7. OpenSearch イメージ・バージョン

(SD v0.8 §7.4 / §7.6 由来。前提。実装時に確認する)

- kuromoji も Sudachi も OpenSearch の既定の配布イメージには含まれない前提で、プラグインを導入した**独自の OpenSearch イメージ**をビルドして配布する。Sudachi は、辞書の入手とライセンスの確認も必要になる。
- OpenSearch 本体とプラグインのバージョンは一致させて固定する。OpenSearch を更新するときは、プラグインも同時に更新して、再インデックスの要否を確認する。
