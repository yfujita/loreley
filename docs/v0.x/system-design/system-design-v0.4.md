## 目的と位置づけ

**目的**：プロダクトデザインの肥大化を解消するため、実装レベルの設計（データモデル、検索インデックス、クロールと削除の処理、ジョブ管理、API・MCPの仕様、セキュリティ実装、コンテナ構成、テスト設計など）を本書に分離する。実装者が、プロダクトデザインを読まずに実装の判断材料を得られる状態にする。

**位置づけ**：

- PD v0.9 は「何を・なぜ作るか」（目的、スコープ、成功指標、主要リスク、方針）を扱う。本書は「どう作るか」を扱う。
- プロダクト判断（目的、スコープ、方針）は本書に書き写さない。プロダクト側の概念を参照するときは「PD v0.9 参照」と書く。各章の冒頭に、プロダクトデザイン上の位置づけを1〜2行で添える。
- 本書の内容は、PD v0.4 の記述・表・仮決定・未決事項を移したものである。移すときに、付録参照や「9.2 #N」などの旧参照を本書の章参照（§3.2など）に直した。一部に推測・導出を含み、該当箇所に注記した。例外として、§3.7内の「旧D.1」「旧D.2」「旧D.3」「旧B.4」などはPD v0.3 の節番号のままである。
- 版の表記：プロダクトデザインの版は「PD v0.N」、本書の版は「本書v0.N」と書く。PD v0.4の付録を指すときは「PD v0.4 付録D.5」のように書く。
- 決定事項は本書とプロダクトデザインの双方を正とし、食い違いは見つけ次第直す。
- MVPの前提（単一ホスト、単一Crawler・単一Indexer・直列実行、認証なし、OpenSearchをStore層のバックエンドにする）は、プロダクトデザインで決めたものである。PD v0.9 までの表記は「単一Worker」で、本書ではWorkerをCrawlerとIndexerに分けて書く（§14）。

- 本書v0.4は、削除の判断・実行をIndexerに移し、削除の承認（保留・承認・却下・全件削除の確認）を廃止して割合ルールに置き換えた（§3.5、§3.9）。PD v0.9 は削除の判断主体を書いていないので、その点では矛盾しない。しかし、承認・保留・0件列挙の異常扱いの記述は、本書v0.4と食い違う。PDの新版は作らず、次にPDを改版するときに直す。それまでの間、削除に関しては本書を正とする。

### 本書v0.3からの変更点（要約）

大方針は「**削除の判断・実行をCrawlerからIndexerへ移す**」の1点である。数値と内部APIの細部は決めず、§12.5に回した。

- **責務**：削除の判断（対象の決定、割合ルール、最小件数ルール、TTL、全件削除するかの判定）と実行は、Indexerの内部モジュール（Sync Manager。独立コンテナにしない）が担う（新設§3.9、§14.2）。Crawlerは検索インデックスを直接読まない（本書v0.3の§3.4・§14.2にあった、削除対象の抽出のための読み取りの例外を解消した）。
- **記録の分離**：同期（削除）に関する記録は、Indexer専用の`loreley-sync`（仮名）に持つ。書き込みはIndexerだけである。`loreley-jobs`はCrawlerだけが書く、という分担は変えない。`loreley-jobs`の削除保留の記録は廃止した（§1.3）。
- **通知**：Crawlerは、ロック取得後・列挙前に開始通知（`POST /syncs/start`）、全バッチ登録の応答確認後に終了通知（`POST /syncs/{crawl_id}/finish`。202で受理）を送る。結果は、IndexerのStatus API（`GET /syncs/{crawl_id}`）をCrawlerがポーリングして確認し、ジョブ記録に要約を残す（§3.9）。
- **世代管理**：`crawl_id`は`job_id`をそのまま使う。Indexerは開始通知でソースごとの現行世代を更新し、終了通知は現行世代と一致するときだけ検証・判断する。古い世代は`discarded`（`stale`）にし、未知の`crawl_id`は記録せず破棄する。
- **検証**：終了通知の`enumerated_count`と、索引の件数（`last_seen_at >= crawl_started_at`の件数 + スキップ文書のうち索引にないもの）を照合する。不一致なら削除しない（`validation_failed`）。検証は状態を持たない。
- **承認の廃止と割合ルール**：削除の保留・承認・却下・全件削除の確認待ちを廃止した。代わりに、削除対象÷削除前の登録文書数がしきい値以下なら削除し、超えれば削除しない（同期結果に理由を記録）。しきい値はデータソースの設定で、既定値は未決である。最小件数ルール（対象が最小件数以下なら割合に関わらず削除）は残した（§3.5）。
- **強制削除モード**：手動実行のクロールの起動時だけ指定でき、割合ルールと最小件数ルールだけを無視する。0件列挙でも全件削除できる（全ファイル削除の経路）。列挙の完了、世代、件数照合、メンテナンスフラグ、スキップ文書の除外、TTLは無視しない（§3.4、§3.9）。
- **ジョブのstatusと削除結果の切り離し**：削除結果はジョブのstatusに反映しない。0件列挙は、ジョブは`succeeded`、同期結果は割合ルールによる削除なしになる（本書v0.3の「0件列挙は`failed`」「全件削除の確認待ち」を廃止。§3.3、§3.4）。
- **ロックと送信順序**：ロックは、同期結果が終端状態になるまで保持する。開始通知・終了通知の失敗はジョブ`failed`にする（削除されないだけで安全。§3.9）。
- **所有確認**：登録・`last_seen_at`の更新の所有確認（本書v0.3 §4.5）は据え置く。削除前のロック所有確認（IndexerとCrawlerの両方）は、世代判定とメンテナンスフラグの確認に置き換えた（§4.5）。世代制御をすべての書き込みへ広げることは将来拡張とした（§4.7）。
- **Admin API**：削除の承認・却下・全件削除確認の中継は不要になった。Admin Viewの表示は、Admin APIが`loreley-sync`を読み取りのみで直接読む。クロールの起動要求に強制削除モードの指定を加えた（§14.2、§14.4）。
- **据え置き**：`loreley-texts`は残す（廃止は本書v0.5で扱う）。Store層が先に消えて検索インデックスに残る極小の窓（§3.9）は、全件更新で自己修復する。本書v0.5の`loreley-texts`廃止で窓自体がなくなる。
- **確認状況**：設計の骨子（Indexerによる判断、`loreley-sync`、通知とStatus API、承認の廃止と割合ルール、強制削除モード、世代管理と件数照合）に加え、強制削除モードを手動実行のみにすること、最小件数ルールを残すことは、プラン全体の承認（2026-11-08）によりユーザー確定である。そのほかの細部（契約の形、状態名、バッチごとの再抽出や削除の窓の扱い、本版で補った競合の扱い、数値など）は案である（§14.7）。

## 1. データモデル

> プロダクトデザイン上の位置づけ：共通ドキュメント形式とID設計は、Connector・Indexer・検索・Store層をつなぐ契約である。Store層は、MVPでは専用DBを置かず、OpenSearchをKVSとして使う（PD v0.9 参照）。

### 1.1 共通ドキュメント形式

ConnectorがIndexerに渡す形式（PD v0.4 付録A.1）。

| 項目 | 説明 |
| --- | --- |
| `source_id` | データソースの識別子。登録後は変更できない |
| `external_id` | データソース内で一意な識別子（ルートからの相対パス、ページID等）。§1.2の正規化を適用する |
| `title` | タイトル（取得できなければファイル名） |
| `url` / `path` | 原文への参照（表示用） |
| `mime_type` | 文書形式 |
| `raw_content` | 取得済みの原本（MVPでは参照ではなく原本そのものを渡す。「原本または参照」の2通りはやめた）。抽出前のデータであり、検索インデックスの`content`（抽出後の本文）とは別物 |
| `content_hash` | 原本のSHA-256 |
| `source_updated_at` | データソース上の更新日時（ローカルでは`mtime`） |
| `size` | 原本のサイズ（バイト） |
| `fetched_at` | 原本を取得した日時。取得を省略した場合は更新しない |
| `metadata` | Connector固有の追加属性 |

`last_seen_at`は共通ドキュメント形式に含めない。クロールの実行コンテキストとして`crawl_started_at`（クロールの開始時刻）をIndexerに渡し、Indexerが`last_seen_at`に書く。`fetched_at`は「取得した日時」、`last_seen_at`は「列挙で見つかった日時」である。毎回の全文upsertで`last_seen_at`が更新されるほか、取得に失敗してスキップした文書の誤削除を防ぐため、列挙で見つかった時点で`last_seen_at`だけを部分更新する（§2.4、§3.1、§3.2）。`crawl_started_at`は開始通知でも`loreley-sync`に渡され（§3.9）、削除前の件数照合は`last_seen_at >= crawl_started_at`の件数を使う。

本システム内で`content`の意味は場所ごとに異なる。

| 場所 | 名前 | 意味 |
| --- | --- | --- |
| Connector → Indexer | `raw_content` | 取得済みの原本 |
| Store層 | `text` | 抽出・正規化後のテキスト（サイズ上限で切り詰め後） |
| 検索インデックス | `content` | `text`と同じ内容を検索用に解析したもの |
| `get_document`の応答 | `content` | `text`の指定範囲 |

### 1.2 ID設計

PD v0.4 付録A.2。

- `document_id` = `SHA-256(source_id + "\0" + external_id)`の16進文字列（小文字）。NUL文字で区切るため、連結で別の組が同じ値にならない。
- `external_id`は、ハッシュの前にUnicode NFCへ正規化し、パス区切りを`/`に統一する（ルートからの相対パス、先頭に`/`を付けない）。大文字小文字は区別したまま扱う。
- 同じ文書を再取得すると同じIDになるため、再実行しても重複しない。検索インデックスとStore層のどちらも、`document_id`を文書IDとして使う。
- `source_id`は登録後に変更できない。変更が必要なときは、新しいデータソースとして登録し直す。
- パスの変更やリネームは「旧IDの削除 + 新IDの追加」として扱う。リネームの追跡は初期要件にしない。
- データソースを削除するときは、まず、そのソースの現行世代と`running`の同期結果を破棄する（Indexerが`discarded`、理由`source_deleted`にする。削除の実行中なら次のバッチの前の確認で止まる）。そのうえで、その`source_id`の文書をStore層、検索インデックスの順にすべて削除し、そのあとで、そのソースのスキップ記録とロック文書（`lock-{source_id}`）、同期の記録（`loreley-sync`の`sync-{source_id}`と、そのソースの`syncresult-*`）を削除し、最後にデータソース設定を削除する。途中で止まった場合に備え、設定の削除は文書、スキップ記録、同期の記録の削除が終わってから行う。実行はCrawlerのジョブとし、世代の破棄、文書の削除、同期の記録の削除はIndexerに要請し（`loreley-sync`に書くのはIndexerだけ。§1.3）、スキップ記録とロック文書はCrawlerが削除する（案。細部は§12.5）。この削除は、期限による削除（§3.4）の判断を通らない（ソース全体の削除であり、割合ルールの対象外）。ソース削除のジョブは、自分のロック文書をこの手順の中で先に削除してからジョブを終了する（§4.6。案）。ポーリングのタイムアウト後にロックが解放された場合などで、ソース削除の時点で同期が`running`でありうるため、世代を先に破棄する。

### 1.3 Store層のデータモデル

PD v0.4 付録C.1。MVPのStore層はOpenSearchをKVSのように使い、設定・ジョブ・抽出済みテキスト・文書ごとの処理状態を保存する。用途ごとに検索インデックスとは別のインデックスを分け、IDをキーにget/put/deleteする。

| インデックス | 内容 |
| --- | --- |
| `loreley-sources` | データソース設定（`source_id`、種別、ルート、周期、TTL、削除率のしきい値、削除の最小件数、除外条件など。認証情報は参照名のみ） |
| `loreley-jobs` | ジョブ状態、ソースごとの実行ロック、スキップ記録（§3.1）。各ジョブに、同期結果の要約を残す（§3.9） |
| `loreley-sync`（仮名） | Indexer専用。同期（削除の判断・実行）の記録：ソースごとの現行世代と設定スナップショット、同期結果（§3.9） |
| `loreley-texts` | 文書ごとの抽出済みテキストと処理状態 |

**書き込み役**：`loreley-jobs`に書き込むのはCrawlerだけである（Admin APIは書かない）。例外は§2.5のメンテナンスフラグで、運用者の手動手順で書く（案。または、Crawlerの固定経路を経由する）。`loreley-sync`に書き込むのはIndexer（Sync Manager）だけで、CrawlerもAdmin APIも書かない。Admin APIは`loreley-jobs`と同じく、`loreley-sync`を読み取りのみで直接読んで表示する。`loreley-sources`（データソースの登録・設定の削除）への書き込みもCrawlerが持ち、Admin APIは固定の経路で中継する（案）。Indexerは`loreley-sources`を読まない（TTLなどは開始通知で渡される。§3.9）。`loreley-texts`と検索インデックスに書き込むのはIndexerだけである（§14.2）。

`loreley-texts`の項目：`document_id`、`source_id`、`external_id`、`title`、`url`/`path`、`mime_type`、`text`、`truncated`、`content_hash`（確定済み）、`pending_content_hash`、`source_updated_at`、`indexed_at`、`size`、`extractor_version`※、`index_status`、`extract_fail_count`※、`pending_since`（`pending_index`になった日時）、`summary`、`summary_content_hash`（要約の生成元の`content_hash`）、`summary_status`、`summary_model`。

※`extractor_version`・`extract_fail_count`は、差分検知（将来拡張。§3.7）で使う予約項目で、MVPでは使わない（新しい項目ではなく、PD v0.3からの項目を残している）。本書v0.1にあった`fetch_fail_count`（恒久失敗の判定用）は、スキップ方針（§3.1）で不要になったため削除した。取得・登録の失敗回数は、`loreley-jobs`のスキップ記録に持つ（新規の文書も含む）。

`pending_content_hash`・`pending_since`・`source_updated_at`・`size`は、MVPでも使う。

**真実の置き場所**：文書の本文・要約・処理状態の正はStore層（`loreley-texts`）。検索インデックスはそこから作る派生物である。ただし`last_seen_at`は検索インデックスだけに持つ。`title`・`url`/`path`・`mime_type`・`indexed_at`もStore層に持つので、§2.5(b)の再構築と`get_document`（§5.4。`title`と`url`/`path`を返す）は、Store層だけで成立する。

### 1.4 マッピング方針

PD v0.4 付録C.2（Store層のインデックス）。

- `dynamic: strict`にして、未定義のフィールドの混入を防ぐ。
- 検索や集計の対象にしない大きな文字列（`text`など）は、解析も索引化もしない（`index: false`、またはオブジェクトの`enabled: false`）。取得はIDによる`_source`の読み出しで行う。
- 条件で一覧する項目（`source_id`、`index_status`、`summary_status`など）は`keyword`にする。
- MVPは単一ノード前提で、`number_of_shards: 1`、`number_of_replicas: 0`とする。

### 1.5 Repositoryインターフェース

PD v0.4 4.8（データストア）の実装に関する部分。コード上は検索インデックスとは別の「Store層」として扱い、アプリケーションはRepositoryインターフェースだけを経由して読み書きする。

- バックエンドは設定で差し替えられるようにする。将来、PostgreSQLやSQLiteを追加しても呼び出し側を変えない。
- インターフェースは、IDによる取得・保存・削除、単純な条件での一覧、条件付き更新（楽観的排他制御）に限る。トランザクションと結合には依存しない。
- 書き込みを担当するコンポーネントは分けてある（§14.2）。Repositoryインターフェースは、各コンポーネントが共通で使う。
- Connectorの認証情報は、Store層に平文で保存しない。環境変数や秘密情報ファイルで参照する（§6.4）。
- 条件付き更新の方法（`if_seq_no`/`if_primary_term`）と、検索ではなくIDによる取得を使う理由は§3.8に記す。
- Repositoryインターフェースの詳細と、OpenSearch以外のバックエンドに移る条件（件数・更新頻度・排他の要件など）は未決定である（PD v0.4 9.2 #6。§12.1）。

## 2. 検索インデックス

> プロダクトデザイン上の位置づけ：1文書 = 1検索レコードを基本とし、タイトル・要約・本文をBM25で検索する。日本語を主な対象とし、英語も併せて解析する。チャンク分割・ベクトル検索は、評価結果を見て判断する（PD v0.9 参照）。

### 2.1 フィールド・Mapping・Analyzer・Shard/Replica

PD v0.4 付録B.1。1文書 = 1検索レコード。`_id`は`document_id`。

| フィールド | 用途 |
| --- | --- |
| `document_id` | 一意な識別 |
| `source_id` | データソースによる絞り込み |
| `external_id` | データソース内の識別子（突合と、削除対象の特定に使う） |
| `title` | タイトル検索 |
| `summary` | 文書全体の主題による検索 |
| `content` | 細かい語句・識別子による全文検索（抽出・正規化後の本文） |
| `url` / `path` | 原文への参照（表示のみ） |
| `mime_type` | 文書形式による絞り込み |
| `source_updated_at` | 更新日による絞り込み |
| `indexed_at` | インデックスに登録した日時 |
| `content_hash` | 要約の条件付き更新の判定に使う |
| `summary_status` / `summary_model` | 要約の生成状態と、生成に使ったモデル・バージョン |
| `index_status` / `truncated` | 抽出状態と、本文を切り詰めたかどうか |
| `last_seen_at` | 列挙クロールで最後に見つかった日時（期限による削除の判定） |
| `acl` | アクセス制御用の属性（MVPでは使わない。将来に備えて予約） |
| `summary_embedding` | 意味検索用のベクトル（任意） |

`summary` / `summary_status` / `summary_model` / `index_status` / `truncated`は、検索結果の表示と絞り込みのための写しである。**正はStore層**に置く。`last_seen_at`だけは検索インデックスが唯一の保存場所である。

`summary_status`の取りうる値：`disabled`（要約が無効）、`pending`、`generated`、`failed`。`index_status`の取りうる値：`pending_index`（Store層のみ。登録前）、`indexed`、`extract_failed`。

**Mapping・Analyzer・Shard/Replica**：PD v0.4は検索インデックスのマッピング全体を定義していない。決まっているのは次の方針で、詳細は実装時に確定する。

- アクセスはエイリアス経由とする（§2.3）。
- ハイライトに使うフィールドは`index_options: offsets`でオフセットを保存する（§2.3）。
- アナライザは、日本語を形態素解析（kuromojiまたはSudachi）、英語を標準アナライザとし、識別子・型番の検索漏れを防ぐためにn-gramのサブフィールドの追加を検討する（§2.2）。選定は評価セットのRecall@10・MRRで行う（PD v0.4 9.2 #1。§12.1）。
- 単一ノード前提のMVPでは、`number_of_shards: 1`、`number_of_replicas: 0`とする。PD v0.4が明記しているのはStore層のインデックス（§1.4）で、検索インデックスにも同じ前提を置く（推測。実装時に確認する）。同様に、`dynamic: strict`と、絞り込みに使う項目（`source_id`、`mime_type`、`index_status`、`summary_status`）の`keyword`化も、検索インデックスに同じ方針で適用する想定である（推測）。
- 専用プラグインを導入した独自のOpenSearchイメージを使う（§7.4）。

### 2.2 検索クエリ・BM25・日本語解析・辞書

PD v0.4 付録B.2、4.3。

- 基本はBM25による全文検索とし、タイトル・要約・本文の重みを調整する。
- 日本語は形態素解析（kuromojiまたはSudachi。評価して決める）で解析し、英語は標準アナライザで併せて解析する。識別子や型番の検索漏れを防ぐため、n-gramのサブフィールドの追加も検討する。
- ユーザー辞書・同義語辞書はファイルで管理し、更新したら再インデックスで反映する（§2.5）。
- 将来は、要約Embeddingによるベクトル検索やハイブリッド検索を追加する。
- データソースから消えた文書は、削除されるまで検索結果に残る。検索時に`last_seen_at`で除外はしない（§3.4）。

### 2.3 ハイライトとインデックス運用

PD v0.4 付録B.3。

- インデックスにはエイリアス経由でアクセスする。マッピングや辞書を変えるときは、新しいインデックスを作ってからエイリアスを切り替える。
- ハイライトに使うフィールド（n-gramなどのサブフィールドを含む）は、`index_options: offsets`でオフセットを保存する。ハイライタはunified（既定）を使う。オフセットがあると、unifiedハイライタは本文を再解析しないため、解析上限（`index.highlight.max_analyzed_offset`、既定は100万文字）は適用されない。この上限を理由に長い文書の本文を切り詰めない。
- plainハイライタは常に再解析し、上限を超えると検索リクエスト全体が失敗するため使わない。
- オフセットの保存でインデックスサイズが増える。増え方は実装時に計測する。本文サイズの上限は、リクエストサイズ・インデックスサイズ・処理時間などの観点で決める（§10.2）。
- 長い文書で検索精度に問題が出た場合は、見出し・セクション単位の補助インデックスを追加できる構成にする。固定長チャンクへの分割は初期要件にしない。

### 2.4 更新処理・競合制御

PD v0.4 付録B.4。検索インデックスへの書き込みは、Indexerだけが行う（§14.2）。書き込みは次の3種類に分ける。MVPは全件更新で、すべての文書を全文upsertする。これに加えて、読めない文書をスキップしても削除されないよう、列挙で見つかった時点の`last_seen_at`の部分更新を行う（§3.1）。

| 種別 | 書くフィールド | 書き込む側 | 競合時の扱い |
| --- | --- | --- | --- |
| 全文upsert | 全フィールド。`last_seen_at`は既存値と`crawl_started_at`の大きい方（スクリプトによるupsert。新規作成時は`crawl_started_at`）、`content_hash`は新しい値。`summary`と`summary_status`は、`content_hash`が既存と同じなら既存の値を保持し、違えば`summary`は書かず`summary_status=pending`（要約が無効なら`disabled`） | Indexer（本文の追加・更新時） | 文書全体を置き換える。本文が変わったときは、旧本文向けの要約を残さない（全件更新で毎回要約を作り直さないよう、本文が同じなら引き継ぐ）。同じデータソースのクロールは1つだけなので、同時の全文upsert同士は起きない。`last_seen_at`は古い値に戻さない（max比較） |
| `last_seen_at`の部分更新 | `last_seen_at`のみ（値は`crawl_started_at`） | Indexer（列挙で文書が見つかった時点。取得より前。Crawlerの要請を受けて書く。§14.3） | 現在値と比べるスクリプト更新（max比較）。新しい値のときだけ書き、古い値で上書きしない。ほかのフィールドは変更しない。検索インデックスに文書がない場合（404）は何もしない（upsertしない）。取得・抽出・登録が失敗しても更新済みのまま残る |
| 要約の部分更新 | `summary`、`summary_status`、`summary_model`、`summary_embedding` | Indexer内部の要約生成（非同期） | **検索インデックス上の`content_hash`が、要約を生成した本文の`content_hash`と一致するときだけ**書く（条件付き更新）。不一致なら捨てる（本文が更新済みで、新しい要約が生成される）。更新の衝突は再試行する。要約生成はクロールと並行しうるため、この条件で正しさを保つ（§4.4） |

**リース切れ後の旧Crawlerの全文upsert**：全文upsertは文書全体を置き換えるため、古い世代のCrawler（からの登録要請）が新しい内容を上書きするのを原子的には拒否できない。MVPでは、単一Crawler・直列実行を基本とし、リース期限切れだけでは自動で引き継がない（§4.3）ことで、この状況が起きにくくする。実行世代番号を持たせて古い世代の上書きを拒否する完全な分散フェンシングは、複数Crawler化の際の将来拡張とする（§4.7）。ここで保証するのは、`last_seen_at`が戻らないことまでである（部分更新もmax比較なので同様に戻らない）。CrawlerとIndexerが別コンテナになっても、この保証は変わらない。ロック所有の確認（§4.5）から書き込みまでの窓はIndexer側にも広がるが、max比較により`last_seen_at`は戻らない。

要約は、生成の完了後にまずStore層へ保存し、そのうえで検索インデックスへ反映する。Store層への保存も、生成元の`content_hash`が一致するときだけ行う（§3.8、§8.4）。

### 2.5 再インデックス

PD v0.4 付録B.5。マッピングや辞書を変えるとき、またはインデックスを作り直すときは、次の2つの手段を使い分ける。どちらも、**再インデックスの対象のデータソース（インデックス全体を作り直すときはすべて）のクロールと要約の書き込みを止めてから**行い、完了後に再開する。削除（Indexerの内部モジュールSync Managerによる削除の実行。§3.9）も実行しない。

**開始前に、実行中の書き込みが終わったことを確認する**。対象のソースに`running`のクロールがなくなり、`loreley-sync`に判定中または削除の実行中の同期結果（`running`で`finish_received_at`があるもの）がなく、Indexerで実行中の要約生成も終わったことを確認する。終わらないときはCrawlerとIndexerを停止してから始める（フラグを立てるだけでは、すでに始まっている書き込みは止まらないため）。要約生成はジョブ記録を持たないため、終了の確認はIndexerの停止が確実な手段である（§4.4）。クロールは単一Crawler・直列実行だが、要約の書き込みはクロールと並行しうる（別コンテナ。§4.4）ため、Indexer側の終了も確認する。

止める手段は、`loreley-jobs`のメンテナンスフラグに一本化する（案）。CrawlerとIndexerがフラグを確認して書き込みを控える。実行ロック（§4.2）は、受付時に作られ（§14.4）、クロールの待機・実行中は常に存在するため、メンテナンス用のロックと区別できない。そのため、メンテナンスには使わない。書き込み停止の対象はCrawlerとIndexerの**両方**で、Indexerでは要約の書き込みに加え、Sync Managerの削除の判定と、削除のバッチごとの実行も止まる（§3.9）。フラグの確認のタイミングや停止中の応答の扱いなど、細部は実装時に決める（§12.5）。MVPでは手動手順（READMEに記載）とする。画面（Admin View）からの実行は将来拡張とする。

| 手段 | 内容 | `last_seen_at` | 要約 | 使う場面 |
| --- | --- | --- | --- | --- |
| (a) `_reindex`で旧インデックスからコピー | 新しいインデックスを作り、旧インデックスの文書をコピーしてエイリアスを切り替える | 保持される | 保持される | マッピング・辞書・アナライザの変更（通常はこちら） |
| (b) Store層からの再構築 | Store層の抽出済みテキストから、検索インデックスを新しく作る。再クロールは不要 | 再構築時刻に初期化される（TTLの時計が再構築時から始まる） | Store層に保存している要約のうち、生成元の`content_hash`が本文と一致するものだけが保持される。不一致は`pending`に戻す | **旧インデックスを失った場合に限る**。抽出ロジックを変えたときは使わず、全件更新の再クロールで反映する（§3.2。差分検知を導入した場合は`extractor_version`の更新による再クロールで反映する。§3.7） |

## 3. クロール・削除

> プロダクトデザイン上の位置づけ：MVPは全件更新（差分検知は将来拡張）で、削除は`last_seen_at`とTTLによる期限で判定する。削除の安全性（誤削除の防止）が成功指標の1つである（PD v0.9 参照）。本書v0.4では、削除の判断・実行をIndexerが担う（§3.9）。

### 処理の流れ（概要）

**Connectorと列挙クロール**（PD v0.4 4.1）：ConnectorはデータソースごとのCrawlerの実装で、Crawlerはその実行・周期・同期状態を管理する。データソースから文書を列挙・取得し、Indexerに共通ドキュメント形式（§1.1）で渡す。CrawlerとIndexerは別コンテナで、HTTPで直接通信する（§14）。削除の判断・実行は、Indexerの内部モジュール（Sync Manager）が担う（§3.9）。

- MVPのConnectorは、ローカルディレクトリ／ファイル共有のみ。HTTPサイト、Confluence、Gitなどは将来の拡張（Webページのスクレイピングも将来）。
- **列挙クロール**：データソース内のすべての文書を列挙するクロール。MVPでは、列挙した文書をすべて取得・抽出して登録する（全件更新。差分検知は将来拡張）。MVPのクロールはすべて列挙クロールである。削除の判断は、列挙の完了を通知されたIndexerだけが行う（§3.9）。
- 追加・更新の検知はせず、毎回すべての文書を処理する（§3.2）。削除は期限（`last_seen_at`とTTL）で判定する（§3.3、§3.4）。
- 読めない文書は、設定した回数だけリトライしてもだめなら、その文書だけスキップする。スキップはクロール全体・他の文書の登録・削除に影響させない（§3.1）。
- 接続設定、認証情報の参照名、実行周期、取得状況、エラーはStore層に保存する（§1.3）。

**収集・更新**（PD v0.4 5.1）：

1. Crawlerがソースのロックを取得したあと、列挙の前に、Indexerへ開始通知を送る（§3.9）。
2. Crawlerがデータソースを列挙する（§3.1）。見つかった文書の`last_seen_at`を、その時点で部分更新する（書き込みはIndexerが行い、Crawlerが要請する。§2.4）。全文upsertでも更新される。
3. すべての文書を取得し、処理する（全件更新。§3.2）。取得できない文書は、リトライしてもだめならスキップして次の文書へ進む（§3.1）。
4. Indexerが本文を抽出・正規化し、Store層と検索インデックスに登録する。登録が成功してから、処理済みの印（`content_hash`など）を確定する。途中で失敗した文書は、Indexerが文書単位の失敗として返し、Crawlerがリトライしてもだめならスキップを判断する。スキップした文書は次回のクロールで再処理される。
5. 要約生成が有効なら、Indexerが内部で要約を非同期に生成し、Store層に保存したうえで、本文が変わっていないときだけ検索インデックスに反映する（§2.4、§3.8、§8）。
6. Crawlerは、全バッチの登録の応答を確認したら、終了通知を送る（202で受理される）。そのあと、IndexerのStatus APIをポーリングして同期結果を確認し、ジョブの記録に要約を残してから、ジョブの最終状態を記録し、ロックを解放する（§3.9）。

**Indexerの登録処理**（PD v0.4 4.2のうち登録に関する部分）：

- 文書形式に応じてテキストを抽出し、正規化する。MVPの対応形式はtxt・Markdown・HTML・PDF。Office文書は次版。文字コードは自動判定し、UTF-8のほかShift_JIS/CP932にも対応する。抽出ライブラリと文字コード判定の方法は未決定（PD v0.4 9.2 #10。§12.1）。
- 抽出済みテキストをStore層に保存する。原本は保存せず、元システムを参照する。
- 検索インデックスへの登録・更新・削除を行う。書き込みの種類ごとの競合の扱いは§2.4に定める。
- 抽出に失敗した文書は、タイトルとメタデータだけを登録し、抽出失敗として扱う（状態値は§2.1）。Admin Viewに表示する。本文がサイズ上限を超える場合は、上限までを索引化して`truncated=true`にする。
- Embeddingの生成は、ベクトル検索と同じ将来拡張とし、MVPでは行わない（PD v0.9 §1.5、§8.4）。
- 検索インデックスへの登録に失敗した場合は、Indexerが文書単位の失敗種別を返し、Crawlerが§3.1のリトライ設定の回数だけリトライする。それでも失敗したら、その文書をスキップして個別文書の失敗として記録する。クロールは部分成功になるが、削除は行う（§3.3）。ジョブ全体の失敗は、列挙の失敗、OpenSearch全体の異常、Indexerの異常（判定基準は§3.1）などに限る。

**削除**（PD v0.4 5.2）：

1. Indexer（Sync Manager）が終了通知を受け、世代が現行であること、メンテナンスフラグがないこと、件数照合が成立することを確認する。列挙クロールが最後まで完了し（`outcome=enumeration_completed`）、これらを満たすときだけ、同じ`source_id`のうち`last_seen_at + TTL < 現在時刻`で、今回スキップした文書でない文書を削除の対象にする（§3.4）。読めない文書のスキップがあってもよい。
2. 割合ルール（§3.5）で、削除するかを決める。削除対象÷削除前の登録文書数がしきい値以下、または対象が最小件数以下なら削除し、超えれば削除せず、同期結果に理由を記録する。承認待ちはない。手動実行で強制削除モードを指定したときだけ、割合ルールと最小件数ルールを無視する（§3.4）。
3. 削除はIndexerが、**Store層、検索インデックスの順**に、バッチごとに再抽出しながら行う（§3.9）。途中で止まっても、検索インデックスに残る文書は次回の削除で再度対象になる。Store層と検索インデックスの食い違いは、突合ジョブで検出する。検索インデックスにだけある文書は削除し、Store層にだけある文書は、MVPでは自動削除せず、Admin Viewでの確認と安全な再登録にとどめる（§3.6）。

### 3.1 発見と取得、リトライとスキップ

PD v0.4 付録D.1、PD v0.9 の「読めない文書はスキップする」方針。MVPのクロールは、列挙した文書をすべて取得・抽出し、全文upsertする。

**発見と取得の分離**：列挙で文書が見つかった時点で、その文書の`last_seen_at`を部分更新する（§2.4。文書が検索インデックスになければ何もしない）。その後の取得・抽出・登録が失敗しても、`last_seen_at`は更新済みのままである。取得の失敗が「見つからなかった」と区別され、読めない文書がTTLで誤削除されない。取得に失敗した新規文書は登録されず、次回のクロールで再度試みる。部分更新は、見つかったすべての文書に行う（§2.4）。書き込み量の増加は§10.3に記す。部分更新が失敗したとき（OpenSearchへの書き込み不可など）は、その文書をスキップとして扱わず、ジョブを`failed`にして削除しない。部分更新の失敗を放置すると、読めない文書の`last_seen_at`が更新されずに誤削除されうるためである。

**リトライとスキップ**：文書の取得（権限エラー、一時的な読み取りエラーなど）と、検索インデックス・Store層への登録が失敗したときは、次の設定でリトライする。取得の失敗はCrawler自身が、登録の失敗はIndexerが返す文書単位の失敗種別を受けてCrawlerが、リトライとスキップを判断する。

| 設定 | 既定値（案） | 内容 |
| --- | --- | --- |
| 最大試行回数 | 3回（最初の1回 + リトライ2回） | 文書ごと・処理段階ごと（取得、登録）に数える。権限エラーなど再試行しても直らないエラーも区別せず、同じ回数を試す（実装を単純にするため） |
| バックオフ | 初回1秒、2倍ずつ、上限30秒、ジッタあり | 指数バックオフ |

設定はグローバルな既定値とデータソースごとの上書きができる。値は案で、実装時に調整する（§12.2）。上限回数まで失敗した文書は**スキップ**する。

- スキップした文書は、その文書の処理だけを終えて次の文書へ進む。クロール全体の継続、他の文書の登録、他の文書の削除判定に影響させない。
- 抽出の失敗は、スキップではなく従来どおり`extract_failed`として、タイトルとメタデータを登録する（§3.2。リトライはしない）。
- **全体異常とスキップの判定基準**（登録・部分更新の失敗時）：次はOpenSearch全体の異常とみなし、スキップせずジョブを`failed`にする：接続エラー、タイムアウト、HTTP 429、5xx、`cluster_block_exception`、circuit breaker（`circuit_breaking_exception`）。リトライ設定の回数まで試しても直らなければ`failed`とする。文書固有の4xxの拒否（マッピング違反、文書の内容に起因する拒否など）だけをスキップにする。文書固有の4xxのスキップが連続して20件（案。設定可能）に達したら、設定や状態の異常の疑いとして`failed`にする。
- **Indexerの異常**：Indexerに接続できない、タイムアウト、サーバ側エラー（HTTP 5xx等）は、OpenSearch全体の異常と同様に扱う。リトライ設定の回数まで試しても直らなければ、スキップにせずジョブを`failed`にして、削除しない。スキップの対象は文書固有の拒否だけで、連続20件（案）で`failed`にする既存のルールも維持する。エラー種別の具体名は実装時に決める（§12.5）。この「Indexerの異常はジョブ`failed`」の扱いの対象は、開始通知、登録、`last_seen_at`の部分更新、終了通知の失敗に限る。Status APIのポーリングの失敗は警告のみで、ジョブのstatusは変えない（§3.9、§14.5）。ロック所有の確認（§4.5）に失敗した場合は、スキップ・リトライの対象にせず、ジョブを`failed`にして削除しない（案）。
- **列挙中のエラー**：ディレクトリにアクセスできない、列挙の途中で読み取りエラーになるなどは、列挙の失敗として`failed`にする。実装は、列挙時のエラーを握りつぶさない（例：Pythonの`os.walk`は既定でエラーを無視するので、`onerror`でエラーを検出して列挙を失敗させる）。一部のディレクトリを列挙できないまま完了扱いにすると、そこにある文書が「見つからなかった」ことになり、誤削除につながるためである（§3.4）。
- スキップした文書は、次回のクロールで通常どおり再処理される。成功すれば、スキップ記録を削除する。

**スキップ記録**：スキップした文書は、`loreley-jobs`に記録する（Store層の文書がない新規の文書も記録できるよう、`loreley-texts`ではなくここに置く）。ID：`skip-{source_id}-{document_id}`。書き込むのはCrawlerだけである。

| 項目 | 内容 |
| --- | --- |
| `source_id` / `document_id` / `external_id` | 対象の識別 |
| `stage` | 失敗した段階（`fetch` / `index`） |
| `reason` | エラーの種類（権限、読み取り、登録拒否など）と短いメッセージ。本文や秘密情報は含めない |
| `attempts` | 直近のクロールでの試行回数 |
| `consecutive_skips` | 連続してスキップされたクロール数。成功時に記録ごと削除する |
| `first_skipped_at` / `last_skipped_at` | 最初・直近にスキップした日時 |
| `last_job_id` | 直近にスキップしたクロールのジョブID |

記録は、(a)同じ文書が後のクロールで成功したとき、(b)文書が削除されたとき、(c)データソースが削除されたとき、(d)次回以降の列挙クロールで、その文書が列挙で見つからなかったときに消す（(d)がないと、削除された元ファイルの記録がAdmin Viewに残り続ける）。ジョブの結果には`skipped_count`（スキップ件数）を別に持たせる。

**Admin Viewの表示項目**：クロール結果にスキップ件数を表示し、データソースごとに「スキップした文書」の一覧を出す。一覧の項目は、`external_id`（パス）、`stage`、`reason`、`attempts`、`consecutive_skips`、`first_skipped_at`/`last_skipped_at`、既存文書か新規文書か（既存なら古い内容のまま検索に残る）、直近のジョブへのリンクとする。管理者は、アクセス権の修正や除外条件への追加で原因を解消し、再実行する。

**削除との関係**：スキップがあっても、列挙が最後まで完了していれば削除は行う（§3.3）。スキップした文書は`last_seen_at`が更新されているので、削除対象にならない。Crawlerは、スキップした文書のIDを終了通知でIndexerに渡し（§3.9）、Indexerはそれらを削除対象から除外する（二重防御。§3.4）。スキップ記録そのものは`loreley-jobs`に残り、Indexerは読まない。

### 3.2 全件更新（差分検知はMVP対象外）

PD v0.4 付録D.2。MVPでは、`mtime`・`size`・`extractor_version`によるスキップ判定をしない。毎回、次の順で全文書を処理する。

1. Connectorが文書を列挙する。
2. 各文書の原本を取得し、`content_hash`を計算する。取得に失敗した文書は、§3.1のリトライとスキップに従う。
3. 抽出・正規化する。取得した`content_hash`が、Store層の確定済みの`content_hash`と**同じ**なら、`pending_index`に遷移せず、全文upsert（`last_seen_at`の更新を含む。要約は引き継ぐ）だけを行う（抽出ロジックを変えた場合に備え、Store層の`text`も抽出し直した内容で更新する）。**変わった（または新規の）場合のみ**、Store層に`text`・`pending_content_hash`・`index_status=pending_index`を書いてから、全文upsertする。これは差分検知ではなく書き込み状態の判定である。変更のない文書で`pending_since`や`index_status`が毎回変わり、§3.6の警告や§5.4の応答が不安定になるのを防ぐ。
4. 全文upsertに成功したら、**最後に**Store層の`content_hash`・`index_status`などを確定し、`pending_index`を解消する。途中で失敗すると確定されないので、次回のクロールで再処理される。
5. 本文が前回と同じ（`content_hash`が同じ）なら、要約を引き継ぐ。違うなら、要約を引き継がず`summary_status=pending`に戻す（§8.5）。

抽出に失敗した文書（`extract_failed`）も、毎回再試行する。回数の上限で止める処理はMVPにはない。そのため、`extract_failed`・`pending_index`の文書は特別な扱いなしに、次のクロールで再処理される。抽出ロジックを変えたときも、次の全件更新で反映される。

手順3〜4のStore層・検索インデックスへの書き込みと確定は、Indexerが文書ごとに行う（Crawlerが原本とメタデータを渡す。§14.3）。

**制限**：変更のない文書も毎回処理するため、クロールの時間と書き込みの負荷は文書数に比例する（§10.3）。

### 3.3 クロールの完了状態・異常系

PD v0.4 付録D.3。

| 状態 | 条件 | 削除 |
| --- | --- | --- |
| 正常完了（`succeeded`） | 列挙が最後まで完了し、スキップした文書がない（抽出失敗は、スキップに含めない）。列挙が0件でも、アクセスできていて最後まで完了していれば`succeeded`である（§3.4） | Indexerが判断する（§3.4、§3.9） |
| 部分成功（`partially_succeeded`） | 列挙は最後まで完了したが、リトライしてもだめでスキップした文書がある（`skipped_count`が1以上） | Indexerが判断する（スキップした文書は`last_seen_at`が更新済みで、さらに削除対象から除外されるので対象にならない） |
| 失敗（`failed`） | 列挙が途中で止まった（アクセスできないディレクトリなど、列挙中のエラーを含む。§3.1）、OpenSearch全体の異常またはIndexerの異常（判定基準は§3.1）、`last_seen_at`の部分更新の失敗、開始通知・終了通知の失敗（§3.9）、またはマウント外れなどの全体の異常 | 行わない（終了通知は`outcome=failed`で送るか、届かない。どちらでも削除されない） |
| 取り消し（`cancelled`） | 管理者が実行を取り消した | 終了通知の送信前なら行わない。送信後は止まらず、同期結果に残る（§3.9） |

部分成功のクロールの結果は、Admin Viewにスキップした文書の一覧（§3.1）とあわせて表示する。

**ジョブのstatusと削除結果は切り離す**：ジョブのstatusは、列挙と登録の結果だけを表す。削除の結果（削除した件数、割合ルールで削除しなかった、件数照合の不一致など）は、同期結果（§3.9）に持つ。ジョブの記録には、その要約を残すが、statusには反映しない。同期結果の確認がタイムアウトしたときも、statusは変えない（警告のみ）。削除されなかったことは、ジョブの失敗ではなく同期結果の状態として、Admin Viewにジョブと並べて表示する。

**読めない文書**：権限エラーなどで読めない文書があっても、その文書をスキップするだけで、他の文書の処理と削除は止まらない。本書v0.1にあった「失敗が続く文書があると削除が止まり続ける」制限は廃止した。管理者はAdmin Viewでスキップした文書を確認し、アクセス権の修正や除外条件への追加など、原因を解消して再実行する。

### 3.4 期限による削除

PD v0.4 付録D.4。本書v0.4で、判断と実行をIndexerに移した（§3.9）。

- 削除の対象は、**列挙が最後まで完了したクロール**（`succeeded`、またはスキップのみの`partially_succeeded`）の終了通知（`outcome=enumeration_completed`）を受け、世代の確認、メンテナンスフラグの確認、件数照合に通った同期で、同じ`source_id`のうち`last_seen_at + TTL < 現在時刻`の文書である。差分だけを取るクロール（将来のConnector）は、`enumeration_completed`として通知しないので、削除されない。列挙の失敗、マウント外れなど、クロール全体の異常では、Crawlerは`outcome=failed`を通知するか通知できず、いずれも削除しない。
- TTLはデータソースごとに指定し、クロールの間隔より長くする。例：日次クロールでTTLが3日なら、3回続けて見つからなかった文書を削除する。Indexerは、開始通知のスナップショットに載ったTTLを使う（§3.9）。
- **0件列挙**：本書v0.3の「0件列挙は異常扱いの`failed`」は廃止した。アクセスできていて最後まで完了した0件列挙は、列挙の完了であり、ジョブは`succeeded`になる。削除するかは、件数照合（`0 = N_seen + E_missing`）を通したうえで、割合ルール（§3.5）が決める。`last_seen_at + TTL`が過ぎていない文書は、対象にならない。TTLが過ぎて対象が分母に近づくと、割合ルールが働いて削除されない。これが、マウント外れや共有の切断による全件削除の保護になる。
- **実際に全ファイルを消した場合（強制削除モード）**：割合ルールでは、全件（100%）の削除は通常行われない。全ファイルを実際に消したときは、管理者が**手動実行のクロールの起動時に**強制削除モードを指定する。このモードは、**割合ルールと最小件数ルールだけ**を無視し、`last_seen_at + TTL < 現在時刻`の文書をすべて削除する。0件列挙でも全件を削除する。次は無視しない：列挙が最後まで完了していること、世代が現行であること、件数照合が成立すること、メンテナンスフラグがないこと、スキップした文書の除外、各文書のTTLの経過（したがって、全件削除は最後に見つかってからTTLが過ぎた後になる）。TTLを過ぎていない文書は、強制削除モードで実行しても対象外で残る。全件を削除したいときは、TTLの経過後に実行する。定期実行からは指定できない。同期結果に、強制削除モードで実行したことを記録する（§3.9）。
- **0件保護の限界**：専用の0件保護はなくなり、割合ルールに一本化した。次は防げない制限事項として残す：(1)一部のディレクトリだけがマウント外れなどで消えた場合、しきい値以下の少数の消失は通常の削除として扱われる。(2)削除対象が最小件数以下の小さなソースでは、0件列挙（マウント外れの空ディレクトリなど）でも、TTLが過ぎた文書は削除される。MVPではこれ以上は作り込まない。
- **二重防御**：削除の対象を決めるとき、今回のスキップした文書のID（終了通知で渡された`skipped_document_ids`）を、明示的に削除対象から除外する。`last_seen_at`の更新が万一漏れていても、スキップした文書は消さない。
- 削除対象は検索で抽出するため、抽出前にリフレッシュする。抽出と削除はIndexerが行い、Crawlerは検索インデックスを直接読まない。削除は、Store層、検索インデックスの順に行い、バッチごとに再抽出する。削除前のロック所有確認は行わず、代わりにバッチごとの世代判定とメンテナンスフラグの確認を行う（§3.9、§4.5）。
- データソースから消えた文書は、削除されるまで検索結果に残る。検索時に`last_seen_at`で除外はしない。クロールが失敗し続けると、全文書が検索から消えてしまうためである。

### 3.5 削除の割合ルール

PD v0.4 付録D.5の「削除の保留」を、本書v0.4で承認のない自動判断に置き換えた。判断はIndexerが行う（§3.9）。

- **判定**：削除対象の件数 T、削除前の同じ`source_id`の登録文書数（分母）D（検索インデックスの件数。リフレッシュ後に数える。登録済みのスキップ文書も含む）として、次の順で判定する。
  1. T が最小件数以下なら、率に関わらず削除する（少数のソースで1件の削除が高い率になるため）。
  2. そうでなければ、T ÷ D がしきい値以下なら削除する。超えるなら削除しない（同期結果の状態は`skipped_by_ratio`。T、D、しきい値、理由を記録する）。
  3. 強制削除モード（§3.4）では、1と2を行わず、削除する。
- **設定**：しきい値と最小件数は、データソースの設定にする（`loreley-sources`）。開始通知のスナップショットでIndexerに渡し、その同期の判断に使う。しきい値の既定値は未決定（§12.5）。最小件数の既定値は未決定（例：10件）。
- **承認はない**：削除の保留、承認、却下、`superseded`のレコードは持たない。割合を超えた同期は、削除しないで終わる。状態は引き継がず、次の同期のたびに新しく判定する。管理者は、Admin Viewで同期結果（`skipped_by_ratio`と、T、D、しきい値）を確認する。大量の削除が意図したものなら、強制削除モードを指定して手動でクロールを実行する（§3.4）。しきい値を変えたときは、次の開始通知から反映される。
- 割合ルールで削除しなかったことは、ジョブのstatusに影響しない（§3.3）。
- しきい値の既定値、最小件数の既定値は未決定（PD v0.4 9.2 #4。§12.1、§12.5）。

### 3.6 突合ジョブ

PD v0.4 付録D.6。検索インデックスとStore層の食い違いを検出し、安全な範囲で直す。Admin Viewから手動で実行する。ジョブとしての起動・管理はCrawler、検索インデックスとStore層の実際の読み書きはIndexerが担う（案。細部は§12.5）。突合ジョブはソースごとの実行ロックを取り、同じソースのクロールと同時には動かさない（案）。定期実行は将来（PD v0.4 9.2 #18。§12.2）。MVPでは、**検出と安全な再登録まで**にとどめる。

**比較する項目**：同じ`document_id`の存在確認に加え、`content_hash`と`index_status`は、次の2つに限って比べる。(1)`pending_index`が`pending_since`から一定期間続いているもの、(2)Store層の`index_status`が`extract_failed`で、検索インデックスの写しが`indexed`である食い違い。更新の途中で通常起きる短時間の不一致は、誤検出しない（検出対象にしない）。

| 食い違い | 対応 |
| --- | --- |
| 検索インデックスにあってStore層にない文書（削除が途中で止まった場合に発生しうる） | 検索インデックスから削除する（Store層が正のため） |
| 同じ`document_id`が両方にあり、上の限定した条件に当てはまる`content_hash`・`index_status`の不一致 | 検出して、Admin Viewに表示する。元ファイルが存在するなら、再索引化（Store層の確定済みの本文からの再登録、または次のクロールでの再処理）を試みる |
| Store層にあって検索インデックスにない文書（`index_status=pending_index`。登録の失敗で発生する） | 次の項目の方針に従う |

**`pending_index`の文書の扱い**：`pending_since`（`pending_index`になった日時。登録に成功して解消するまで更新しない）は、**削除条件にしない**。期限を過ぎたことだけを理由に消すと、一時的な障害で登録できなかっただけの実在文書を誤って消すためである。`pending_since`は異常検知にだけ使う。

| 状況 | 対応 |
| --- | --- |
| `pending_index`が続いている | Admin Viewで警告する（`pending_since`からの経過期間を表示） |
| 元ファイルが存在する | 再索引化を試みる（次のクロールで再処理される。突合ジョブからの手動の再登録も可） |
| 列挙が正常に完了し、元ファイルの不存在を確認できた | 削除候補とする。MVPでは自動削除せず、Admin Viewで確認して手動で削除する（将来の方式は未決定。PD v0.4 9.2 #17。§12.2） |
| 元ファイルの存在を確認できない（取得エラー、マウント外れなど） | 自動削除しない |

MVPでは、**Store層にだけ存在する文書の自動削除は行わない**。検出、Admin Viewの表示、手動確認（安全な再登録を含む）にとどめる。スキップが続く文書（§3.1）も、Admin Viewで確認して手動で扱う。`pending_index`を警告するまでの期間は未決定（PD v0.4 9.2 #4。§12.1）。

### 3.7 将来拡張：差分検知と関連機能

PD v0.4 付録D.7。MVPの全件更新（§3.2）の負荷が問題になったときに導入する設計である。PD v0.4 の付録D.7の記述を、ほぼそのまま移している（この冒頭の文面は、本書v0.2で元の意図を推測して直したものである。推測）。これを導入する場合は、あわせて`extractor_version`・`extract_fail_count`（§1.3の予約項目）を使う。`last_seen_at`の部分更新と、読めない文書のスキップ（§3.1）はMVPで導入済みである。導入の条件は未決定（PD v0.4 9.2 #9。§12.1）。

以下の「旧D.2」「旧B.4」などは、PD v0.3 での節の位置を指す。

**差分検知（旧D.2）**

列挙のたびに、文書ごとに次の順で判定する。

1. **スキップ条件**：次のすべてを満たすときだけ、取得も`content_hash`の計算も省略する（Connectorが列挙時に取得した`mtime`・`size`とStore層の値を比べる。`source_mtime`・`source_size`は列挙時の値、`stored_mtime`・`stored_size`はStore層に保存した`source_updated_at`・`size`に対応する）。

   ```text
   can_skip = (index_status == "indexed"
               or (index_status == "extract_failed"
                   and extract_fail_count >= 上限))
              and source_mtime == stored_mtime
              and source_size == stored_size
              and extractor_version == current_extractor_version
   ```

   `pending_index`の文書、および失敗回数が上限未満の`extract_failed`の文書は、`mtime`・`size`が一致していても**スキップしない**（処理が完了していないため）。上限に達した`extract_failed`は、`mtime`・`size`・`extractor_version`が変わらない限りスキップする（停止中）。
2. スキップしない場合は原本を取得して`content_hash`を計算する。確定済みの`content_hash`と同じで、かつ`extractor_version`も現在と同じで、かつ`index_status=indexed`なら、本文の再処理は省略し、`mtime`/`size`だけを更新する。
3. `content_hash`が違えば、再抽出して全文upsertする。
4. `extractor_version`（抽出ロジックとライブラリのバージョン）が変わった場合は、**`content_hash`が同じでも再抽出する**。`extractor_version`の変更は、ステップ2の`content_hash`の一致より優先する。全件を一度に再処理しないよう、クロールの中で順次処理する。
5. 検索インデックスへの登録に成功してから、**最後に**Store層の`content_hash`・`mtime`・`size`・`extractor_version`をまとめて確定する（`extract_failed`で終わった場合も、`mtime`・`size`・`extractor_version`は確定する。上限到達後のスキップ判定に使うため）。途中で失敗すると確定されないので、次回のクロールで再処理される。登録前の間は`pending_content_hash`と`index_status=pending_index`を持つ。本文を更新した文書は、要約を引き継がず`summary_status=pending`に戻す。

`mtime`と`size`が同じまま内容だけが変わると見逃す。これは既知の限界で、MVPでは許容する。

**抽出失敗の再試行**：`extract_failed`の文書は、連続して失敗した回数（`extract_fail_count`）が上限（例：3回）に達するまで、次のクロールで再処理する（上記のとおりスキップしない）。上限に達したあとは、**`mtime`・`size`・`extractor_version`のいずれかが変わるか、管理者が手動で再試行するまで**、自動では再処理しない。`content_hash`は、`mtime`・`size`が変わって取得し直したあとに、再抽出が必要かを判定するために使うもので、停止の解除条件そのものではない。`extract_fail_count`は、解除条件を満たして再処理を始める時点で0に戻す。上限到達後の文書は、スキップされるのではなく「停止中」としてAdmin Viewに表示する。

**発見と取得の分離（旧D.1）、`last_seen_at`の部分更新（旧B.4）**

MVPに取り込み済み（§3.1、§2.4）。差分検知を導入して、スキップ条件に一致する文書の取得を省くときも、列挙時の`last_seen_at`の部分更新は引き続き必須である（取得しない文書が、TTLで削除されないようにするため）。

**間引き（任意）**：§2.4の部分更新の書き込み量を減らすため、現在の`last_seen_at`がTTLの1/3より新しければ更新しない。判定に必要な現在の`last_seen_at`は、検索インデックスから読む（スクリプト内の比較、または一括取得）。間引くと、判定上のTTLは最大でTTLの1/3だけ短くなる（実効TTLは最短でTTL×2/3）。そのため、TTL×2/3がクロール間隔より長くなるように設定する。

**恒久失敗（旧D.3）**

本書v0.1では、同じ文書の取得・登録の連続失敗回数（`fetch_fail_count`）が上限に達したら「恒久失敗」として部分成功の判定から除外する設計だった。MVPでは、読めない文書をスキップしても削除が止まらない（§3.1、§3.3）ため、この判定は不要になり、`fetch_fail_count`は廃止した。連続失敗の回数は、スキップ記録の`consecutive_skips`が持つ（新規文書も記録できる）。

将来、差分検知の導入時に、長く読めない文書のリトライ負荷を下げたい場合は、`consecutive_skips`が上限を超えた文書の試行回数を減らす（例：リトライなしの1回だけ試す）拡張を検討する。導入の条件は未決定。

### 3.8 Store層と検索インデックスの整合性・排他

PD v0.4 付録C.3。

- OpenSearchの検索はリフレッシュ後にしか反映されない（ニアリアルタイム）。状態の確認や排他の判定には、検索ではなくIDによる取得（リアルタイム）を使う。
- 条件付き更新には`if_seq_no`/`if_primary_term`を使う。要約をStore層へ保存するときは、読み出した文書の現在の本文のハッシュ（確定前は`pending_content_hash`、確定後は`content_hash`）が生成元と一致し、かつ`if_seq_no`/`if_primary_term`が一致するときだけ書く。本文が変わるとき（`content_hash`が既存と違うとき）は、Store層の要約を消して`summary_status`を`pending`（要約が無効なら`disabled`）に戻す。
- 初回の作成は、存在しない場合だけ成功する作成（create）を使う。
- Store層と検索インデックスは別のインデックスであり、またがるトランザクションはない。更新の途中では、両者の内容（本文の`content_hash`や`index_status`）が一時的に食い違う。MVPでは短時間の不一致を許容し、検出と復旧は突合ジョブ（§3.6）、読み出し時の扱いは`get_document`（§5.4）に定める。
- ノードが1つなので、データの消失に備えてスナップショットを取る（§9）。

### 3.9 同期管理（Sync Manager）

本書v0.4で新設した。削除の判断と実行を担う、Indexerの**内部モジュール**（独立コンテナにしない）である。クロール1回を「同期」と呼ぶ。CrawlerからIndexerへの通知を受けて、記録、検証、判断、削除を行う。Crawlerは検索インデックスを読まず、削除の判断にも関わらない。通知や応答の形は案で、細部は§12.5に回す。

**責務の分担**

| 項目 | 担当 |
| --- | --- |
| 列挙の完了とスキップの確定、開始・終了通知の送信、Status APIのポーリング、結果の要約のジョブ記録 | Crawler |
| 世代の管理、検証、削除対象の決定、割合ルール、TTLの判定、削除の実行 | Indexer（Sync Manager） |
| `loreley-sync`への書き込み | Indexerだけ |
| 同期結果の表示 | Admin API（`loreley-sync`を読み取りのみで直接読む） |

**`loreley-sync`の記録**（インデックス名は仮名）

| ID | 内容 |
| --- | --- |
| `sync-{source_id}` | ソースごとの現行世代：`crawl_id`、`crawl_started_at`、設定スナップショット（TTL、しきい値、最小件数）、`force_delete`、更新日時。開始通知で更新する |
| `syncresult-{crawl_id}` | 同期結果：`source_id`、`status`、`reason`、`outcome`、`enumerated_count`、`n_seen`、`e_missing`、`target_count`（T）、`denominator`（D）、`deleted_count`、`forced`（強制削除モードで実行したか）、`finish_received_at`、`deletion_started_at`、開始・終了日時。ソースごとに直近N件を保持し、古いものはIndexerが消す（Nは§12.5） |

**`crawl_id`と世代**：`crawl_id`は、CrawlerのジョブIDをそのまま使う（新しいIDを採番しない）。現行世代は、そのソースで最後に受理した開始通知の`crawl_id`である。単一Crawler・直列実行なので、通常は同時に1つの世代しかない。

**開始通知**（`POST /syncs/start`。案）

- 送るタイミング：ロック取得後、列挙の前。
- 内容：`crawl_id`、`source_id`、`crawl_started_at`、設定スナップショット（`ttl`、`ratio_threshold`、`min_delete_count`）、`force_delete`（既定は`false`）。
- 拒否（409。案）：次のどちらかなら、開始通知を拒否する。(1)`crawl_started_at`が、現行世代の`crawl_started_at`より古い（遅れて届いた古い通知で、世代が巻き戻らないようにする）。(2)`syncresult-{crawl_id}`がすでに終端状態である（終了した同期の通知が再送されても、`running`に戻さない）。Crawlerは、409をジョブ`failed`として扱う。
- Indexerの動作：同じ`crawl_id`の再送で、同期結果が`running`なら、状態を変えずに成功を返す。それ以外は、`sync-{source_id}`の現行世代を更新し、`syncresult-{crawl_id}`を`running`で作る。同じソースに、終端状態でない旧世代の同期結果があれば、削除の判定中または実行中だったものは`interrupted`（理由：`superseded`）、それ以外は`discarded`（理由：`superseded`）にする（終了通知が届かなかった世代の整理を兼ねる）。
- 通知の失敗（リトライ設定の回数まで試しても直らない場合）は、ジョブを`failed`にする。削除は行われないだけで、安全である。

**終了通知**（`POST /syncs/{crawl_id}/finish`。案）

- 送るタイミング：すべてのバッチ登録（と`last_seen_at`の部分更新）の応答を確認したあと。列挙の失敗・取り消しの場合は、`outcome=failed`または`cancelled`を可能なら送る（届かなくても、削除されないので安全）。取り消しが有効なのは、終了通知を送る前だけである。終了通知を送ったあとに取り消しても、同期は止まらない（下の「Crawlerの手順と送信順序」）。
- 内容：`source_id`、`outcome`（`enumeration_completed` / `failed` / `cancelled`）、`enumerated_count`（Crawlerが`document_id`で重複を除いて数えた、列挙で見つかった文書の数。スキップ・抽出失敗の文書を含む）、`skipped_document_ids[]`、`skipped_count`、`finished_at`。
- 応答は**202のみ**（受理。判断は非同期）。判断の結果は応答に含めない。Crawlerは、Status APIで確認する。Indexerは、`finish_received_at`を`loreley-sync`に永続化してから202を返す（202のあとに再起動しても、受理した事実が残り、再起動時に`interrupted`にできる）。
- 再送は冪等である。受理済みの`crawl_id`は再処理しない。内容が最初と異なる再送は、409で拒否する（案）。
- 受理後の分岐：(1)`crawl_id`が現行世代と一致しない場合：その`crawl_id`の同期結果があって`running`なら、`discarded`（理由：`stale`）にする。すでに終端状態なら何もしない。開始通知を受けていない未知の`crawl_id`は、同期結果を作らず（記録しない）、ログに残すだけである。どちらも応答は202で、削除しない。(2)`outcome`が`failed`または`cancelled`なら、`failed`（理由に`outcome`）を記録して削除しない。(3)`enumeration_completed`なら、下の判定に進む。

**検証**（状態を持たない）：次が成立するときだけ、削除の判断に進む。

```text
enumerated_count == N_seen + E_missing
  N_seen    = 当該source_idで last_seen_at >= crawl_started_at の件数（リフレッシュ後の検索インデックス）
  E_missing = skipped_document_ids のうち、検索インデックスにないものの件数
```

スキップした既存文書は、列挙時の`last_seen_at`の部分更新で`N_seen`に数えられる。スキップした新規文書（検索インデックスにない）は`E_missing`に数える。不一致なら削除せず、`validation_failed`として、3つの数値と`enumerated_count`を記録する。許容差は設けない（案）。`skipped_document_ids`が上限（§12.5）を超えるときも、削除せず`validation_failed`にする（案）。

**件数の数え方**（案）：`enumerated_count`は、Crawlerが`document_id`で重複を除いて数える（列挙が同じ文書を2回返しても1と数える）。抽出に失敗した文書（`extract_failed`）は、タイトルとメタデータが登録されて検索インデックスにあるので、`N_seen`に数えられる。`N_seen`は、列挙以外の書き込みでも増えうる（例：突合ジョブの再登録）。その場合は不一致になり、削除しない（安全側）。突合ジョブ（§3.6）は、同じソースのロックを取るジョブとして、クロールと同時には動かさない前提とする。

**判定の順序**（`enumeration_completed`の終了通知を受けたとき。判定中も、同期結果は`running`である）

| 順 | 確認 | 満たさないとき |
| --- | --- | --- |
| 1 | 世代が現行 | `discarded`（理由：`stale`） |
| 2 | メンテナンスフラグ（`loreley-jobs`）がない | `interrupted`（理由：`maintenance`） |
| 3 | 件数照合が成立 | `validation_failed` |
| 4 | 削除対象の決定（`last_seen_at + TTL < 現在時刻`、スキップ文書を除外） | 対象が0件なら、`deleted`（`deleted_count=0`） |
| 5 | 割合ルール・最小件数ルール（§3.5）。強制削除モードは無視 | `skipped_by_ratio` |
| 6 | 削除の実行（バッチごとに、実行の直前に世代とメンテナンスフラグを確認する。最初のバッチの前も含む） | 通らなければそのバッチを実行せず、`interrupted` |

**強制削除モード**：クロールの起動時に、手動実行でのみ指定できる（定期実行からは指定できない。§14.4）。開始通知の`force_delete`で渡し、`sync-{source_id}`に記録する。順5の割合ルールと最小件数ルールだけを無視する。順1〜3、4（TTLとスキップ文書の除外）、列挙の完了は無視しない。0件列挙でも、対象があれば全件を削除する。同期結果の`forced`に、強制削除モードで実行したことを記録する。

**削除の実行**

- **バッチの流れ**：(1)対象を再抽出する（リフレッシュ後。バッチ件数は§12.5）。(2)**バッチの実行の直前に**、世代（`sync-{source_id}`の現行世代が自分の`crawl_id`か）とメンテナンスフラグを確認する。最初のバッチの前も含む。通らなければ、そのバッチは実行せず、`interrupted`（理由：`superseded`または`maintenance`）にして止める。(3)バッチの各文書について、削除の直前に、検索インデックスから現在の`last_seen_at`をIDで読み直し、`last_seen_at + TTL < 現在時刻`を再確認する。満たす文書だけ、Store層、検索インデックスの順に削除する。満たさない文書（抽出のあとに更新された文書）は削除しない。実行中のバッチは、途中で世代が変わっても止まらず（止まるのはバッチの単位）、次のバッチの前の確認で止まる。TTLの再確認があるので、その間に新しいクロールが更新した文書は消えない。
- **順序と窓**：Store層（`loreley-texts`）、検索インデックスの順に削除する。検索インデックスの削除にも同じ条件を付ける（条件付きの削除）。再確認からStore層の削除までの極小の窓で`last_seen_at`が更新された場合や、Store層の削除の後に止まった場合は、Store層だけが消えて検索インデックスに文書が残る。この文書は、次の全件更新で全文upsertされ、Store層も復旧する（自己修復）。突合ジョブ（§3.6）が先に走ると、検索インデックスの文書は削除され、次の全件更新で再登録される。この窓は、本書v0.5で`loreley-texts`を廃止すると消える。
- Indexerが判定中または削除の実行中に再起動した場合は、その同期結果を`interrupted`（理由：`indexer_restart`）にし、再開しない。起動時に、`finish_received_at`があって終端状態でない同期結果を対象にする。残りの削除は、次のクロールに委ねる（TTL方式のため、削除が遅れるだけである）。
- Indexer側の削除のエラーは、リトライ設定（§3.1）の回数まで試し、直らなければ`failed`（理由にエラーの種類）にして止める。それまでの削除件数は記録する。

**同期結果の状態**（`status`）

| 状態 | 意味 |
| --- | --- |
| `running` | 開始通知を受けてから終端状態になるまで（終了通知待ち、判定中、削除中を含む） |
| `deleted` | 判断を通り、削除を完了した（対象が0件の場合を含む）。`deleted_count`を記録する。強制削除モードなら`forced=true` |
| `skipped_by_ratio` | 割合ルールで削除しなかった。T、D、しきい値を記録する |
| `validation_failed` | 件数照合の不一致、またはスキップ文書IDの上限超過。数値を記録する |
| `discarded` | 古い世代（`stale`）、新しい開始通知で置き換えられた（`superseded`）、ソース削除で破棄された（`source_deleted`）。`reason`に区別を記録する。未知の`crawl_id`は記録しない |
| `interrupted` | 判定中または削除の途中で、メンテナンスフラグ、新しい開始通知、Indexerの再起動により止まった。再開しない |
| `failed` | クロールの失敗・取り消し（`outcome`）の通知、またはIndexer側の削除のエラー |

`running`以外が終端状態である。

**Status API**（`GET /syncs/{crawl_id}`。案）：同期結果を読み取りで返す。内容は、`status`、`reason`、`forced`、`target_count`、`denominator`、しきい値、`deleted_count`、`enumerated_count`と`n_seen`・`e_missing`（検証の数値）、時刻である。保持件数を超えて消えた`crawl_id`、開始通知を受けていない`crawl_id`、`loreley-sync`を失った場合は404を返す。Admin Viewの表示は、同じ内容をAdmin APIが`loreley-sync`から直接読む。

**Crawlerの手順と送信順序**

1. ソースのロックを取得する。
2. 開始通知を送る。
3. 列挙、`last_seen_at`の部分更新、バッチ登録を行う（§3.1、§3.2）。
4. 全バッチ登録の応答を確認する。
5. 終了通知を送り、202を確認する（これより前なら、取り消しで`outcome=cancelled`を送って終えられる）。
6. Status APIをポーリングして、同期結果が終端状態になるのを待つ。間隔と上限時間は§12.5。
7. 同期結果の要約（状態、T、D、削除件数、強制削除の有無、理由）をジョブ記録に残し、ジョブの最終状態を記録する。
8. ロックを解放する。

ロックは、同期結果が終端状態になるまで保持する（次のクロールとの競合を減らす）。ポーリングの失敗は警告にとどめる。タイムアウト、および接続エラー・5xx・404（保持件数の超過、または`loreley-sync`の喪失）がリトライ設定の回数まで続いた場合は、警告をジョブ記録に残すだけで、ジョブのstatusは変えない。そのあとロックを解放する（案。次のクロールの開始通知は、旧世代を中断・破棄する）。ポーリング中もジョブは`running`で、ハートビートを続ける（§4.3）。列挙が失敗または取り消しになったときは、ポーリングせず、ジョブを終えてロックを解放する。**終了通知を送ったあとの取り消し**は、同期を止めない。ジョブは`cancelled`になり、Crawlerはポーリングを打ち切ってロックを解放するが、Indexerは判断と削除を続け、結果は同期結果に残る（削除結果とジョブのstatusは切り離されている。§3.3）。

**競合と失敗の扱い**

| 状況 | 扱い |
| --- | --- |
| 旧世代の削除中に、新しいクロールの開始通知が来る | 進行中のバッチは完了しうるが、次のバッチの実行前の世代確認で止まる（`interrupted`）。最初のバッチの前に届いた場合は、そのバッチを実行せず止まる。新世代の終了通知で改めて判断する |
| 古い`crawl_started_at`の開始通知（遅れて届いた、再送）、終端状態の`crawl_id`の開始通知 | 409で拒否する。世代は変わらない。ジョブは`failed` |
| 終了通知の重複 | 冪等。再処理しない |
| 終了通知が届かない（Crawlerの停止、通信失敗） | 同期結果は`running`のまま。削除されない。次の開始通知で`discarded`になる |
| 開始通知なしの終了通知、未知の`crawl_id` | 同期結果を作らず（記録しない）、202を返す。削除しない |
| 旧世代の遅れた終了通知 | 同期結果が`running`なら`discarded`（理由：`stale`）。削除しない |
| 終了通知を送ったあとの取り消し | 同期は止まらない。ジョブは`cancelled`、削除結果は同期結果に残る |
| Status APIのポーリングの失敗 | 警告のみ。ジョブのstatusは変えない |
| メンテナンスフラグ | 判定の前と各バッチの実行の前に確認し、立っていれば止める（`interrupted`）。削除の実行も、メンテナンス停止の対象である（§2.5） |
| ソース削除（§1.2）のときに同期が`running` | 世代を先に破棄してから、同期の記録を削除する |
| 時刻 | `crawl_started_at`、`last_seen_at`、TTLの判定は、CrawlerとIndexerが同じホストの時計で動く前提（時刻ずれは想定しない） |

**受容事項**：(1)新しいクロールが、削除の前に始まると、旧世代の削除は破棄される。(2)新しいクロールが失敗し続けると、削除は遅れるだけである（TTL方式のため安全）。(3)登録・`last_seen_at`の更新は世代を確認しない（所有確認のみ。§4.5、§4.7）。件数照合は、遅れた登録の取りこぼしがあれば不一致になり、削除を止める。(4)ポーリングのタイムアウト後、または終了通知後の取り消し後は、ロックが解放されるので、突合ジョブや次のクロールが旧同期の削除と重なりうる。件数照合の不一致なら削除されず、削除の実行中は各削除の直前のTTL再確認と、次のバッチ前の世代確認が働くので、安全側に倒れる（D-30）。

## 4. ジョブ管理

> プロダクトデザイン上の位置づけ：クロールはジョブとして管理する。MVPは単一Crawler・直列実行を基本とし、これ以上の異常系は作り込まない（PD v0.9 参照。PD v0.8 までの表記は「単一Worker」で、本書では Crawler と Indexer に分けた。§14）。

本章のジョブ・ロック・リース・スキップ記録は、**Crawlerが持つ**。`loreley-jobs`に書き込むのはCrawlerだけである（Admin APIは書かない。例外はメンテナンスフラグ。§1.3、§14.2）。削除の判断・実行に関わる世代と同期結果は、Indexerが`loreley-sync`に持つ（§3.9）。要約生成はIndexer内部の非同期処理で、本章のジョブ・ロックの対象ではない（§4.4）。

### 4.1 状態遷移と基本方針

PD v0.4 付録E.1、4.7。状態は、実行待ち・実行中・成功・一部成功・失敗・取り消しの6つ。

`queued` → `running` → `succeeded` / `partially_succeeded`（スキップした文書がある。削除は行う）/ `failed` / `cancelled`。

- ジョブの状態はStore層（`loreley-jobs`）に保存する。ジョブの起動はCrawlerへのHTTP要求で行い、Crawlerは受け付けたときにロックとジョブ（`queued`）を記録してから受付応答を返す（§14.4）。実行は非同期・直列である。
- 同じデータソースのクロールは同時に1つだけ実行する。止まったジョブは`failed`として検知する。再実行は、Crawler再起動または管理者のロック解放のあとに行う（§4.3）。
- 一時的なエラーは、§3.1のリトライ設定（既定は最大3回試行、指数バックオフ）に従ってリトライする。文書単位の失敗は、リトライしてもだめならその文書をスキップする。ジョブ全体の失敗（OpenSearchやIndexerへの接続不可など）は、ジョブを`failed`にする。失敗したジョブは、Admin Viewから再実行できる。
- 文書ごとの処理状態（`index_status` / `summary_status`）はジョブとは別に保持する（§2.1）。

### 4.2 排他とリース

PD v0.4 付録E.2。以下の操作は、すべてCrawlerが行う。

- ジョブには、`owner`（実行しているCrawler）、`heartbeat_at`、`lease_expires_at`を持たせる。
- `queued`から`running`への遷移は、`if_seq_no`/`if_primary_term`を使った条件付き更新で行う。
- データソースごとの実行ロックは、`loreley-jobs`のロック用文書（ID：`lock-{source_id}`）で表す。存在しない場合だけ成功する作成（create）でのみ取得する。ロックの対象は、クロールと突合ジョブである（案。§3.6）。Crawlerは、起動要求を受け付けたときにロックの作成とジョブ（`queued`）の保存を行ってから、受付応答を返す（§14.4）。リース期限切れのロックの引き継ぎは、Crawler再起動時と管理者の解放に限る（§4.3）。
- **MVPは単一Crawler・直列実行を基本とする**。複数のCrawlerを同時に動かす構成はMVPでは対象にしない。

### 4.3 ハートビート・リース切れ・Crawler引き継ぎ

- 実行中のCrawlerは、リース期間（例：5分）の1/3程度の間隔でハートビートを送り、`lease_expires_at`を延長する。Indexerへの同期HTTP呼び出しの待ち時間中もハートビートが途切れないようにする（方法は実装時に決める。§12.5）。
- `lease_expires_at`を過ぎた`running`のジョブは、`failed`として表示する。ただし、**リース期限切れだけでは、別のCrawlerが自動でロックを引き継がない**（前のCrawlerが停止したのか、遅いだけなのかを区別できないため）。
- 引き継ぎは次の場合に限る。(1)単一Crawlerの再起動時（前のインスタンスは停止済みとみなし、自分のものだった期限切れのロックを引き継ぐ）、(2)管理者がAdmin Viewでロックを解放したとき（Admin APIがCrawlerに中継する。§14.4）。ロックが保持されている間は、そのソースのジョブを再実行できない。このときの起動要求（409）には、既存ジョブの状態を含める（§14.4）。
- **Crawler起動時の回復**：未完了のジョブを次のように扱う。`queued`のジョブは再投入する。`running`だったジョブは`failed`にする。細部（再投入の順序、ロックの扱い）は実装時に決める（§12.5）。
- **孤児ロックとリース**（案）：ロックの作成とジョブの保存は原子的でないため、ジョブのないロック（孤児ロック）が残りうる。孤児ロックも、Crawler起動時の回復の対象にする。`queued`の間はロックを保持するが、リースの失効判定の対象にせず（起動時の回復で扱う）、`queued`から`running`への遷移時に`lease_expires_at`を設定し直す。
- 前Crawlerの停止を確認する方法は実装時に決める（PD v0.4 9.2 #14。§12.2）。再起動時の引き継ぎは、再起動前後で同じ安定したCrawler IDを使うことが前提である（PD v0.4 9.2 #14）。
- リース期間の既定値は未決定（PD v0.4 9.2 #4。§12.1）。

### 4.4 要約生成

要約生成はIndexer内部の非同期処理であり、`loreley-jobs`のジョブ・ロック・リースの対象にしない（`loreley-jobs`に書くのはCrawlerだけのため。要約の状態は`summary_status`で持つ。§2.1）。要約生成の再開・リトライ・負荷制御の方法は実装時に決める（§12.5）。

本書v0.2では、単一Worker・直列実行により「クロールの実行中には要約を書かない」としていた。CrawlerとIndexerが別コンテナになるため、要約の書き込みがクロールと並行する場合がありうる。**厳密な直列は保証せず、`content_hash`の条件付き更新で正しさを保つ**方針に緩和する。すなわち、要約を検索インデックスとStore層に書くときは、生成元の`content_hash`が現在の本文と一致するときだけ書き、不一致なら捨てる（§2.4、§3.8、§8.4）。

メンテナンス（再インデックス）のために`loreley-jobs`のメンテナンスフラグが立っている場合、Indexerは書き込み前にそれを確認し、書き込まずに止まる（§2.5）。実行ロックは、クロール用のロックと区別できないため判別に使わない。確認の詳細は実装時に決める（§12.5）。

**要約生成の再開**（案）：要約生成はジョブ記録を持たない。Indexerの再起動後は、`summary_status=pending`の文書（正はStore層）を再走査して再開する。したがって、要約生成の終了確認（§2.5）は、Indexerの停止が確実な手段である。

### 4.5 リース切れ後の旧Crawler対策（フェンシング）

検索インデックスやStore層への書き込み（登録、`last_seen_at`の更新）の前に、**Indexerが**ロック文書をIDで取得し、書き込みを要請したジョブの所有者であり期限内であることを確認する。確認に必要な情報（`owner`と`job_id`）は、Crawlerが書き込み要請に添えて渡す。確認できなければ（期限内でなければ）書き込みを中止する。再開はCrawlerの再起動か管理者の操作で行う。確認と書き込みの間にはわずかな窓が残る（窓はIndexer側にも広がる）が、`last_seen_at`は全文upsertでも古い値で上書きしない（§2.4）。

**削除の前**：本書v0.3では、削除の前にIndexerとCrawlerの両方がロックの所有を確認していた。本書v0.4では、削除の判断と実行をIndexerが非同期に行い、Crawlerのロックは同期結果の確認後（またはタイムアウト後）に解放されるため、ロックの所有は削除の条件にならない。代わりに、Indexerが**世代の判定**（`sync-{source_id}`の現行世代が自分の`crawl_id`か）と**メンテナンスフラグの確認**を、判定の前と削除のバッチごとに行う（§3.9）。確認できなければ（世代が変わった、フラグが立った）削除を中止する。

確認の対象は、要請に由来する書き込み（登録、`last_seen_at`の更新）である。要約の書き込みは、この確認ではなく、§4.4の条件付き更新とメンテナンスフラグの確認で守る。Crawlerがタイムアウトした後もIndexerの処理が続く窓と旧要請の扱いについては、Indexerは要請を直列に処理し（単一Indexerの前提）、所有確認を文書ごとに行う（案）。それでも残る窓は、MVPでは既知の制限として許容し、完全なフェンシングは§4.7とする。

### 4.6 ロックの解放

同期結果が終端状態になった（またはポーリングがタイムアウトした）あと、ジョブが`succeeded` / `partially_succeeded` / `failed` / `cancelled`になったとき、所有者であるCrawlerが自分のロック文書を条件付きで削除する（送信順序は§3.9）。列挙の失敗、または終了通知前の取り消しでは、ポーリングをせずにロックを解放する。終了通知後の取り消しでは、ポーリングを打ち切ってロックを解放する（同期は止まらない。§3.9）。Crawlerが落ちた場合は、期限切れだけでは別のCrawlerは取得できない。Crawler再起動時の引き継ぎか、管理者のAdmin Viewからの解放を待つ。ソース削除のジョブ（§1.2）は、自分のロックを手順の中で先に削除してからジョブを終了する（案）ため、この解放は不要になる。

### 4.7 将来拡張：複数Crawler化

完全な分散フェンシングは、MVPでは行わない。複数Crawlerにするときに、ロックの取得ごとに増える実行世代番号を持たせ、全文upsertを含むすべての書き込みで古い世代の上書きを原子的に拒否する方式を導入する。

本書v0.4で、削除については`crawl_id`による世代制御を導入した（§3.9）。登録・`last_seen_at`の更新を含むすべての書き込みへ、世代の確認を広げ、古い世代の書き込みを拒否することは、複数Crawler化とあわせた将来拡張とする（現状は所有確認のみ。§4.5）。

## 5. Search API・MCP・文書取得

> プロダクトデザイン上の位置づけ：検索機能はSearch APIとMCPで提供する。MCPはSearch APIを公開するアダプタで、独自の検索ロジックは持たない。認証・認可はMVPでは実装しない（PD v0.9 参照）。

※エンドポイントとリクエスト形式は実装時に確定する。以下は要点である。

### 5.1 Search API

PD v0.4 4.4、付録F.1。OpenSearchを使った共通の検索・文書取得インターフェースを提供する。MCP ServerとWeb UIは、原則としてこのAPI（または同じサービス層）を使う。

- ドキュメント検索：クエリ、データソース・文書形式・更新日による絞り込み、件数。
- ドキュメント取得：本文はStore層の抽出済みテキストから返す。AgentやUIを圧迫しないよう、文字オフセットと最大長で範囲を指定して取得できる。
- 検索結果の整形：タイトル、要約、関連箇所、出典、スコア。
- 認証・認可は将来拡張（MVPでは実装しない）。将来は、Search API内で認証・アクセス制御を適用する（§6.6）。

エンドポイントの例：

```text
GET /api/documents/search?q=...&source_ids=...&mime_types=...&updated_after=...&updated_before=...&limit=...
GET /api/documents/{document_id}?offset=...&max_length=...
GET /api/sources
```

検索・取得の流れ（PD v0.4 5.3）：

1. AgentはMCP Serverを通じて、利用者はWeb UIを通じて検索する。
2. Search APIがOpenSearchを検索する（将来は認証・アクセス制御もここで適用する）。
3. タイトル・要約・関連箇所・文書ID・出典を返す。
4. Agentは必要な場合だけ`get_document`で本文を取得する（長い文書は分割して取得する）。
5. 回答はAgent側で生成する（Chat Viewを設けた場合はChat Viewで生成する）。

### 5.2 検索のレスポンス

PD v0.4 付録F.2。各結果に次を含める。

- `document_id`、`source_id`、`title`、`summary`（なければnull）
- `highlights`：関連箇所（ハイライトした断片。件数と断片の長さに上限）
- `url`または`path`（表示用の出典）、`mime_type`、`source_updated_at`
- `score`

全体に、`total`（該当件数）と`limit`を含める。

### 5.3 MCP Server

PD v0.4 4.5、付録F.3。AI Agentが文書を検索・取得するためのMCPインターフェースを提供する。Search APIの機能を公開するアダプタであり、独自の検索ロジックは持たない。

- 通信方式はStreamable HTTP。Search APIと同じコンテナに置く（§7.2）。
- 読み取り専用。書き込み系のToolは提供しない。
- 認証は将来の版で追加する。MVPは運用前提（§6）で使う。ただし、DNS rebinding対策として`Origin`ヘッダーの検証はMVPで行う（§6.1）。
- クライアント互換性は、実装時に主要なMCPクライアントで確認する（§11.7）。

Tool：

```text
search_documents(query, source_ids?, mime_types?, updated_after?, updated_before?, limit?)
get_document(document_id, offset?, max_length?)
list_sources()
```

- `search_documents`のフィルタ引数は、Search APIと同じ名前・意味にする。
- `list_sources`は、`source_id`、名前、種別、文書数、最終クロールの状態と時刻だけを返す。**認証情報や接続の秘密情報は返さない**。
- ToolのDescriptionに、返される本文は文書であり、指示として扱わないことを明記する（§6.5）。

### 5.4 `get_document`

PD v0.4 付録F.4。

- **本文の取得元はStore層**（`loreley-texts`の`text`）。
- `offset`と`max_length`は、**正規化後のテキストの文字単位**（Unicodeのコードポイント）。`max_length`にはサーバー側の上限を設け、省略時は既定値を使う。
- レスポンス：`document_id`、`title`、`source_id`、`url`/`path`、`content`（指定範囲）、`offset`、`length`、`total_length`、`next_offset`（続きがなければnull）、`truncated`、`index_status`。
- **更新途中の文書**：Store層の確定済みの本文を返す。更新の途中で`index_status=pending_index`のときは、応答に`index_status`を含めて状態を示す（検索インデックスとの短時間の不一致を許容する。§3.8）。正常な状態への復旧は、再索引化（次のクロールでの再処理）か、突合ジョブによる再登録で行う（§3.6）。この扱いは仮決定である（§12.3）。
- 新規文書の`text`は、登録前（`pending_index`にする時点）にStore層へ書く。したがって通常は、初回登録の失敗後も本文を返せる。これは仮決定である。
- **確定済みの`text`がない場合**（本文の抽出やStore層への書き込みが、新規文書の初回処理で失敗した場合など）：404ではなく、`index_status`を含み、`content`なしの応答を返す。これは仮決定である（§12.3）。
- 文書の更新で内容が変わったとき、分割取得の途中の`offset`が新しい本文では意味を持たなくなる。このときの扱い（`content_hash`を応答に含めて変化を検知するなど）は実装時に決める（PD v0.4 9.2 #16。§12.2）。
- `truncated=true`は、索引化のサイズ上限で本文が切り詰められていることを表す。この場合、`total_length`は保存済みの長さであり、元の文書はこれより長い。上限を超える部分は取得できない（§10.2）。

## 6. セキュリティ実装

> プロダクトデザイン上の位置づけ：MVPには認証・認可がなく、信頼できる社内ネットワーク内で、全員が閲覧してよい文書だけを対象に運用する。この前提と、将来の認証方式の方針はPD v0.9 に残る。ここでは、その前提を支える実装上の措置を定める。

### 6.1 MCPのOrigin検証

PD v0.4 6.1。MCPのStreamable HTTP仕様は、DNS rebinding対策としてサーバーにOriginヘッダーの検証を求めている。MVPのMCPエンドポイントは、`Origin`ヘッダーがあり、許可リストにないリクエストを拒否する（HTTP 403）。

- `Origin`ヘッダーのないリクエスト（ブラウザ以外のMCPクライアント）は拒否しない。
- **認証とOrigin検証は別の問題**であり、Origin検証を入れても認証は実装しない（このため、到達できる人は誰でも検索できる前提は変わらない）。
- 設定名、許可リストの書式、ポート指定の扱いは実装時に決める（PD v0.4 9.2 #15。§12.2）。

### 6.2 許可リスト

PD v0.4 6.1。許可するOriginは環境変数または設定ファイルで指定する（例：`MCP_ALLOWED_ORIGINS`にカンマ区切りで列挙。名称は例）。

- 既定はlocalhost系（`http://localhost:*`、`http://127.0.0.1:*`）のみ。
- 社内ネットワークへ公開するときは、公開先のOriginを追加する。

### 6.3 バインド先とポート制限

- 既定ではlocalhostだけで待ち受ける。社内ネットワークへ公開するには、バインド先を設定で明示的に変更する。この前提はREADMEと導入手順で明示する。
- **OpenSearchの保護**：OpenSearchとDashboardsのポートはホストの外に公開しない。Search APIだけを公開の窓口にする（§7.3）。

**内部通信**：CrawlerとIndexerのHTTPは、Composeの内部ネットワークだけで通信し、ホストにポートを公開しない（§7.3、§14.1）。認証なしの前提は変えないため、内部ネットワークに届く範囲が境界になる。

### 6.4 読み取り専用マウント・秘密情報の管理

**読み取り専用マウント（実行環境側の境界）**（PD v0.4 6.1）：Admin Viewは認証を省く代わりに、読み込めるディレクトリをComposeのマウントで限定する。検索対象のディレクトリは、Crawlerに**読み取り専用（`:ro`）**でマウントし（Indexerなど他のコンテナにはマウントしない）、それ以外のホストのパスはコンテナに見せない。Admin Viewは認証なしで任意のローカルパスを登録できるが、コンテナにマウントしたディレクトリ以外は読めない。将来の版で、登録できるルートパスの制限と管理者トークンを追加する。

**秘密情報の管理**（PD v0.4 6.2、4.8）：

- Connectorの認証情報は、Store層（`loreley-sources`）に平文で保存しない。環境変数や秘密情報ファイルで参照する。設定ファイルにも平文で書かない方法を用意する。
- ログに本文や秘密情報を記録しない。
- `list_sources`は認証情報や接続の秘密情報を返さない（§5.3）。

### 6.5 外部通信・プロンプトインジェクション対策

PD v0.4 6.2。

- **外部通信**：要約・Embeddingに外部LLMを使う場合は、明示的な設定を必須にする。既定の構成はオフラインで動作する（§8.1）。
- **プロンプトインジェクション**：文書を加工せずに返す。そのうえで、返す内容が「データソースから取得した文書」であることを出典とあわせて明示し、MCPのTool説明で、本文を指示として扱わないようAgentに注意を促す（§5.3）。
- **運用性**：クロール失敗の再実行、同期状態の確認、ログ、ヘルスチェック、バックアップ・リストア手順（§9）を用意する。

### 6.6 将来の認証・認可（実装上の方針）

将来の版で、API/MCPのトークン認証、管理者トークン、登録できるルートパスの制限、データソース単位のアクセス可否、文書単位のACL同期、SSO連携を順に追加する。Search APIとMCPで同じ権限判定を適用する。検索インデックスには、アクセス制御用の`acl`フィールドを予約している（§2.1）。将来の認証方式（トークンの発行・管理方法、データソース単位の権限モデル）は、PD v0.9 の未決定事項として扱う（PD v0.4 9.2 #7）。

## 7. コンテナ構成・技術スタック

> プロダクトデザイン上の位置づけ：Docker Composeによるセルフホスト配布を基本とし、外部サービスへの通信を必須としない（PD v0.9 参照）。

### 7.1 論理構成

PD v0.4 3章。

```text
[社内ドキュメント / ファイル / Wiki / Git 等]
                    |
        Crawler / Connector（別コンテナ。ジョブ・ロックを管理）
                    |  HTTP（同期バッチ登録。§14）
        Indexer（別コンテナ）
        (抽出・正規化・要約生成・削除の判断と実行[Sync Manager]。検索インデックスとStore層の書き込み役)
               /         \
     検索インデックス      Store層（設定・ジョブ・同期の記録・抽出済みテキスト・処理状態）
               \         /     ※バックエンド差し替え可
               OpenSearch
          (検索用インデックス + KVS用インデックス)
                    |
                Search API
               /     |     \
         MCP Server Web UI  外部APIクライアント
              |       |
           AI Agent  利用者・管理者
```

※論理構成である。Crawler と Indexer は別コンテナとし、メッセージブローカーを介さずHTTPで直接通信する（§14）。管理操作（クロールの起動など）は、Admin APIがCrawlerにHTTPで中継する。ジョブ状態の表示は`loreley-jobs`の読み取りで行う（図には書いていない。§14.4）。削除の判断と実行は、Indexerの内部モジュールSync Managerが行い、同期の記録を`loreley-sync`に持つ（§3.9）。同期結果の表示は、Admin APIが`loreley-sync`を読み取りで直接読むため、`api`から`indexer`への通信は置かない。Search API・MCP Server・Web UIなど他のコンポーネントは、初期版では同じプロセスやコンテナにまとめてもよい。

### 7.2 Composeのサービス分割

PD v0.4 7章を、本書v0.3でCrawler / Indexerの分離に合わせて改めた。本書v0.4で、`indexer`にSync Manager（削除の判断・実行）を加えた。

- `api`：Search API / MCP Server（同居）。管理操作の窓口（Admin API）もここに置く想定（案。§14.4）
- `crawler`：Crawler / Connector / 定期実行。ジョブ・ロック・リース・スキップ記録の管理。開始通知・終了通知の送信とStatus APIの確認
- `indexer`：Indexer（抽出・正規化・登録・要約生成）と、内部モジュールSync Manager（削除の判断・実行、世代・同期結果の記録）。`loreley-sync`に書く唯一のコンテナ。独立したコンテナにはしない
- `opensearch`：検索基盤。MVPではStore層のバックエンドも兼ねる
- `web`：Web UI（APIと同居してもよい）
- `opensearch-dashboards`：管理・デバッグ用（任意）
- `embedding` / `llm`：ローカルモデルを使う場合だけ（任意）

コンテナの分割方針のうち、CrawlerとIndexerを別コンテナにすることは本書v0.3で決めた。Web UIの技術スタックなど、ほかは未決定（PD v0.4 9.2 #5。§12.1）。

### 7.3 ネットワーク・ボリューム・配置

- 接続先、データの保存先、モデルの利用有無は、設定ファイルや環境変数で切り替えられるようにする。
- 永続データはボリュームに保存する。
- OpenSearchとDashboardsのポートはホストの外に公開せず、Search API（`api`）を公開の窓口とする（§6.3）。既定のバインド先はlocalhostである。
- **内部通信**：`crawler`と`indexer`の内部HTTPは、Composeの内部ネットワークだけに置き、`ports:`でホストに公開しない（§6.3）。`api`から`crawler`への管理操作の中継も内部ネットワークを通る。`crawler`から`indexer`への開始通知・終了通知・Status APIの確認も同じ内部HTTPで行う。`api`は同期結果を`loreley-sync`の読み取りで表示し、`indexer`には接続しない（通信経路を増やさない）。起動順や稼働確認（healthcheckなど）の方法は実装時に決める（§12.5）。
- 検索対象のディレクトリは、`crawler`にだけ読み取り専用（`:ro`）でマウントする。`indexer`には不要である（§6.4）。
- 単一ホスト、`crawler`と`indexer`はそれぞれ1つ（単一Crawler・単一Indexer・直列実行）の構成を前提とする（§4.2）。

### 7.4 日本語アナライザのプラグイン（前提。実装時に確認する）

PD v0.4 7章。

- kuromojiもSudachiも、OpenSearchの既定の配布イメージには含まれない前提で、プラグインを導入した**独自のOpenSearchイメージ**をビルドして配布する。Sudachiは、辞書の入手とライセンスの確認も必要になる。
- OpenSearch本体とプラグインのバージョンは一致させて固定する。OpenSearchを更新するときは、プラグインも同時に更新して、再インデックスの要否を確認する（§2.5）。

### 7.5 技術スタック

- **バックエンド**：Crawler / Indexer / Search API / MCP ServerをPythonとする（PD v0.4 3章）。
- **Pythonライブラリ**：各文書形式（txt・Markdown・HTML・PDF）の抽出ライブラリと、文字コード判定（UTF-8、Shift_JIS/CP932）の方法は未決定（PD v0.4 9.2 #10。§12.1）。
- **Web UI**：技術スタックは未決定（PD v0.4 9.2 #5。§12.1）。Search View（利用者向け）とAdmin View（管理者向け）を持つ。
- **OpenSearchプラグイン**：日本語アナライザ（kuromojiまたはSudachi）。選定は評価セットで行う（§2.2）。
- **Store層のバックエンド**：MVPではOpenSearch。Repositoryインターフェースにより、将来PostgreSQLやSQLiteに差し替えられる（§1.5）。
- **MCP**：Streamable HTTP。

### 7.6 バージョン管理（再現性）

PD v0.4 6.2、7章。OpenSearchとプラグイン、各コンポーネントのバージョンを固定し、更新手順を提供する。OpenSearch本体とプラグインのバージョンは一致させる（§7.4）。

## 8. 要約生成

> プロダクトデザイン上の位置づけ：要約は検索用のものである。既定では無効で、LLMを明示的に設定したときだけ有効になる。要約なしでも検索できる（PD v0.9 参照）。

### 8.1 方針

PD v0.4 4.2。

- 文書全体の**検索用の要約**を生成する。主題、重要な概念、その文書で答えられる質問を表現する。要約の生成と書き込みは、Indexerが内部で行う（§14.2）。
- 既定では無効で、LLMを明示的に設定したときだけ有効になる。外部LLMを使う場合は明示的な設定を必須にする（§6.5）。既定の構成はオフラインで動作する。
- Embeddingの生成は、ベクトル検索と同じ将来拡張とし、MVPでは行わない（PD v0.9 §1.5、§8.4）。

### 8.2 非同期処理

- 要約の失敗・遅延では、要約なしで先に登録し、後から非同期に生成する。
- 要約生成はIndexer内部の非同期処理である。別コンテナになるため、クロールとの厳密な直列は保証しない。`content_hash`の条件付き更新で正しさを保つ（§4.4）。
- Indexerは、要約の書き込みの前に、メンテナンスフラグが立っていないかを確認する（§4.4、§2.5）。再起動後は、`summary_status=pending`の文書から再走査して再開する（案。§4.4）。

### 8.3 生成状態

- 要約の生成状態とモデル名・バージョンを保持し、後から再生成できるようにする。
- `summary_status`：`disabled`（要約が無効）、`pending`、`generated`、`failed`。`summary_model`にモデル名・バージョンを持つ（§2.1）。

### 8.4 保存先と書き込みの整合

- 要約はStore層にも保存し、再インデックスで失わないようにする。Store層の要約には、生成元の`content_hash`（`summary_content_hash`）を持たせる（§1.3）。
- 要約は、生成の完了後にまずStore層へ保存し、そのうえで検索インデックスへ反映する。
- Store層への保存は、生成元の`content_hash`が、現在の本文のハッシュ（確定前は`pending_content_hash`、確定後は`content_hash`）と一致し、かつ`if_seq_no`/`if_primary_term`が一致するときだけ行う（§3.8）。
- 検索インデックスへの反映は、検索インデックス上の`content_hash`が生成元と一致するときだけ行う。不一致なら捨てる（本文が更新済みで、新しい要約が生成される）。更新の衝突は再試行する（§2.4）。

### 8.5 再生成・本文更新との整合

- 本文が変わるとき（`content_hash`が既存と違うとき）は、Store層の要約を消して`summary_status`を`pending`（要約が無効なら`disabled`）に戻す（§3.8）。検索インデックスの全文upsertでも、`summary`は書かず`summary_status=pending`（無効なら`disabled`）にする（§2.4）。
- 本文が同じ（`content_hash`が同じ）なら、要約を引き継ぐ。MVPは全件更新で毎回すべての文書を処理するため、毎回の要約の再生成を避けるのがこの引き継ぎの目的である（§3.2）。
- Store層からの再構築（§2.5(b)）では、Store層の要約のうち、生成元の`content_hash`が本文と一致するものだけが保持される。不一致は`pending`に戻す。

### 8.6 モデル選定

要約生成に使うモデル、コスト、生成にかかる時間は未決定（PD v0.4 9.2 #3。§12.1）。要約の品質・コストは、測定して決める（§10.4）。

## 9. バックアップ・リストア

> プロダクトデザイン上の位置づけ：運用性の要件として、バックアップ・リストア手順を用意する。MVPの受け入れ基準に、スナップショットによるバックアップとリストアの手順をREADMEに記載することを含む（PD v0.9 参照）。

PD v0.4は、バックアップの対象と再構築の方針を定め、手順の細部は「READMEに記載する」としている。手順の中身（コマンド、保存先、周期）はPD v0.4に記述がなく、実装時に決める（§12.2への追加項目として扱う）。

### 9.1 バックアップの対象

PD v0.4 6.2。MVPではStore層もOpenSearchにあるため、**OpenSearchのスナップショットと設定ファイル**をバックアップの対象とする。OpenSearchのスナップショットには、`loreley-sync`（§1.3、§3.9）も含める（Store層のインデックスをすべて対象にする）。

### 9.2 スナップショット

PD v0.4 付録C.3、6.2。ノードが1つなので、データの消失に備えてスナップショットを取る（§3.8）。ノード障害時のデータ消失は、OpenSearchをKVSにすることのリスクである（PD v0.9 参照）。

### 9.3 リストア手順

OpenSearchのスナップショットによるバックアップとリストアの手順を、READMEに記載する（PD v0.4 8.2の受け入れ基準）。手順の中身は未決定である。

### 9.4 障害時の再構築

PD v0.4 6.2、付録B.5。

| 状況 | 対応 |
| --- | --- |
| マッピング・辞書・アナライザを変更する | 新しいインデックスを作り、旧インデックスからコピー（`_reindex`）してエイリアスを切り替える（§2.5(a)）。通常はこちらを使う |
| 旧の検索インデックスを失った（Store層は残っている） | Store層の抽出済みテキストから、検索インデックスを再構築する（§2.5(b)）。このとき`last_seen_at`は再構築時刻に初期化される。要約は、生成元の`content_hash`が本文と一致するものだけが保持される |
| 検索インデックスとStore層の両方を失った | 再クロールが必要である |
| `loreley-sync`を失った（復元できない） | 次のクロールの開始通知で、現行世代が作り直される。それまでに届く終了通知は未知の`crawl_id`として破棄され、削除は行われない。同期結果の履歴は失われる。削除が遅れるだけで安全である（§3.9） |
| 抽出ロジックを変えた | Store層からの再構築は使わず、全件更新の再クロールで反映する（§3.2） |

検索インデックスは、通常は旧インデックスからのコピーで作り直す。旧インデックスを失った場合に限り、Store層から再構築する。

## 10. 非機能設計

> プロダクトデザイン上の位置づけ：非機能要件（文書数・レイテンシ・同時利用数など）は、設計段階では目標値を置かず、実装後に実測して決める。規模は1万〜10万文書を想定するが、目標値ではない（PD v0.9 参照）。

### 10.1 想定規模

- 最初のデータソースはローカルディレクトリ／ファイル共有で、規模は1万〜10万文書を想定する（目標値ではない。PD v0.4 9.1。要確認）。
- 数十万件を超える規模や、高可用構成は対象外である。単一ホスト、単一ノードのOpenSearchを前提とする。

### 10.2 文書サイズ上限

- 文書の最大サイズ（索引化の上限）と、長い文書に対する検索品質は未決定（PD v0.4 9.2 #2。§12.1）。上限は、リクエストサイズ・インデックスサイズ・処理時間などの観点で決める（§2.3）。
- Crawler → Indexer の登録では、大きな原本に上限を設ける（§14.3）。値、形式、上限を超えた原本の扱いは未決定（§12.5）。扱いにかかわらず、`last_seen_at`は列挙時に更新済みで、削除対象にならない。
- 本文がサイズ上限を超える場合は、上限までを索引化して`truncated=true`にする（§3、Indexerの登録処理）。Store層の`text`は、サイズ上限で切り詰めた後のテキストである（§1.1）。`get_document`の`total_length`は保存済みの長さで、上限を超える部分は取得できない（§5.4）。
- ハイライトの解析上限（`index.highlight.max_analyzed_offset`）を理由に、本文を切り詰めない（§2.3）。
- オフセット保存（`index_options: offsets`）による索引の増加量と、上限値は実測して決める。
- 長い文書で検索精度に問題が出た場合は、見出し・セクション単位の補助インデックスを追加できる構成にする（§2.3）。

### 10.3 書き込み負荷

- MVPは差分検知をせず、毎回すべての文書を取得・抽出し、全文upsert（`last_seen_at`の更新を含む）する。列挙時の`last_seen_at`の部分更新（§3.1）も加わり、文書ごとの書き込みが増える（全文upsertが成功する文書にも行う。§2.4）。文書数に比例して、クロール時間、OpenSearchの書き込み量とセグメントのマージ負荷、Store層の書き込みが増える。1万〜10万文書の想定でも、クロール間隔内に完了するかは未検証である。
- 緩和策：クロール間隔は所要時間より長く設定する。本文が変わらない文書の要約は引き継ぎ、要約の再生成を避ける（§2.4、§8.5）。負荷が問題になれば、差分検知（§3.7）を導入する。
- `last_seen_at`は検索インデックスの文書に持つため、その書き込み負荷はリスクとして扱う。負荷の実測方針は維持する。
- Crawler → Indexer は同期HTTPで完了を確認しながら進めるため、Indexerが遅いとクロール全体の所要時間が延びる。MVPでは許容する。バッチの大きさやタイムアウトなどの数値は実装時に決める（§12.5）。
- 全件更新の負荷の実測と、差分検知を導入する条件は未決定（PD v0.4 9.2 #9。§12.1）。

### 10.4 性能測定

実装時に、次を実測する。

- 代表的な規模で、クロール所要時間と、書き込み量・インデックスの増加を測る（全件更新の負荷。§10.3）。
- オフセット保存による増加量と、本文サイズの上限値を測る（§10.2）。
- 要約モデルの選定のため、生成時間・コストを測る（§8.6）。
- 検索レイテンシ、同時利用数、ホスト要件などの非機能要件は、設計段階では目標値を置かず、実測して決める（PD v0.4 9.2 #8。§12.1）。
- 検索品質（Recall@10、MRR）は評価セットで測る。これは検索方式の評価であり、PD v0.9 の評価方法に従う。

### 10.5 リソース要件

ホスト要件（CPU、メモリ、ディスク）は未決定である（PD v0.4 9.2 #8）。PD v0.4は数値を置いていない。制約として、次を前提にする。

- 単一ホストにDocker Composeで導入する。外部サービスへの通信を必須としない。
- OpenSearchは単一ノード（`number_of_shards: 1`、`number_of_replicas: 0`）で、ノード障害時のデータ消失に備えてスナップショットを取る（§9）。
- ローカルの要約・Embeddingモデル（`embedding` / `llm`）を使う場合は、別途リソースが必要になる（任意。§7.2）。

## 11. テスト設計

> プロダクトデザイン上の位置づけ：MVPの受け入れ基準（完成の定義）はPD v0.9 に残る。本章は、その基準を満たすための詳細なテストケースを、異常系、競合、削除の判断（割合ルール・同期管理）、リース切れ、再インデックスに分けて定める。

**導出元**：PD v0.4の8.2（受け入れ基準）と2章（検証項目）に加え、付録B〜Fの仕様から、テストする観点を導いた（導出であり、PD v0.4に列挙されていたものではない）。ケースの粒度は実装時に調整する。

### 11.1 方針

- 異常系の試験は、MVPで保証する範囲（単一Crawler・直列実行、削除の安全性）に限る。これ以上の異常系は作り込まない。
- 排他とリース切れの動作は、実装時に試験する（PD v0.4の2章の検証項目）。
- 各ケースの根拠として、対応する章を示す。

## 14. コンポーネント間通信の方針

> プロダクトデザイン上の位置づけ：コンポーネントを疎結合に保つ構成方針である。プロダクト判断（スコープ、前提）は変えない。MVPの前提（単一ホスト、認証なし、OpenSearchをStore層とする）は維持する。

本章は本書v0.3で追加し（章番号を既存のまま保つため、末尾に置く）、本書v0.4で削除の判断・実行のIndexerへの移管に合わせて更新した。**大方針だけ**を定め、内部APIの細部は§12.5に回す。§14.1〜§14.4には、確認状況が案の項目（Admin APIの読み取りでの直接参照、固定経路の中継、`:ro`、内部ネットワーク、開始・終了通知とStatus APIの形など）を含む（§14.7）。

### 14.1 方針

- メッセージブローカー（キュー）は使わず、コンポーネント間はHTTPで直接通信する。
- CrawlerとIndexerは別コンテナ（`crawler`、`indexer`。§7.2）。ジョブの起動もHTTPで行う。
- 内部通信はComposeの内部ネットワークだけで行い、ホストに公開しない（§6.3、§7.3）。`:ro`マウントはCrawlerだけである（§6.4）。
- 単一ホスト、単一Crawler、単一Indexer、直列実行、認証なし、OpenSearchをStore層とする前提は維持する。
- 契約を明確にし、将来キューが必要になったとき、HTTP部分をメッセージングに置き換えられるようにする（§14.6）。
- Indexerは、削除の判断・実行を担う内部モジュール（Sync Manager）を持つ。Crawlerは、開始通知・終了通知をHTTPで送り、結果をIndexerのStatus APIで確認する（§3.9）。

### 14.2 責務

| 責務 | 担当 |
| --- | --- |
| ジョブ（状態、起動の受付、直列実行）、ロック、リース、ハートビート | Crawler |
| `loreley-jobs`への書き込み（ジョブ、ロック、スキップ記録、同期結果の要約） | Crawler（唯一）。Admin APIは書かない。例外はメンテナンスフラグ（運用者の手動手順。案。§1.3） |
| `loreley-sync`への書き込み（現行世代、同期結果） | Indexer（Sync Manager。唯一）。CrawlerもAdmin APIも書かない |
| データソースの列挙、原本の取得、定期実行 | Crawler |
| リトライ・スキップの判断（§3.1） | Crawler。Indexerは文書単位の失敗種別を返す |
| 開始通知・終了通知の送信、Status APIのポーリング、結果の要約のジョブ記録（§3.9） | Crawler |
| 削除の判断（対象の決定、割合ルール、最小件数ルール、全件削除するかの判定）、世代の管理、件数照合、削除の実行 | Indexer（Sync Manager）。Crawlerは検索インデックスを直接読まない |
| 抽出・正規化 | Indexer |
| 検索インデックスと`loreley-texts`への書き込み（全文upsert、`last_seen_at`の部分更新、削除） | Indexer（唯一）。期限による削除はSync Managerが決めた対象だけで、Crawlerは要請しない（ソース削除のジョブ§1.2と突合ジョブ§3.6での削除要請は従来どおり。案） |
| 要約の生成と書き込み | Indexer内部（Crawlerからは呼ばない） |
| 書き込み前のロック所有確認（登録、`last_seen_at`の更新） | Indexer（Crawlerが`owner`と`job_id`を渡す） |
| 削除前の確認 | Indexer。世代の判定とメンテナンスフラグの確認（ロック所有の確認は行わない。§4.5） |
| 突合ジョブ | 実処理はIndexer。ジョブとしての起動・管理はCrawler（案） |
| ジョブ状態の表示 | Admin API。`loreley-jobs`を読み取りのみで直接読む |
| 同期結果（削除の結果）の表示 | Admin API。`loreley-sync`を読み取りのみで直接読む |
| クロールの起動（強制削除モードの指定を含む）、取り消し、ロック解放、突合の起動 | Admin APIがCrawlerにHTTPで中継する（固定の経路のみ）。削除の承認・却下・全件削除の確認は、承認の廃止により存在しない |

検索・文書取得（Search API、MCP）は読み取りのみである。

### 14.3 通信の流れ

```text
Admin API ──起動要求(HTTP)──▶ Crawler ──(列挙・取得)──▶ データソース
                                 │
                                 │ ① 開始通知 POST /syncs/start（ロック取得後・列挙前）
                                 │ ② 見つかった文書の last_seen_at 部分更新を要請
                                 │ ③ 文書のバッチ登録（同期。文書単位の結果が返る）
                                 │ ④ 終了通知 POST /syncs/{crawl_id}/finish（202で受理）
                                 │ ⑤ 結果の確認 GET /syncs/{crawl_id}（ポーリング）
                                 ▼
                              Indexer（Sync Manager）──▶ 検索インデックス / loreley-texts / loreley-sync
                                 削除の判断・実行はIndexerが非同期に行う
```

- Crawler → Indexerの文書の登録は**同期HTTPのバッチ登録**とし、完了を確認しながら進める。登録と`last_seen_at`の更新の完了を確認してから終了通知を送るため、削除の安全性（§3.4）と相性がよい。
- 応答は**文書単位**に結果を返す。失敗した文書だけを再送でき、再送しても結果が変わらない（冪等。`document_id`と`content_hash`で判定する）。
- 大きな原本には上限を設ける。値と形式は決めない（§12.5）。
- `last_seen_at`の部分更新も、Crawlerが要請してIndexerが実行する。期限による削除はCrawlerが要請せず、終了通知を受けたIndexerが判断して実行する（ソース削除と突合ジョブでの削除要請は除く。§1.2、§3.6）。
- 開始通知・終了通知の契約と、Status APIによる結果の確認は§3.9に定める。

### 14.4 ジョブの起動

1. Admin API（または定期実行）が、CrawlerにHTTPで起動を要求する。起動要求には、強制削除モードのパラメータ（`force_delete`）を指定できる。ただし、指定できるのは**手動実行（Admin API経由）だけ**で、定期実行は指定しない（Crawlerは、定期実行の起動では`force_delete`を常に`false`にする。案）。
2. Crawlerは、ロック（`lock-{source_id}`）とジョブ（`queued`）を`loreley-jobs`に記録してから、受付応答（202とジョブID）を返す。突合ジョブの起動も同じ手順で、同じロックを取る（案。§3.6）。`force_delete`はジョブに記録し、開始通知でIndexerに渡す（§3.9）。
3. 同じソースが実行中または待機中の場合は重複として扱い、既存のジョブIDを返す（409）。応答には既存ジョブの状態も含める（案）。重複した起動要求の`force_delete`は、既存のジョブには反映されない。Admin Viewで、指定が無視されたことを管理者に通知する（案。§12.5）。Admin APIは、通常はこの応答を成功として扱うが、既存ジョブがリース切れの`failed`、または失効したロックのときは、成功扱いにせずAdmin Viewで警告する（案。§4.3、L-2）。
4. 実行は非同期で、直列に行う。
5. Crawlerは起動時に未完了のジョブを回復する（`queued`は再投入、`running`は`failed`。§4.3）。
6. Admin APIが`loreley-jobs`と`loreley-sync`に書くことはない。Admin APIは、起動・操作を固定の経路だけCrawlerに中継し、任意のパスは転送しない。ジョブ状態と同期結果の表示は、読み取りのみで行う。

### 14.5 障害時の考え方

- **Indexerのダウン・遅延**（接続不可、タイムアウト、サーバ側エラー（HTTP 5xx等））：OpenSearch全体の異常と同様に扱う。リトライして直らなければジョブを`failed`にし、削除しない。スキップにはしない（§3.1）。開始通知・終了通知の失敗（開始通知の409を含む）も同様に、ジョブを`failed`にする（削除されないだけで安全。§3.9）。この扱いの対象は、開始通知、登録、`last_seen_at`の部分更新、終了通知の失敗に限る。Status APIのポーリングの失敗は含まない（下記）。
- **文書固有の拒否**だけをスキップの対象とする（§3.3の既存ルールを維持）。ロック所有の確認に失敗した場合は、スキップにせずジョブを`failed`にする（案。§3.1）。
- **タイムアウト後のIndexerの処理**：Crawlerがタイムアウトした後も、Indexerの処理が続く窓がありうる。Indexerは要請を直列に処理し、所有確認を文書ごとに行う（案）。残る窓は既知の制限である（§4.5）。
- **同期結果の確認（Status APIのポーリング）の失敗**：タイムアウトのほか、接続エラー・5xx・404（保持件数の超過、または`loreley-sync`の喪失）がリトライの上限まで続いた場合も、警告をジョブ記録に残すだけで、ジョブのstatusは変えない（§3.9）。
- **終了通知を送ったあとの取り消し**：同期は止まらない。ジョブは`cancelled`になり、削除結果は同期結果に残る（§3.9）。取り消しが有効なのは、終了通知を送る前だけである。
- **Indexerの再起動**：削除の実行中だった同期は`interrupted`にして再開しない。削除は次のクロールに委ねる（§3.9）。
- **Crawlerの停止**：リース切れで`failed`と表示し、再起動時に回復する（§4.3）。終了通知が届かない同期結果は、削除されないまま、次の開始通知で`discarded`になる。
- **Admin APIからCrawlerに届かない場合**：起動や操作はできないが、ジョブ状態と同期結果の表示は`loreley-jobs`・`loreley-sync`の読み取りなので続けられる（推測。細部は実装時に確認する）。
- **メンテナンス**：書き込み停止の対象はCrawlerとIndexerの両方で、Indexerの削除の実行も含む（§2.5）。細部は§12.5。
- 同期HTTPでは、遅いIndexerがクロール全体の所要時間を決める。MVPでは許容する（§10.3）。

### 14.6 メッセージングへの移行の前提

将来キューが必要になったとき、HTTP部分をメッセージングに置き換えられるよう、契約は次を満たす。

- **少なくとも1回配送でも安全**：登録、`last_seen_at`の部分更新は、重複して届いても結果が変わらない（`document_id`と`content_hash`、max比較、条件付き更新による）。開始通知・終了通知も、`crawl_id`で冪等である（同じ`crawl_id`の再送は再処理しない。古い世代・未知の`crawl_id`は破棄する。開始通知は、古い`crawl_started_at`か終端状態の`crawl_id`なら409で拒否するので、遅れて届いた古い通知で世代が巻き戻らない。§3.9）。削除は、各文書の「その時点でもTTLを過ぎている」条件により、重複して実行されても結果が変わらない。
- **文書単位の結果が互いに依存しない**：文書単位の処理結果は、互いの順序に依存しない。ただし、遅れて届く旧要請への完全な対策はフェンシング（§4.7）の対象である。終了通知を、全登録の応答確認のあとに送ることは、Crawlerの進行制御で保つ。キューに置き換えて、終了通知が登録より先に処理される可能性が出ても、件数照合が不一致になり、削除を止める（§3.9）。
- **同期応答は結果イベントに置換可能**：登録の応答で返す文書単位の結果は、後から届く結果イベントとしても扱える形にする。Status APIによる同期結果の確認は、結果イベントの購読に置き換えられる。
- ジョブの状態は`loreley-jobs`、同期の状態は`loreley-sync`にあり、Crawler・Indexerの起動時に回復できる。メッセージが失われても、再実行で復旧できる（推測を含む）。

置き換えても、責務の分担（§14.2）は変えない。ブローカーの選定は本書の対象外である。
