## 2. interface 対応表

interface 4章(文書メタデータ)・5章(識別子規則)の各要素に対する、Web での値の想定(推測)。値の方式は詳細設計で決める。

### 2.1 要素ごとの想定

| interface の要素 | Web での値(想定。推測) | Web で決めること |
| --- | --- | --- |
| `external_id` | 正規化した URL。組み立ては Connector、規則の適用と検証は共通処理(interface 5.1) | URL の正規化規則、スキーム・ホストを含めるか、リダイレクト・canonical での確定点(CW-U-1、2、20) |
| `DocumentRef.locator` | URL と取得条件 | 秘密情報を含めない(CW-U-17) |

| `source_updated_at` | `Last-Modified`。ないことがある | 取れないときの値(CW-U-10。interface CI-U-5) |

| `size_hint` | `Content-Length`(任意。ないことがある) | 事前判定に使うか(CW-U-13) |
| `size`、`content_hash` | レスポンスボディのバイト列から共通処理が導出(interface 5.4) | 「原本」とするバイト列の範囲(展開後か、レンダリングの要否)(CW-U-13) |

### 2.2 `external_id` の規則(interface 5.1)を URL に当てはめた見込み

| 規則 | Web での見込み(推測) |
| --- | --- |
| 1 NFC | URL をパーセントエンコードした ASCII の形で持てば不変。IRI(非 ASCII のまま)の形なら適用される(CW-U-1) |
| 2 `/` 統一・`\` の置換 | ASCII の形なら `\` は `%5C` で現れない。ただし URL を解釈する実装の中には `\` を `/` として扱うものがある(推測。未確認)。interface I-10 の衝突要因(`\`、NFC/NFD)は URL では起きにくい(推測)(CW-U-1) |
| 3 先頭に `/` を付けない | 絶対 URL(`https://…`)なら満たす。ホストを省いたパスだけの形にすると違反する(CW-U-1) |
| 4 大文字小文字を区別 | スキームとホストは大小を区別しない仕様のため、Connector が小文字にして値を作る。共通処理は変換しない |
| 5 4096 バイト以内 | 通常は収まる。長いクエリで超える URL は文書単位の `invalid_external_id` になる(architecture 4.6・7.7 の扱い。`partially_succeeded`)。長いクエリ付き URL を捨てるかは CW-U-1 |
| 6 孤立サロゲートなし | ASCII の形なら発生しない。それ以外は共通処理のエスケープ対象(interface 5.1) |

## 3. 列挙の完全性と削除安全性の論点

本章は論点の列挙で、方式は決めない。規則の再掲はしない(interface 3.3、architecture 4.6・4.8)。

### 3.1 前提(参照)

- 列挙は `Completed` か `Failed` で終わり、`Completed` は範囲内の文書を取りこぼしなく返したときだけ(interface 3.3 の 1・2)。
- 列挙が `Failed` になると、ジョブは `failed`、終了通知は `outcome=failed` で、削除されない。それまでに登録した文書は残る(architecture 4.6・4.8)。終了通知が受理される前の失敗では削除されない(確定。CW-K-3)。
- 削除の最後の防御は Indexer の割合ルールと件数照合。一部の消失・少数の消失・最小件数以下の小さなソースの 0 件列挙は防げない(MVP の制約。PD v0.19)。

### 3.2 Web で性質が変わる点

1. **列挙と取得が交互になる**。リンクを知るには本文を取得する必要があり、列挙の `next()` の中で HTTP 取得が起きる。interface 3.3 の 7 はこれを許す。architecture 4.6 は列挙をチャンクに区切って取得するため、Connector は列挙を保留したまま `fetch` を受ける(論点 B。CW-U-14)。
2. **存在の根拠がリンクだけ**。FS は「ディレクトリを読めたか」で完全性を判定できるが、Web は「リンクで到達できたか」しか分からない。到達できなかったページと、存在しないページを区別しにくい(論点 A)。
3. **範囲が外部の状態で動く**。同じ設定でも、リンクの増減やサイトの障害で、到達できる集合が変わる。変動は削除判断(期限・割合ルール)に直結する。
4. **判定不能が起きやすい**。一時的な 5xx・429、認証切れ、遮断、ログイン画面への転送などで、1 ページが読めないだけで、その先のリンクを列挙できなくなる。

### 3.3 完全性の方針の確認(案。CW-P-2)

方針: 「到達できなかったから存在しない」と扱わない。観測結果が (i) 存在しない・範囲外と**判定できた**ものは列挙に影響させず、(ii) **判定できなかった**ものがあれば `Completed` にせず `Failed`(`enumeration_incomplete`)にする。architecture 4.6・4.8(列挙の失敗)と整合し、削除を安全側に倒す(architecture 1.4 の 1)。

観測結果ごとの暫定の見立て(推測。判定表の確定は CW-U-9):

| 観測結果 | 暫定の見立て |
| --- | --- |
| リンク先が 404・410 | 存在しない。列挙に載せず、`Completed` に影響させない |
| 5xx、タイムアウト、接続エラー、429 の継続 | 判定不能。`Failed`。一時失敗の吸収方法は I-40 |
| 401・403 | 範囲外か判定不能か未決。認証切れを範囲外と誤認すると誤削除につながる |
| robots で拒否 | 範囲外(対象外=列挙しない。interface 3.3 の 4)とする案。robots.txt 自体の取得失敗は判定不能として `Failed` が安全側 |
| リダイレクト(範囲外へ、ログイン画面へ、ループ) | 未決(CW-U-2) |
| 200 だがエラー画面・ログイン画面・遮断画面 | Connector で判定できないことがある。検知方式は未決。残る防御は Indexer の割合ルールと件数照合 |
| 上限(ページ数・時間)への到達 | 打ち切りであり、設定した範囲による対象外とは区別する。`Completed` にしない案(CW-U-15) |

### 3.4 論点(完全性・削除安全性への影響)

各論点の詳細は詳細設計で決める(5章に一覧)。

- **URL 正規化・重複・リダイレクト**(CW-U-1、2): 正規化が粗いと同じページが別の文書になり、細かすぎると別のページが同じ文書になる。`external_id` が変わると旧 ID の削除と新 ID の追加になる(確定。CW-K-5)。
- **探索の範囲・深さ**(CW-U-3): 範囲の指定による対象外は削除対象になりうる(interface 3.3 の 4)。深さを最短経路で数えるなら探索順(幅優先か)が完全性に影響する。範囲外リンクの扱いも決める。
- **サイトマップの併用**(CW-U-4): 発見の手段にするか、完全性の根拠に使えるか。サイトマップに載ったページが、リンク探索では到達できないことがある。
- **robots.txt**(CW-U-5): 従うか、拒否を範囲外とするか分類とするか、取得失敗時の扱い、列挙時と取得時で内容が変わったときの扱い。
- **認証**(CW-U-6): 方式、認証情報の参照名の解決(認証情報は平文で保存せず参照で持つ。確定。CW-K-4。解決の仕組みは interface CI-U-7)、認証切れの検知、副作用のあるリンク(ログアウトなど)を辿らない手段。認証切れを検知できないと、ログイン画面を文書として登録する。
- **レート制限・ペーシング**(CW-U-7): 間隔、同時接続、`429`・`Retry-After`(論点 D)。所要時間に直結する(CW-U-16)。
- **一時失敗の吸収**(CW-U-8): 列挙中の 1 件の一時失敗で列挙全体が `Failed` になる問題(I-40)。
- **動的コンテンツ**(CW-U-13): JavaScript で生成されるリンク・本文を取得するか。取得しない場合、リンクを列挙できず完全性が下がる。
- **上限とクロールトラップ**(CW-U-15): 無限に続く URL 空間(日付違いのカレンダー、検索結果の組み合わせなど)での打ち切りと、打ち切り時の列挙の終端。
- **所要時間**(CW-U-16): 長時間の列挙で、リース更新・取り消し・期限(TTL)・定期起動の間隔と両立すること。リース更新は独立したハートビート(architecture 5.3)なので列挙の長さでは途切れない。一方、`next()` が長時間 `DocumentRef` を返さない場合(リンクだけのページを辿り続けるなど)、architecture 4.6 の確認点(各リクエストの前・文書の区切り)に制御が戻らず、取り消し・メンテナンスフラグの反映が遅れる。
- **URL 内の秘密情報**(CW-U-17): URL のクエリやユーザー情報にトークンが含まれると、`external_id`・`url`・スキップ記録・ログに漏れる。

## 4. 共通 interface への適用結果

### 4.1 判定(結論)

- **interface の要素・操作の構造(操作、戻り値、識別子規則、エラー分類、設定の扱い)は、変更不要で Web でも成立する**。要素を変えなければならない確定的な齟齬は見つからなかった。
- ただし、次の 3 種類は区別する。
  1. **契約の設計判断(I-40)**: 列挙中の一時失敗の扱いは、interface 3.1(CI-P-5)と architecture 6.2 の方針に関わり、Web の実用性を左右する。選択肢は 4.5 のとおり。(a) interface 3.1・CI-P-5 の方針変更、(b) `EnumerationStream` に失敗後の再開の契約を追加、(c) architecture 6.2 の方針変更(6.2 は再開できないことを理由に列挙のやり直しをしない)、(d) 現状維持。(d) では、一時失敗が 1 件でもあると列挙全体が `Failed` になるため、大規模サイトでは列挙がほぼ完了しない(推測)。Web の詳細設計の前に判断する。
  2. **文言・テスト観点の補足(I-41、I-42)**: 契約の変更は伴わない。
  3. **Web 以前の問題と、Web で顕在化する既存制約**: I-43 は architecture 7.7 と interface 3.2 の内部矛盾で、FS を含む MVP の実装に影響していたが、解消済み(architecture 7.7 で、表示用の値を規則適用前の `external_id` の切り詰めに変更。interface 3.2 は変更なし)。I-44 は Web で顕在化する Indexer 側の既存制約(FS にも当てはまる)。
- interface 9章へ差し替える結論の文案(案。差し替えは interface 側の改訂事項): 「Web 概要(`connector-web-v0.1.md`)で確認した結果、本書の要素・操作の構造は Web でも成立する。列挙中の一時失敗の扱い(3.1 の CI-P-5、architecture 6.2)は契約の設計判断で、Web の詳細設計の前に決める(I-40)。3.3 の 2 の文言(I-41)と 10章 #8(I-42)は補足が要る。」

### 4.2 要素別の適用結果

| interface の要素 | 判定 | 根拠・備考 |
| --- | --- | --- |
| 列挙と取得の分離、`enumerate`・`fetch`・`close`(3.2、3.3 の 7) | 成立 | 列挙中の内容の再利用は Connector 内部の最適化にできる。保持量は有界にする(CW-P-4。architecture 7.3 の「チャンクに残るのは `DocumentRef` と ID だけ」の前提を守るため)。方式は CW-U-14 |
| 列挙の終端(3.3 の 1) | 成立 | 終端なしは完了にしない。Web でも同じ |
| 完全性(3.3 の 2) | **条件付き(I-41)** | 「存在し続けた文書は必ず返す」は、リンクで到達できない文書には満たせない。範囲の定義を Connector が与える必要がある |
| 過剰は許容(3.3 の 3) | 成立 | 列挙後に消えたページは `fetch_not_found` |
| 対象範囲(3.3 の 4、CI-K-7) | 成立 | CI-K-7 は FS の確定で、Web への一般化は導出(CW-P-3)。設定の範囲は対象外にできる。robots は設定でなく外部の状態で、範囲が外部の状態で動く点は CW-U-3・5 |
| 重複と順序(3.3 の 5) | 成立 | 同じ文書の複数回返却は共通処理が除く。内容が同じで URL が違うページは別文書になる(CW-U-2) |
| ストリーミング(3.3 の 6)、契約テスト #8 | **条件付き(I-42)** | 3.3 の 6 は「`DocumentRef` を全件保持しなくてよい」という許容で、禁止ではない。10章 #8 は「Connector が保持する `DocumentRef` の量が件数に比例しない」を期待する。Web の訪問済み URL の集合は `DocumentRef` ではないため文言上は衝突しないが、趣旨(件数に比例する状態を Connector が持たない)とは衝突する。未処理 URL の待ち行列(frontier)も件数に比例する |
| `external_id`・`document_id`・衝突(5.1〜5.3) | 成立 | 2.2 のとおり。I-10 の衝突要因は URL では起きにくい(推測) |
| `content_hash`・`size`(5.4) | 成立 | 動的なページは取得のたびに内容が変わりうる。Indexer では本文の変化として扱われる(MVP は全件更新。PD v0.19 4.1) |
| `title`・`path`・`url`(4章) | 成立 | 任意の `path`・`url` で足りる。値の方式は CW-U-11 |
| `mime_type`(4章) | 成立(要確認 1 点) | interface 4章の CI-P-16(対応外 MIME を理由に拒否しない)と、Web で列挙対象を `Content-Type`・拡張子で絞ることの関係は要確認(3.3 の 4 の「設定による包含・除外」の範囲とみなせるか。CW-U-3・12)。文字コードの制約は I-44 |
| `source_updated_at`(4章。論点 C) | 成立(値の方針が要る) | 型は必須で、値がないことを表せない。値の選択が Indexer の書き込みに影響する(4.3 の C) |
| エラー分類(6章) | 成立 | 想定の対応は 4.4。分類名の追加は不要の見込み。robots・TLS・リダイレクト異常・遮断画面の帰属は CW-U-18。失敗した URL の診断情報は `message` に載せられる(interface 6.1。CI-P-17。URL 内の秘密情報の除去は CW-U-17) |
| Connector は内部でリトライしない(3.1、CI-P-5) | **成立するが契約の設計判断が必要(I-40)** | 列挙中の一時失敗を吸収する手段がなくなり、Web の実用性を左右する。interface の要素の変更ではなく、interface 3.1 / architecture 6.2 の方針の判断 |
| `oversize`・`fetch(ref, max_bytes)`(7章) | 成立 | `Content-Length` が不正・欠落でも、読み取り中の中断で判定できる。測る対象は展開後とする想定(推測。CW-U-13) |
