## 1. 位置づけと前提

- MVP は単一ホスト・単一 Crawler・単一 Indexer・直列実行・認証なし(PD §8.1、§6.1。`CAPI-K-7`)。Admin View も認証なしで、任意のローカルパスを登録できる。信頼できる環境だけで使う(PD §6.1。確定)。
- Admin View は Admin API を通して動く。Admin API は、操作(クロール起動・取消・ロック解放・設定の登録/更新・ソース削除ジョブ起動)だけを Crawler に中継し(crawler-api §1、§2.1。承認済みの案。SD §14.4)、状態の表示は Store 層(`loreley-sources`・`loreley-jobs`・`loreley-deletions`)を**読み取りのみで直接読む**。Crawler に読み取り API は置かない(PD §3、§4。crawler-api §2.3。`CAPI-K-5` 確定、`CAPI-P-16` 承認済みの案、`CAPI-U-2` はユーザー回答 2026-11-16 で解消)。Admin API は Store 層に書かない。
- Admin API は、検索インデックスを読み取り専用で参照してよい(`extract_failed` の文書の一覧や文書数など。IA K53。確定)。取得条件・形は未決(IA U-30。AF-U-6)。
- 同じデータソースのクロールは同時に 1 つだけ(PD §4.7、§8.1)。

## 3. MVP の機能

### 3.1 データソース設定の管理(AF-1、AF-2)

区分: MVP。目的: 管理者がデータソースを登録し、クロールの設定を変えられるようにする(要件 0000「Crawler設定の管理」)。

**AF-1 登録・更新**

- 設定する項目: データソース(識別子 `source_id`、種別 `connector_type`、取得設定 `connector_config`)、実行周期(`schedule_cron`)、TTL、削除の割合ルールのしきい値(0%以上100%未満)、最小件数(PD §4.6。確定。項目名は CA §3.2、crawler-api §4.4.1)。
  - MVP の `connector_type` はローカルディレクトリ/ファイル共有(`file_system`)のみ(PD §8.1)。`connector_config` の項目と検証は Connector 設計が定め、本書は扱わない。認証情報は参照名だけを持つ(PD §4.8)。
  - 実行周期は cron 式で、空(null)は手動のみ。cron 式の検証細部は `CAPI-P-30`(ユーザー未確認)。
- 検証: しきい値の範囲(0 以上 1 未満)は Admin API だけが検証し、範囲外は Crawler に渡さない(`CAPI-K-3`、PD §8.2 のしきい値の項。確定)。型・形式・`connector_config` は Crawler 側が検証し、違反は項目ごとに返る(`CAPI-P-8`、`CAPI-P-13`。承認済みの案。cron 式の検証の細部は `CAPI-P-30`。ユーザー未確認)。表示は項目単位で示す(示し方は後続設計)。
- 更新は項目の全置換で、必須項目を省略できない。`source_id` と `connector_type` は登録後に変更できない(`CAPI-P-7`、`CAPI-P-9`。承認済みの案)。`status=deleting` のソースは更新できない(`CAPI-P-9`。承認済みの案。crawler-api §4.4.1)。
- 反映: ジョブは実行開始時(実行待ちから実行中になった直後)に設定を 1 度だけ読む。実行中のジョブには更新が反映されず、実行待ちのジョブには(開始時に読むため)反映される(crawler-api §4.4.1、§2.2、CA §3.2。承認済みの案 `CA-P-51`。実行待ちへの反映は crawler-api §4.4.1 の導出)。登録・更新では接続確認をしないため、接続の不備はジョブ開始時に検出されて失敗になる(`CAPI-P-8`。承認済みの案)。AF-8 で確認する。
- 定期実行の無効化は、実行周期を空にして手動のみにすることで代替する(専用の切替は置かない。UC-2。AF-27)。
- 既定値: `ttl`・しきい値・最小件数は必須で既定値がない(`CAPI-P-7`)。Admin View 側で既定値を補うか、しきい値の入力単位(%)は未決(AF-U-7)。

**AF-2 参照**

- 登録済みデータソースの一覧と現在の設定値を見られる。Admin API が `loreley-sources` を直接読む(`CAPI-U-2` 解消)。全置換の更新には現在値の表示が前提になる(`CAPI-U-3` の注記)。表示名の項目はなく、`source_id` で識別する(`CAPI-U-4` 解消)。区分の根拠: PD §4.6 の設定の管理に付随する(導出)。

### 3.2 クロールの操作(AF-3〜AF-7)

区分: MVP(AF-3 の再書き込みモードは UC-9、AF-5 の指定の引き継ぎは UC-11・UC-17、AF-7 は UC-4)。目的: クロールの起動・停止と、止まったジョブの復旧を行えるようにする(要件 0000「起動/停止」)。

**AF-3 手動起動**

- 指定したデータソースのクロールを手動で起動する(PD §4.6、§4.7。確定)。起動は受付までが同期で、ジョブ ID が返り、実行は非同期(crawler-api §2.2)。
- **強制削除**を手動起動のときだけ指定できる(割合ルールと最小件数ルールだけを無視し、TTL が経過していない文書は消えない。定期実行では指定できない)(PD §4.6、§5.2、§8.2。`CAPI-K-2`。確定)。強制削除の指定方法と確認の出し方は PD §9.2 #10 が未決。確認の要否を含め画面設計で決める(AF-U-7)。
- **再書き込みモード**(`rewrite_mode`。差分チェックをしない全件再書き込みのクロール指定)も、強制削除と同じく手動起動のときだけ指定できる(定期起動は常に指定なし)。手動限定は承認済みの案(crawler-api §4.1、CA §4.4。`CAPI-P-3`、`CA-P-13`。強制削除の手動限定 `CAPI-K-2` は確定)。Indexer への指定経路は IA K26・K41(確定)。MVP の Admin View で指定できる(UC-9。ユーザー確認済み)。AF-3 の一部として扱い、機能 ID は分けない。失敗ジョブの再実行での引き継ぎは AF-5(UC-17)。
  - 再インデックス(SD §2.5。画面実行は将来拡張の AF-21)とは別物。削除の判断には影響しない(IA K26)。
  - `true` で運用する前の準備(Indexer の要約生成を止めて終えておく)は Indexer の運用手順が定め、本書は定めない(CA §4.4、IA K26)。画面での指定方法と注意の出し方は未決(AF-U-7)。

**AF-4 取消**

- 実行待ち・実行中のクロールジョブを、どちらも取消の対象にする(要件 0000「停止」。UC-2。実行待ちを含めることは UC-13。ユーザー確認済み)。操作の存在は crawler-api §4.2 で確定(同書 §4.2 の確認状況)。ソース削除ジョブは取り消せない(crawler-api §4.2。承認済みの案)。
- 実行待ちは取消完了、実行中は「取消要求の受付」までで、最終状態はジョブ状態(AF-8)で確認する(crawler-api §4.2。承認済みの案)。終了済みで取消できなかったとき(`job_already_finished`)は成功として扱い、終了済みの状態を示す(AF-P-2)。
- 終了通知の送信を始めた後の取消は、Indexer の削除を止めない(`CA-K-9`。確定)。Admin View での示し方は未決(`CAPI-U-6`。AF-U-6)。リース切れの実行中ジョブは取消が完了しないことがある。その場合は AF-7 を使う(crawler-api §4.2)。

**AF-5 失敗ジョブの再実行**

- 失敗したクロールジョブは、Admin View から再実行できる(PD §4.7。確定)。再実行は、同じデータソースへの AF-3 の起動として行う(導出)。失敗したソース削除ジョブの再実行は AF-16。
- **元ジョブの `force_delete` と `rewrite_mode` の両方の指定を引き継ぐ**(元ジョブがどちらかを指定して起動されていれば、再実行でも同じ指定で起動する。`force_delete` は UC-11、`rewrite_mode` は UC-17。いずれもユーザー確認済み)。再実行は新しいジョブとして起動し(CA §3.2)、起動 API は渡された指定を受け取るだけで(crawler-api §4.1)、Crawler が元ジョブの指定を引き継ぐ規定は確認した範囲にない。元ジョブの両指定はジョブ記録に残る(CA §3.3.1)ので、Admin API が読んで起動の指定に渡す(導出)。強制削除の確認操作の要否は未決のまま(AF-U-7)。
- **引き継ぎで起きること(注意)**: `force_delete`=true の再実行では、割合ルール・最小件数ルールが再び無視される(TTL が経過していない文書は消えない。PD §5.2)。`rewrite_mode`=true の再実行では、要約生成を止めておく準備(CA §4.4、IA K26。手順は Indexer の運用手順)が再び必要になる。管理者が引き継がれる指定を確かめられるよう、元ジョブの指定は AF-8 で参照できる。再実行時の指定の提示・確認の要否は AF-U-7。

**AF-6 起動拒否の理由の表示**

- 起動が拒否されたとき、理由を表示し分ける: ロック保持中(`lock_held`)、メンテナンス中(`maintenance_enabled`)、ソース削除中(`source_deleting`)(`CAPI-P-4`。承認済みの案。表示し分けは AF-P-1)。
- ロック保持中のときは、既存ジョブ(種別・状態・リース期限)を案内する。`force_delete` と `rewrite_mode` の指定は、どちらも既存ジョブに反映されない(crawler-api §4.1、CA §4.4)。指定が無視されたことを管理者に知らせる(`force_delete` は SD §14.4 の案。`rewrite_mode` への拡張は導出。方式は AF-U-3(a))。既存ジョブがリース切れの失敗、または失効したロックのときは、成功扱いにせず警告して AF-7 へ導く(SD §14.4。案)。
- 設定が存在しないソースへの起動は拒否される(crawler-api §4.1)。

**AF-7 止まったジョブの復旧(UC-4)**

- 表示: 実行中のままリース期限が切れたジョブを「失敗」として表示する(CA §5.4。承認済みの案。判定方法は Admin API 設計。CA-U-12。AF-U-6)。
- 操作: ロックを解放する。解放できるのは、孤児ロック(ジョブ記録がない、またはジョブが終了済み)と、リース切れの実行中ジョブのロック。後者では、ジョブが失敗(`lock_released`)になる(crawler-api §4.3。承認済みの案)。
- 解放できない場合の案内: リース期限内の実行中・実行待ちのクロールは「取消(AF-4)を使う」、リース期限内のソース削除は待つ、取得直後(受付の途中)のロックは時間をおく(crawler-api §4.3)。
- 解放しても、ジョブは再起動されない。復旧後の再実行は AF-3(ソース削除は AF-16)(crawler-api §4.3)。
- 範囲外: リース期限内で止まって動かない実行中ジョブからの脱出は、Crawler の再起動による回復だけ(MVP。crawler-api §4.3)。コンテナの再起動は Admin View の機能にしない(AF-26)。
- 出典の確度: PD §4.7「止まったジョブは失敗として検知し、管理者が復旧する」(確定)。画面からのロック解放を MVP に含めることは UC-4(ユーザー確認済み)。

### 3.3 ジョブ状態とクロール結果の参照(AF-8〜AF-10)

区分: MVP。目的: クロールの実行状態と結果を確認できるようにする(要件 0000「実行状態の参照」)。Admin API が `loreley-jobs` と `loreley-deletions` を読み取りのみで直接読む(PD §3、§4.8。SD §14.2)。メールなどの通知はなく、Admin View の表示が管理者への通知である(PD §4.6。AF-24)。

**AF-8 ジョブ状態・エラー・警告・起動時の指定・最終クロール完了日時**

- 扱う情報(CA §3.3.1、§4.2、§4.8。承認済みの案): ジョブ種別(クロール/ソース削除)、起動の種別(手動/定期)、起動時の指定(`force_delete`・`rewrite_mode`。ジョブ記録に受付時の指定として残る。CA §3.3.1、§4.4。`CA-P-37`、`CA-P-13`。表示は導出。AF-5 で引き継ぐ指定の確認元になる)、状態(実行待ち・実行中・成功・一部成功・失敗・取消)、起動・開始・終了の日時、失敗の理由と説明。リース切れの実行中ジョブは「失敗」として示す(AF-7)。
- 状態・エラー・最終クロール完了日時の確認は PD §4.6(確定)。
- 最終クロール完了日時: 出典は PD §4.6 のみ。ジョブ記録の終了日時(`finished_at`。CA §3.3.1)から導くのは推測。どのジョブを「完了」とみなすか(一部成功を含めるか、失敗・取消を除くか)は未決(AF-U-9)。
- 警告の表示: ジョブ記録の警告(識別子エラーの件数、0 件列挙、確認の打ち切りなど。CA §3.3.1)を状態と併せて参照できる(UC-10。ユーザー確認済み。管理者が警告に気づく運用が前提。CA §7.7、`CA-P-52`)。警告コードの種類と形式は `CA-P-73`(案。承認の範囲外)。
- 表示範囲(履歴の件数・絞り込み)は後続設計。ジョブ記録は MVP では自動で消さない(CA §3.5。ユーザー回答 2026-11-16)。

**AF-9 登録結果**

- 最低限の表示項目: 列挙件数、登録件数(新規・更新)、スキップ件数、原本サイズ超過件数、エラー件数(PD §4.6。確定。保持は `loreley-jobs`。SD §3.3)。エラー件数は抽出に失敗した文書の件数(CA §7.7。`CA-U-4` 解消)。
- 集計の途中か確定済みかを区別して示す(CA §7.7 の `partial`。承認済みの案。導出)。
- 数え方の細部(新規/更新の内訳は目安に近い、など)は PD §9.2 #12 で未決(AF-U-10)。

**AF-10 削除結果**

- 項目: クロールごとの削除件数、割合ルールで削除しなかった場合の理由と件数(PD §4.6、§8.2 の割合ルールの項。確定。しきい値・削除対象数・削除前の登録文書数は loreley-deletions §2.2 の記録項目)。
- 削除が行われなかった、または完了しなかった場合は、理由つきの失敗として示す(PD §4.7。確定)。状態名・理由コードの名称は案(loreley-deletions §3、§3.1)。
- 確認が終わらなかった場合は「結果未確認」または「結果不明」と表示する。Crawler がジョブ記録に持つ確認結果の区分と、`loreley-deletions` の現在値を併記する(PD §4.7。確定。区分の名称と判定は承認済みの案。CA §7.6 の `CA-P-30`)。再確認は行わない。
- 削除の承認・却下の操作はない(PD §4.6。確定)。

### 3.4 文書単位の確認ビュー(AF-11〜AF-14)

区分: MVP(範囲は UC-6)。データソースごとに、確認が必要な文書を一覧できる。範囲は PD・SD で決定済みのものに限る。文書ブラウザ・文書単位の手動再試行・「停止中」表示は将来拡張(AF-29〜31)。

共通: 管理者は、確認した結果をもとに原因を解消(アクセス権の修正、データソース設定の除外条件など)し、**データソース単位の再クロール**(AF-3)で再処理する(PD §4.6。確定。SD §3.1)。文書単位の再試行はしない(UC-6)。

**AF-11 スキップされた文書**

- 項目: `external_id`、`stage`(取得/登録)、`reason`、`attempts`、`consecutive_skips`、`first_skipped_at`・`last_skipped_at`、既存文書か新規文書か(既存なら古い内容のまま検索に残る)、直近ジョブへのリンク(SD §3.1「Admin Viewの表示項目」。案。記録項目は CA §3.3.3。承認済みの案)。確認できること自体は PD §4.6、§8.2(確定)。
- 「既存/新規」は記録項目になく、Admin API での導出が必要(SD §3.1)。方法は後続設計(AF-U-5(b))。
- 本文が上限を超えて切り詰められた旨の表示先は未決(AF-U-5(c))。
- 表示は直近のクロールの結果で、後のクロールで成功した文書や、列挙で見つからなくなった文書の記録は消える(SD §3.1。CA §6.4)。

**AF-12 抽出失敗の文書**

- 抽出に失敗してタイトルとメタデータだけを登録した文書(`index_status=extract_failed`)を一覧する(PD §4.2、§4.6、§8.2。確定)。スキップではなく、スキップ件数にも数えない(PD §4.2)。
- 取得元は検索インデックス(Admin API の読み取り専用参照。IA K53。確定)。取得条件・形・表示は未決(IA U-30。AF-U-6)。

**AF-13 原本サイズ超過**

- 上限を超えた原本は取り込まれず、原本サイズ超過として記録される。存在確認日時は更新され、削除されず、索引にある同じ文書はそのまま残る(PD §4.2、§8.2。確定)。Admin View で確認できる(同。ユーザー決定)。
- 項目(CA §3.3.4。承認済みの案): `external_id`、検出した側(Crawler/Indexer)、サイズ(分かる場合のみ)、初回・直近の検出日時、直近ジョブ。ジョブの状態には影響しない(CA §6.5。承認済みの案)。
- Admin View での表示方法は未決(PD §9.2 #8 は「利用者への表示方法」として未決、CA-U-12。AF-U-5(a))。

**AF-14 要約未生成の文書**

- 要約が有効で、まだ生成されていない文書(`summary_status=pending`)を一覧する(PD §4.6。確定。状態値は search-index §2.3)。要約が無効(既定。`disabled`)の文書と、抽出失敗の文書は対象にしない(search-index §2.3。導出)。
- 要約は既定で無効で、モデルを設定したときだけ有効になる(PD §4.2)。生成の失敗・遅延では要約なしで先に登録され、後から非同期に生成される。失敗しても `failed` にせず `pending` のまま再走査で再試行する暫定方針である(確定。IA K64、search-index §2.3。PD §9.2 #13 は細部を案とする)。`failed` への遷移条件と明示的な再実行の手段は未決(IA U-9、PD §9.2 #13。AF-U-4)。なお現状は、要約を有効にすると LLM プロバイダが未実装のため Indexer が起動しない(IA K64、PD §9.2 #13)。
- 取得元は検索インデックス(IA K53。確定。形は IA U-30 未決。AF-U-6)。手動再試行は将来拡張(AF-30)。
- 区分の根拠: PD §4.6 の確認対象に「要約未生成」があり決定済みで、MVP に含めることはユーザー確認済み(UC-14)。
- 要約を有効にした後の既存文書の再生成には、Admin View から `rewrite_mode` を指定してクロールする手段がある(AF-3。UC-9。IA K64 の暫定方針と同じ代替)。ただし PD §9.2 #13 の未決(`failed` への遷移条件、明示的な再実行の手段、有効化後の既存文書の一括生成)の解消ではない(AF-U-4)。
- `rewrite_mode`=true のクロール後は、要約が有効なら全件(抽出失敗の文書を除く)が `pending` に戻る(IA K26。search-index §2.3)ため、この一覧の対象が一時的に大量に増える。

### 3.5 インデックス件数の確認(AF-15)

区分: MVP。

- データソースごとの検索インデックスの登録文書数を確認できる(PD §4.6。確定)。粒度が「データソースごと」であることは PD に明記がなく、ユーザー確認済み(UC-8)。取得は検索インデックスの読み取り専用参照(IA K53「文書数など」。確定)。`source_id` は絞り込み用の項目で、数える手段はある(search-index §4。導出)。
- AF-17 との住み分け: AF-15 は**データソース単位の文書数**で、AF-17 とは別の独立した機能として残す(UC-8)。AF-17 は OpenSearch 汎用の情報だけを出し、データソースなど Loreley 固有の概念を持たない(3.7)。
- 抽出失敗の文書を件数に含めるかなどの数え方は後続設計(AF-U-6)。

### 3.6 データソースの削除(AF-16)

区分: MVP(UC-5)。

- データソースの削除は、**ソース削除ジョブの起動**として行う。設定レコードだけを消す操作は置かない(`CAPI-K-8`、`CA-K-22`。確定)。
- 削除されるもの: そのソースの索引済み文書、スキップ記録・原本サイズ超過記録、削除の記録、設定(CA §8.1)。取り返しがつかない。API には確認の仕組みがなく、誤操作の防止は Admin View 側に委ねられている(crawler-api §4.6)。**確認操作を機能要件に含める**(UC-5。確認の出し方は後続の画面設計。AF-U-7)。
- 進行中の表示: 設定の `status=deleting` の間は、クロールの起動はできない(`CAPI-K-4`。確定)。設定の更新もできない(`CAPI-P-9`。承認済みの案)。拒否理由は AF-6 のとおり。
- 完了の判断: ジョブの状態が成功で、設定が消えていること(crawler-api §4.6。Admin API が `loreley-sources` を読んで確かめる)。
- 取消できない。途中で失敗したら、同じ操作を再度行って復旧する(`CAPI-K-4` 確定。再実行の手段を操作の再呼び出しとすることは `CAPI-P-12`。承認済みの案)。メンテナンス中は起動を拒否する、またはジョブが `maintenance` で失敗する。フラグが下りた後に再実行する(crawler-api §4.6)。
- 設定の削除の後にロックだけが残った場合は、再実行ではなくロック解放(AF-7)で消す(crawler-api §4.6)。

### 3.7 OpenSearch 最小ビュー(AF-17)

区分: MVP(UC-1)。

- AF-17 は Admin View 内の読み取り専用ビューで、OpenSearch Dashboards(製品。AF-20 の導線先)とは別。AF-18 の Loreley ダッシュボードとも別。
- 目的: OpenSearch のクラスタの状態を Admin View で確認する。要件 0000 は cerebro のような UI を理想とするが、当初は最小限とし、拡張は将来(AF-28)。
- **独立した OpenSearch ダッシュボードとして振る舞う**。表示は OpenSearch 汎用の情報だけで、Loreley 固有の概念(データソース、ジョブ、文書の状態など)は含めない(UC-8)。データソース単位の文書数は別機能の AF-15(3.5)。
- 見られる情報: クラスタの状態、インデックス一覧、ドキュメント件数、シャードの配置(UC-1)。
- **読み取り専用**。インデックスの削除、シャードの再配置、設定変更などの操作は含めない(UC-1)。
- PD v0.19 にない機能で、要件 0000 とユーザー確認(UC-1)による追加。PD の追従改訂が必要(6.1、AF-U-2)。取得の経路・形は後続の Admin API 設計(PD §3、§4 は Admin API の読み取りを Store 層に限る書き方で、これを超えるため。0003 G)。
- OpenSearch はホスト外に公開しない方針(PD §6.2)に反しない。ビューは `api` が内部で読むだけで、OpenSearch を外に出さない(導出。6.2)。

### 3.8 Loreley ダッシュボード(AF-18)

区分: MVP(UC-3、UC-7)。

- 目的: 各コンポーネントが落ちていないかを確認する(要件 0000「各コンポーネントの起動状態」)。
- 対象: `crawler`、`indexer`、`opensearch`、`api`・`web`。任意コンテナ(`opensearch-dashboards`、`embedding`、`llm`)は設定されている場合のみ表示する(UC-3。PD §7、SD §7.2)。
- 表示は死活のみで、区分は「正常」「異常」「未設定(任意コンテナ)」程度(UC-7)。履歴・推移・アラートはない(AF-32)。現在値のみで、手動更新と、表示中の定期更新を行う(UC-7)。更新間隔は後続設計(AF-U-3(c))。
- 「起動状態」の意味: Crawler の稼働確認用の `/healthz` が示すのは「受付が始まっている」ことだけで、起動後の OpenSearch・Indexer への到達性や Job Runner の稼働は示さない(crawler-api §4.7。導出)。Indexer の `/healthz` は起動時の整理が終わるまで応答しない(indexer-api §1。`IA K67` 確定)。ダッシュボードの死活は「起動が完了して応答できる」ことを意味し、ジョブが止まっていないかは AF-8・AF-7 で確認する(導出)。
- **取得経路は未決**(AF-U-1): `CAPI-K-9`(確定)は Crawler に稼働確認用 API を置くこと。それが「Admin API の契約外」であることは `CAPI-P-19`(承認済みの案。crawler-api §1、§4.7)。Indexer の `/healthz` が契約外であることは `IA K67`(確定。indexer-api §1)。SD §7.3 は「`api` は `indexer` に接続しない」とし、起動順や稼働確認(healthcheck など)の方法は実装時に決めるとする(§12.5。SD。補助)。OpenSearch の状態は AF-17 と同じ読み取りで得られる可能性がある(推測)。`api`・`web` 自身の表示方法も後続設計。

## 4. 横断的な機能要件

**AF-19 メンテナンス中の表示**(区分: MVP。AF-P-3)

- メンテナンスフラグは Admin View から操作しない(AF-22)。フラグが立っている場合は、起動の拒否(`maintenance_enabled`。AF-6)と、ジョブの失敗理由・削除結果の失敗理由(`maintenance`。CA §4.8、loreley-deletions §3.1)を表示するのみ。書き込み手段は運用者の手動手順(CA §7.9。`CA-U-3` 承認済みの案)。

**AF-20 OpenSearch Dashboards への導線**(区分: MVP。任意)

- 管理者向けに OpenSearch Dashboards への導線を置いてよい(任意。一般利用者には公開しない)(PD §4.6。確定)。OpenSearch Dashboards は任意のコンテナで、設定されていない場合は表示しない(AF-18 と同じ扱い。導出)。
- OpenSearch と Dashboards はホストの外に公開しない(PD §6.2)ため、導線の到達先と経路は後続設計(AF-U-11)。

**共通の制約**

- 認証なし。任意のローカルパスを登録できる(PD §6.1。確定)。信頼できる環境だけで使い、既定では localhost だけで待ち受ける。認証・権限は将来(AF-23)。
- データソース削除(AF-16)には確認操作を置く(UC-5)。
- 強制削除(AF-3)の指定方法と確認の出し方は PD §9.2 #10 が未決。確認の要否を含め画面設計で決める(AF-U-7)。
- Crawler の起動時の回復が終わるまでは、Admin API から接続エラーに見える。Admin API の扱いは Admin API 設計(crawler-api §3.1。`CAPI-U-1`)。状態の表示は読み取りなので、Crawler に届かなくても続けられる(推測。crawler-api §2.3)。
- 用語は PD の用語集に従う(データソース、削除結果、結果未確認など)。

## 6. 既存設計との関係

### 6.1 PD v0.19 への追加・追従改訂が必要な点

本書は PD・SD を変更しない。次は別タスクでの PD 追従改訂が必要である(AF-U-2)。1〜3 を改訂対象にすることはユーザー確認済み(UC-12)。4 も UC-16 でユーザー確認済み(旧 AF-P-8)。

### 6.2 PD §6.2 / SD §7.3・crawler-api・indexer-api との整合

- PD §6.2「OpenSearchとDashboardsはホストの外に公開しない。Search APIだけを公開の窓口にする」。AF-17・AF-18 は `api` が内部ネットワークから読み取るだけで、OpenSearch を外に出さないため反しない(導出)。AF-20 の導線は到達性を要確認(AF-U-11)。
